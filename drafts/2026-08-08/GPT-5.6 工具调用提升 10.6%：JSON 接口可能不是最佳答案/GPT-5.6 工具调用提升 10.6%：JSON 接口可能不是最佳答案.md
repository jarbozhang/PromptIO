# GPT-5.6 工具调用提升 10.6%：JSON 接口可能不是最佳答案

如果你正在维护 Agent 的工具调用层，这项研究值得看。它挑战了一个很常见的默认选择，模型调用工具，就该逐次生成 JSON。

研究者在 BFCL v4 上比较了 14 个模型。程序化工具调用在其中 11 个模型上追平或超过原生 JSON 调用，GPT-5.6 系列的提升达到 10.6%。

我更关心的不是这个数字本身，而是它给出的架构信号。模型已经会写代码时，让它用程序表达调用关系，可能比把每一步压成孤立 JSON 更自然。

## 误解一，JSON 越结构化，工具调用就越可靠

JSON 的优势很明确。字段固定、容易校验、便于记录，也能把模型限制在清晰的接口里。

所以很多调用层采用同一种循环。模型生成一次 JSON，系统执行工具，把结果塞回上下文，再让模型决定下一次调用。单步任务里，这套方式足够直观。

问题出在多步任务。模型不只要选对工具，还要反复表达依赖关系、分支条件和并行调用。原本可以用几行代码说清楚的控制流，被拆成多轮生成和解析。

程序化工具调用采用了另一种表达。工具以带类型的 Python stub 暴露给模型，模型编写脚本完成调用、串联与并行，执行和结果处理集中在一次 Agent turn 中。

结构化没有消失，只是从 JSON 字段上移到了类型、函数签名和代码执行边界。

## 误解二，代码调用只是把 JSON 换了一层语法

如果任务永远只有一次函数调用，两种方案的差别可能确实不大。

但只要出现扇出并行，代码就开始表达 JSON 不擅长表达的东西。多个调用可以自然并发，后续步骤可以引用前序结果，条件分支也不必依赖模型再生成一轮请求。

论文结果支持了这一点。在 parallel fan-out 条件下，程序化工具调用在 14 个模型中的 13 个上追平或超过基线。

上下文变长时，差异也没有消失。在 context rot 条件下，JSON 基线平均下降 2.3%，程序化方案保持稳定。这里更准确的判断不是代码永远更强，而是当任务结构变复杂时，代码提供了更贴近任务本身的表示方式。

我会把它理解成一次表示层升级。模型不再逐张填写调用申请单，而是一次交付可执行的调用计划。

## 误解三，榜单提升足以证明调用层应该立刻重写

还不能这样下结论。

这项研究覆盖 14 个模型，并且程序化方案在 11 个模型上达到不低于 JSON 基线的结果，但仍有 3 个模型没有做到。论文摘要也没有提供每种业务工具、权限模型和错误恢复策略下的完整结论。

更重要的是，代码执行会扩大控制面。JSON 调用通常只能选择工具并填写参数，程序化调用还涉及脚本运行、资源消耗、异常传播和中间结果处理。

这是我的工程判断，不是论文给出的安全评测结论。若把 PTC 接进生产系统，至少需要继续保留类型校验、工具白名单、超时限制、资源配额、审计日志和隔离执行环境。不能因为模型生成的是 Python，就默认它拥有普通应用代码的信任级别。

## 判断现有调用层值不值得改

我不会按模型名称直接做决定，而会看调用图是否已经超出 JSON 循环的舒适区。

如果主要任务是单工具查询，现有 JSON 接口清晰、稳定、容易审计，改造收益可能有限。

如果任务经常需要多个独立工具并行执行，或存在明显的前后依赖、条件分支和中间结果转换，PTC 就值得进入验证范围。上下文持续增长、调用轮次过多，也是在提醒你检查表示层。

验证时不必先动整套系统。挑一个调用链最长的代表任务，同时保留 JSON 基线，比较任务成功率、模型往返轮次、工具调用错误、延迟和上下文消耗。安全测试则要覆盖死循环、越权工具、异常参数、超时和过量并发。

只有业务任务上的收益能覆盖新增执行面，改造才成立。BFCL v4 的 10.6% 是一个值得追踪的信号，不是可以直接兑换成生产收益的承诺。

## 把模型输出从请求改成计划

这篇论文真正纠正的误解，不是 JSON 已经过时，而是结构化调用只有 JSON 一种形态。

对简单任务，JSON 仍然是一条低复杂度路径。对调用关系密集的 Agent，代码可能是更合适的中间表示，因为链式执行、并行扇出和结果复用本来就是程序结构。

我接下来会先检查调用日志，而不是先换框架。找到那些反复生成 JSON、反复回填结果的长链任务，再用同一组验收条件做一次双轨验证。是否改造，应该由调用图和安全边界决定。
