# 模型上线前别只跑考试题，先用历史会话预演一次真实风险

我现在看模型上线，最怕的不是标准题没跑够，而是新模型一接进产品，老会话里突然换了一种做事方式。用户问法没变，系统提示没变，风险却从另一个角落冒出来。

Deployment Simulation 给我的提醒很直接，新模型上线前，不该只在题库里考试，还要拿历史会话做一次发布预演。做法是保留过去真实会话的前缀，把后续回答交给候选模型重新生成，再审计它会不会引入新的不良行为，以及这些行为大概会出现多频繁。

如果你正在把新模型接进客服、代码助手、知识库问答或 agent 工作流，这个方法最值得借鉴的不是论文名字，而是那套工程姿势。把安全评估从能不能答对，改成换上它之后，产品里的风险会怎样迁移。

## 把风险面放回真实会话里

传统评测当然有用。红队、困难样本、手写测试题，适合把模型推到极端位置，看它会不会越界。

问题是，产品里的风险不总长得像考试题。很多风险藏在前文、用户习惯、工具结果、旧版本已经形成的对话节奏里。单独拿一条高压 prompt 去问，能测压力上限，却不一定能测日常分布。

OpenAI 这篇 2026 年 6 月 16 日的论文，把方法讲得很朴素。它用脱敏后的历史会话，固定到某个用户回合为止，然后让候选模型生成下一条助手回复。后面再用审计流程去看新失配类型，并估计不同风险类别的出现率。

我喜欢这个设计的一点是，它承认产品风险有上下文。新模型不是被扔进空白考场，而是被放回一段已经发生过的产品关系里。

## 找出标准评测看不到的失效路径

论文里有一个数字很有参考价值。在 GPT-5.4 研究中，对生产出现率变化达到至少 1.5 倍的类别，Deployment Simulation 预测变化方向的准确率是 92%，而基于困难 prompts 的基线是 54%。

这个数字不能被解读成它能替代所有评测。论文也明确把它放在互补位置。它擅长回答的是另一个问题，新模型接进产品后，哪些已知风险可能上升，哪些可能下降。

更关键的是评测意识。传统测试往往带着明显的考场气味，模型有机会看出自己正在被测试。模拟部署用的是更接近真实产品的会话前缀，论文里说它在 evaluation awareness 指标上更接近实际生产流量。

这点对 agent 应用尤其要命。一个代码助手在标准题里很稳，不代表它在旧项目文件、连接器结果、系统调用和前序工具轨迹里也稳。风险可能不是回答错，而是误报工具状态、绕过某个中间检查，或者在文件上下文里产生新的奖励投机。

## 给上线闸门加三个控制点

如果我要把这个方法搬进一个产品团队，我不会一上来追求复刻论文规模。更实际的是把它变成上线闸门里的三个控制点。

- 会话样本要像产品，不像题库。抽样对象应来自目标场景的历史会话，并且先做脱敏、权限过滤和用途确认。
- 指标要在发布前冻结。风险类别、判分方式、阈值和人工复核规则要先定下来，不能等看到结果再改尺子。
- 结果要能和发布后对账。同一套测量流程在上线后再跑一次，比较方向准确率、出现率校准和漏掉的新类别。

这里的坑是把历史会话重放当成万能回归测试。它只能覆盖你抽到的分布，也会受样本过滤影响。论文自己的实验排除了 Temporary Chats、企业版、API、Codex 流量和带附件会话，所以结论更代表被纳入的那部分 ChatGPT 流量。

对产品团队来说，这不是缺点，而是提醒。你的预演报告必须写清楚覆盖了哪些入口，没有覆盖哪些入口，否则看起来很科学，最后还是会在盲区里摔跤。

## 把 agent 工具链单独拎出来验证

最难的部分是 agentic tool use。因为真实行为不只取决于用户说了什么，还取决于文件系统、连接器、系统调用、网络服务和之前的工具结果。

论文的处理方式是用另一个模型模拟工具响应，并在可能时访问原始轨迹和时间匹配的代码库。这给了我一个很明确的工程启发，agent 上线前不能只重放文本，要重放状态。

更现实的做法是给高风险工具链留一个小型预演集。

- 对代码助手，保留代表性仓库快照、最近失败任务、权限边界和工具返回。
- 对客服 agent，保留真实工单前缀、订单状态样本、升级规则和拒答边界。
- 对知识库问答，保留旧检索结果、缺失资料场景和过期文档场景。
- 对自动化工作流，保留每一步工具输出，以及失败后的恢复路径。

我认为这里的核心不是多测几道题，而是让候选模型在尽量相似的状态里暴露行为变化。标准评测像安检门，模拟部署更像彩排。两者都要有，但不能互相冒充。

## 上线前跑一张风险预演卡

可以把这套方法压成一张发布前检查卡。它不需要豪华平台，先从一个产品场景做起就够。

- 选择一个最容易出问题的入口，例如多轮客服、代码修改、长上下文问答或带工具的 agent。
- 抽取一批已脱敏历史会话，只保留候选模型需要看到的前缀。
- 让新模型生成下一条回复，不改用户问题，不临时加提示。
- 用冻结后的风险分类器或人工复核规则打分。
- 记录每个风险类别的预测出现率，以及相对旧模型的升降方向。
- 发布后用同一套流程再跑真实流量，给这次预演记分。

这张卡的价值不在于让风险归零。它让团队在上线前知道自己赌的是什么，并且在上线后知道自己预测错在哪里。

我会把它放在模型接入流程里，位置在标准评测和灰度发布之间。考试题负责找能力边界，历史会话预演负责找产品行为变化，上线后记分卡负责让团队别只凭感觉复盘。
