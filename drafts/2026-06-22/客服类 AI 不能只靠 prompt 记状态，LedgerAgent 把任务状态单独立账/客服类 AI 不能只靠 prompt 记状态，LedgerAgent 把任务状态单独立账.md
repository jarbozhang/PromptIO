# 客服类 AI 不能只靠 prompt 记状态，LedgerAgent 把任务状态单独立账

客服、工单、订单处理这类 AI，最怕的不是答错一句话，而是拿旧信息去改真实系统。

用户前面改了地址，工具刚返回库存不足，政策里又写着某些条件不能退款。模型如果每轮都靠长 prompt 自己回忆状态，就很容易看起来回答合理，动作却错了。

LedgerAgent 这篇论文给我的最大提醒很简单，状态不要只塞进 prompt，要像账本一样单独维护。尤其在会改变环境的工具调用前，先用当前状态过一遍策略检查。

## 确认它是不是状态密集型任务

我会先问一个问题，这个客服 AI 的下一步动作，是否依赖前几轮积累出来的事实。

如果只是查 FAQ，长 prompt 还能撑一阵。但如果它要处理退货、改签、取消订单、更新账户、创建工单，状态就不是背景材料，而是动作依据。

论文里说的 task states，包含相关事实、标识符、约束和条件。这些东西可能来自用户对话，也可能来自工具返回。比如订单号、用户资格、当前库存、政策条件、已经确认过的地址。

问题在于，标准工具调用 Agent 通常没有把这些状态单独表示出来。观察结果、工具返回、政策说明都被放进 prompt，模型每次决策时再从里面重新拼出当前状态。

这就是事故的入口。

## 把状态从长 prompt 里拆出来

LedgerAgent 的做法不是换一个更会聊天的模型，而是在推理阶段维护一份独立 ledger。可以把它理解成任务状态账本。

这份账本记录已经观察到的任务状态，再把状态渲染回 prompt，让模型决策时看到更明确的当前上下文。

我更关心它对产品设计的启发，客服 AI 不应该只保存对话历史，还应该保存可执行动作依赖的状态。

一张短卡片就够用。

- 用户身份和关键标识是否已确认
- 当前任务目标是否还有效
- 工具返回的新事实是否覆盖了旧事实
- 领域政策依赖的条件是否已更新
- 下一次工具调用会不会改变订单、账户、工单或权限

这不是为了做一套复杂数据库，而是为了避免模型在一屏又一屏上下文里自己捞关键状态。

## 在改系统前做策略检查

LedgerAgent 更关键的一步，是把 ledger 用在 state-dependent policy constraints 上。也就是那些依赖当前状态才能判断的政策约束。

很多客服规则不是静态的。能不能退款，取决于时间、订单状态、用户条件、商品类型和前面工具查到的结果。工具调用语法正确，不代表这个动作允许执行。

所以我会把会改变环境的工具调用单独列出来。

- 创建或关闭工单
- 修改用户资料
- 取消订单
- 发起退款
- 修改配送信息
- 调整权限或订阅状态

这些动作前面都应该有一次策略检查。检查对象不是整段聊天记录，而是当前 ledger。

如果 ledger 里缺少关键状态，就不要让模型猜。它应该补查、追问，或者停在人工处理边界。

## 识别旧信息做错动作的信号

这类失败通常不会表现成语法错误。工具名对，参数也像真的，日志看起来甚至很顺。

我会重点看这几个信号。

- 用户已经更正过信息，Agent 后面仍然用了旧值
- 工具返回改变了条件，Agent 的后续动作没有跟着变
- prompt 里有政策说明，但动作判断依赖的状态不完整
- 多轮重复执行同一任务时，有时通过，有时违反政策
- 失败不是不会调用工具，而是调用时机和调用条件错了

论文摘要里提到，LedgerAgent 在四个客服领域、开放权重和闭源权重模型混合面板上，相比标准 prompt 工具调用方法提升了平均 pass@k，在更严格的多次一致性指标下收益更明显。

这个结果很符合我的直觉。客服系统最怕的不是一次答对，而是同一类任务跑十次，有几次悄悄踩线。

## 用一个最小工单验证 ledger 是否值得加

落地前我不会先改完整架构。更稳的做法，是挑一个最容易出错的状态密集任务。

比如退款资格判断。

给它设计三组对话。第一组是用户中途改信息，第二组是工具返回让资格条件变化，第三组是政策需要多个条件同时满足。每组都让 Agent 走到一个会改变环境的工具调用前。

验收不看它话术漂不漂亮，只看三件事。

- ledger 是否保留了最新状态
- 缺状态时是否停止执行或补充查询
- 工具调用前是否按当前状态做策略检查

如果这三件事做不到，prompt 再长也只是把风险藏得更深。

我的判断是，客服类 Agent 的关键工程边界正在从“会不会调用工具”转向“什么时候允许调用工具”。LedgerAgent 这篇论文的价值，不在于给所有人一个现成产品，而是把状态管理从模型记忆里拿出来，变成可以检查、可以拦截、可以复盘的工程对象。

准备上线客服 AI 时，先别急着扩写系统提示词。先把一个会改系统的任务拿出来，给它立一本状态账。
