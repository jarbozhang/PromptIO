# 知识工作不能照搬写代码工具，过程记录比最后文件更重要

我最近看到 Ethan Mollick 对 Codex、Cowork、Code 这类工具的批评，第一反应不是“他说 Agent 不行”，而是他点中了一个更难处理的问题。

很多人把写代码 Agent 的范式直接搬到研究、分析、管理里，以为只要最后交出一份文档、PPT 或任务列表，就算工作完成。可知识工作最值钱的部分，常常不在最后那个文件里。

真正容易丢掉的，是探索路径、失败分支、临时假设、观点变化，还有那些看起来没被采用、但帮你排除错误方向的过程记录。

## 误解一，把最终文件当成真相来源

写代码时，最后的代码库通常可以承载大量上下文。你可以看 diff、看测试、看 commit，反推它为什么变成现在这样。代码虽然不等于全部事实，但它确实是一个强真相来源。

Mollick 的批评在这里很尖锐，Codex、Cowork、Code 这些工具仍然很“软件脑”。它们天然相信最后交付物最重要，软件本身能代表工作结果。

可研究报告不是代码库。PPT 也不是代码库。

一个分析师最后交出 20 页材料，里面可能只剩结论、图表和建议。被删掉的部分，可能包括三条被推翻的假设、两个没跑通的原型、一组不可靠的数据来源，以及一次观点反转。

如果 Agent 只读最终文件，它会以为这是一条直线。可真正的知识工作更像学习循环，你一边找资料，一边换问题，一边修正判断。

## 不完整的地方，是过程被压扁了

很多 Agent 工具喜欢用待办事项表示进度。完成 A，完成 B，完成 C，然后上下文压缩，继续推进。

这对软件任务有时够用。比如修一个 bug，待办写清楚复现、修改、测试，压缩后还能继续。

但对管理和分析任务，待办列表很容易变成“看起来有进展”的幻觉。

“调研竞品”这个任务完成了，Agent 知道它完成了什么，却未必知道它为什么放弃某个方向。“比较三个方案”这个任务打勾了，Agent 可能保留了结论，却丢掉了判断标准变化的过程。

我认为这就是 Mollick 说的断层。经理和分析师思考问题时，不只是往交付物上堆内容。他们在不断调整问题本身。

一旦过程被压扁，后续 Agent 再接手时，看到的是一个干净结果，却看不到这个结果是怎么被筛出来的。

## 更准确的判断，知识工作需要过程账本

所以我不太赞成一句话把问题归成“Agent 还不够聪明”。更准确的说法是，很多 Agent 工作台默认保存错了东西。

写代码可以把代码当主线。知识工作必须把过程也当主线。

这里的过程账本，不是流水账，也不是把每次对话完整存档。它至少要留下四类东西。

第一，当前问题是怎么被改写的。很多研究不是回答原问题，而是发现原问题问错了。

第二，哪些路径试过但失败了。失败分支不是垃圾，它能防止下一轮又走回旧路。

第三，判断标准发生过什么变化。比如一开始看成本，后来发现可靠性才是约束。

第四，最终交付物和过程证据之间的关系。结论从哪里来，哪些地方只是暂时判断，哪些地方需要复核。

这套东西如果没有被保存，最后文件越漂亮，后续协作反而越危险。因为它会给人一种“已经想清楚了”的错觉。

## 调整做法，把 Agent 当研究同事而不是文档机器

如果你现在已经在用 Agent 做知识工作，我会先改一个习惯，别只让它产出最终稿。

更稳的方式，是每轮让它留下一个简短的过程记录。不是长篇解释，而是能帮助下一个人接着思考的工作痕迹。

可以这样要求它记录本轮做了什么、放弃了什么、判断怎么变了、还有什么没确认。这个记录应该和最终稿并列存在，而不是藏在聊天记录深处。

对管理、研究、分析类任务，我还会避免只用“任务完成率”判断进展。更有价值的问题是，现在我们比上一轮少了哪些误解，多了哪些可验证判断。

这也是长时间运行模型做深度知识工作时的难点。Mollick 提到，像 Fable 这类长运行模型被设计成最后给你交付产品。你可以靠提示词绕过一部分问题，但工具外壳仍然在把你推向“交付最终物”。

这不是完全不能用，而是要有意识地反着用。让它交付文件之前，先交付思考路径。

## 真正的分水岭，不是会不会写更多文件

我对这条批评的理解是，Agent 想走出写代码场景，不能只学会打开更多应用、生成更多文档、完成更多待办。

它需要理解知识工作里的“半成品”也有价值。

一次失败实验，一条被否掉的路线，一个中途改变的判断标准，都是工作资产。它们不一定出现在最终 PPT 里，却决定了这份 PPT 是否可信。

如果一个工具只能保存最后文件，它更像文档生产器。如果它能保留学习循环，它才开始像研究同事。

我会把下一次分析任务改成两份交付，一份是最终稿，一份是过程账本。前者给人看，后者给未来的自己和下一个 Agent 看。

别急着问 Agent 最后能产出什么。先问它，能不能把自己怎么想过也留下来。
