# RepoPrompt 开源后，写代码前最该补的是上下文工程

我现在看代码类工具，第一反应已经不是它能不能把 prompt 写长，而是它能不能帮我把问题切小。

RepoPrompt 开源这件事，最值得看的也不是免费了、上 GitHub 了，而是它把一个老问题摆到台面上，写代码前，很多人缺的不是更强的模型，是更干净的上下文。

如果你经常把整个仓库丢给 Claude Code、Codex、OpenCode 或 Gemini CLI，然后等它自己理解一切，这篇可以当成一次自查。读完至少能做一件事，把下次代码提问从“全仓库求解”改成“挑文件、拆任务、分执行”。

## 选一个会浪费 token 的真实任务

我建议别拿“重构整个项目”这种大词测试。它太虚，模型很容易给你一堆看起来有道理、落不到文件里的建议。

更适合 RepoPrompt 的最小场景，是这种任务。

- 改一个登录流程里的错误提示
- 给某个 API handler 补一个边界判断
- 找出一个组件为什么状态没有刷新
- 让一个 CLI 命令多支持一个参数

这类任务的特点很清楚，相关文件有限，但散在不同目录里。你真正想给模型看的，不是整个仓库，而是入口文件、调用链、类型定义、测试或示例。

RepoPrompt 最早做的事情就很朴素，帮开发者从代码仓库里挑文件，拼出一段更高质量的 prompt，再交给 ChatGPT 或 Claude。听起来像“小工具”，但它踩中的是代码提问里最贵的一层成本。

超过 32K token 的 prompt 不只是贵，还可能让模型表现变差。上下文越多，不等于理解越好。很多时候，模型被你塞进去的无关文件拖慢了判断。

## 把仓库切成模型真正需要看的几块

我会把一次代码任务拆成四类上下文，而不是按目录全选。

可收藏的上下文检查表。

- 任务入口，用户操作、命令、路由、组件或函数从哪里进入
- 关键调用链，入口往下走会碰到哪些核心文件
- 约束文件，类型、schema、配置、权限、错误码
- 验收材料，现有测试、fixture、README 示例或复现步骤
- 明确不要看的部分，构建产物、无关页面、旧实验代码、大段锁文件

这一步的价值，是把“让模型读仓库”改成“让模型读证据”。

我认为 RepoPrompt 开源后的核心启发就在这里。它不是教你拼一个更长的 prompt，而是提醒你，代码生成前还有一道工程动作，叫上下文选择。

很多人把 prompt 写得很认真，但文件选得很粗。结果是模型回答时像在猜，它不是能力不够，而是你给它的证据混乱。

## 让规划和执行分开跑

这次开源版变化更大的地方，是架构反过来了。

旧理解里，RepoPrompt 像一个把文件打包给模型的桌面工具。开源后的方向更像一个上下文工程入口，内置 MCP server 成为主控，底层命令行工具变成可替换的执行层。

来源材料里提到的执行层包括 Claude Code、Codex、OpenCode、Gemini CLI。也就是说，你可以把一个推理模型放在规划位置，让它做任务分解，再把子任务交给不同 agent 执行。

这个设计对代码工作流很重要。

规划模型不一定直接改代码。它更适合回答，哪些文件相关、任务能不能拆、每个子任务需要哪些证据、交付后怎么验收。

执行模型也不必看完整上下文。一个 agent 负责测试，一个 agent 负责实现，一个 agent 负责检查调用链，每个 agent 只拿自己需要的文件。

这比“一个大 prompt 里塞所有东西，然后祈祷模型别跑偏”稳得多。

## 用验收标准防止 agent 自嗨

上下文工程不是选完文件就结束。真正能救质量的，是在 prompt 里提前放验收标准。

对一个最小任务，我通常会把交付口径写得很硬。

- 需要改哪些行为
- 哪些行为不能变
- 应该补什么测试或检查
- 不能修改哪些文件
- 如果信息不够，先返回缺失上下文，不要直接猜

这里最容易踩坑的是，把 RepoPrompt 当成“提示词美化器”。那会用错它。

它更适合做代码任务的分诊台。你先用它把仓库里的证据切出来，再决定交给哪个 CLI 跑，最后用测试、diff 和人工 review 收口。

如果没有验收标准，agent 很容易把“完成任务”理解成“生成一段像答案的代码”。上下文选得再好，也会在最后一步发散。

## 常见坑不是不会用，是太想一次做完

我看到很多代码提问质量低，不是因为开发者不会写 prompt，而是每次都想让模型一次性解决太多事。

RepoPrompt 这次开源，反而让我更确认一个判断，agent 应用的上限不只看模型，也看任务拆分有没有工程化。

几个坑可以直接避开。

- 不要把整个仓库当默认上下文，先挑入口、调用链、约束和验收材料
- 不要把“修 bug”和“重构架构”放进同一个任务，先让模型解决可验证的一段
- 不要让每个 agent 都读同一堆文件，按子任务分配上下文
- 不要只写需求不写禁区，明确哪些行为和文件不能动
- 不要用长 prompt 掩盖不清楚的任务，信息缺失时让模型先反问缺什么

目前社区版只支持 macOS，安装入口是 Homebrew，命令是 `brew install --cask repoprompt-ce`。跨平台版本还在开发中，落地前可以先用一个小仓库验证这套方法，不必一上来迁移主力项目。

下一次你准备让 AI 改代码前，先别急着打开对话框。把任务写成一句话，再列出它真正需要看的文件。

如果这一步列不出来，问题大概率不在模型，在上下文还没工程化。
