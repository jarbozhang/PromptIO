# Qwen3.6-27B MTP 在 llama.cpp 跑到 60 tokens/s 4090 本地 coding agent 又快了一截

本地 coding agent 最烦人的不是模型不会写代码，而是它慢。

你让它读一圈仓库、改一批文件、跑一轮测试，中间每一步都在吐 token。速度一慢，人就会下意识接管，agent 工作流也就断了。

所以今天这条 Qwen3.6-27B MTP + llama.cpp 的消息值得单独拎出来。

中文社区里 @9hills 给出了一套实测参数，llama.cpp main 分支，Qwen3.6-27B MTP GGUF，4090 上跑到 60 tokens/s。llama.cpp 作者 Georgi Gerganov 也转发说，llama.cpp 已经给 Qwen3.6 family 加上 MTP，这对本地 AI 生态是一个重要节点。

这篇不写“谁赢谁输”。本地推理已经写得够多了，今天只看一件事，怎么把速度和上下文留给 coding agent。

## MTP 改的不是模型人设，是等待时间

MTP 可以理解成一种投机解码路线。模型不是一个 token 一个 token 地老实排队，而是尝试一次往前草拟多个 token，再由主路径确认。

对用户来说，结果很直观，输出更快。

last30days 抓到的 r/unsloth 和 r/LocalLLaMA 讨论里，Qwen3.6 MTP GGUF 的热度也集中在吞吐上。有人反馈从 70 t/s 到 105 t/s，也有人讨论 `spec-draft-n-max` 设 4、5、6 的取舍，还有 RTX 5090、Strix Halo、12GB 显存跑长上下文的不同结果。

这些讨论说明，MTP 不是一个论文词，而是在进入普通玩家的参数表。

## 4090 这组参数怎么读

@9hills 给出的命令里，几个参数很关键。

`--flash-attn on` 是基本项，能开就开。

`--cache-type-k q8_0` 和 `--cache-type-v q8_0` 是在给长上下文省显存。

`--ctx-size 128000` 看着很诱人，但他也提醒，Q3 量化只是勉强支持到 100K 上下文，可能会 OOM。

真正和 MTP 相关的是这几项，`--spec-type draft-mtp`、`--spec-draft-p-min 0.75`、`--spec-draft-n-max 2`。

如果你只是想复现，别一上来追最大上下文。先把上下文压到 32K 或 64K，确认速度、稳定性和显存占用，再往上推。

本地 agent 最怕的是跑到一半 OOM。一次 128K 很漂亮，但能稳定跑完十轮任务更重要。

## 它适合什么任务

我会优先把它放在三类任务里。

第一，仓库阅读。让模型读目录、接口、测试结构，给出项目地图。这类任务 token 多，但风险低。

第二，代码初稿。让它先生成小函数、脚本、测试样例，再交给更强的云端模型或人工审阅。

第三，本地隐私任务。公司内部日志、私有文档、不能随便传出机器的代码，可以先在本地跑一轮摘要和分类。

不建议一上来让它接管生产级重构。不是 Qwen 不行，而是本地 agent 的瓶颈通常在工具调用、测试反馈、上下文裁剪和权限边界，不只在模型分数。

## 显存账要先算清楚

@9hills 的判断很实在，如果真要用于 Coding Agent，更推荐 4090 魔改 48GB，或者双卡 24GB。

这句话比 60 tokens/s 更重要。

因为 coding agent 不只是生成答案。它会读文件、保留上下文、调用工具、吃测试日志。模型本体能塞进去，只是第一步。KV Cache 能不能撑住，才决定它能不能干长活。

如果你只有 24GB 卡，可以试，但别把预期设成“本地替代云端全流程”。更合理的定位是，本地先筛、先读、先写草稿，关键决策再交给更稳的模型或人工。

## 我的判断

Qwen3.6-27B MTP 这波真正的价值，是把本地 coding agent 的体感往前推了一格。

60 tokens/s 不会自动让 agent 变聪明，但会让人更愿意把任务丢给它跑完。AI 编程工具的很多改变，不是来自一次惊人的 benchmark，而是来自等待时间一点点变短。

如果你今天要试，别先跑大项目。找一个非核心仓库，让它做三件事，生成项目地图、改一个小脚本、补两条测试。

能稳定跑完这三件事，再谈 128K 上下文和全天候本地 agent。
