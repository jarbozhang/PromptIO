# Agent Game Forge 把 Codex 和 Claude Code 接进 2D 游戏 IDE AI 不只会出概念图

AI 做游戏，最尴尬的阶段是“图很好看，游戏跑不起来”。

你可以让模型画角色、写背景故事、出关卡概念图，但真正要变成一个能玩的原型，还得有人把精灵图、碰撞框、物理、道具、陷阱、场景切换和导出流程接起来。

Agent Game Forge 有意思的地方，就在这里。

它不是再做一个文生图玩具，而是把 Codex CLI 或 Claude Code 接进本地 2D 游戏 IDE，让 agent 在一个可视化游戏工程里干活。

## 它解决的是中间那段脏活

项目 README 把 Agent Game Forge 定位成 local-first、bring-your-own-agent 的 2D game IDE。

你可以接 Codex CLI，也可以接 Claude Code。agent 负责生成游戏素材、关卡布局、精灵图、视差背景、碰撞框、陷阱、拾取物和基础逻辑。

人不是完全退出，而是在可视化编辑器里拖拽微调，然后直接 Play。

默认导出是 vanilla JS + Canvas，推到 GitHub Pages 就能跑。Godot 4 和 Unity 在路线图里。

这条路线对独立开发者很现实。你不一定先学完整引擎，也不一定先组一个美术和程序小队。你先做一个能玩的 2D 原型，再决定要不要继续投入。

## 本地优先这个选择很对

做游戏原型，项目文件很容易乱。

素材、脚本、场景配置、导出产物、临时图像、提示词，全都混在一起。如果每一步都跑在远端黑盒里，你很快就不知道哪个文件是谁改的。

Agent Game Forge 选择本地优先，项目文件留在本地磁盘，服务跑在本机，keys 也在自己机器上。README 里写的默认服务是 daemon 在 localhost:7621，Web UI 在 localhost:7620。

这对 agent 工作流很重要。

因为你可以把它当成一个真实工程，而不是一次性生成器。今天改碰撞框，明天改移动手感，后天换一组背景，所有变化都能被 Git 接住。

## 社区里最有价值的一句话

last30days 抓到一个 r/aigamedev 帖子，作者说自己不是游戏开发者，只是想做游戏想了 20 年，但不会画图，也不喜欢学引擎，于是做了这个自己想要的工具。

这句话比项目功能表更能说明问题。

AI 游戏工具如果只服务专业团队，它会被现有引擎和流程挤压。但如果它服务的是“有想法、能判断、缺执行能力”的人，它的入口就完全不同。

Agent Game Forge 的目标用户，可能不是 Unity 老手，而是产品经理、独立开发者、设计师、编剧、学生，甚至是会写一点脚本但做不了完整游戏的人。

## 不要期待它一步生成成品

我不会把它理解成“输入一句话，得到商业游戏”。

更合理的期待是，输入一句话，得到一个可编辑的第一版场景。

这中间差很多。

可编辑，才是重点。你能改角色位置，改碰撞范围，改跳跃高度，改陷阱触发，改关卡节奏。agent 生成的不是最终答案，而是一个能继续被人加工的工程状态。

这个思路比“AI 一次生成完整游戏”靠谱得多。

## 我会怎么试

如果今天拿它做实验，我不会上来做 RPG 或开放世界。

我会选三个最小原型。

第一个，横版跳跃，只有移动、跳跃、平台、陷阱、终点。

第二个，俯视角收集，角色移动、拾取物、计分、倒计时。

第三个，单屏解谜，开关、门、钥匙、障碍物。

这三类原型能测出最关键的东西，agent 能不能理解关卡规则，生成的碰撞框能不能用，人能不能在编辑器里快速修正。

如果这三关过了，再谈美术风格、剧情和多关卡。

## 这个方向值得盯

AI+游戏过去有点虚，原因是太多 demo 停在概念图和宣传片。

Agent Game Forge 这种工具把问题拉回工程现场，文件、场景、Canvas、Play 按钮、导出路径、GitHub Pages。

它不一定马上变成主流游戏开发工具，但它指向一个更扎实的方向，AI 先帮你把可玩的原型搭起来，然后人用编辑器接着改。

对独立开发者来说，能玩的粗糙原型，比十张漂亮概念图更值钱。
