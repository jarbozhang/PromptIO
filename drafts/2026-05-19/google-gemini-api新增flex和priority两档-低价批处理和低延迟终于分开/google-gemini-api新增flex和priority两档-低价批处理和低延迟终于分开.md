# Google Gemini API 新增 Flex 和 Priority 两档 低价批处理和低延迟终于分开

Gemini API 这次更新，真正有用的不是多了一个参数，而是 Google 终于把两种完全不同的请求拆开了。

一种请求要便宜，可以慢一点，可以排队，可以重试。另一种请求要稳，要快，要在用户还盯着屏幕的时候回来。

以前很多团队会把这两类任务混在同一个 API 账户、同一个队列、同一套超时策略里。结果很尴尬，批量任务把额度吃紧，在线请求被拖慢；为了保在线请求，又不得不给所有任务都按高优先级算账。

Gemini API 新增的 Flex 和 Priority inference tier，解决的是这个工程问题。

## 两个档位，不是两个营销名词

Google 官方博客把 Flex 定位成低成本、资源可用时执行的推理档。它适合那些不需要马上返回的任务，比如夜间批处理、长文档摘要、离线评测、数据清洗、内容标签、日志归类。

Priority 则反过来，目标是低延迟和更稳定的服务体验。它适合在线产品里的用户请求，比如聊天、搜索增强问答、客服辅助、代码补全、实时工作流编排。

开发者在请求里用 `service_tier` 做选择。这个设计不复杂，但对实际成本控制很关键。

以前你只有一个水龙头，现在至少能分出两个管道。便宜管道跑后台活，优先管道接用户活。

## Webhooks 补上了另一个缺口

另一个容易被忽略的更新，是 Gemini API 的 Webhooks。

Google 把它描述成 push-based notification system，用来替代低效轮询。也就是说，长任务跑完以后，服务端主动通知你，而不是你的后台每隔几秒去问一次“好了没”。

这对 agent 后台很实际。

很多长任务不是模型慢，而是系统设计把等待做得很笨。轮询会制造三种浪费，API 请求浪费、队列 worker 浪费、状态机复杂度浪费。

Webhooks 的价值，是把“等待模型返回”变成“收到事件再继续”。如果你已经在做队列、任务编排或多 agent 协作，这个变化比多一个模型名字更值得看。

官方文档里还提到，Webhook 请求带签名校验，失败后会重试。这两个细节说明它不是只给 demo 用，而是在往生产任务的方向补基础设施。

## 国内开发者怎么用

我会把它拆成三条队列。

第一条是在线队列。用户点了按钮、正在等结果、等待时间直接影响体验，这类请求走 Priority。这里不要省错钱。

第二条是离线队列。每天凌晨跑内容归档、把客服记录做摘要、把代码仓库做索引、给商品图打标签，这类请求走 Flex。它们不该和在线请求抢资源。

第三条是长任务队列。视频理解、大文件处理、多阶段 agent、批量报告生成，用 Webhooks 接回调，不再靠 worker 原地等。

如果你做的是 AI 应用，而不是单纯调 API 玩，真正该关心的不是“哪个模型又强了几分”，而是任务怎么分层。

模型调用会越来越像云服务。你要为延迟、可靠性、回调、重试、预算上限分别建规则。

## 这次更新也暴露了一个新现实

社区里最近对 Gemini API 的反馈并不全是兴奋。last30days 抓到的讨论里，有人关注 Webhooks，也有人在抱怨 API key、账单和大图请求稳定性。

这类反馈反而说明 Gemini API 正在进入更真实的生产场景。玩具阶段大家只问效果；生产阶段大家开始问账单、失败、延迟和密钥管理。

Flex、Priority、Webhooks 不是让 Gemini 一夜之间变成所有场景的默认选择。它们更像是 Google 承认了一件事，AI API 不能只按模型列表来设计，必须按工作负载来设计。

今天如果你有一个 AI 应用在跑，建议先做一件小事，把所有模型调用按“用户等待”和“后台处理”分成两列。

能放后台的，不要走在线预算。需要用户等待的，不要和批处理混在一起。

这一步做完，Gemini 这次更新才真正有意义。
