# Bun 用79分钟把 Issue 变成可审查 PR：真正有效的不是模型，而是证据门禁

一次 Issue 提交后，Bun 的 robobun 用 79 分钟给出了修复 PR。真正值得复用的不是这个速度，而是 PR 里那组无法含糊的证据。

回归测试必须在主分支失败，在修复分支通过。ASAN 和 release 配置各跑一次，输出随 PR 一起交给审查者。Agent 说自己修好了没有用，门禁只认机器留下的结果。

对正在搭建自动修复流程的团队，这个案例提供了一套更重要的设计原则。生成可以交给 Agent，可信度必须来自可复现证据，合并权则要留在生成链路之外。

## 还原这次79分钟的修复现场

这次流程从人类提交 Issue 开始。robobun 响应问题，定位代码，补上修复与回归测试，再创建 PR，整个过程用了 79 分钟。

表面上看，这是一个 Claude Code 自动修 Bug 的故事。继续拆开才会发现，模型只是 worker。公开仓库里的 `CLAUDE.md`、`REVIEW.md`，以及 `.claude/` 下的 hooks 和 skills，才是它执行任务时依赖的工程上下文。

robobun 也不是 GitHub App，而是普通用户账号。真正的编排器运行在 Bun 自己的机器里，GitHub Actions 只承担 lint 和治理，外部无法从工作流文件看到完整引擎。

这解释了为什么照着页面上的 Actions 配置抄一遍，很难得到相同结果。可见部分负责约束和留痕，不可见部分负责任务调度，两者并不是同一个系统。

## 找到自动修复最危险的失效点

自动修复最常见的失败，不是 Agent 完全不会改代码，而是它交出一个看起来合理、却无法证明有效的补丁。

测试只在修复分支通过，证据仍然不完整。因为这个测试可能在主分支原本就通过，它没有真正覆盖 Issue 描述的故障。更糟的情况是，Agent 修改了测试，让错误表现跟着断言一起消失。

Bun 的门禁要求同时保留两份输出。相同回归测试在主分支上失败，说明它能捕获原问题。在 PR 分支上通过，说明代码变化修复了这条失败路径。

如果无法完成证明，Agent 不能用一段自由发挥的解释蒙混过去。它必须明确承认证据缺失，并从固定词表里选择原因。这里控制的不是文风，而是失败状态的可观测性。

## 理解为什么提示词和多跑测试仍然不够

给模型写更长的提示词，确实能改善局部行为，却不能替代验收协议。提示词告诉 Agent 应该怎么做，证据门禁决定什么结果才有资格进入审查。

多跑几套测试也不等于证据充分。ASAN、release 或更多测试矩阵可以扩大检查面，但如果缺少主分支失败这一半，审查者仍然无法确认新增测试是否对应真实回归。

Bun 还把历史审查经验变成了可执行约束。`REVIEW.md` 来自约 2500 个已合并 PR 的 review 记录，审查者实际卡过的问题被提炼成规则，再交还给 Agent。

这比凭空编写一份理想规范更扎实。规则来自仓库真实发生过的缺陷，Agent 学到的不是通用代码常识，而是这个项目愿意合并什么、经常拒绝什么。

## 把生成、审查和合并拆成三种权力

robobun 只负责开 PR，不负责合并。PR 创建时，Jarred 会被设为 assignee，另外两个 bot 参与审查，最终 merge 权只在两名人类手里。

这种分权避免了最危险的闭环。若同一个 Agent 负责生成补丁、解释证据、批准审查并完成合并，它既是提交者，也是裁判。任何一步的误判都会顺着自动化链路直接进入主分支。

根据源材料披露的数据，robobun 每天创建约 142 个 PR，占仓库历史全部 PR 的 38%。它合并后被 revert 的比例为 0.34%，人类作者对应比例为 1.33%。证据门禁上线后累计合并 1186 个 PR，记录为零 revert。

但流程并没有消灭成本。两名人类面对每天约 142 个 PR，中位合并时间为 3.2 小时，尚有 2671 个 open PR。生成吞吐提高后，瓶颈转移到了审查容量。

## 修复自己的自动修复流程

迁移这套方法时，优先改 PR 契约，而不是继续堆模型调用。每个自动修复 PR 至少要回答三个问题。

- 哪个测试能够稳定复现 Issue
- 同一测试在主分支上的失败输出是什么
- 同一测试在修复分支上的通过输出是什么

再把无法证明的情况做成结构化状态，限制原因选项，并让流水线检查证据是否齐全。审查 bot 可以提供意见，但不能和提交 bot 共用最终决定权。合并权限应由独立的人或受控流程持有。

Bun 仓库还保留了一个直接的人工止损机制。人类给低质量 PR 添加 `slop` 标签后，PR 会自动关闭，标题也会改成 `ai slop`。自动化负责扩大处理能力，人类仍负责定义不可接受的结果。

## 留下一张自动修复事故卡

**事故表现**　Agent 提交了语义合理的补丁，但无法证明它复现并修复了原问题。

**关键根因**　团队把模型回答当成验证结果，让生成者同时掌握解释权和放行权。

**检测信号**　PR 只有修复分支通过记录，没有同一测试在主分支上的失败记录。

**控制动作**　强制提交成对测试证据，结构化记录无法验证的原因，拆分生成、审查与合并权限，并保留人工关闭入口。

自动修复流程是否可靠，不取决于 Agent 能写多少代码，而取决于一次没有证据的修复，能不能被系统明确挡住。
