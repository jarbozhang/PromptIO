# Codex 为什么把 Word 逐页看成图片：文档交付前别省掉视觉验收

一份 Word 文档能正常抽出文字，不等于它能正常交付。分页突然断开、表格越过页边距、字体被替换、图片压住正文，这些问题都可能躲过文本检查。

如果你经常让 Codex 生成报告、方案或交付文档，真正该关注的不是它有没有写完，而是它有没有看到读者最终看到的页面。

更稳妥的办法，是把文档制作拆成两种阅读。结构化读取负责核对内容，逐页渲染负责检查成品。两者缺一项，验收都不完整。

## 看着 Codex 一页页打开文档

Michael Anti 观察 Codex 工作时，发现它反复使用 View Picture 阅读 DOCX 的每一页。这个动作很像人工交付前翻阅最终稿，而不是把文件抽成一段纯文本后快速扫完。

讨论里有人猜测它是为了更快，也有人担心逐页查看会消耗更多 token 和网络流量。更有解释力的线索来自文档本身。

DOCX 实际上是一个压缩包，正文、样式和排版关系分散在 XML 中，图片则放在独立的 media 目录。评论者 Andrew 提到，如果缺少 Word 原生接口，直接解析这些内容很容易误判排版，处理图片还要再走另一条路径。

于是，逐页看图未必是一条省资源的捷径。它更像是在承认一个现实，解析器知道文档里有什么，却未必知道成品看起来怎样。

## 让结构读取负责内容正确

文档生成过程仍然需要结构化读取。标题层级、段落内容、表格单元格、批注、页眉和链接，都更适合从文档结构中提取和修改。

假设 Codex 正在制作一份客户方案。它可以先检查章节是否齐全，数字是否前后一致，表格有没有漏列，引用链接是否存在。到了这一步，交付物在逻辑上可能已经成立。

但文本抽取会把页面空间压平。原本位于页眉、正文、表格和批注里的内容，可能变成顺序混乱的文本片段。它能告诉你一句话存在，却回答不了这句话是否被图片挡住，也无法判断一张表是否被分页切得难以阅读。

结构读取解决的是内容有没有进入文件，不是内容有没有正确出现在页面上。

## 把成品渲染成读者看到的样子

流程进入渲染阶段后，DOCX 会被转换成逐页图像或 PDF 页面。此时检查对象不再是 XML 节点，而是一张张最终页面。

在这个场景里，视觉验收会暴露四类文本解析难以发现的问题。

分页问题会让标题落在页尾，正文被推到下一页。错位问题会让表格、页眉或图片偏离预期位置。字体替换会改变字宽和行高，进而带动整页重新排版。图文遮挡则可能让文字真实存在，却无法被读者完整看到。

佟振保在讨论中补充，不同办公软件的排版规则并不完全一致。即使 DOCX 和演示文稿的内部数据没有报错，最终页面仍可能出现只有视觉检查才能发现的问题。

这也解释了为什么一次编辑后需要重新渲染。改动一段文字，影响的可能不只是这一段，还可能是后续多页的分页位置。

## 让交付物经历两轮不同的验收

回到那份客户方案。经过结构检查，它的章节、数字和链接都没有遗漏。逐页渲染后，却可能发现封面副标题换行、第三页表格被切断、第六页图片盖住脚注。

修复这些问题后，还要再次读取结构，避免排版调整意外删除内容，再重新渲染受影响页面。流程由此形成一个短循环。

文档结构进入 Codex，Codex 修改内容，渲染器生成页面，Codex 逐页查看，发现问题后回到文档继续调整。最终交付物的变化，不只是文字更准确，而是从一个可以打开的文件，变成一个可以放心发出的成品。

我的判断是，文档生成任务的完成条件不该是文件已保存，而该是内容检查和视觉检查同时通过。前者像代码的逻辑测试，后者更接近真实界面的验收。只做其中一项，都可能把错误留给收件人。

## 给下一份文档加上双重完成条件

下次让 Codex 制作 Word 报告时，可以把任务拆成结构生成、内容核对、逐页渲染、视觉检查、修复后复验。不要只要求生成 DOCX，也要明确要求检查每一页的分页、字体、表格边界、图片位置和页眉页脚。

如果文档要在不同办公软件中打开，还应使用实际交付环境再渲染一次。渲染结果才是读者拿到的版本，源文件结构正确只是中间状态。

先拿一份三到五页的旧报告验证这条流程。故意加入一张靠近页边的图片和一个跨页表格，再比较纯文本检查与逐页检查分别能发现什么。那几页差异，会比任何文档生成提示词更快地说明视觉验收的价值。
