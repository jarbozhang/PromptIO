# LEANN 本地 RAG 省 97% 存储，个人知识库不用先买硬盘

本地 RAG 最大的痛点，经常不是模型跑不动，而是索引太占地方。

今天 GitHub Trending 里 yichuan-w/LEANN 又冲上来。

仓库描述写的是，RAG on Everything，97% storage savings，fast、accurate、100% private RAG application on your personal device。

GitHub API 现在显示 11370 stars、1014 forks，MIT License。今天 trending 抓到日增 +186。

## 本地 RAG 为什么会膨胀

很多人做个人知识库，流程都差不多，

PDF、Markdown、网页剪藏、邮件、聊天记录，切 chunk，跑 embedding，塞进向量库，再接 Ollama 或本地模型问答。

小规模没问题。

但你一旦想把「所有东西」都塞进去，问题就来了。

微信聊天记录、邮箱、代码仓库、浏览器收藏、PDF 报告、Notion 导出，加起来不是几千个 chunk，而是几十万、几百万个 chunk。

向量、元数据、索引结构、备份文件会一起膨胀。

最后你会发现，原文没多大，索引反而多出一大坨。

你本来想做私有知识库，结果第一步先买硬盘。

LEANN 打的就是这个点，省 97% 存储。

## 它真正的卖点

公开描述里最关键的是三个词，

storage savings，省空间
private，隐私留本地
personal device，个人设备能跑

个人知识库最怕的是能跑但越跑越贵。如果索引体积压不下来，本地 RAG 很难长期存在。

邮件、聊天记录、公司文档、个人笔记，也不适合随便上传给云服务。

所以 LEANN 的方向很明确，本地 RAG 的下一阶段不是更会聊天，而是能不能把你的全部个人数据装下。

## 适合先放什么数据

我会从四类材料开始试，

1. PDF 和长文档，论文、研报、产品手册
2. 聊天记录，微信群、飞书群、Slack
3. 代码和 issue，适合找历史设计原因
4. 个人写作资料，公众号草稿、摘录、网页剪藏

真正的知识往往不在正式文档里，而在讨论记录里。

## 我的判断

本地 RAG 的竞争会从「谁接的模型多」转向「谁能长期管理个人数据」。

前两年大家关心本地模型能不能跑，Ollama、llama.cpp 解决了第一层。

后来大家关心能不能问自己的文档，各种 RAG 工具解决了第二层。

现在第三层来了，数据越来越多后，索引成本、增量更新、隐私边界、长期维护会变成核心问题。

LEANN 站在第三层。

它不一定替代现有 RAG 工具，但会逼大家重新重视索引体积。

个人知识库如果只能装 500 篇文档，那只是玩具。

如果能装 10 年聊天记录、5 年邮件、全部 PDF 和代码仓库，才真的接近第二大脑。

## 建议怎么试

不要直接把全部资料丢进去。

先选一个小但真实的数据集，

500 篇收藏文章，或一个项目的全部文档，或三个月聊天导出。

记录三组数字，原始文件大小、索引大小、检索延迟。

再问 20 个你真的关心的问题。

比如，去年我在哪篇笔记里提过这个需求？这个项目为什么放弃旧方案？某个概念我最早从哪里看到？

体积和答案都过关，再扩大到全量个人知识库。
