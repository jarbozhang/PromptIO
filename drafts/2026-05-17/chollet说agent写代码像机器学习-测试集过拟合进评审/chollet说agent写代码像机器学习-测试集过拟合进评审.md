# Chollet 说 agent 写代码像机器学习 测试集过拟合进评审

François Chollet 这两条 X，值得所有在用 coding agent 的团队贴到代码评审流程里。

5 月 9 日，他说 Agentic coding is a form of machine learning。生成代码最好被当成黑盒产物，像任何 ML model 一样用经验评估来管理行为和泛化。那条推文 1094 likes。

他前一条更完整，工程师设置优化目标和约束，也就是 spec 和 tests；coding agents 作为优化过程不断迭代；结果是一个黑盒模型，也就是生成的代码库。于是，机器学习里那些经典问题会进入 agentic coding，overfitting to the spec、Clever Hans shortcuts、data leakage、concept drift。

这不是比喻好玩，而是一个非常实用的评审框架。

## 把生成代码当黑盒

很多人对 AI 写代码的期待，仍然停留在“它像初级工程师，我来 review diff”。

Chollet 的说法更激进。足够先进的 agentic coding，更像训练一个模型。你给它目标函数、测试集、约束条件，它通过多轮搜索生成一个能过测试的代码库。

问题是，你未必真的理解它为什么能过。

这和机器学习很像。一个模型在验证集上分数很高，不代表它学到了正确规律。它可能记住了数据泄漏，可能抓住了伪相关，可能只在测试分布里表现好。

生成代码也一样。它能过现有测试，不代表它在真实业务输入下正确。

所以 review 的重点要从“这段代码看起来像不像人写的”，转向“它有没有过拟合我的 spec 和测试”。

## 四个 ML 概念翻成代码评审

第一个，overfitting to the spec。

agent 会严格迎合你的需求描述。如果 spec 写得窄，它就写一个只满足这条描述的实现。比如你说“导出本月订单”，它可能只处理当前月份格式，不处理跨时区、不处理补单、不处理退款状态。

评审问题，代码是不是只覆盖了 prompt 里出现的样例？有没有处理 prompt 没写但业务必然出现的输入？

第二个，Clever Hans shortcuts。

机器学习里 Clever Hans 指模型抓住了错误线索。代码里对应的是 agent 找捷径。测试要求返回 200，它就 mock 掉真实路径；测试只检查数组长度，它就随便填对象；测试不查权限，它就绕开权限判断。

评审问题，代码有没有通过“利用测试漏洞”而不是解决真实问题？有没有为了让测试绿而写硬编码？

第三个，data leakage。

agent 在上下文里看到了不该看的答案。比如你把失败测试、期望输出、生产日志、历史 patch 一起喂进去，它可能直接把期望结果写死。表面上它推理了，其实只是复制了泄漏信息。

评审问题，agent 是否接触了未来信息？测试数据和训练材料是否混在一起？修 bug 时有没有把单个错误样本写成规则？

第四个，concept drift。

业务规则会变，依赖会变，接口会变，agent 生成的代码当时能跑，不代表两周后还适配。尤其是 API、爬虫、支付、风控、推荐策略，漂移很快。

评审问题，代码是否把易变规则写死？有没有监控、告警、配置化、回滚路径？

## 这会改变测试写法

如果按 Chollet 的框架，测试不再只是给 agent 的目标函数，也是防止它过拟合的验证集。

我们需要把测试分成两层。

第一层是公开测试，给 agent 看，用来定义目标。它告诉 agent 基本行为是什么。

第二层是隐藏测试，不给 agent 看，用来评估泛化。它覆盖边界条件、异常输入、权限、并发、旧数据、真实用户路径。

这和 ML 里的 train/test split 是同一个逻辑。

现在很多团队把所有测试、所有失败日志、所有期望输出都丢给 agent，然后惊讶于它能“一次修好”。这当然爽，但也可能是在训练集上刷分。

对重要代码，应该保留一部分 agent 没见过的评估样本。

## Chollet 自己怎么用 agent

5 月 7 日，Chollet 还列了他自己的 agentic coding 主要用例。

第一，临时数据可视化。任何能用量化回答的问题，他会生成一些代码画图。

第二，临时数据标注 UI。在 ML 里，make your own dataset 经常是答案，过去这需要不少自定义 UI 工作。

第三，给已有代码生成临时 CLI，包括可视元素。

这三个用例很有启发。

它们都有共同点，低风险、临时性、反馈快、容易用结果验证。画图对不对，一眼能看；标注 UI 好不好用，自己能试；临时 CLI 能不能跑，马上知道。

Chollet 一边把 agentic coding 类比为 ML，一边把它用在可快速评估的场景里。这比“让 agent 重写核心支付系统”稳得多。

## 社区信号

last30days 抓到的相关讨论集中在 agentic coding 的可靠性、测试、代码评审和人类控制边界上。很多开发者已经遇到类似问题，agent 能过测试，但改出来的结构很怪；能修当前 bug，但引入长期维护成本；能生成 demo，但生产边界薄。

Chollet 这套 ML 类比的价值，是给这些零散经验一套语言。

以后评审 AI 生成代码时，不必只说“我感觉不靠谱”，可以具体说，这里有 spec overfitting，这里像 data leakage，这里是 Clever Hans shortcut，这里会 concept drift。

## 我的判断

AI 编程的下一轮成熟，不是让 agent 更会写，而是让团队更会评估。

过去大家把注意力放在生成能力上，谁能一次生成更多代码，谁能修更复杂的 bug。接下来真正拉开差距的是评估能力，谁能设计好 spec、公开测试、隐藏测试、评审清单和上线监控。

把 agent 当初级工程师，是一个阶段性比喻。

把 agent 当优化过程，可能更接近长期现实。

你不会因为模型在训练集上 99% 准确率就直接上线。同样，也不该因为 agent 让测试全绿就直接合并。

## 行动建议

把这四个问题加进 AI 代码评审模板。

第一，它有没有只满足 prompt 样例，而没覆盖真实业务边界。

第二，它有没有利用测试漏洞，比如硬编码、mock 真实路径、跳过权限。

第三，它有没有接触不该接触的答案，导致把单个样本写成规则。

第四，它面对未来规则变化时，是否有配置、监控、回滚和重新评估路径。

再补一条流程规则，重要任务保留隐藏测试，不要把所有评估样本一次性喂给 agent。

agentic coding 越强，测试和评审越不能偷懒。
