# 百度 Qianfan-OCR-Fast 上 OpenRouter，国产 OCR 多模态文档解析新选项

5 月 16 日，百度的 Qianfan-OCR-Fast 静悄悄出现在 OpenRouter 模型列表里。

没有发布会，没有官方推文，模型卡只有短短两行描述，周用量也才 4.27M tokens。但对中文 RAG 和文档解析的人来说，这是一个值得记下来的时间点，国产 OCR 多模态阵营又添了一个能用统一 API 调起来的选项。

## 模型卡上写了什么

先把硬指标摆清楚。

Qianfan-OCR-Fast 的 model id 是 `baidu/qianfan-ocr-fast`，上下文 65,536 tokens，输入支持文本和图像，输出文本。定价 $0.68/M 输入 + $2.81/M 输出，按当前汇率折算大致是 4.9 元/M 输入 + 20 元/M 输出。

官方对它的描述只有一句话，"一个专为 OCR 构建的领域专精多模态大模型，在保留多模态通用智能的同时，用 OCR 专门训练数据带来了相对 Qianfan-OCR 的性能升级"。

换成实操语言，这是百度千帆把已经在云端跑了一段时间的 OCR 专精模型，挂上了 OpenRouter 的统一计费通道。开发者不用单独申请百度智能云账号、不用走鉴权 SDK，一行 OpenAI 兼容的 HTTP 请求就能调起来。

## 国产 OCR 多模态阵营的四种路线

把 Qianfan-OCR-Fast 放回国产 OCR 模型的版图里，会更容易看清它的位置。

**PaddleOCR**，百度自家的开源 OCR 工具链，本地部署，免费。CPU 也能跑，企业内网友好，但对扫描件倾斜、表格嵌套、混排公式这些复杂场景，需要堆 pipeline、调参数、训练专用模型，工程量不小。

**GLM-OCR / Qwen-VL Plus**，智谱和阿里通义的视觉语言模型路线。不是 OCR 专精，是通用多模态里附带强 OCR 能力。GLM-OCR 在表格结构化、关系抽取上表现稳定，Qwen-VL Plus 走全能型路线，对图文混排、图表理解、视觉问答都能接，价格也比 OCR 专精模型便宜。

**OmniOCR**（OmniParser 类），OCR + 文档结构理解的开源项目，强在版面分析（layout analysis），把 PDF 拆成有语义的块，配合 RAG 流水线效果好。但模型本身不做高阶推理，需要下游模型接力。

**Qianfan-OCR-Fast**，OCR 专精的多模态大模型路线。专精意味着训练语料和优化目标都围绕 OCR，对古籍、合同、票据、手写笔记这类"读不清楚"的场景压力测试更充分，代价是通用视觉理解能力不如 Qwen-VL Plus 全面。

这四条路不是替代关系。本地大批量处理用 PaddleOCR，需要图文混合推理用 Qwen-VL Plus，需要结构化拆 PDF 用 OmniOCR，需要把模糊扫描件读准用 Qianfan-OCR-Fast。各有各的活儿。

## 价格的真实位置

$0.68/M 输入 + $2.81/M 输出，这个定价值得细看。

参照系，Qwen-VL Plus 在 OpenRouter 上的定价是 $0.40/M 输入 + $1.20/M 输出，便宜大约 40%。GPT-4o 的视觉模式按图像 tile 计费，单页扫描件折下来 $0.001-0.003 一张。Claude 3.5 Sonnet 的视觉调用大约 $0.0048 一张图。

Qianfan-OCR-Fast 比 Qwen-VL Plus 略贵，但比海外头部多模态便宜。对中文 OCR 场景，价格区间合理，没有出现"国产专精模型却比通用模型贵两倍"的离谱定位。

跑一个量化估算。一份 100 页中文合同扫描件，每页大约 800 tokens 文字 + 一张图，总输入估计 200K tokens，输出结构化文本 80K tokens，单次调用成本大约 $0.36（约 2.6 元人民币）。对法律文书数字化、票据批处理这种典型 B 端场景，这个单价能进决策视野。

## OpenRouter 这层中间件的意义

为什么百度把模型挂到 OpenRouter 上值得拿出来说？

国内开发者要调用百度千帆原生 API，走的是百度智能云的鉴权体系，需要 access token 轮换、AK/SK 管理、SDK 升级，对接 RAG 流水线时和 OpenAI/Anthropic 的协议是两套接口。如果一个项目要同时调通义、智谱、千帆做能力对比，光是 SDK 适配就要写一层适配器。

OpenRouter 把这层差异抹平了。所有模型走 OpenAI 兼容协议，HTTP 请求格式统一，model id 一改就能切换底层。Qianfan-OCR-Fast 上 OpenRouter，意味着对横向测评、A/B 路由、按场景动态选模型的工程模式友好了一截。

更微妙的是，OpenRouter 在国内可以直连，不需要任何额外网络配置。对不想自建千帆账号、又想试一下国产 OCR 专精模型效果的小团队，这是低摩擦的入口。

## 社区视角里它还很冷

这个发布在英文社区基本没掀起水花。Reddit 上和 Baidu Qianfan OCR 直接相关的近 30 天讨论几乎为零，r/StableDiffusion 有一篇本地 AI 月报覆盖到了，r/TouchDesigner 有一篇 OpenRouter 工具链相关的帖子，但都不是直接讨论这个模型。

中文圈也安静，没有看到大型测评、没有横评跑分、没有民间 benchmark 出来。

这种"低噪声发布"在国产模型上不是孤例。GLM、Qwen 系列早期版本都经历过先在 OpenRouter 静默上线、几周后才被社区注意到的阶段。先上线、再被发现、再被测评、最后被纳入主流路由方案，是国产模型出海的一种常见节奏。

对实操者而言，"社区还没开始测"反而是个机会窗口。在大家都还没出对比报告之前，自己跑一遍真实业务样本，比之后看十篇二手测评的判断更准。

## 实际能用在哪里

按目前模型卡的描述和 OCR 专精模型的常规能力，几个典型场景值得验证。

**中文合同 OCR + 结构化抽取**。合同里的甲方乙方、金额、生效日期、违约条款，传统 PaddleOCR 流水线要写正则 + 规则引擎，多模态大模型可以直接 prompt 出结构化 JSON。

**票据批处理**。发票、火车票、餐饮小票这类排版混乱但字段固定的文档，是国产 OCR 模型训练数据相对充足的场景。

**古籍 / 手写笔记**。这是 OCR 专精模型对通用多模态模型差距最明显的地方，繁体竖排、行草、墨色模糊，专精模型的训练数据密度通常更高。

**RAG 文档预处理**。把扫描版 PDF 转成 markdown 喂给下游 LLM，是当下 RAG 流水线的标准前置步骤。65K 上下文意味着单次能塞下一份完整中等长度文档，不用切片。

需要泼一盆冷水的是，专精模型在通用视觉推理上的表现通常逊于全能模型。如果业务里 OCR 只占一部分，还需要图表理解、视觉问答、图像描述，Qwen-VL Plus 这类全能模型更省事。

## 怎么开始测

打开 OpenRouter 文档页 `openrouter.ai/models/baidu/qianfan-ocr-fast`，注册账号，充 5 美元够跑很多次测试。

设置 `Authorization: Bearer <your-key>` 请求头，POST 到 `/api/v1/chat/completions`，model 字段填 `baidu/qianfan-ocr-fast`，messages 里塞一张 base64 图片 + 一句中文 prompt，比如"请识别图中所有文字并按版面结构组织成 markdown"。

准备 5-10 张真实业务样本，覆盖最难的场景（最模糊的扫描件、最复杂的表格、最潦草的手写）。同一组样本同时跑 Qwen-VL Plus 和 Qianfan-OCR-Fast，做一次盲评。

判断维度，识别准确率（字符级 + 字段级）、结构保留度（表格行列对齐情况）、单次调用延迟、单页综合成本。两到三小时能跑完一轮，比看任何测评文章都更接近你自己业务的真实表现。

## 收尾的判断

国产 OCR 模型的格局正在从"PaddleOCR 一家独大的开源工具链"变成"开源工具 + 通用多模态 + OCR 专精"的多层供给。每一层有自己的最优场景。

Qianfan-OCR-Fast 上 OpenRouter，是百度把 OCR 这块自己积累最深的能力，用最低摩擦的方式放到全球开发者面前。它不会替代 PaddleOCR，也不会让 Qwen-VL Plus 失色，但它让"国产 OCR 多模态"这个选项多了一个版本号。

下次做 RAG 文档预处理选型时，多一个模型可以放进对比矩阵，就是这件事的全部意义。
