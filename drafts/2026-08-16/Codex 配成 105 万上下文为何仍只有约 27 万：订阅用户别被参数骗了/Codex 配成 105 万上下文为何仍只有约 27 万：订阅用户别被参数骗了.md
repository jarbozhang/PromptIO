# Codex 配成 105 万上下文为何仍只有约 27 万：订阅用户别被参数骗了

如果你给 Codex 配了 105 万上下文，却发现长任务依然提前压缩，问题可能不在配置语法，而在运行通道真正放行的窗口。

一份公开运行记录里，`model_context_window` 被设为 1,050,000，CLI 也做了强制覆盖。新任务能够正常读取配置，但记录中的实际数值仍是 258,400。

这件事最有用的地方，不是争论 Codex 到底算 27 万还是 105 万，而是提醒我们把模型规格、产品通道和本地配置拆开看。确认实际窗口后，才能决定任务怎么拆、缓存怎么留。

## 误解不在数字，而在把三层能力当成一层

看到模型标称 1.05M context，再看到 Codex 提供 `model_context_window`，很容易得出一个直觉判断，只要把配置改成 1,050,000，订阅通道也会获得同样的窗口。

这个推理少了一层关键约束。

模型 API 规格描述模型能够支持的上限。Codex 的运行通道还可能设置自己的限制。本地配置项则负责向运行时表达期望值，它能被解析，不代表服务端一定按这个值分配资源。

我更愿意把它理解成三道门。模型规格决定理论容量，运行通道决定当前可用容量，本地配置只能在前两道门允许的范围内调整行为。

所以，配置成功不等于扩容成功。没有语法报错，也不能证明 105 万窗口已经生效。

## 约 27 万和 258,400，并不是同一个口径

原帖把当前限制概括为约 272K，但运行记录显示的是 258,400。评论里还出现了 373K 截断、最多可改到约 373K 等不同观察。

这些反馈可以证明一件事，不同用户看到的配置值、运行预算和截断位置可能并不完全一致。它们还不足以证明所有账户、模型和任务都遵循同一个固定上限。

因此，我不会拿某个评论里的 373K 当作通用配置答案，也不会把 258,400 直接解释成模型的完整上下文规格。更稳妥的判断是，运行记录比配置文件更接近当前任务真正拿到的预算，而公开讨论中的近似数字只能作为排查线索。

订阅用户最容易踩的坑，是不断抬高本地数值，然后用任务没有立刻报错来判断扩容成功。真正该看的，是新任务启动后的运行记录有没有变化，以及长任务在什么位置开始压缩或截断。

## 把验证对象换成运行记录

我会用一个全新的长任务验证，而不是沿用已经积累大量历史的会话。先记录默认状态下的运行数值，再修改 `model_context_window`，重新创建任务，比较两次记录。

判断结果可以压成三种情况。

本地值和运行记录一起变化，说明配置至少影响了当前通道。配置被读取但运行记录不变，说明更高数值没有转化为实际窗口。运行记录变化但任务仍提前压缩，则需要继续区分窗口预算、保留空间和压缩策略，不能只盯着一个配置项。

原帖已经展示了第二种情况。1,050,000 能被解析，CLI 覆盖也能执行，但新任务记录仍停在 258,400。基于这份材料，能成立的结论是这次订阅通道没有因为本地配置获得 105 万窗口，而不是所有 Codex 通道永远只能使用同一个数值。

## 窗口没有变大，工作流就要换算法

如果运行记录确认实际窗口仍在约 27 万量级，继续把配置往上堆没有多少价值。我的调整会落在上下文组织上。

长任务按交付阶段拆开，让每个会话只保留当前决策、必要代码和验收条件。稳定背景写进仓库文档，避免每轮重复发送。大段日志和检索结果只保留结论及定位入口，需要时再读取原文。

评论里有人提到，窗口过大可能不利于上下文缓存发挥。源材料没有给出可量化结果，但这个提醒值得保留。更大的窗口并不自动等于更快、更省或更稳定，重复前缀能否复用、无关内容占了多少预算，同样会影响长任务体验。

我认为，对 Agent 应用更重要的能力不是把所有历史一次塞满，而是知道哪些内容必须常驻，哪些内容可以按需取回，哪些阶段应该生成一份短交接后重新开始。

把 105 万写进配置很容易。把一次复杂交付拆成可恢复、可验证、能利用缓存的上下文结构，才是真正能降低失败成本的工作。
