# BaoCut 把字幕处理从 31 分钟降到 18 分钟：真正的瓶颈不是模型

一段视频的字幕处理跑了 31 分钟，工程师最容易怀疑模型不够快、并发不够高，或者 worker 还没压榨到极限。

BaoCut 的这次优化却绕开了这些常见答案。真正拖慢流程的，是模型输出了一份过于复杂的 JSON。改掉输出协议后，调用次数从 33 次降到 12 次，处理时间从 31 分钟降到 18 分钟。

这个案例对视频创作者和工具开发者都很实用。字幕翻译、润色、分段看起来是模型任务，真正决定交付速度的，却可能是模型与程序之间如何交换数据。

## 一次局部优化为什么迟迟没有突破

事情起于用户反馈 BaoCut 转录速度慢。作者反复使用 Codex 转录视频，再让 Codex 或 Fable 分析瓶颈。

它们给出的建议并不离谱。增加 workers，也就是 subagent，给 workers 预热，继续优化现有执行流程。方案实施后有些改善，但幅度不明显。

问题出在优化目标的视野里。Agent 看到的是已有流程和端到端耗时，于是自然会在现有流程图里寻找可调整的节点。并发、预热、调度都属于这条路径，但它没有主动质疑数据的表达方式。

直到作者开始分析数据包，瓶颈才显现出来。字幕任务要求模型返回很长的 JSON，生成这些结构需要更多 token，随后还要完成格式校验。模型不只在处理字幕内容，也在花时间维护大量字段、层级和符号。

## 把复杂工作从模型移回程序

复杂 JSON 对程序非常友好。字段稳定，边界明确，解析完成后就能直接进入后续流程。代价是模型必须承担结构生成和格式正确性。

如果输出改成纯文本或简单 HTML，模型的负担会明显下降。可程序接手的工作随之增加。

以字幕润色为例，纯文本只告诉程序最终句子变成了什么。程序还要比较润色前后的差异，识别哪些词发生变化，再把改动映射回原字幕中的单词和时间位置。原本由 JSON 显式携带的关系，现在要靠 diff 和对齐逻辑恢复。

于是，优化不是凭空消灭复杂度，而是重新分配复杂度。

旧流程让程序简单，让模型输出复杂结构。新流程让模型输出更轻，让程序承担解析、差异比较和字幕对齐。前者开发方便，后者运行效率更高。

## 交付时间是怎样被压下来的

沿着这条路线调整后，BaoCut 的调用次数从 33 次降到 12 次，耗时从 31 分钟降到 18 分钟。作者还用一期接近 7 小时的访谈测试完整润色，处理时间为 42 分钟。

这些数字来自作者公开的优化复盘，反映的是这次具体流程调整，不能直接套用到所有视频和模型组合。但变化方向很清楚，减少结构化输出后，生成和校验环节都变轻了。

交付物本身没有被降级。目标仍然是可继续处理的字幕，而不是为了速度只返回一段无法定位的文本。区别在于，字幕结构的恢复工作从模型侧转到了确定性的程序逻辑里。

这也是整个案例最有价值的部分。快并不是来自少做一步，而是把不同工作交给更合适的执行者。模型负责语言理解和润色，程序负责 diff、映射与校验。

## 重新设计一条字幕链路

如果自己的字幕翻译或润色流程也卡在生成阶段，可以把一次任务按四类时间拆开记录。

- 模型实际生成了多少输出 token
- 结构校验失败后发生了多少次重试
- 程序解析和字幕对齐分别用了多久
- 每次调用是否都需要返回完整字幕结构

这不是为了立刻删掉 JSON。字段不多、输出短、下游强依赖固定结构时，JSON 依然可能是合理选择。

真正需要警惕的是，为了让第一版程序少写一些解析逻辑，把越来越多的结构责任推给模型。字幕变长后，隐藏成本会同时出现在 token、生成时间、校验和重试中。

更稳妥的验证方法，是选一段固定字幕，同时跑复杂 JSON 和轻量文本两条路径。记录生成 token、总耗时、重试次数和对齐准确性，再决定复杂度应该放在哪一侧。

## 给 Agent 一张更完整的性能地图

这次复盘也解释了为什么 Agent 能持续给出合理建议，却没有找到突破口。它拿到的是一个过于笼统的目标，只知道流程慢，不知道时间消耗在输出 token、校验、解析还是重试。

让 Agent 参与性能优化时，可以把 profiling counters 拆得更细，并要求它比较不同表示协议，而不只是调整现有参数。否则，多开 workers 可能只是让一套成本过高的数据协议跑得更并行。

BaoCut 从 31 分钟降到 18 分钟，留下的不是一个通用加速比例，而是一条很具体的工程经验。模型输出越规整，程序未必越高效。下一次字幕任务变慢时，先同时画出模型计算和数据表示两张图，再决定该优化哪个节点。
