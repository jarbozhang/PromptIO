# 消费级显卡跑 Qwen 27B 值不值：效果很强，但 120K 上下文吞掉了近一小时

如果你正准备在消费级显卡上跑 27B 模型，真正该算的不是每秒能吐多少 token，而是它完成一整个 Agent 任务要多久。

一组 Qwen3.8-27B 运行记录给出了很有意思的答案。模型能独立完成设计、动画、代码和页面整合，效果获得测试者很高的评价，但任务总耗时达到 2 小时 53 分，其中 58 分钟用在反复读取已经读过的上下文。

我重新算完这笔账，判断很明确。27B Dense 模型的能力已经值得认真考虑，真正拖慢本地 Agent 的，可能不是生成速度，而是上下文管理。

## 判断你是否真的需要 27B

测试任务并不简单。提示词要求用 Three.js 和 SVG 制作 4 个骑自行车动画版本，再做 3 个电风扇动画，最终装进一个完整的卡片展示页。

没有设计稿，也没有详细规格。模型需要自己补齐视觉设计、动画逻辑、代码结构和页面整合，相当于一次完成 4+3+1 个交付单元。

这类任务最能暴露小模型的短板。它不仅要写局部代码，还得记住多个组件之间的关系，维护统一风格，并把结果收进一个可运行页面。测试记录显示，Qwen3.8-27B 完成了这个闭环。

所以，适合考虑 27B 的人并不是只想补几行代码的人，而是希望本地模型接住完整前端任务、连续调用工具，或在多个文件之间保持一致性的开发者。

## 别让 50 tok/s 替你做决定

这次记录中，Qwen3.8-27B 单路基准速度约为 50 tok/s。放到 Claude Code 的完整工作流里，实际速度更慢，因为还要承担长上下文预填充、键值缓存（KV Cache）和工具调用开销。

上下文达到 120K token 后，预填充速度为 1573 tok/s。单次读取需要 87.9 秒。更关键的是，当工作流没有缓存，模型会在多轮调用中重新读取相同内容。

整个任务有 133 分钟生成时间，其中 58 分钟消耗在重复预填充上。也就是说，接近一半的生成阶段并没有产生新内容，而是在重新建立模型已经拥有过的上下文状态。

这也是我认为最容易算错的一笔账。benchmark 测的是发动机转速，Agent 总耗时还取决于你让它反复搬了多少行李。

## 按瓶颈选择部署路线

这份选型判断清单，比单看模型大小更有用。

- 任务需要跨多个文件规划、生成和修正，优先验证 27B 的完整任务能力
- 显存难以容纳非量化权重、视觉编码器和足够的 KV Cache，优先考虑量化版本
- 生成速度可以接受，但首 token 等待明显，重点检查上下文长度和预填充耗时
- 多轮工具调用反复读取相同内容，优先处理提示缓存和上下文复用
- 任务资料很多，但真正相关内容很少，缩短上下文通常比更换显卡更直接
- 只做补全、改函数或单文件修改，不必为了参数规模承担完整的长上下文成本

评论里还有一条独立案例，M5 128G MBP 使用 Qwen3.8-27B-MIX-4bit 配合 Claude Code，约 30 分钟制作了一个五子棋项目。由于硬件、量化方式和任务都不同，这个结果不能直接与前面的完整前端任务对比，但它说明量化路线值得单独验证。

## 用一个完整任务完成验货

我不会用一句“写个登录页”判断本地模型值不值。更可靠的验证方式，是准备一个包含规划、跨文件修改、工具调用和最终整合的真实任务，同时记录下面这些数据。

- 模型与量化规格
- 实际上下文长度
- 首 token 延迟
- 预填充速度与累计耗时
- 生成速度与生成总时长
- 工具调用次数
- 峰值显存或统一内存占用
- 最终交付是否可运行，返工了几轮

硬件信息在这份源记录中没有完整披露，因此不能据此推导某一张具体显卡必然跑得动。尤其是带视觉的非量化 27B 模型，权重、视觉编码器和 KV Cache 会共同争夺可用内存，落地前必须以自己的运行配置为准。

我的选择会很实际。需要完整 Agent 能力时，我愿意保留 27B，但会先砍掉无关上下文，再验证缓存，显存仍然吃紧才换量化模型。若主要工作只是短代码补全，我不会为 120K 上下文和近一小时的重复预填充买单。

先挑一个你每周都会做的完整任务跑一遍。把总耗时拆成预填充、生成和工具调用三段，你很快就会知道该升级模型、优化缓存，还是删掉那一大段根本没被用上的上下文。
