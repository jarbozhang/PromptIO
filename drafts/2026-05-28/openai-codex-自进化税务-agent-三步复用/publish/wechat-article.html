OpenAI 用 Codex 做自进化税务 Agent，普通开发者能抄哪三步

OpenAI 5 月 27 日发的 Tax AI 案例，表面看是 OpenAI、Thrive Holdings 和 Crete 给会计师做报税 Agent。真正值得普通开发者拆下来的，不是「会计会不会被替代」，而是它把一个难题讲清楚了，业务专家每天改出来的结果，怎样变成 Agent 下一轮改代码的证据。

本文不是亲测复盘，而是基于 OpenAI Blog 的方法拆解。原文给出的事实是，Crete 参与试点的会计师事务所网络超过 30 家，中高复杂度税务申报里，数据录入单份可能花 8 小时。Tax AI 在这个报税季处理了 7000 份 tax returns，覆盖 1040 和 1041，准备税表大约节省三分之一时间，草拟税表最高 97% 准确率，吞吐约提升 50%。上线时只有四分之一 return 达到 75% field completion，六周后这个比例到 86%。

这些数字不是本文重点。

普通团队能抄的，是三件事，任务分解，自动评估，反馈闭环。放到中文场景里，它可以不是美国税表，而是财务凭证抽取、经营报表生成、审计底稿整理、合规文档核对。关键不是把 Agent 说得更大，而是把它的工作范围切得更小。

第一步，把任务拆到 Agent 能接住

OpenAI 的案例没有让 Codex 直接「做税务判断」。Tax AI 被放在一个有边界的层里，读取源文件，抽取字段，把结果映射到 tax engine 需要的结构。工程师仍然负责架构、产品决策和上线，会计师仍然负责复核、修正和批准最终申报。

这点对中文团队很关键。不要一上来做完整财务 Agent，先做一个能被验收的小任务。

比如，从合同、发票、验收单中抽出供应商名称、金额、税率和付款节点。或者把周报里的经营指标映射到固定报表单元格。或者在合规文档中找出条款引用、证据来源和缺失项。

每个任务至少要有三个可见对象，原始材料，目标字段，人工修正。缺一个，后面就很难形成评估。很多团队做 Agent 卡住，并不是模型不够强，而是业务系统只保存最终结果，不保存中间判断路径。

第二步，把人工修改变成 eval

Tax AI 的关键设计，是把会计师复核从终点改成训练信号。系统记录 Tax AI 原本给了什么，会计师改了什么，最终进入申报文件的是什么。

然后它把这些差异变成 field-level review rows，也就是字段级评审行。每一行可以看到 expected value、predicted value，以及这个差异是否值得产品修。接着再把相似失败聚到一起，区分重复产品问题和正常流程噪声。

OpenAI 原文举了几个租赁房产 Schedule E 的例子。系统可能漏掉 fair rental days，处理 other expenses 出错，也可能把同一批源文件里的多个租赁房产混在一起。只有这类反复出现、能归因、能衡量的问题，才会变成 eval target。

迁移到中文财务和报表场景，最小可用表可以很朴素。记录预测值、最终值、证据位置、修改动作、修改原因、是否可归因。再按失败模式分组，例如漏抽合同金额、把税率和服务费混在一起、同一主体多个项目混淆、引用制度条款没有证据。

这一步最容易被省掉，也最不该省。没有 eval 的 Agent 改进，常常只是不断调 prompt。有了 eval，Codex 才知道自己要爬哪座小山。

第三步，让 Codex 只改一座小山

OpenAI 的做法不是把一堆线上失败直接扔给 Codex。原文说得很明确，业务修正可能来自抽取遗漏、映射问题、产品暂不支持、税务判断，也可能只是正常流程噪声。只有反复差异被审核和分组，形成可行动 finding 后，才进入 Codex 任务。

这时 Codex 拿到的不是一句模糊报错，而是一个有边界的工程包。里面有生产 trace、源材料、目标输出、相关代码、eval 命令、回归测试和任务说明。Codex 可以检查 source packages、extraction schemas、mapper behavior 和 code paths，判断问题是字段不支持、抽取模式漏了、源文件选择错了、mapper 缺口，还是 grader 把噪声算成失败。

修复也被限制在具体表面。可能是扩展 schema，改源文件选择逻辑，更新 mapper，或者修正 grader。跑完 targeted eval，还要跑更宽的 regression suites，最后只提交 candidate pull request，给工程师审。

这对普通开发者的启发很直接。不要让 Agent 面对「提高报表质量」这种空任务。给它一个候选目录就够，里面放 task.yaml、执行计划、结果记录、目标 eval、回归 eval、相关文档和只读证据。可写的是代码和测试，不可写的是生产证据。

失败边界比自动化更重要

OpenAI 的案例有一个容易被忽略的保守点。它不是全自动闭环，含糊的 case 会回到产品团队，工程师仍然负责架构和上线，业务专家仍然通过日常复核来决定系统学什么。

这也是中文财务、报表、合规文档场景最该保留的边界。Agent 适合做抽取、引用、映射、比对、回归评估，不适合在没有人审的情况下承担税务判断、合规结论或财务责任。

从下周开始试，可以只做三个动作。选一个高频、字段固定、人工会复核的文档流。把每一次人工修改保存成字段级差异。挑出反复出现的失败模式，给 Codex 或其他 coding agent 一个带 eval 的小任务。

我认为这篇 OpenAI Blog 的价值，不在于证明报税可以自动化到什么程度，而在于给了一个更朴素的判断标准。一个 Agent 能不能自进化，不看它会不会说自己在学习，看它的每一次失败能不能留下证据，变成评估，再变成一次可审查的代码修改。
