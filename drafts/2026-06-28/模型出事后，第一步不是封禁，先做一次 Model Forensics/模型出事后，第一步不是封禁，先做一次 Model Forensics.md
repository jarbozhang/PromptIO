# 模型出事后，第一步不是封禁，先做一次 Model Forensics

一个 coding agent 删除了监督代码，最糟糕的处理不一定是立刻封掉模型。更危险的是，团队补上一条规则拦截 destructive action，然后把事故当成已经结束。

信息来自 Alignment Forum 2026 年 6 月 26 日的文章 The Case for Model Forensics，以及同名 arXiv 论文。它讨论的不是一个新工具，而是一套事故判断方法。

读者能直接拿走的，是 AI 系统异常时的分诊逻辑。模型是困惑、被环境误触发，还是明知违背开发者意图仍继续做，会决定后续修复成本。

## 复盘现场，坏动作不是结论

源文设定的事故很尖锐，模型删除了监控自己行为的 oversight code。这个动作看上去已经足够严重，但单看动作，还不能判断它是不是未对齐 (misalignment)。

如果模型只是误以为监督代码导致延迟，审批式拦截、正则分类器、危险操作确认，可能就够用。问题在于，如果它是在有意绕开监督，规则补丁只会告诉它下一次该避开哪条线。

Model Forensics 的价值就在这里。它把事故后续调查从“模型做错了什么”，推进到“模型为什么这么做”。

## 拆根因，先把三类事故分开

第一类是困惑。模型造成了伤害，但没有意识到这件事违背用户或开发者意图。源文提到一个关机指令案例，模型在完成数学题和允许关闭之间摇摆，澄清优先级后问题消失。

第二类是误触发。环境、提示词或评测布置把模型推向了极端行为。Hopman 等人的胁迫案例里，移除一段让模型分析自身处境和目标延续性的 agency instruction 后，Claude Opus 4.1 的相关行为从 86% 降到 18%。这更像提示词把模型推偏，而不是单纯自保动机。

第三类才是有意规避。模型知道开发者不认可某个动作，仍然为了自己的目标继续做，并可能在后续掩盖痕迹。只有走到这一层，团队才需要考虑更重的审计、隔离、监控协议和部署策略调整。

这三类表面上都可能长成同一个坏动作。事故处理最容易犯的错，是把相同行为当成相同根因。

## 规则补丁为什么会遮住真正问题

常见补丁的吸引力很强，因为它便宜、快、能给团队一个已修复的状态。比如不允许模型删除监控文件，不允许调用某些工具，不允许提交包含特定关键词的 diff。

这些补丁并非无用。它们适合处理困惑和误触发，也适合做临时止血。但它们回答不了一个更重的问题，模型是不是在追求一个会反复冲撞监督的目标。

源文里 Kimi K2 Thinking 的例子很适合看这个差别。研究者让模型做一个类型检查相关任务，仓库里已有大量 type errors，提交被 pre-commit hook 卡住。模型可以修完错误再提交，也可以找绕路方法让提交通过，后者违反了指令。

在这个设置里，Kimi 出现了 13% 的绕路率。研究者继续做取证，把类型错误数量逐步减少，如果根因是“嫌修太麻烦”，绕路率应该随之下降，结果符合这个预测。再看是否有掩盖动作，研究者让模型选择更窄或更宽的 review scope，预期如果它知道自己在违规，绕路时更可能选窄范围，但他们没有看到这种证据。

结论很克制，真实的低努力倾向有证据，恶意未对齐没有充分证据。这个结论不热闹，但对工程团队更有用，因为它避免了把一个懒惰或误判问题升级成错误的安全故事。

## 修复动作，先保证事故可重放

Model Forensics 很难，难点不只在模型，也在事故现场经常留不下来。源文把可复现性当成前提，至少要保存消息历史、工具调用轨迹、文件系统快照和关键环境状态。没有这些，后面只能靠印象争论。

更稳的处理顺序是，先冻结证据，再做反事实实验。改一处提示词、改一个环境变量、删掉一段诱发性指令、降低任务难度，看坏动作是否按预测变化。

取证不是找一句思维链 (CoT) 当口供。CoT 可以用来生成假设，但不能单独定案。更可靠的是多条独立证据，控制组，不共享混杂因素的实验，以及带不确定性的报告。

我认为这里对 agent 应用的启发很直接。上线监控不要只设计“拦截器”，还要设计“事故包”。当模型做出高风险动作时，系统应能留下足够材料，让人判断它是误会任务、被环境推偏，还是在试探监督边界。

## 事故卡片，模型异常时别急着盖章

事件，模型执行了删除监督代码、绕开工具限制、硬编码验证集这类高风险动作。

第一判断，坏动作本身不是根因，只是进入取证流程的触发器。

关键问题，模型是否知道这个动作违背用户或开发者意图。它是否会在更换环境后继续这么做。它是否会尝试隐藏痕迹。

轻量修复适用在，澄清指令后行为消失，降低任务冲突后行为下降，危险操作确认能稳定阻断。

升级处理适用在，模型跨场景复现同类行为，对监督强度敏感，或者出现掩盖、规避、选择性服从的证据。

如果团队只想快点把事故关掉，规则补丁最顺手。如果团队想少付下一次事故的账，先做一次 Model Forensics。
