# Codex 开放 100 万上下文：这三行配置该不该开？

如果你正让 Codex 读大型代码库、追一条跨模块调用链，或者连续调试几天，这个 100 万 token 开关值得关注。

但如果任务只是改接口、补测试、修页面，我的判断很直接，保留默认窗口通常更合适。窗口越大，不等于模型越聪明，也不等于它会更准确地利用每一段历史。

这次真正有用的信息，不是把数字从 27.2 万拉到 100 万，而是 Codex 把上下文窗口和自动压缩阈值留成了可配置项。我们终于可以按任务规模选择，而不是所有工作都套同一个窗口。

## 旧问题不只是上下文装不下

大型代码库里，Codex 经常要同时保留目录结构、关键文件、工具输出、报错记录和多轮修改历史。会话拉长后，较早的信息可能被压缩，排查路径也可能逐渐断掉。

把窗口扩大，确实能推迟压缩发生的时间。原帖给出的配置如下。

```toml
model = "gpt-5.6-sol"
model_context_window = 1000000
model_auto_compact_token_limit = 900000
```

其中 90 万的自动压缩阈值，为 100 万窗口留下了约 10 万 token 缓冲。两个值不应设成一样，否则会把会话推到缺少余量的位置。

不过，配置文件接受 100 万这个数字，并不能单独证明每次 Codex 会话都获得完整的有效窗口。原帖评论里也有人指出，Codex 的公开说明仍显示 27.2 万。这个差异需要以当前版本的官方文档、运行状态和实际 token 记录继续验证。

## 新配置解决的是容量，不是注意力

我不会把 100 万窗口理解成一次模型升级。它主要改变三个环节。

| 变化 | 默认窗口 | 100 万模式 |
| --- | --- | --- |
| 可保留材料 | 更早进入压缩 | 能容纳更多文件与工具输出 |
| 任务节奏 | 适合短任务和频繁开新会话 | 适合长链路调查与复杂重构 |
| 使用成本 | 输入规模较容易控制 | 超长输入可能进入更高计费区间 |

原帖提到，输入超过 27.2 万 token 后，输入与输出计费会提高。具体倍率和生效条件仍应按当前官方计费说明核对，不能只凭配置值估算账单。

更大的问题是注意力。材料进入窗口，不等于每一段都会获得同等关注。长上下文常见的中段信息弱化现象，可能让模型记得文件，却漏掉藏在会话中间的约束。

所以，窗口不足会导致信息被压缩，窗口过大也可能让有效线索被噪声淹没。100 万解决的是能否装下，不能自动解决如何找到。

## 哪些任务开始变得可用

我认为，大窗口最有价值的不是日常补全，而是那些不能轻易切断历史的任务。

一次性分析 monorepo 时，Codex 可以同时保留多个包的接口、构建配置和调用关系。长期调试时，它能带着前几轮假设、日志和失败修改继续排查。复杂重构或逆向工程中，大量工具输出也不必过早被压缩成摘要。

这些场景有一个共同点，丢失历史的代价，高于多读一些 token 的代价。

日常开发恰好相反。任务边界清楚、改动集中在少数文件时，默认窗口已经能覆盖主要材料。盲目扩大窗口，可能只是把旧日志、重复文件和失效假设留得更久。

## 按任务决定是否升级

我会把选择压成一个判断。

当任务需要跨越大量文件，而且前面的工具输出会持续影响后续决策时，可以临时开启 100 万模式。原帖还给出了单次启动方式，不必永久修改默认配置。

```bash
codex -m gpt-5.6-sol -c model_context_window=1000000 -c model_auto_compact_token_limit=900000
```

如果任务能拆成独立阶段，我更愿意继续使用默认值。完成一次调查后，把结论写进仓库文档或任务说明，再开启干净会话，通常比无限保留聊天历史更容易控制质量。

这也是这次更新对 Agent 应用最有用的启发。上下文不该只有一个全局档位，而应成为任务调度的一部分。短任务用默认窗口，长调查临时扩容，关键结论沉淀到文件，过期工具输出及时退出会话。

## 用一个真实仓库验证开关

别从日常默认配置动手。挑一个确实会跨模块、跨工具输出的任务，分别用默认窗口和临时 100 万模式跑两次，记录压缩发生的位置、遗漏的约束、输入规模和最终修改质量。

如果大窗口只是让会话更长，却没有减少重复读文件和重新解释约束，它就不值得常开。如果它能让一条原本会断掉的调查链完整走到交付，再把配置固化到对应工作流。

100 万上下文不是满血按钮，更像一个昂贵的长桌。只有材料之间真的有关联，桌面变大才有价值。
