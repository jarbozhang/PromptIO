# Hermes Studio v0.6.15 长对话、技能命令和本地 Runtime 都更顺了

如果你已经在用 Hermes Studio，我建议这次 v0.6.15 不要只当作一次普通修补看。

它没有把重点放在更大的概念上，而是集中处理几个很日常、也很磨人的问题，长对话乱、skill 命令不好找、模型配置切换不够顺、本地 runtime 状态不透明、桌面端退出后进程残留。

这类更新不一定适合拿来讲宏大趋势，但很适合做成一份升级检查清单。因为真正用 agent 应用的人，最怕的不是少一个按钮，而是一次对话跑长以后，状态、模型、runtime 和 gateway 开始互相拖后腿。

## 先看长对话会不会更容易接住

这次聊天侧栏完成了重设计，还优化了历史加载控制。对我来说，这个点比它看起来重要。

长对话里的 agent，不只是多聊几轮那么简单。它会积累任务背景、工具调用记录、reasoning 片段和用户临时补充，一旦导航变乱，后面就很容易从“继续推进任务”变成“找刚才那一步在哪里”。

v0.6.15 把侧栏和历史加载控制放在一起改，说明它不是只在修视觉，而是在处理长对话的可回溯性。

我会优先检查这三件事。

- 打开一个已有长会话，看历史加载是否更可控
- 在多轮消息之间来回切换，看侧栏能不能帮我定位上下文
- 观察 Thinking 状态和工具栏是否会打断消息流

来源里提到，Thinking 状态更新了指示器和工具栏布局，reasoning 进度更容易阅读，也不会打断消息流。这个改动适合用在需要长时间等待模型推理的任务里，比如多文件分析、工具链调用、长文改写和桌面 agent 操作。

这里不要急着评价“变强了没有”。更实际的判断是，长任务里少一次迷路，就少一次人工救场。

## 把 skill 命令从记忆负担里拿出来

v0.6.15 新增了技能命令选择器，可以更快发现并从输入框插入可用的 skill 命令。

这个更新我会直接归到 agent 产品的可用性改进里。因为 skill 命令一多，真正的问题不是“有没有能力”，而是用户能不能在该用的时候想起来、找得到、插得进去。

过去很多 agent 工具的问题是，能力藏在文档里，输入框只负责接收文字。结果就是熟手靠肌肉记忆，新用户靠试错，团队交付时还要额外写一份“常用命令说明”。

命令选择器把这件事提前到了输入阶段。

可收藏检查清单如下。

- 适合谁，已经有一组固定 skill，经常在会话里切换任务的人
- 怎么做，升级后从输入框里找可用 skill 命令，不要只靠手输
- 坑点，不要把所有任务都塞进 skill，先保留真正高频、低歧义的命令
- 下一步动作，整理自己最常用的 5 个命令，看选择器是否能减少来回查文档
- 交付形态，团队内部可以把它当成“可发现能力入口”，而不只是快捷输入

我的判断很简单，agent 应用要从玩具变成日常工具，命令发现这类小入口比大口号更关键。用户不是不愿意用复杂能力，用户是不想每次都重新记一遍入口。

## 检查模型配置切换有没有少卡一步

这次新增 Claude 和 Gemini OAuth Provider，还修正了 Gemini 模型 ID 规范化，并支持在模型选择器里手动刷新 config.yaml 变更。

这段先别当成完整接入教程，来源没有给出具体配置路径和参数。更稳妥的用法，是把它当作升级后必须检查的模型配置链路。

尤其是手动刷新 config.yaml 变更这个点，很贴近日常使用。

很多桌面端或本地 agent 工具里，模型配置最烦人的地方不是配置本身，而是你改完文件以后，不确定应用有没有读到。最后只能重启、切窗口、再试一次，排查成本被放大。

v0.6.15 让模型选择器支持手动刷新 config.yaml 变更，至少把“我改了配置但界面没同步”的不确定性往前推了一步。

这里最容易踩坑的是，把 OAuth Provider、模型 ID 规范化、config.yaml 刷新混成一个问题。它们其实对应三层体验。

- Provider 解决账号或授权入口
- 模型 ID 规范化解决模型名称识别
- 手动刷新解决配置文件变更后的可见性

如果你已经在维护多个模型配置，升级后先别跑复杂 workflow。先改一项 config.yaml，再到模型选择器里手动刷新，看界面状态是否符合预期。

## 本地 Runtime 先按启动链路验一遍

v0.6.15 的 Runtime 启动流程会先检查本地 runtime，再展示下载源选择，并在启动继续时保持检查状态可见。

这个顺序改动很务实。因为本地运行最怕一上来就让用户选下载源，却没有先说明机器上到底有没有可用 runtime。

我会按这个顺序验。

1. 打开 Runtime 启动流程，先看本地 runtime 检查是否出现
2. 再看下载源选择是否在检查之后展示
3. 启动继续时，确认检查状态还留在界面上
4. 如果流程失败，记录失败发生在本地检查、下载源选择，还是继续启动阶段

这不是为了追求仪式感，而是为了把问题切开。agent 应用一旦依赖本地 runtime，失败原因可能来自安装、下载、启动、端口、gateway 或桌面端桥接。界面把检查状态留住，排查时就不用全靠猜。

## 退出时别留下 backend、bridge 和 gateway

桌面端这一轮也做了几处清理。

来源里提到，桌面端自更新不再被残留应用进程阻塞，Windows 退出时的 gateway 清理更完整。应用退出时会停止托管的 gateways，托管运行期间异常退出的 gateway 仍会自动拉起。桌面端退出时也会更平滑地关闭 server，减少 backend、bridge 和 gateway 孤儿进程残留。

这部分我会重点给已经在跑本地 gateway 的读者。

因为本地 agent 不是网页工具，退出不干净会带来一串后续问题。端口被占、后台进程还在、下一次启动状态不一致、自更新被旧进程挡住，这些问题单个看都不大，叠起来就是“今天怎么又不稳定”。

我的避坑判断是，升级后别只看界面能不能打开，要专门做一次退出检查。

- 启动一次托管 gateway
- 让应用正常退出
- 再启动一次，观察是否需要手动清理残留进程
- 如果使用 Windows，额外关注 gateway 退出清理
- 如果遇到异常退出，观察 gateway 是否会自动拉起

这类检查不华丽，但能直接影响日常信任感。本地 agent 工具只要让人产生“每次退出都可能留东西”的感觉，后面再强的能力都会被打折。

## 我会这样安排这次升级

如果你已经在 Hermes 生态里做长期会话、技能命令或本地运行，我会把 v0.6.15 当作一次稳定性升级，而不是功能猎奇。

我的建议顺序是。

1. 先用一个已有长对话检查侧栏、历史加载和 Thinking 状态
2. 再从输入框试 skill 命令选择器，确认高频命令是否更好找
3. 改一次 config.yaml，用模型选择器手动刷新验证配置同步
4. 走一遍 Runtime 启动流程，记录本地检查和下载源选择的顺序
5. 最后做一次桌面端退出检查，重点看 gateway、server、backend、bridge 是否留下异常状态

这套检查不需要把所有能力跑满。它的目标是回答一个更实用的问题，升级以后，Hermes Studio 有没有减少你在长对话、模型切换和本地进程清理上的人工维护。

对 agent 应用来说，这就是很关键的进步方向。不是每次都要新增一个巨大能力，有时候把会话接住、把命令找出来、把本地运行关干净，才是用户愿意继续用下去的原因。
