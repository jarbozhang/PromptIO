# vLLM 0.27.0 上手判断：Kimi K3、Qwen3.5 现在怎么部署更稳

如果你正准备部署 Kimi K3，vLLM 0.27.0 已经进入值得验证的版本。它不是只补一个模型定义，而是把核心模型文件、算子、前端、量化检查点和专家并行相关能力集中落进同一次发布。

Qwen3.5 用户也有明确收益，文本版 Dense 和 MoE 模型获得支持。不过我不会因为模型列表变长就直接升级，PyTorch 2.13.0、torchvision 0.28.0 和 Triton 3.7.1 的同步变化，才是这次决策里代价最高的一部分。

我的结论很直接。新部署可以优先从 0.27.0 开始验证，正在稳定运行的服务则不该原地覆盖。先复制环境和流量特征，再决定是否迁移。

## 判断这次升级究竟买到了什么

Kimi K3 是 0.27.0 最完整的一条新增能力线。

发布说明列出的范围包括核心模型文件与算子、Python 和 Rust 前端、AttnRes 算子、DeepGEMM 支持、compressed-tensors 量化检查点、DSpark AR fusion，以及把共享专家切分而不是复制的选项。

我更看重这种一次性落完整栈的方式。大模型能被框架识别，只代表请求可能启动。前端解析、量化权重、注意力算子和专家切分能否接上，才决定它能不能进入真实部署链路。

Qwen3.5 的边界需要看得更细。0.27.0 明确支持文本版 Dense 和 MoE 模型，不能顺手把它扩大理解成所有模态、所有权重格式和所有运行后端都已经获得同等覆盖。

所以我会把两者分开判断。Kimi K3 是完整能力链值得评估，Qwen3.5 则是文本推理路径已经打开，具体检查点仍要逐项核对。

## 把环境变化算进迁移成本

这次最容易被版本亮点遮住的，是 PyTorch 2.13.0 升级。vLLM 同时跟进 torchvision 0.28.0 和 Triton 3.7.1，CPU 与 XPU 路径也转向 torch 2.13。

发布说明已经把它标为 breaking environment change。对已有部署而言，风险不只在 vLLM 自身，还会传到自定义算子、镜像基础层、驱动与运行时组合、监控探针，以及团队额外安装的 Python 包。

我的判断维度不是“新版本能不能装上”，而是旧环境里那些默认成立的组合，在新依赖下是否仍然成立。安装成功只是入口，请求结果、显存占用、首个请求延迟和持续负载下的稳定性才是验收对象。

0.27.0 还加深了 SM100 上的 FlashAttention 4 集成，包括 FP8 键值缓存和 headdim 256 支持。新的 JIT 预热基础设施与 Triton 算子预热用于减少首次请求的编译停顿。这些改进很有价值，但硬件和注意力后端不匹配时，不能把发布说明里的收益直接套到自己的服务上。

## 用三个维度决定是否切换

我会把升级判断压在三个维度里。

第一是模型必要性。只有 0.27.0 才能满足当前 Kimi K3 或 Qwen3.5 文本部署需求时，升级收益明确。如果现有模型已经稳定服务，新模型支持本身不足以构成迁移理由。

第二是环境可替换性。能够重建镜像、保留旧版本并做隔离验证的团队，试错成本可控。依赖共享环境、历史自定义算子或难以复现镜像的服务，应该把 PyTorch 2.13 视为一次环境迁移，而不是普通补丁更新。

第三是验收能力。至少要能比较输出正确性、吞吐、首个词元延迟、显存峰值和长时间运行稳定性。缺少这些基线时，升级后即使出现变化，也很难判断来自模型、vLLM、PyTorch、Triton还是注意力后端。

## 哪些人适合升级，哪些人适合等待

适合优先验证的人，是准备上线 Kimi K3 的团队、需要 Qwen3.5 文本版 Dense 或 MoE 支持的开发者，以及能够维护双环境并执行回归测试的平台团队。

不适合直接切换的人，是已有服务稳定运行但没有新模型需求、镜像无法快速回滚、依赖未验证自定义算子，或者只准备在原环境里覆盖安装的团队。

这里没有“越新越稳”的简单答案。0.27.0 对新模型部署更完整，却也主动抬高了环境变化幅度。收益集中在新能力，代价集中在兼容性，两者必须放在同一张决策单里。

## 我的选择是新项目采用，旧服务并行验证

如果今天新建 Kimi K3 部署环境，我会从 vLLM 0.27.0 建立基线。完整栈支持比在旧版本上拼接零散补丁更容易维护，也更便于后续定位问题。

如果迁移现有服务，我会保留旧镜像，用相同模型检查点、请求样本和运行参数建立并行环境。验证重点不是版本号，而是新依赖组合能否保持结果正确，并在目标硬件上兑现可接受的延迟、吞吐和显存表现。

Qwen3.5 则先限定为发布说明确认的文本版 Dense 与 MoE 路径。权重格式、量化方式和实际后端组合，都应在进入正式流量前单独验证。

这次真正值得采用的不是“立即升级”，而是把模型支持和环境迁移拆成两个决定。先让 0.27.0 在隔离环境里证明自己，再让它接管已有服务。
