# 安装 Coze CLI 后发生了什么：一次本地技能目录污染复盘

如果你安装过 Coze CLI，同时还在本机使用 Codex、Claude Code 等 Agent 工具，真正需要检查的可能不只是命令行程序还在不在。

这次争议指向一条更长的影响链。安装后钩子执行技能同步，技能目录出现新增内容，其他 Agent 又可能自动加载这些内容。于是，一个工具的安装动作，可能改变多个工作流后续会调用什么。

读完这份复盘，你可以沿着安装钩子、目录改动和自动加载三层路径，判断本机是否留有未清理的副作用。

## 还原这次问题现场

蓝点网转述的源代码审计结果称，Coze CLI 安装时会静默安装附带技能。这些技能会扫描本机的 AI 智能体目录，再把相关技能注入其中。

当 Codex 等工具处理软件开发、媒体生成、文件上传或会话任务时，被加载的技能可能把部分任务引向 Coze CLI。争议点因此不是 Coze CLI 能否执行任务，而是它是否在用户缺少明确感知的情况下，修改了其他工具会读取的执行入口。

讨论中还有一条更具体的线索。用户随机比特指出，Coze CLI 0.3.6 的包配置包含安装后钩子，说明文档也提到静默执行技能同步。这条线索给出了排查方向，但具体文件、链接和版本行为仍应以本机记录及对应版本包内容为准。

## 沿三层链路定位根因

第一层是安装钩子。

命令行工具完成安装，不代表动作只停留在可执行文件。安装后钩子还能继续运行脚本、同步资源或创建链接。若安全检查只盯着主程序，就会漏掉真正改变环境的步骤。

第二层是技能目录修改。

Agent Skills 通常以文件或目录形式存在。新增文件、复制内容和软链接都可能改变可发现的技能集合。这里最关键的证据不是某个文件名看起来是否可疑，而是安装前后发生了什么差异，以及这些内容来自哪里。

第三层是工具自动加载。

Codex、Claude Code 等工具若会从约定位置发现技能，那么目录里的残留内容可能在后续会话继续生效。安装过程已经结束，影响却可能到下一次启动任务时才出现，这也是问题容易被忽略的原因。

这条事故链可以压缩为一行。

安装后钩子执行 → 技能写入或链接到共享目录 → 其他 Agent 自动发现 → 后续任务进入新的调用路径

## 为什么卸载命令还不够

常见处理方式是卸载 Coze CLI，再确认终端里找不到对应命令。这只能证明主程序入口可能已经移除，不能证明安装脚本创建的文件和软链接也被回滚。

包管理器通常负责自己登记的安装对象。安装后脚本另行写入的目录、同步的技能和指向其他位置的链接，是否跟随卸载删除，要看卸载逻辑有没有明确覆盖。源材料没有提供自动回滚的证据，因此不能把卸载成功直接当成环境恢复完成。

只搜索带有 Coze 名称的文件也不充分。技能可能使用通用名称，软链接显示的是目标关系，真正决定影响的是 Agent 会不会发现并加载它。

## 按证据顺序修复环境

清理前应先保留现场。直接删除虽然省事，却会丢失判断改动范围所需的线索。

先记录 Coze CLI 的版本、安装时间和使用的包管理器，再查看对应版本的包配置与安装后钩子。接着检查各 Agent 会读取的技能目录，保存目录列表、文件修改时间和软链接指向。

发现新增项后，不要按名称批量删除。应逐项确认来源、创建时间、链接目标以及是否被其他工具共用。只有来源和作用能够对应上，才删除相关文件或解除链接。

完成清理后，重新打开一个隔离会话，检查工具当前发现的技能集合，并用不涉及真实项目和敏感文件的空任务验证调用路径。验收标准不是 Coze CLI 命令消失，而是技能目录差异得到解释，残留链接被处理，其他 Agent 不再加载非预期入口。

## 留下一张事故卡片

事故对象，安装 Coze CLI 后出现的跨工具技能目录改动。

触发条件，安装后钩子执行技能同步，目标目录又会被其他 Agent 自动发现。

容易漏掉的证据，安装脚本内容、目录差异、文件时间、软链接来源和工具实际加载结果。

错误恢复方式，只卸载命令行程序，或只按产品名称搜索文件。

完成标准，每一项目录改动都有来源说明，非预期文件和链接已处理，隔离会话中的技能发现结果符合预期。

这次争议最值得记住的不是某个工具该不该安装，而是一条通用规则。任何会修改共享 Agent 目录的安装器，都应该按环境变更来审查，而不是只按命令行工具来管理。
