# 一个人怎么用 ChatGPT 顶半个团队？关键不是多提问，而是划清权限边界

一个人同时写代码、整理资料、推进项目，真正缺的通常不是更多答案，而是有人接走一段可以验收的工作。

一位独立工作者分享了自己的连续工作流。Codex 修改限定目录里的代码，Git 负责回退，Obsidian 接收整理后的知识，手机上的 ChatGPT App 用来派发任务。人只保留需求判断和最终复核。

这套做法最值得借鉴的地方，不是让 ChatGPT 替代多少人，而是把零散问答改造成一条可控的交付链条。

## 误解一，多写提示词就能得到一个团队

提示词当然重要。评论里有人追问，需求、缺陷和业务逻辑仍然要反复沟通，不可能靠一句话让 ChatGPT 猜中所有意图。也有人问，新项目的 PRD 应该怎么描述，为什么做到一半总会变得四不像。

这些问题指出了同一件事。模型可以快速生成内容，却不会自动获得项目上下文、风险偏好和验收标准。把需求写得更长，只是增加输入，并没有解决交付责任落在哪里。

更准确的判断是，个人效率的分水岭已经不只是会不会提问，而是能不能定义一块足够清楚、出了问题也能恢复的工作空间。

## 让代码修改发生在可回退的房间里

原帖作者把代码交给 Codex，但前提有两个。项目文件夹提前划好边界，修改过程由 Git 兜底。

文件夹边界决定它能碰什么。Git 回退决定它做错以后，损失能否被控制。两者合在一起，才让“放手执行”从一句口号变成工程动作。

一个更稳妥的交付链条可以写成下面这样。

需求说明 → 限定目录 → Codex 修改 → 查看差异 → 运行检查 → 人工确认 → 提交 Git

这里不需要迷信所谓的代码准确率。准确率会随项目、上下文和任务复杂度变化，源材料也没有提供可验证数字。真正可控的是改动范围、差异记录、测试结果和回退路径。

## 把知识库维护改成待审核交付

第二个场景是 Obsidian。对话结束后，相关内容进入知识库，由人负责 review。

常见误解是，自动写入就等于自动沉淀。其实未经筛选的对话很容易制造重复笔记、错误结论和失效上下文。知识库一旦变成聊天记录仓库，搜索结果只会越来越吵。

更合适的做法，是让 ChatGPT 交付一份待审核的知识条目，而不是直接改写整个资料库。它可以整理标题、来源、结论和待办，人负责确认事实、删除重复内容，并决定放进哪个目录。

权限也应跟着任务收窄。让它写入专门的收件箱目录，比开放全部笔记更容易复核。审核完成后再由人移动到正式目录，知识库才不会因为追求自动化而失去可信度。

## 手机派活不等于手机验收

第三个场景看起来最轻松。路上想到任务，在 ChatGPT App 里发出去，到家查看结果。

真正有价值的不是随时聊天，而是把碎片时间用于启动任务。任务能否独立推进，取决于它有没有明确对象、允许修改的范围和完成标准。

“优化一下项目”很难验收。“只检查登录模块，把发现的问题写入任务文件，不修改其他目录”就清楚得多。手机适合派发边界明确的工作，涉及架构选择、删除数据和发布上线的动作，仍应停在人工确认之前。

这也解释了为什么手机端和电脑端是否同步，并不是这套方法的核心。真正需要同步的是任务状态、修改记录和交付物，而不只是聊天记录。

## 真正省下来的，是切换和盯人的时间

原帖作者称，自己两个月没有招人，ChatGPT 承担了过去助理加开发的一部分工作量。这个案例能说明一种工作方式，却不能直接推导出所有人都能获得相同结果。

它更像一次权限设计。代码只能在指定目录改，知识先进入待审核区，移动端只派发可验收任务，Git 和人工复核守住出口。

我的判断是，独立工作者不该先追求让 ChatGPT 做更多，而该先让每次出错都容易发现、容易撤回。权限越清楚，能放心交出去的工作反而越多。

选一个正在维护的测试仓库，只开放一个低风险目录，交给 Codex 完成一项能检查差异的小修改。保留回退点，并亲自走完一次复核流程。能稳定交付一次，再扩大下一次的边界。
