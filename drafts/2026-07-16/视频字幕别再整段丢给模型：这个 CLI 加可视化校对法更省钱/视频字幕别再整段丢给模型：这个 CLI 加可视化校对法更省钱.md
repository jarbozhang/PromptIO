# 视频字幕别再整段丢给模型：这个 CLI 加可视化校对法更省钱

做长视频字幕，真正烧钱的往往不是第一次翻译，而是改一个断句后，又把翻译、对齐和视频生成重新跑一遍。这个案例适合经常处理视频字幕，又不想把最终判断交给模型的创作者。

它给出的不是一个更强的模型，而是一套新的分工。Agent 负责翻译和纠错，CLI 负责调用 App 的能力，图形界面负责预览和二次编辑，人保留最终校对权。

我认为这次迭代最值得借鉴的地方，是把省钱目标从寻找低价模型，换成减少重复生成。

## 看清整段翻译怎样变成重复账单

原分享里的字幕 App 最初是作者自己使用的。旧方案先让 LLM 整体翻译，再按句子配对，最后继续交给 LLM 拆分。

问题出在最后一步。字幕拆分效果总是不理想，一旦断句或配对需要调整，工作流就容易回到模型侧继续处理。

`整段翻译 → 按句配对 → LLM 拆分 → 人工发现问题 → 再次处理`

模型调用本身也有门槛。普通用户需要配置 API Key，作者提到，使用 Gemini 3.5 Flash 处理一部长一点的视频也要花几美元。

这里不只是单次价格的问题。翻译、拆分和对齐被绑在同一条链路里，任何局部修改都有可能带来新的模型调用。

## 把 App 变成 Agent 能调用的执行层

这次迭代的转折点不是更换模型，而是改走 Agent 加 Skill 的路线。

作者先把 App 的能力封装成 CLI，让 Agent 可以通过命令行调用。CLI 不再是要求普通用户记住的一组命令，而是 Agent 和 App 之间的接口。

转录、润色、翻译、对齐和剪辑这些常用流程，则被固化进 Skill。Agent 不必每次重新摸索执行顺序，可以沿着已经整理好的工作流操作。

原分享还提到，Agent 本身具备不错的纠错能力。即使没有专门提供纠错工具，它也能在翻译过程中同步发现和修正问题。

新的链路变成了另一种形态。

`Agent 读取 Skill → 调用 CLI → App 执行字幕能力 → 产出可预览结果`

我更看重 CLI 在这里扮演的角色。它没有抢走 App 的价值，而是把适合重复执行的能力交给 Agent 编排，让 App 集中处理机器不擅长替人决定的部分。

## 把交付物留在还能修改的状态

Agent 操作结束，不等于字幕已经可以直接交付。

如果人只能阅读文本字幕，定位问题会很慢。如果每改一点内容，都要重新用 ffmpeg 生成一遍视频，等待和重复操作又会堆起来。

这个 App 因而保留了图形化预览和二次编辑。人可以快速查看 Agent 处理后的结果，再完成最终校对。

| 交付节点 | 原来的状态 | 调整后的状态 |
| --- | --- | --- |
| 模型处理后 | 还要继续修正拆分问题 | Agent 按 Skill 编排并同步纠错 |
| 人工介入时 | 阅读文本或重新生成视频 | 在图形界面预览并二次编辑 |
| 局部修改时 | 容易牵动整条处理链路 | 尽量把修改留在可编辑环节 |

交付物由一次性的模型输出，变成了一个仍然可以检查、修改和确认的中间状态。对字幕工作来说，这个变化比完全自动化更实用。

## 用一次小修改验收这条链路

复用这套思路时，可以拿一段有断句或对齐问题的字幕做验证。

- 让 Agent 按固定 Skill 完成转录、润色、翻译和对齐
- 通过 CLI 调用已有 App 能力，不手工重复搬运文件
- 在图形界面检查字幕，保留人工二次编辑
- 修改其中一句，观察是否还要重新调用整段翻译并完整生成视频

验收重点只有两个。Agent 能否稳定复用工作流，人工修改能否停留在预览和编辑环节，而不是不断回到整条链路的起点。

当前公开信息主要呈现了架构取舍，具体 CLI 参数仍需以项目说明为准。

## 把省钱算在少走回头路上

作者还提到一个现实条件，很多人已经在使用通用 Agent，包月 Token 经常没有用完，用来处理字幕工作正合适。

这不代表 Agent 没有成本。它的优势是可以复用已有额度，同时让 Skill 保存成熟流程，目标是减少反复翻译、拆分和重新生成带来的消耗。

我的判断是，字幕 App 不该只做一个输出结果的机器。模型适合处理翻译和纠错，命令行适合连接可重复执行的能力，图形界面适合承接预览，人则负责最后那次确认。

找一条你最近反复修改过的字幕，把每次返回模型和重新生成视频的位置标出来。哪些动作可以封装成 CLI，哪些流程应该写进 Skill，哪些决定必须留给预览界面，答案会比再换一次模型更接近真正的省钱方案。
