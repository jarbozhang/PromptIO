# Karpathy 写代码踩的坑被收成 60 行 CLAUDE.md，一夜涨 2409 星

先解释一下，Karpathy 是前特斯拉 AI 总监、OpenAI 创始团队成员，最近这两年他在 X 上零零碎碎吐槽过很多"AI 写代码翻车点"。他没自己写代码，是别人替他收拾出来的。

那天我刷 GitHub Trending，单日新增 stars 排第一的不是新模型也不是 agent 框架，是个**只有一个 CLAUDE.md 文件的仓库**，`forrestchang/andrej-karpathy-skills`，单日 +2409，正文不到 60 行。

我把它装进自己的项目跑了一周，写下这篇。

## 60 行写了 4 条原则

**1. Think Before Coding，写之前先想**

不要默认假设、不要藏着困惑、看到更简单的方案要顶回去、不清楚就停下问。

治的就是"AI 一上来就开始写"。我写 RSS 抓取脚本时，需求里其实有"是否带重试"的可选项，老版本 Claude Code 直接帮我做主全堆上 retry，我得回头删。

**2. Simplicity First，能 50 行别写 200 行**

不实现没要求的功能、不为单次代码做抽象、不加没人要的"灵活性"、不为不可能的场景做错误处理。

最后一句最狠，"资深工程师会觉得这个过度复杂吗？如果会，就简化"。国内很多人写代码喜欢"先把架构铺好"，AI 学了这习惯就会把 30 行的脚本写成带 plugin 系统的小框架。

**3. Surgical Changes，外科手术式改动**

只动你必须动的，别"顺手"优化注释格式、别 refactor 没坏的东西、哪怕你不喜欢也要遵循已有风格。

判断标准是"每一行改动都能追溯到用户的请求"。维护老项目的人尤其有用，AI 一上手爱顺手"美化"，commit 打开 100 行变更只有 10 行是真需求。

**4. Goal-Driven Execution，把任务变成可验证目标**

- "加个校验" 改成 "为非法输入写测试，让它通过"
- "修这个 bug" 改成 "写一个能复现 bug 的测试，让它通过"

逼 AI 把"我做完了"换成"我跑过了"。

## 为什么是 60 行就 2409 星

我去 r/ClaudeAI 翻评论，最高赞回答只有一句话，"因为很多人按了 star 按钮"。第二高赞那条更扎心，"容易抄、有 Karpathy 名字、戳中了真痛点"。第三条是 203 赞的总结，"原来每个人都需要给 AI 配一套同款家长控制"。

每个用 AI 写代码的人都在装"家长控制"。

## 装上一周我看到的差别

我把这份 CLAUDE.md 直接塞到项目根目录，覆盖了原来 200 行的 rules，对比最近 30 个 commit 的 diff 模式。

**第一，开始问问题了。** 让它给文章生成脚本加"按 voice 分流"逻辑，新版本第一句是"voice 是指你 prompt 里写的 first-person/narrative/analytical/retro 这四种吗，还是另有定义"。我才反应过来 voice 这个词在两个 prompt 文件里其实定义不一致。

**第二，diff 变小了。** 抽 7 个 commit 看，平均改动行数从 80 行降到 30 行左右。

**第三，开始写测试再写代码。** 我没要求 TDD，但 Goal-Driven Execution 那条让模型把"修 bug"自动翻译成"写复现测试 → 让它过"。

但也不是没坑。它在改一个脚本时"过度遵守"Surgical Changes，看到一个明显写错的变量名也不动。Simplicity First 让它"too simple"，写 RSS 解析器只写了一种通用 case，没处理 Atom 和 RSS 1.0 的差异。

## 我的判断

这份 CLAUDE.md 不是模板，是清单。

它的真正价值不是写得多好，是给了你一个**和 AI 对齐的术语表**。下一次 AI 又开始过度发挥，你不用解释一大段，你只要说"这违反了 Surgical Changes"，模型立刻知道你在说什么。

国内开发者下一步可以做两件事。一，直接 fork 到自己常用的项目根目录，不要做任何"中国特色"加工，它的好就好在通用。二，过 5-7 天回头扫 git log，看 commit 平均行数有没有变化。如果没变化，说明你需要的不是规则，是换个模型。

那个曾经"什么都帮你做主"的 AI，是时候被你重新驯化一遍了。
