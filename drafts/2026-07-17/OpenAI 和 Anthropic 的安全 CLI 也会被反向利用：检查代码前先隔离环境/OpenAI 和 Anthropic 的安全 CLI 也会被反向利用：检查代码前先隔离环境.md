# OpenAI 和 Anthropic 的安全 CLI 也会被反向利用：检查代码前先隔离环境

把陌生依赖交给 Claude Code 或 Codex CLI 做安全检查，听起来是在降低风险。但 AI Now Institute 公布的一项概念验证表明，审查工具本身也可能成为攻击链的一环。

这项研究覆盖 Anthropic Claude Code CLI 和 OpenAI Codex CLI。研究者展示的路径并不要求先攻破开发者电脑，而是把恶意内容放进等待检查的开源或第三方库，再诱导防御型智能体执行危险操作，最终触发远程代码执行。

对使用编码智能体审查依赖、处理安全告警或分析陌生仓库的团队，关键动作很明确。不要让审查任务直接继承日常开发环境的权限、凭证和网络能力。

## 重新划定代码审查的风险面

传统代码审查通常把仓库当作被观察对象。智能体式审查改变了这个关系，因为工具不只读取文件，还可能调用命令、解释项目配置，并沿着任务链继续行动。

一旦被审查仓库能够影响工具看到的上下文，攻击者就有机会把恶意指令伪装成正常的项目内容。此时，安全 CLI 虽然承担防御任务，却仍然运行在一个可能被输入操纵的执行循环里。

AI Now Institute 披露的概念验证针对 Claude Code 的默认配置，涉及 Claude Sonnet 4.6、Claude Sonnet 5 和 Claude Opus 4.8，也覆盖搭配 GPT-5.5 的 Codex CLI。研究结论针对特定配置与测试链条，不能直接推导为所有版本、所有任务都会被利用，但足以说明默认信任模型需要调整。

## 沿着失效链条检查权限

这类问题可以拆成四个连续环节。

1. 恶意内容进入待审查的开源库或第三方依赖。
2. 安全 CLI 在分析过程中读取受到攻击者控制的文件与指令。
3. 工具被诱导调用命令，审查行为从静态阅读跨入主动执行。
4. 命令继承工作环境的权限，攻击影响扩展到主机、凭证或可访问资源，并可能形成远程代码执行。

真正决定损失大小的，往往不是模型是否识别出恶意内容，而是第三步之后还有多少权限可用。模型层防护可能失败，操作系统和运行环境的边界不能跟着失效。

## 把控制点放在模型之外

适合团队保存的防护动作可以压缩成下面这张清单。

- 隔离工作区，在临时容器、虚拟机或专用执行环境中打开陌生仓库，不与日常开发目录混用。
- 收紧文件权限，只挂载审查必需的代码，并优先采用只读方式提供输入。
- 清空敏感凭证，不向审查环境注入代码托管令牌、云密钥、签名材料和生产配置。
- 限制网络能力，按任务需要设置允许访问的目标，避免审查进程拥有不受约束的连接能力。
- 收紧命令执行，对安装脚本、构建钩子、测试命令和解释器调用设置人工确认或明确规则。
- 保留执行记录，记录工具调用的命令、参数、工作目录、文件变更和网络行为。
- 设置生命周期，任务结束后销毁环境，不把受污染状态带入下一次审查。

这些控制并不依赖模型每次都作出正确判断。即便诱导成功，攻击仍需要继续穿过权限、网络和环境销毁机制。

## 上线前跑一次对抗验证

不要用真实业务仓库完成第一次验证。准备一个不含凭证的测试项目，在其中放入会诱导工具读取额外文件、修改目录或调用无害命令的内容，然后观察审查环境如何响应。

验收时重点核对四件事。

- 未授权命令是否被阻止或要求确认。
- 容器之外的文件是否无法读取和修改。
- 非必要网络请求是否被拒绝并留下记录。
- 任务结束后，工作区和临时凭证是否被彻底清理。

如果日志只能显示最终回答，却看不到命令调用与文件变化，这套审查流程仍然缺少关键证据。安全评估需要能够还原执行过程，而不只是保存模型生成的结论。

安全 CLI 可以提高审查效率，但不能同时充当执行者和唯一的安全边界。把陌生仓库视为不可信输入，把智能体视为可能被诱导的自动化进程，再用隔离环境限制后果，才是更稳妥的上线顺序。
