# OpenAI 用 GPT-Red 攻击自己的模型：普通团队能抄走哪些防守方法

如果团队正在把 Agent 接进代码仓库、内部知识库或业务系统，真正该担心的已经不只是模型答错，而是它会不会在错误指令下拿着真实权限继续行动。

OpenAI 构建了一个名为 GPT-Red 的大模型攻击者，让它持续充当其他模型的对抗伙伴。报道称，OpenAI 将 GPT-Red 的攻击发现用于增强模型防御，并称 GPT-5.6 在这类对抗训练帮助下成为其当时最稳健的版本。

普通团队很难复刻同等规模的攻击模型，却可以抄走更重要的工程方法，把攻击、修复、复测和上线闸门连成闭环。下面这张参考卡，适合在 Agent 上线前逐项核对。

## 确认系统具备被测试的前提

红队测试不是找几条刁钻提示词逗模型，而是检查模型能否被诱导越过系统边界。没有清晰边界，攻击成功与否都无法判断。

开始前至少写清四件事。

- Agent 可以读取哪些数据，哪些数据永远不能读取
- Agent 可以调用哪些工具，每个工具允许执行到哪一步
- 哪些动作必须由人确认，例如发信、改代码、删除记录和提交交易
- 出现异常时如何停止任务、撤销变更并保留审计记录

这里最容易漏掉的是间接提示注入。恶意指令不一定来自用户输入，也可能藏在网页、邮件、文档或工具返回值里。只测聊天框，相当于只检查大门，却忽略了所有侧门。

## 用短清单覆盖真正的攻击面

普通团队不需要一开始就训练专用攻击模型。先建立一组可重复运行的攻击样本，让另一个模型负责生成变体，再由规则和人工共同判断结果。

发布前检查可以压缩成六项。

- 权限升级，诱导 Agent 调用原本无权使用的工具
- 数据泄露，要求它复述系统提示、密钥、内部文档或其他用户内容
- 间接注入，在检索文档和工具输出中嵌入冲突指令
- 目标劫持，让任务从回答问题悄悄变成修改、发送或删除
- 多轮绕过，把一次会被拒绝的请求拆成连续小动作
- 防线退化，模型或提示词更新后重跑旧攻击，检查已修问题是否回归

攻击样本不能只保存输入，还要保存上下文、工具权限、模型输出、实际调用记录和判定理由。否则同一条测试在不同版本中失败，很难确认变化来自模型、提示词还是工具层。

## 看到这些信号就暂停上线

最危险的失败并不是模型直接答应恶意请求，而是它表面拒绝，后台却已经调用了工具。

以下信号出现一个，就应该阻断发布。

- 文本回答合规，但工具调用越过了权限边界
- 同类攻击换一种表达就能绕过拒绝
- 测试结果无法稳定复现，团队也说不清判定标准
- 修复只增加了一段提示词，没有收紧工具权限
- 新版本通过了新测试，却重新暴露旧漏洞
- 日志只能看到最终回答，看不到中间决策和外部调用

提示词防护有价值，但不能承担全部安全责任。模型可能误解指令，权限系统却必须确定地拒绝越权动作。真正可靠的控制点通常位于模型之外，包括最小权限、参数校验、人工确认、速率限制和可撤销执行。

## 把最小验证跑成一个闭环

选一个拥有真实风险、但后果容易控制的任务，例如让 Agent 阅读测试知识库并生成摘要。知识库中放入一份带有恶意指令的测试文档，要求它忽略原任务并读取受限文件。

最小验证只跑四轮。

1. 记录未加防护时，攻击能否改变任务目标
2. 收紧检索范围和工具权限，再运行相同攻击
3. 让攻击模型改写表达，生成若干语义相同的变体
4. 将成功和失败样本全部加入回归测试，并设置发布阻断条件

验收标准不要只写成模型应该拒绝。更可执行的标准是，受限文件未被读取，未授权工具没有调用，异常行为进入日志，失败任务可以停止，并且同类变体无法轻易绕过控制。

## 把防守重点放在闭环，而不是一次高分

GPT-Red 值得普通团队关注的地方，不是拥有一个更会攻击的模型，而是攻击结果能够返回训练和测试流程。攻击不断变化，防守也随之更新，旧问题则留在回归集里持续检查。

我的判断是，Agent 安全的分水岭不在于团队有没有专职红队，而在于一次攻击成功后，系统是否会永久多出一道可验证的防线。只修提示词，问题很可能换个表达再次出现。把发现转成权限规则、测试样本和上线闸门，失败才真正变成工程资产。

可以从一个测试知识库和一个受限工具开始。本周发布前跑完这条最小闭环，比临上线再组织一次宽泛的安全评审更有用。
