# 用 Vercel 的 100 项测试检查网站：AI 能不能真正读懂并操作你的产品？

如果你在做 SaaS、开发者工具或带工作流的网站，这份检查卡能帮你回答一个新问题。AI Agent 进入页面后，究竟只能读几段文字，还是能发现功能、调用接口并完成操作。

Vercel 推出的 is-agentic 会执行 100 多项检查，给网站生成 Agent Readiness Score。它覆盖页面发现、内容读取、结构化接口、API、OAuth、MCP 和 GraphQL 等能力，还能针对问题生成修复 Prompt。

我更关心的不是分数好不好看，而是它能不能暴露产品交付中的真实断点。下面这套短清单，可以直接用于一次发布前检查。

## 选一个能完成任务的真实页面

不要只测首页。首页通常内容完整、链接清楚，却很难代表 Agent 真正使用产品时会遇到的路径。

我会选择一个带明确任务的真实入口，例如文档搜索页、商品详情页、预约页、控制台帮助页或 API 文档页。验收目标只写一句话，例如“Agent 能否找到创建项目所需的信息和接口”。

运行入口可以使用命令行。

`npx is-agentic <domain>`

保存总分，同时记录每个失败项指向的具体页面。单独抄一个分数没有多少价值，能定位断点才有用。

## 按五类检查项过一遍

这份发布前检查卡不需要很长，我会集中看五类问题。

- 页面发现，关键页面能否被找到，导航和入口是否形成清楚路径
- 内容读取，标题、正文、链接和操作对象是否容易被解析
- 结构化接口，机器是否能获得比页面文本更稳定的数据表达
- 身份与授权，OAuth 等机制是否让 Agent 在受控条件下继续任务
- 操作能力，API、MCP 或 GraphQL 是否覆盖页面宣称的核心动作

这五类检查对应两种完全不同的失败。第一种是 Agent 看不懂页面，第二种是它看懂了，却没有可调用的动作。

很多网站只解决了前一种。文档写得很全，页面也能读取，但关键能力仍然被锁在按钮、弹窗和人工流程里。对 Agent 来说，这类产品更像一本说明书，而不是一个可以使用的系统。

## 用失败信号判断问题轻重

我会把报告里的问题分成三档，而不是照着列表逐条修改。

高优先级信号是核心页面无法发现、关键内容无法读取，或者产品宣称能完成某项任务，却没有稳定的结构化入口。这些问题会直接中断任务链。

中优先级信号是已经存在 API、OAuth、MCP 或 GraphQL，但命名、授权范围或文档入口不清楚。Agent 可能有能力继续，却需要猜测下一步。

低优先级信号通常是补充性元数据或非核心页面问题。它们可以改善分数，但未必改善关键任务的完成率。

我的判断很简单。修复顺序不该由扣分多少决定，而该由失败项是否阻断真实任务决定。一个让 Agent 找不到结算、创建或提交入口的问题，通常比多个边缘页面的小缺口更重要。

## 筛掉不该直接采纳的修复 Prompt

自动生成修复 Prompt 很省事，但不能直接等同于正确改动。Coding Agent 能快速改代码，也可能扩大接口暴露范围、改变授权边界，或者为提高分数加入产品并不需要的能力。

我会在采纳前检查四件事。

- 是否对应刚才选定的真实任务
- 是否只改必要页面和接口
- 是否改变 OAuth 权限或数据暴露范围
- 是否有清楚的回归验证方式

如果建议只是为了补一个检查项，却无法解释它会改善哪条用户任务，我会暂缓采纳。如果建议涉及身份、权限或写操作，我会把它当成一次接口变更审查，而不是普通文案修补。

## 把最小验证压到一次完整任务

完成一轮修改后，不必立刻追求满分。重新运行同一个域名，再用最初那句话验收。

例如，Agent 是否能找到创建项目的文档，识别所需参数，发现授权方式，并定位可调用接口。只要其中一步仍靠猜，任务链就还没有闭合。

官方展示的评分里，Ora 为 98，Vercel 为 90，Stripe 为 80，OpenAI 和 GitHub 均为 72，Linear 为 64，Anthropic 为 62。这些数字适合用来理解评分跨度，不适合直接变成产品优劣排名。

更实用的做法，是给自己的网站留下一张验证记录。测试页面、目标任务、主要失败项、采纳的修复建议和复测结果，各写一行。下一次发布时继续跑同一个任务，分数变化才有上下文。

现在就选一个承载核心动作的页面，运行一次 `npx is-agentic <domain>`。先修掉最早中断任务的那个失败项，再判断分数是否真的跟着产品可操作性一起改善。
