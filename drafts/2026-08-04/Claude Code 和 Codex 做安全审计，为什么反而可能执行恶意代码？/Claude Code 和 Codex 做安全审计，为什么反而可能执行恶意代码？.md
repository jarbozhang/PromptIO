# Claude Code 和 Codex 做安全审计，为什么反而可能执行恶意代码？

让 Claude Code 或 Codex 检查一个陌生依赖，看起来是一项防御任务。研究人员披露的概念验证却指出，代码代理可能在审计过程中被目标影响，最终触发远程代码执行。

这类风险值得做安全审计、依赖评估和开源选型的工程师关注。真正需要重新划线的，不只是模型能读哪些文件，而是它能否下载依赖、运行构建、启动测试，以及调用本机命令。

读完最该带走的判断很直接。未知仓库不是一份等着阅读的文本，而是一组可能改变代理行为的输入。审计权限一旦接近开发权限，防守动作也可能变成执行入口。

## 还原一次由审计发起的失控

AI Now Institute 披露了一项概念验证攻击。研究人员称，当 Claude Code CLI 和 Codex CLI 被用于防御性评估开源项目或第三方库时，攻击可在开箱配置下造成远程代码执行。

披露点名的组合包括 Claude Code CLI 搭配 Claude Sonnet 4.6、Claude Sonnet 5、Claude Opus 4.8，以及 Codex CLI 搭配 GPT-5.5。

事件里的角色发生了错位。操作者希望代码代理寻找恶意行为，待审计对象却成了能够影响代理的输入。代理若继续拥有执行能力，风险就不再停留在错误结论，而会落到真实的系统动作。

这正是 Friendly Fire 这个名字传达的冲突。负责防御的代码代理没有被要求主动攻击系统，却可能在完成防御任务时把危险动作带进本机环境。

## 把事故链拆成四道权限转换

这次披露提供的是概念验证结论，简短材料没有展开载荷设计和完整利用细节。不过从暴露的任务边界看，事故链可以按权限变化来理解。

第一道转换发生在接收目标时。第三方仓库从被检查对象，变成了代理需要读取和处理的工作材料。

第二道转换发生在理解任务时。代码代理不仅分析操作者的要求，也会接触目标项目提供的内容。未经信任的内容由此进入决策环境。

第三道转换发生在验证阶段。安全审计常常需要构建、测试或运行样例。只读分析由此跨进命令执行，而仓库中的依赖和脚本也获得了被调用的机会。

第四道转换落在宿主系统。代理沿用当前进程拥有的文件、网络和命令权限，错误动作的影响范围也随之扩大。远程代码执行不是一次答错，而是决策错误穿过工具权限后的结果。

## 为什么常见的审计习惯挡不住它

很多团队会把注意力放在提示词上，例如要求代理保持怀疑、不要相信仓库说明、发现异常立即停止。这些约束有价值，却不能代替系统隔离。

原因很简单。提示词约束的是代理如何判断，权限控制约束的是判断失败后还能做什么。只要一次错误判断就能调用高权限命令，防线仍然押在模型每次都判断正确。

人工确认也未必足够。一个看似正常的安装、构建或测试命令，很容易被当作审计的必要步骤。确认窗口展示的是即将执行的动作，却不一定能把依赖脚本和后续行为解释清楚。

把仓库放进新目录同样不是完整隔离。目录边界无法自动限制进程读取凭据、访问其他文件或使用当前环境提供的网络能力。真正有效的边界必须落到运行环境和权限上。

## 用权限设计修复审计流程

修复重点不是让 Claude Code 或 Codex 更谨慎地阅读，而是把阅读、构建、测试和执行拆成不同阶段。

初始审阅只开放必要文件，并关闭不需要的执行能力。需要构建或测试时，把任务转移到一次性隔离环境，不挂载个人目录、项目密钥、SSH 配置和长期凭据。

网络权限也应按任务开放。若验证不需要联网，就不提供网络。确实需要下载依赖时，应把下载阶段与运行阶段分开，并记录来源、产物和实际执行的脚本。

高风险动作不能沿用日常开发会话。陌生仓库的审计环境应该假设目标内容可能主动影响代理，并把最坏结果限制在可销毁的工作区内。

修复是否有效，可以用一个问题验收。即使代码代理完全听从了目标仓库里的恶意指令，它还能接触哪些文件、凭据、命令和网络入口。如果答案仍包含日常开发环境，隔离就还没有完成。

## 留下一张陌生仓库事故卡片

事故类型　防御性代码审计触发远程代码执行

风险对象　使用 Claude Code CLI 或 Codex CLI 检查开源项目及第三方库的人员

关键失误　把不可信输入与可执行权限放进同一代理会话

常见误判　认为安全审计天然是只读任务，或认为确认一条命令就能看清完整后果

控制重点　分离阅读、下载、构建、测试和执行，并把后四类动作放进低权限、无长期凭据、可销毁的环境

验收标准　目标仓库即使成功影响代理，也无法越过隔离区触碰真实工作资料和长期身份凭据

代码代理可以扩大安全审计的覆盖面，但不能同时充当不可信输入的解释器和高权限执行者。审计陌生仓库时，最可靠的防线不是期待它永远识破陷阱，而是让一次误判没有继续扩大的权限。
