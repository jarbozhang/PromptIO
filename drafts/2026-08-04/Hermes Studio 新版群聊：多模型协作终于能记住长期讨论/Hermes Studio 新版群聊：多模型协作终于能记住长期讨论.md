# Hermes Studio 新版群聊：多模型协作终于能记住长期讨论

如果你让多个 Agent 围绕同一个任务持续讨论，大概率会遇到两个麻烦。角色越多，对话越容易偏离最初目标。历史消息越长，送给模型的上下文也越重。

Hermes Studio 预告的新版群聊，瞄准的正是这两个问题。它允许自由组合 Agent、模型与 Profile，并通过滚动总结压缩长对话，在控制上下文长度的同时保留关键讨论。

我更关注后半部分。把几个模型放进一个群聊并不难，难的是让它们聊了几十轮以后，仍然记得已经确认的事实、没有解决的分歧，以及接下来应该交付什么。

## 别让角色数量拖垮讨论质量

旧式多 Agent 群聊很容易停在展示层。一个角色负责提方案，一个角色负责质疑，再加一个角色做总结，看起来分工完整，实际运行久了却会暴露三个问题。

历史消息持续膨胀，后加入的角色需要读取越来越多内容。早期约束可能被后续对话淹没。多个角色还会重复解释同一件事，让上下文成本继续增加。

这不是多加几个角色就能解决的问题。参与者越多，系统越需要一套稳定的会议记录机制，否则群聊只是把单模型的上下文混乱放大了。

Hermes Studio 这次重构群聊上下文系统，并引入滚动总结。按照预告，系统会在持续讨论中动态提炼关键信息，控制上下文长度，并尽量维持连贯性与核心记忆。

## 把角色、模型和配置真正拆开组合

新版群聊支持任意 Agent、任意模型和任意 Profile 的自由组合。这三层拆开后，群聊不再只是几个固定助手轮流发言，而更像一个可以按任务临时组建的协作空间。

| 变化 | 解决的问题 | 对协作的价值 |
|---|---|---|
| 自由选择 Agent | 固定角色难以覆盖不同任务 | 可以按交付目标安排研究、质疑、整理等职责 |
| 自由选择模型 | 所有环节被迫使用同一种能力 | 不同任务可交给更匹配的模型处理 |
| 自由选择 Profile | 角色设定与运行配置难以复用 | 同一套角色配置可以进入不同讨论 |
| 滚动总结 | 长对话越来越重、重点逐渐丢失 | 用压缩后的关键状态延续讨论 |

我认为，这里的关键不是“模型更多”，而是角色、能力和配置开始解耦。一个 Agent 可以承担稳定职责，模型提供具体能力，Profile 则保存行为偏好或配置。任务变化时，不必把整套协作逻辑推倒重来。

不过，预告没有展开滚动总结的触发条件、保留格式、可编辑能力和失败处理方式。这些细节会直接决定它能否用于严肃交付，也应成为版本开放后的重点验证项。

## 用滚动总结守住长期讨论

滚动总结可以理解为持续更新的讨论状态。系统不必把全部历史逐字交给每个参与者，而是不断提炼已经确认的信息，再让后续角色围绕这份状态继续工作。

一份有效的群聊记忆，至少要区分几类内容。哪些事实已经确认，哪些结论仍有争议，哪些约束不能被覆盖，哪些任务已经完成，以及谁负责下一步。

如果总结只保留最终结论，群聊可能忘记结论成立的条件。如果压缩过度，少数意见和未解决风险也可能消失。滚动总结缓解的是上下文长度问题，它并不自动保证记忆完全准确。

这给 Agent 应用一个很直接的启发。长期记忆不能只是把旧消息塞回提示词，更需要维护一份可更新、可检查的任务状态。多 Agent 协作的质量，最终取决于这份状态是否比原始聊天记录更清楚。

## 判断哪些任务适合放进群聊

我会优先用新版群聊验证需要多种能力、又必须保持共同上下文的任务。

产品方案评审是一个合适场景。一个 Agent 提方案，一个检查用户路径，一个关注工程约束，最后由另一个角色收束仍未解决的分歧。滚动总结应当保存决策依据，而不只是最后选择。

研究与写作也适合。不同模型可以分别负责资料归纳、反方审查和结构整理，群聊记忆则持续保存来源、核心判断与待核实信息，减少反复复述背景。

代码设计讨论同样值得验证。让角色分别关注接口、测试和风险，再观察长对话后是否仍能保留最初约束。涉及真实代码变更时，最终结论仍要回到仓库、测试和人工审查中确认。

短问答、一次性改写或目标含糊的开放聊天，则未必需要多角色群聊。协作角色越多，协调成本越高。没有清晰交付物时，多模型更可能增加声音，而不是增加答案质量。

## 等版本开放后验证一场真实会议

新版目前处于预告阶段。开始验证时，我会选一场能够在有限轮次内验收的任务，例如评审一页产品方案，并提前写清角色职责、共同约束和最终交付物。

讨论进行一段时间后，重点检查滚动总结是否保留关键决策、未决问题和责任分工。再让新角色加入，观察它能否仅凭当前上下文接续任务。如果必须重新讲一遍背景，长期讨论的记忆链仍然没有真正建立。

Hermes Studio 这次更新最值得看的，不是群聊里能放多少个模型，而是它能否把一场不断变长的讨论，维持成一份仍可继续工作的共同记忆。
