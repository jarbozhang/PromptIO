# DeepSeek Harness 还是 Pi：线上项目别只追新，先算稳定性成本

如果团队正在做一个必须上线、必须持续运行的 Agent 项目，我会优先选 Pi，而不是把新架构押在主路径上。

这个选择并不代表 DeepSeek Harness 没有价值。真正影响交付的，是团队愿意为架构的新颖度承担多少稳定性成本。

我现在做选型，会把主路径复杂度、运行稳定性、权限边界、测试覆盖和迁移成本放进同一张备忘录。框架能力只是其中一项，项目能不能按时交付才是最后的判断标准。

## 把主路径长度算进交付成本

宝玉在原帖里的判断很直接，年轻时会选 DeepSeek Harness，现在会选 Pi。原因不是技术偏好变保守了，而是评价标准从“我能学到什么”变成了“团队要为它承担什么”。

讨论中有人把 Pi 的相对稳定归因于主路径短、变化面小。这个角度比罗列功能更接近线上项目的现实。链路每增加一层，团队就多一个需要理解、监控和排查的接口。

新架构的吸引力也是真实的。它可能提供更完整的工具组织方式，也可能更接近团队未来想要的 Agent 形态。问题在于，这些潜在收益能否覆盖当前的集成和排障成本。

我的判断很简单。若项目的核心目标是验证新架构，复杂度可以成为研究对象。若核心目标是把业务交付出去，复杂度就是需要付利息的负债。

## 用故障半径判断稳定性

“稳定”不能只理解成程序能启动。线上 Agent 会调用工具、读写文件、执行命令，还要面对模型输出变化和依赖更新。真正需要评估的是，一次异常能影响多大范围，以及团队多久能定位到问题。

Pi 的主路径较短，减少了需要同时观察的变化面。但评论中也指出一个重要边界，Pi 默认继承启动用户的权限，没有提供沙箱能力。把它放进生产环境时，简单并不会自动带来安全。

这也是我不会只凭“成熟稳定”四个字拍板的原因。主路径短降低的是工程复杂度，沙箱和最小权限处理的是执行风险，两者不能互相替代。

如果团队没有独立运行账户、权限隔离或执行边界，Pi 的简单可能把风险推到系统层。如果团队已经有成熟的隔离设施，较短的主路径反而更容易被纳入现有控制体系。

## 用测试覆盖购买迁移自由

很多团队押注新框架，是担心今天选简单方案，明天会被锁死。宝玉给出的反向判断更值得琢磨，有 AI 协助编码后，只要测试覆盖足够，未来更换底层并没有想象中困难。

我认同这个方向，但前提不是“AI 会帮我重写”，而是业务行为已经被测试固定下来。需要保护的不是某个框架调用，而是工具输入输出、权限拒绝、失败重试、状态恢复和关键业务结果。

测试覆盖不足时，无论选择 Pi、DeepSeek Harness，还是直接用 TypeScript 手写，迁移都会变成一次重新猜测业务规则的过程。测试覆盖足够时，框架才更接近可替换部件。

所以我会把一部分原本用于追新框架的时间，换成契约测试和关键路径测试。这笔投入既保护当前交付，也降低以后迁移到 DeepSeek Harness 或其他方案的成本。

## 分清谁该先交付，谁适合先押注

适合优先选 Pi 的，是已经背着上线时间、团队规模有限、业务路径还在变化，并且愿意自行补齐权限隔离的团队。它的价值不是功能更多，而是让主路径保持可理解。

适合验证 DeepSeek Harness 的，是 Agent 基础设施本身就是产品能力、团队能承担早期变化，并且愿意为新架构建立测试与观测体系的团队。此时，探索不是额外成本，而是项目目标的一部分。

还有第三条路。评论中有开发者选择直接用 TypeScript 手写，以换取更高的定制程度。它减少了不需要的框架能力，却把长期维护责任完整留给团队。这条路适合边界清晰、工程能力充足的项目，不是天然更省事。

## 我的选择是把新架构移出主路径

如果今天要为线上项目做决定，我会让 Pi 承担当前交付，再把 DeepSeek Harness 放进独立验证分支。验证重点不是功能演示，而是同一组业务测试能否通过、权限边界是否清楚、故障是否容易定位。

等新方案在这些指标上给出更好的答案，再迁移也不迟。测试不是给现有框架修围墙，而是在给团队保留换底层的自由。

真正成熟的选型，不是永远选择旧方案，也不是永远追逐新方案。它是在项目最需要确定性的时候，把不确定性留在不会拖垮交付的位置。
