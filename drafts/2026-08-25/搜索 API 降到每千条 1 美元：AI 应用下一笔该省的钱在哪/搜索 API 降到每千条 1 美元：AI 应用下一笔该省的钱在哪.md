# 搜索 API 降到每千条 1 美元：AI 应用下一笔该省的钱在哪

如果你正在做带搜索能力的 Agent，模型单价可能已经不是最该盯的数字。一次任务要调用多少次搜索、读取多少网页、保留多长上下文，正在决定真实账单。

Search Fast API 把价格压到每千个搜索结果 1 美元。更值得算的是，在 Parallel 公布的完整 Agent Task 测试里，它的搜索成本占比不到 12%，其他受测方案约为 48% 到 68%。

我会把这组数据当成一次选型提醒。别再拿模型 Token 单价代替任务成本，应该把推理、搜索、浏览器、上下文、记忆和沙箱放进同一张账单，再决定钱该省在哪里。

## 判断你是否真的需要换搜索方案

并非所有团队都要立刻追逐每千条 1 美元。如果搜索只占任务成本的一小部分，迁移接口、重做评测和处理返回格式的投入，可能超过节省的调用费。

下面几类应用更需要重新选型。

- 一个任务会连续发起多轮查询，例如研究助手、销售情报和资料核验
- 搜索调用已经接近或超过模型推理成本
- 单次任务利润薄，搜索费用会直接影响毛利
- 用户量增长后，搜索次数近似线性增加
- 搜索之后还要抓取、解析、去重，失败重试会继续放大成本

原帖评论里有一个很具体的问题，约 700ms 延迟下如何同时处理去重和解析。这个问题比报价更接近生产环境，因为便宜的结果如果要反复解析、重试或补查，账单仍会回来。

## 把单价改成完整任务成本

我现在更愿意用一个简单口径看 Agent 成本。

完整任务成本 = 模型推理 + 搜索调用 + 页面获取与解析 + 上下文处理 + 记忆读写 + 沙箱执行 + 失败重试

这里不需要复杂财务模型。先从调用日志里抽取 100 个典型任务，记录每项费用和成功率，就能看到真正的成本中心。

Parallel 给出的数据很有代表性。过去几个月，达到 Artificial Analysis Intelligence Index 60 及以上的模型成本下降了 8.5 倍，达到 50 及以上的模型成本下降了 12.5 倍。模型降价越快，搜索等外围环节在总账单里的比例就越显眼。

在其测试中，Parallel Fast 的搜索成本占比不到 12%，Brave Search 和 Exa Search Fast 约为 48%，Tavily Search Basic 达到 68%。Parallel 据此宣称，完整任务成本可分别降低 2.2 倍、2.35 倍和 2.79 倍。

这些数字适合用来发现问题，不能直接替代自己的业务评测。任务长度、搜索轮数、结果数量和失败率不同，最终账单也会不同。

## 按任务分支做选择

如果你的应用只需一次检索，我会优先看结果质量和接入成本。搜索费占比低时，为低单价迁移未必划算。

如果任务会反复搜索，我会先比较每个成功任务的搜索费用。此时每千条结果的报价才会明显影响毛利，但仍要把去重、解析和重试算进去。

如果任务依赖深度浏览，我不会只选搜索 API。搜索只是找到入口，页面获取、内容清洗、长上下文和沙箱执行可能成为下一笔大账。

如果应用处于早期验证阶段，我会选择能快速记录调用明细的方案。早期最重要的不是把某一项压到最低，而是知道一次成功交付究竟花了多少钱。

## 用一组真实任务完成验证

选型时，我会保留这张判断清单。

- 固定 20 到 100 个真实任务，不用临时编的简单查询
- 记录每个任务的搜索次数、结果数、延迟和失败重试
- 检查搜索结果是否需要额外抓取、解析与去重
- 同时记录模型、上下文、记忆和沙箱费用
- 用成功任务数做分母，不用请求次数做分母
- 比较总成本、成功率和延迟，不只比较公开单价
- 给高峰流量和失败兜底预留预算

我的判断是，模型变便宜不会自动让 Agent 变便宜。成本只是从推理层转移到了搜索、浏览器、上下文、记忆和执行环境。

真正该优化的也不是账单里最显眼的单价，而是每完成一个有效任务要付出的全部成本。下一次技术选型，先挑一组重复率最高的真实任务，把完整账单跑出来，再决定是否更换搜索方案。
