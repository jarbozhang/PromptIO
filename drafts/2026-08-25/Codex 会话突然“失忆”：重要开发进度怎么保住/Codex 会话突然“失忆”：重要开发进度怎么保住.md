# Codex 会话突然“失忆”：重要开发进度怎么保住

长时间用 Codex 写代码的人，最该防的不是回答偶尔跑偏，而是会话突然退回几个小时前。代码可能还在，Agent 对任务目标、失败尝试和当前进度的记忆却断了。

近期有用户反馈，Codex 的部分 Session 出现历史记录缺失、旧对话反复出现、刷新后内容再次消失等现象，Mac 和 Windows 均有人遇到类似情况。部分 Mac 用户还报告了聊天窗口闪退。

这类故障提醒了一件更重要的事。关键开发进度不能只存在于会话窗口里。及时提交代码、保存任务状态、恢复前核对工作区，能把一次会话异常限制在可控范围内。

## 还原这次“失忆”的现场

原帖汇总的现象并不完全一致。有的 Session 只少了最近几轮，有的长会话恢复后只剩开头一轮，还有记录隔几个小时重新出现、刷新后又消失的情况。

这种忽隐忽现与彻底删除不同。原帖后续指向 Codex GitHub 的 #38792，并称原始 rollout 数据仍然存在，异常集中在 `thread_history` 的索引或 projection。线索中还有一个 110MB、持续两天的 Session，通过重建 projection 恢复了完整记录。

这些信息更支持一种故障链条。

会话数据仍在存储层，索引或投影没有正确映射最新状态，客户端读取到不完整历史，Agent 随后基于旧上下文继续工作。用户看到的是消息消失，真正危险的是工作状态发生了静默回退。

## 找到比聊天记录更脆弱的部分

Coding Agent 的长会话不只保存聊天内容。它还承载大量没有写进仓库的临时状态，例如为什么放弃某个方案、哪些测试已经失败、当前改动还差什么、下一轮准备验证什么。

一旦 Session 回退，Agent 可能重新尝试已经排除的路径，也可能把旧判断当成当前事实。工作区中的文件没有消失，并不代表开发进度完好无损。

事故的关键因而不是“能不能找回聊天”，而是项目是否拥有会话之外的事实来源。Git 提交记录、测试结果和任务状态文件，都比客户端窗口更适合承担这项职责。

## 解释为什么常见补救不够

继续刷新看起来最省事，但原帖已经出现记录恢复后再次消失的反馈。刷新只能重新触发加载，不能证明索引已经稳定，也不能证明当前展示的是最新状态。

直接 resume 同样有风险。如果恢复出来的历史停在旧节点，Agent 会带着过期上下文进入工作区。此时让它继续修改，可能把正确的新代码覆盖成旧方案。

把所有信息复制到另一个聊天窗口也只能临时缓解。项目一长，人工复制很容易漏掉决策依据、未完成项和验证结果。更可靠的做法，是把关键状态写成仓库内可检查的交付物。

## 把修复动作放进日常开发

重要修改完成一个可验证单元就提交，不必等整项功能结束。提交信息应说明改了什么、为什么改，以及当前测试状态。这样即使会话回退，也能从 Git 历史重建事实链。

长任务可以保留一个简短的状态文件，例如 `TASK_STATE.md`。内容只记录当前目标、已完成事项、待处理问题、失败方案和下一次验证动作。它不是聊天备份，而是给人和 Agent 共用的恢复锚点。

发现历史异常后，不要立即让 Agent 接着写。先检查 `git status`、最近提交、未提交差异和测试结果，再将这些事实与恢复出的会话内容对照。只有时间线一致，才适合继续任务。

需要尝试重建 projection 时，也应先保留原始数据副本，并在隔离环境验证恢复结果。原帖提供了成功恢复的线索，但单个案例不能替代备份和完整性检查。

## 留下一张事故卡片

**故障信号**　Session 缺少最近记录、反复跳回旧对话、刷新后内容变化、窗口异常退出。

**主要风险**　Agent 使用过期上下文继续修改，重复失败路径，覆盖较新的工作结果。

**可信锚点**　Git 提交、工作区差异、测试输出、任务状态文件、原始会话数据。

**恢复顺序**　暂停写入，保存现场，核对仓库，验证会话时间线，再恢复执行。

**长期控制**　让会话负责推理，让仓库负责记忆。任何无法从仓库和验证记录重建的关键进度，都仍处在单点故障里。
