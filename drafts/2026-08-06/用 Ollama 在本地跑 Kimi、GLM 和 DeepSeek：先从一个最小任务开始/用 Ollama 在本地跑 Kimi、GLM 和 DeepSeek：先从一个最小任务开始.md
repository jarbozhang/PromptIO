# 用 Ollama 在本地跑 Kimi、GLM 和 DeepSeek：先从一个最小任务开始

如果你想知道自己的电脑适合跑哪一档模型，最有效的办法不是盯着参数规模，而是让 Kimi、GLM 和 DeepSeek 完成同一件小事。

我会选摘要或结构化提取。它们输入固定、结果容易检查，也能同时暴露内存压力、生成速度和指令遵循能力。

跑完这一轮，你应该得到一张属于自己机器的选择表。以后换模型时，不必重新被参数和榜单牵着走。

## 选一个能重复检查的任务

我更推荐结构化提取，因为答案是否合格一眼就能看出来。

准备一段五百到一千字的中文材料，里面放入明确的人名、日期、机构、事件和结论。然后要求模型只返回固定字段，例如人物、时间、事件、核心结论和待确认信息。

这份测试材料要满足四个条件。

- 三个模型使用完全相同的原文
- 提示词和输出字段保持一致
- 每次都从新会话开始
- 原文里故意保留一项缺失信息，检查模型会留空还是自行补全

摘要任务也能用，但不要只写一句“帮我总结”。我会限定字数，并要求保留关键数字、行动项和不确定信息。这样才能判断输出质量，而不是比较三个模型谁写得更顺口。

## 沿着 Ollama 的可验证入口运行

Ollama 仓库明确列出了 Kimi-K2.6、GLM-5.2、DeepSeek，以及 MiniMax、Qwen、Gemma、gpt-oss 等模型。具体可用模型、名称和运行方式可能继续变化，执行前应以仓库 README 和官方文档为准。

我的操作路径会压缩成一条线。

1. 打开 Ollama 仓库，确认当前系统的安装入口
2. 在官方模型入口核对 Kimi、GLM 和 DeepSeek 对应的可用版本
3. 每次只准备并运行一个模型，避免同时加载干扰内存记录
4. 输入同一份材料和同一条提示词
5. 保存原始输出，不在中途修改问题
6. 完成记录后退出当前模型，再测试下一个

这里不要急着追求最大的版本。测试的目标是找到稳定完成任务的档位，而不是证明机器勉强能把模型载入。

## 用三项记录判断机器适合哪一档

每个模型至少记录内存占用、速度和输出质量。

内存占用看两个时刻。一个是模型载入后的稳定值，另一个是开始生成后的峰值。如果系统已经频繁交换内存，即使任务最终完成，我也不会把它记作适合长期使用。

速度不要只凭体感。记录从提交提示词到出现首段输出的等待时间，再记录完成整份结果所需时间。Ollama 或当前运行环境若提供生成统计，可以一并保留，但三个模型必须使用同一种口径。

输出质量采用固定检查项。

- 字段是否齐全
- 是否遵守指定格式
- 关键事实是否与原文一致
- 缺失信息是否被擅自补全
- 摘要是否保留数字和行动项
- 同一提示重复运行时，结构是否稳定

我会把每项记为通过、可接受或不通过。结构化任务不需要复杂评分，能稳定交付比偶尔写出漂亮答案更重要。

## 把结果变成自己的选择规则

跑完后，不要直接宣布哪个模型最好。更实用的结论应该落到具体场景。

如果一个模型质量更好，但加载后明显挤压其他应用，它适合作为按需启动的工具。如果较小档位速度稳定、字段准确，日常批量提取反而更适合交给它。若模型经常改写字段或补充原文没有的信息，即使生成很快，也不适合直接接入自动流程。

我的判断很简单。机器能加载模型，只能证明它能启动。连续完成同一任务、不给系统造成明显压力，并且输出可验收，才说明这个档位真正可用。

## 避开四个常见误判

模型尺寸、量化方式、上下文长度和任务类型都会改变结果。一次测试不能替代所有场景，但足以帮你排除明显不合适的档位。

- 不要给三个模型使用不同长度的输入
- 不要一边运行其他高内存任务，一边记录峰值
- 不要只比较第一段输出有多快
- 不要把语言流畅当作事实准确

还要警惕缓存带来的偏差。测试顺序可能影响第二次运行的等待时间，因此需要保留测试顺序，并在相同条件下复测表现接近的候选项。

现在可以准备一段真实工作材料，从 Kimi、GLM 和 DeepSeek 中各选一个官方当前可用版本。完成这张表后，再决定是否尝试更大档位，比直接下载一串模型更省时间。
