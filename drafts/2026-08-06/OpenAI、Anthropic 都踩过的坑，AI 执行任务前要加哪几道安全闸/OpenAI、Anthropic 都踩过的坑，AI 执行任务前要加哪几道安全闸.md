# OpenAI、Anthropic 都踩过的坑，AI 执行任务前要加哪几道安全闸

当 AI Agent 被用来检查风险、分析文件或处理可疑内容时，一个反直觉的问题出现了。它原本负责防御，却可能被攻击者利用已有弱点，转而在部署它的系统中执行恶意代码。

AI Now Institute 披露的研究涉及 Anthropic 和 OpenAI 构建的热门 AI Agent。对个人开发者和小团队来说，真正需要检查的不是模型会不会偶尔答错，而是它答错以后，是否立即拥有执行、联网和修改系统的能力。

把攻击链拆开后，可以看到四道应该彼此独立的安全闸。权限限制拦越权，沙箱拦扩散，网络出口拦后续连接，人工确认拦高风险动作。任何一道都不能替代其余三道。

## 还原防御任务怎样变成攻击入口

这类事故的起点不是用户主动让 Agent 运行恶意程序，而是 Agent 在执行防御任务时接触了攻击者可控的内容。研究摘要确认，攻击者能够利用模型已有弱点，让用于防御的 AI Agent 反过来对部署系统执行恶意代码。

按工程链路拆解，风险通常经过四次状态变化。

输入从普通分析对象变成了诱导源，模型把有害指令当成任务的一部分，工具层把模型输出变成真实操作，运行环境又给了这个操作足够的系统能力。

真正造成损失的不是某一句模型输出，而是从不可信输入到系统执行之间没有强制断点。模型判断一旦直接连接执行器，概率性的错误就会变成确定性的系统动作。

## 把根因定位到模型之外

把问题归结为提示词不够严密，很容易得到错误的修复方向。更长的系统提示、更多禁止语句和二次模型检查，都可以降低部分风险，但它们仍然依赖模型正确理解并服从规则。

攻击输入针对的恰好就是这种不稳定性。只要最终是否执行仍由同一个模型链路决定，防线就没有脱离被攻击对象。

根因更接近权限架构错误。系统把内容判断、行动规划和操作授权压在了同一个 Agent 身上。它既读材料，又解释材料，还能调用工具改变真实环境。一处判断偏移，就可能穿过整条链路。

所以修复重点应从如何让模型更听话，转向模型失误以后还能造成多大影响。

## 让四道安全闸各拦一次

第一道是最小权限。Agent 只获得当前任务必需的目录、命令和凭据。做静态分析时默认只读，需要写入时限定到临时目录，不让一次工具调用自然继承宿主机的完整权限。这道闸负责阻止模型把错误意图扩大成越权操作。

第二道是隔离执行。模型生成的命令、脚本和待分析文件进入可销毁的沙箱，不直接接触真实工作区。沙箱需要限制文件挂载、进程能力和资源占用。即使恶意代码已经开始运行，影响也应停在隔离环境内。

第三道是收紧网络出口。防御任务不应默认拥有任意联网能力。确实需要访问公开资源时，可以按任务开放目标和协议，并记录请求。这样能拦住恶意程序继续获取内容、连接控制端或向未知位置发送数据。

第四道是高风险动作确认。执行代码、读取敏感目录、访问凭据、修改仓库、安装依赖和扩大网络权限，都不应因为模型说有必要就自动通过。确认界面需要展示具体命令、目标文件、权限变化和网络目的地，让人审的是动作，而不是一段模糊的自然语言理由。

四道闸的顺序也很重要。人工确认不能成为唯一防线，因为人会疲劳，也可能看不懂经过混淆的命令。确认通过以后，动作仍然要受最小权限、沙箱和网络策略约束。

## 检查常见修补为什么不够

只做提示词加固，无法为代码执行建立硬边界。只加人工确认，会把大量低质量判断推给操作者。只用容器，也不等于完成隔离，如果容器挂载了工作目录、继承了凭据或拥有宽松网络权限，攻击仍可能越过边界。

关闭网络同样不是完整答案。恶意代码仍可能删除文件、污染构建结果或窃取已经挂载的数据。反过来，只限制文件权限也拦不住进程利用网络继续扩大影响。

可靠的控制设计应该假设模型可能被诱导，也假设某一次确认可能误放。每道安全闸都要独立降低影响，不能把全部希望押在某一个组件永远正确。

## 留下一张可复用的事故卡片

事故类型，防御型 Agent 被不可信输入诱导，执行了违背用户目标的代码。

直接风险，部署 Agent 的系统承担文件、凭据、进程和网络层面的影响。

架构根因，模型判断与真实执行之间缺少独立授权边界。

阻断位置，最小权限拦越权，沙箱拦扩散，网络策略拦后续连接，人工确认拦高风险动作。

验收标准，即使模型生成并尝试执行恶意代码，动作也不能接触非任务目录、长期凭据和未授权网络目标，沙箱销毁后不留下持久修改。

给自动执行环境做安全检查时，可以直接用一个问题收尾。假设模型这一轮已经被诱导成功，系统里还有哪一道闸能让它失败。
