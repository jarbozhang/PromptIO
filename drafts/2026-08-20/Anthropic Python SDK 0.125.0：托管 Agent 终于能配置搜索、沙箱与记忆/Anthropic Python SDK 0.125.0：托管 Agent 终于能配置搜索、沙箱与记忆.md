# Anthropic Python SDK 0.125.0：托管 Agent 终于能配置搜索、沙箱与记忆

如果你正在把 Agent 从演示推向生产，0.125.0 值得关注。它触及的不是模型能力，而是两个更难收尾的工程问题，搜索如何受控，沙箱里的记忆如何保留。

我更关心的是，这次更新把多少基础设施责任交给了 SDK，又有哪些责任仍然留在应用侧。读完这份版本解读，你可以判断项目是否值得升级，以及验证时该盯住哪些架构边界。

目前发布说明确认了两项新增能力，托管 Agent 的网页搜索配置，以及自托管沙箱记忆。具体字段、调用示例和依赖条件没有在这份简短说明中展开，因此真正接入前仍需核对完整变更和官方文档。

## 旧接法为什么容易卡在生产门口

过去接入托管 Agent 时，能调用搜索不等于能放心上线。生产系统还要回答搜索是否开启、哪些任务允许使用、结果如何进入上下文，以及失败后由谁兜底。

如果这些控制散落在提示词、业务判断和工具封装里，调试会很麻烦。同一个 Agent 在不同环境里可能表现不一致，搜索策略也很难成为可审查的配置。

沙箱记忆是另一条链路。自托管沙箱负责隔离执行，但 Agent 要跨任务保留什么、重启后还能找回什么、数据存在哪里，都属于状态管理问题。状态一旦和执行环境绑死，迁移、清理与故障恢复都会变重。

所以我看 0.125.0，不是把它理解成又加了两个开关，而是 SDK 开始覆盖 Agent 的运行环境配置与状态承载。

## 新版本把两个缺口放进 SDK

| 变化 | 旧问题 | 现在可以验证的方向 |
| --- | --- | --- |
| 托管 Agent 网页搜索配置 | 搜索控制可能分散在应用层 | 搜索策略能否跟随 Agent 配置统一管理 |
| 自托管沙箱记忆 | 执行隔离与持久状态需要自行拼接 | 记忆能否在自有沙箱架构中获得明确承载 |

网页搜索配置最直接的价值，是让搜索从隐含行为变成显式能力。对于研究助手、资料整理和需要补充最新信息的任务，这会影响权限设计、调用成本、可观测性与结果追溯。

自托管沙箱记忆则面向另一类团队。你希望执行环境掌握在自己的基础设施里，同时又不想让 Agent 每次任务都从空白状态开始。版本说明确认了这项能力，但没有给出持久化范围、生命周期和清理语义，不能仅凭功能名称推断生产行为。

## 哪些能力开始具备工程价值

搜索和记忆放在一起看，比单独看更有意思。一个负责获取新信息，一个负责保留历史状态，两者共同决定 Agent 能否完成跨阶段任务。

例如，一个持续整理资料的 Agent，需要搜索新的公开页面，也需要记住已经处理过的内容。没有搜索，它拿不到变化。没有记忆，它会重复工作。0.125.0 至少让这两个关键控制面在 SDK 层出现了明确入口。

我的判断是，这次更新的价值不在于让 Agent 更会回答，而在于让团队更容易定义它能访问什么、能留下什么。对生产系统而言，权限和状态通常比提示词技巧更难补。

不过，SDK 提供能力并不等于替你完成治理。搜索结果是否可信、记忆是否包含敏感数据、沙箱之间是否隔离、状态如何删除，这些仍需要应用架构给出答案。

## 升级前确认依赖与责任边界

已经使用托管 Agent，并且业务需要网页搜索的团队，可以优先验证 0.125.0。重点不是确认请求能否成功，而是确认配置是否能进入现有的环境管理、审计和故障处理流程。

采用自托管沙箱的团队，更应该先画清状态边界。记忆由哪一层持久化，沙箱销毁后是否保留，多个 Agent 是否共享，以及删除请求如何落地，都要在接入前确定。

如果项目只做短会话问答，不需要搜索，也不保留跨任务状态，这次升级的即时收益可能有限。为了追版本而升级，会额外引入兼容性验证成本。

还要特别检查从 0.124.0 到 0.125.0 的完整变更。发布摘要只列出了功能名称，没有给出 Python 版本要求、可选依赖、初始化参数、迁移步骤或兼容性说明。现有项目不应根据摘要直接修改生产配置。

## 用一条任务完成升级验证

我会选一个同时需要搜索和连续状态的测试任务，例如分两次整理同一组公开资料。第一次记录已处理对象，第二次确认 Agent 是否能避开重复内容，并检查搜索关闭时是否按预期降级。

验证结果至少应回答三个问题。搜索配置是否真的受环境控制，记忆是否拥有清晰生命周期，失败时应用是否还能恢复到无搜索、无历史状态的可预测路径。

跑通这条任务后，再决定是否扩大接入范围。0.125.0 给出了值得验证的新入口，但能否进入生产，取决于你是否把搜索权限、沙箱隔离和记忆治理当成同一套系统设计。
