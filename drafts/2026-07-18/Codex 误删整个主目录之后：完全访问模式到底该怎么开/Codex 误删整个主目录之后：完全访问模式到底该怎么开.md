# Codex 误删整个主目录之后：完全访问模式到底该怎么开

如果你会让 Codex 清理文件、修改配置或执行终端命令，这起事故值得认真看。真正危险的并不是某一条删除命令，而是完全访问、关闭沙盒、缺少自动审查和环境变量误判同时出现。

这条事故链给出的工程结论很直接。完全访问模式不该成为日常默认项，它只适合边界清楚、数据可恢复、危险动作能够被拦截的环境。

读完这次复盘，你至少应该重新检查三件事。Codex 能访问哪些目录，删除操作是否需要确认，当前工作区能否从备份或版本库恢复。

## 还原主目录被删除的事故链

根据 X 用户 dotey 转述的信息，GPT-5.6 在执行编程任务时，可能删除用户的整个主目录 `$HOME`。

当时几个条件同时成立。用户为 Codex 开启了完全访问模式，关闭沙盒保护，也没有启用自动审查。模型执行清理任务时，试图重写 `$HOME` 环境变量，把它指向一个临时目录。

问题出在变量与真实目录被混淆。原本应该作用于临时目录的清理动作，最终落到了真正的 `$HOME` 上。

事故链可以压缩成一条路径。

`完全访问 → 沙盒关闭 → 自动审查缺席 → 重写 $HOME → 目录识别错误 → 清理真实主目录`

单独看其中任何一环，都未必必然造成严重后果。它们叠在一起后，模型既有执行能力，又缺少隔离边界和最后一道人工确认，变量误判便直接变成文件系统事故。

## 找到真正失效的控制点

把责任只归到模型误判，会漏掉更重要的问题。Agent 的输出具有不确定性，工程系统本来就应该假设它偶尔会理解错变量、路径或任务意图。

沙盒承担的是影响范围控制。即便模型生成了错误命令，只要它碰不到真实主目录，损失仍可被限制在隔离环境里。

自动审查承担的是动作拦截。删除目录、批量移动文件、覆盖配置以及改写关键环境变量，都应该在执行前被识别为高风险操作。

完全访问则把两种风险放大。它让模型能够越过工作区边界，把一次局部清理变成用户级文件操作。权限越大，路径判断错误的代价就越高。

这里的关键判断不是 Codex 能不能获得完全访问，而是什么条件下才允许获得。没有隔离、确认和恢复能力时，完全访问相当于把一次推理错误直接接到了真实文件系统。

## 为什么一句谨慎操作还不够

常见做法是提醒模型不要删除重要文件，或者要求它执行前仔细检查。这类自然语言约束有帮助，但不能替代权限控制。

模型可能把 `$HOME` 当成已经重写后的临时路径，也可能认为清理命令完全符合任务目标。此时它并不觉得自己正在执行危险操作，提示里的谨慎二字无法形成可靠拦截。

只检查命令文本也不够。`rm` 的目标可能来自环境变量、脚本参数或路径拼接，真正的落点要到变量展开后才能确认。安全检查必须关心命令最终会作用于哪里，而不只是命令看起来像什么。

备份同样不能替代隔离。备份负责事故后的恢复，沙盒和权限限制负责减少事故发生时的破坏范围。缺少前者会让恢复困难，缺少后者则会让错误触达更多真实数据。

## 把完全访问改成临时授权

更稳妥的用法，是把完全访问视为一次受控升级，而不是固定配置。

日常编码、读写仓库文件和运行测试时，权限范围应停留在当前工作区。只有任务确实需要访问工作区之外的资源，才临时扩大权限，并在任务完成后恢复限制。

高风险命令还需要独立确认。删除目录、清空文件、批量覆盖、移动用户级配置，以及修改 `$HOME` 等关键环境变量，不应因为开启完全访问就自动放行。

执行这类动作前，审查层至少要看到变量展开后的绝对路径。若目标指向主目录、主目录上层或工作区之外，流程应该停止并要求确认。

恢复能力也必须提前验证。重要项目进入 Agent 工作流前，应确认版本库状态、未提交文件和备份是否可用。备份是否存在与备份能否恢复是两回事，未经验证的恢复路径不能算完整防护。

## 留下一张可复用的事故卡片

事故对象是 Codex，失效模式是清理任务误删真实主目录。

触发条件包括完全访问已开启、沙盒已关闭、自动审查未启用，以及 `$HOME` 被错误识别为临时目录。

需要拦截的信号包括删除目标越过工作区、关键环境变量被重写、变量展开后指向用户级目录，以及清理操作没有人工确认。

防护顺序应当保持清楚。权限隔离限制影响范围，高风险命令确认阻止错误落地，版本库与备份负责恢复。三者解决的不是同一个问题，不能互相替代。

转述信息还提到，OpenAI 正在更新开发者提示，引导用户采用更安全的权限模式，并计划在 Codex Harness 中加入额外安全检查。Tibo 同时表示，后续会发布更详细的事后分析。

在这些改进落地前，最实际的动作不是停用 Agent，而是取消日常完全访问，把危险命令确认和可恢复性检查放回执行链。能力可以按任务临时放开，主目录不该成为试错空间。
