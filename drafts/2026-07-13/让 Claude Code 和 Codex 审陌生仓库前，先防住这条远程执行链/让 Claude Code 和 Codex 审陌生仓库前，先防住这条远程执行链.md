# 让 Claude Code 和 Codex 审陌生仓库前，先防住这条远程执行链

最危险的瞬间，可能不是让代码代理修改项目，而是请它检查一个陌生仓库有没有安全问题。

AI Now Institute 披露了一项概念验证。当 Claude Code CLI 和 Codex CLI 被用于防御性审查开源或第三方代码时，攻击者可以把审查任务反过来利用，最终触发远程代码执行。报告涉及 Claude Sonnet 4.6、Sonnet 5、Opus 4.8 与 GPT-5.5。

对经常让 Agent 阅读依赖库、分析样例项目或复核供应链风险的开发者来说，关键收益很明确。不要把安全审查理解成纯阅读任务，要把陌生仓库、代理工具权限和本机执行环境放进同一张威胁图里。

## 还原一次被反向利用的安全审查

任务的起点看起来足够合理。开发者拉取一个待评估的仓库，让 Claude Code 或 Codex 寻找恶意逻辑、危险依赖与可疑脚本。

问题在于，代码代理面对的不只是程序源码。仓库中的说明文件、配置、测试数据和其他文本内容，都可能进入模型上下文。原本等待检查的材料，也可能成为影响代理行为的输入。

这条事故链可以压缩成四段。

陌生仓库内容 → 模型解释内容 → 代理调用获准工具 → 命令落到本机环境

AI Now Institute 的概念验证把终点推进到了远程代码执行。防御者发起的审查没有挡住攻击，反而替攻击内容提供了读取入口、决策能力和执行通道。

## 沿执行链找到三个失守点

第一个失守点是信任边界。团队通常知道陌生源码不能直接运行，却容易把 README、注释和配置当成无害背景。对代码代理而言，它们都可能参与下一步决策，文件是不是可执行格式并不是唯一判断标准。

第二个失守点是工具权限。模型生成一段危险建议，和模型能够调用终端、读取文件、启动进程，是两个完全不同的风险等级。Agent 一旦同时拥有理解不可信内容和操作环境的能力，内容风险就可能跨过执行边界。

第三个失守点是本机上下文。命令落到开发机后，影响范围取决于代理进程原本能够访问什么，包括工作目录、用户文件、环境变量、凭据和网络。模型权限没有单独存在，它继承的是承载进程的权限。

所以，问题不能只归结为模型受到了误导。真正需要复盘的是，一段不可信内容为什么能一路走到有副作用的工具，再从工具走到真实机器。

## 识别那些看似稳妥却不够的防线

给代理写一句“只审查，不执行”，可以表达任务意图，却不是强制安全控制。提示词仍由模型解释，而隔离、权限和系统策略由运行环境执行，两者的可靠性不能混为一谈。

把 Git 仓库设成只读也不够。它可以减少源码被修改，却没有自动限制终端、网络、宿主目录和其他进程。只读仓库不等于只读机器。

逐条确认命令同样可能失效。如果确认窗口只展示一条看似普通的命令，却不展示工作目录、环境暴露、文件范围和后续副作用，人工确认很容易退化成连续点击。

信任 Claude Code 或 Codex 的能力，也不能延伸成信任它正在阅读的内容。能力越强，越要把输入和权限拆开治理。

## 按隔离、权限、确认重排防护顺序

第一层应当是隔离环境。陌生仓库进入一次性虚拟机、沙箱或专用系统用户，与个人主目录、长期凭据和其他项目分离。容器如果挂载了宿主目录或敏感凭据，隔离效果仍然有限。

第二层是最小权限。静态阅读阶段只开放完成分析所需的文件访问，不默认开放终端、网络、安装脚本和工作区外写入。需要复现行为时，再为单独阶段增加一项明确能力，并在完成后撤销。

第三层才是人工确认。确认点应放在跨越安全边界的位置，例如启动进程、访问网络、执行项目脚本、读取凭据或写出工作区。确认界面至少要让人看见具体命令、执行目录、文件范围与可能暴露的环境信息。

顺序不能颠倒。人工确认负责处理例外，最小权限负责缩小入口，隔离环境负责在前两层失效后限制损害范围。

## 把事故卡贴进审查流程

下次把陌生仓库交给代码代理前，可以用这张事故卡做放行判断。

- 不可信输入，不只包括源码，也包括仓库内会进入上下文的内容
- 执行入口，检查终端、网络、脚本、进程和工作区外写入
- 影响范围，检查主目录、环境变量、凭据与宿主挂载
- 确认质量，确认信息是否足以判断真实副作用
- 失败兜底，当前环境被接管后是否能够直接销毁并重建

安全审查不是天然安全的任务。只要审查者既读取对手提供的内容，又握着真实执行能力，防守动作本身就可能成为攻击链的一环。
