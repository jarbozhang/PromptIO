# 同花顺开放 A 股数据 API：不用自己维护爬虫了

如果你正在维护 A 股行情爬虫，这套同花顺金融数据 API 值得放进替换候选。它覆盖行情快照、日 K、财报、板块、涨停和龙虎榜，并提供 REST、Python、CLI、MCP 多种接入方式。

读完可以完成一次最小验证，用同一把 Key 查询行情、财报和龙虎榜，再决定现有采集脚本该全部替换，还是只保留难以迁移的部分。

我更关心的不是接口数量，而是它能否减少验证码、页面改版、字段漂移和定时任务失效带来的维护工作。对数据工程来说，少修一次爬虫，往往比多接十个字段更有价值。

## 选一个能暴露问题的最小场景

不要一开始就迁移整条数据链路。选一只股票和一个明确日期范围，依次请求行情快照、财报与龙虎榜，已经足够检查认证、字段、频率和数据落库方式。

最小验证可以保留四份交付物。

- 一份行情快照原始响应
- 一份最近可用财报响应
- 一份指定日期的龙虎榜响应
- 一张记录请求时间、返回状态和异常信息的验收表

这三类数据放在一起很合适。行情考验时效，财报考验报告期与字段稳定性，龙虎榜考验日期覆盖和空结果处理。只跑日 K 很容易得到一个过于乐观的结论。

## 用四种入口走完同一条查询

拿到 Key 后，按官方文档提供的示例请求执行，不要自行猜测端点、参数名或返回字段。先用 REST 保存原始响应，它最适合确认接口行为，也方便用 curl 或任意 HTTP 客户端复现问题。

第二遍换 Python。目标不是立刻做策略，而是把三次查询封装成三个小函数，并统一处理认证失败、空结果、超时和字段缺失。原始响应也要保留，避免清洗逻辑把问题藏起来。

CLI 更适合定时任务和临时排查。它能直接进入 shell 脚本，查询失败时也容易保留退出码与日志。需要让 Cursor、Claude 一类 Agent 调取数据时，再接 MCP，让 Agent 通过工具调用完成查询，而不是把 Key 写进提示词。

我的选择顺序是 REST 验证接口，Python 固化处理，CLI 接自动任务，MCP 留给 Agent。四种入口共用一把 Key，减少了多套凭证和重复封装，但 Key 仍应放在环境变量或密钥管理工具中。

## 把返回结果落进 DuckDB 验收

本地 DuckDB 适合承担轻量验收层。每次查询保留原始响应，同时把常用字段整理成行情、财报、龙虎榜三张表，并额外记录抓取时间与来源。

验收时重点检查这些结果。

- 同一个查询重复执行，字段结构是否稳定
- 空结果与接口错误能否被明确区分
- 财报报告期是否符合任务预期
- 龙虎榜日期条件是否得到正确处理
- 行情返回速度能否满足你的实际任务
- 数据写入 DuckDB 后能否按股票和日期关联

完成这些检查，才能判断它是否适合替换采集脚本。能返回数据只是起点，可重跑、可追踪、可处理失败才是生产工作流需要的能力。

## 用验收标准决定替换多少

我不会因为官方提供 API 就直接删除旧爬虫。更稳妥的做法是让两条链路并行跑一小段验证任务，对照覆盖范围、字段含义、响应时间、调用限制和异常恢复能力。

目前公开讨论里，用户最关心的是免费版本的速度、限制、数据反馈时间、定价，以及其他市场和期货数据的覆盖。这些问题不能靠接口列表回答，需要以官方说明和自己的请求记录为准。

判断是否替换时，可以守住三条线。

- 核心字段连续缺失，暂不迁移
- 响应时间无法满足任务，保留原链路兜底
- 调用限制或成本不清楚，只做小规模验证

金融数据还要保留风险边界。行情延迟几秒可能影响某些任务，本文的验证路径适合数据分析、研究与工作流评估，不构成投资建议，也不应用来承诺交易结果。

## 避开四个常见坑

第一个坑是把接口可用等同于数据适用。日 K 分析和需要低延迟行情的任务，对时效要求完全不同。

第二个坑是只看成功响应，不测空数据、错误码和限流。真正拖垮自动化任务的，通常是失败分支没有被记录。

第三个坑是让 Agent 直接拼接未经核对的参数。MCP 降低了接入成本，却不能替代字段校验、权限控制和日志审计。

第四个坑是过早移除旧采集链路。先挑一只股票跑通行情、财报和龙虎榜，把结果落进 DuckDB，再根据验收表决定替换范围。

这个最小任务跑通后，下一步不是扩充股票池，而是故意制造一次空结果和一次认证失败。能把这两种情况处理清楚，这套接口才真正进入了可用状态。
