# 用 OpenAI 给衣服自动建档：这个开源衣橱还能生成真人搭配预览

如果你的相册里存着不少穿搭照，却从来记不清自己有哪些衣服，这个开源项目提供了一条很具体的整理路径。上传一张穿搭照，它会识别上衣、裤子和鞋子，再把单件衣物抠成接近商品图的素材。

整理完成后，衣物图片和 JSON 数据会保存在本地 `data/` 目录。你还可以上传自拍参考图，让 OpenAI 生成换装预览，或者从现有衣物里组合 Lookbook。

读完这份操作路径，你可以判断三件事，自己的衣橱是否值得数字化、第一批该导入哪些照片，以及 API 成本和照片隐私是否在可接受范围内。

## 选一套穿搭验证完整链路

我不会一开始就把整个相册扔进去。更稳妥的做法，是选一张衣物边界清楚、能同时看到上衣、裤子和鞋子的穿搭照，用它验证识别、抠图、建档和预览能否连起来。

Wardrobe 的处理链路很直观。

- 从穿搭照中识别不同类别的衣物
- 调用 OpenAI Images API，把单件衣物抠成产品图
- 将原图、处理图和 JSON 数据写入本地 `data/` 目录
- 从衣橱中挑选单品，生成搭配 Lookbook
- 结合自拍参考图，生成真人换装预览

这个最小场景足够暴露主要问题。识别错了，后面的目录就会乱。抠图边缘不好，Lookbook 和换装预览也很难提供有效参考。

## 跑通本地衣橱的操作路径

项目采用常见的 Node.js 启动方式。源材料给出的基础命令如下。

```bash
git clone https://t.co/kw9Za3NBih
cd wardrobe
npm install
# 配置 OPENAI_API_KEY 和一张自拍参考图
npm run dev
```

我会把第一轮导入控制在一套穿搭，而不是追求数量。完成后检查 `data/` 目录，确认原始照片、处理后的单品图和 JSON 数据是否都已经落盘。

如果照片集中放在一个文件夹里，还可以使用项目提供的 Codex CLI 技能。给出类似“把 `~/Pictures/outfits` 里的衣服导入衣橱”的任务后，让它完成抠图和建库。批量处理前仍建议跑通单张照片，避免错误分类被成批写入。

## 用四个结果验收这次建档

功能能启动，不等于衣橱已经可用。我更关心下面四个交付结果。

- 衣物分类正确，上衣、裤子和鞋子没有混入错误目录
- 单品主体完整，袖口、裤脚和鞋底没有被明显裁掉
- 本地目录可追溯，原图、处理图和 JSON 数据能够对应
- 换装预览能辅助判断轮廓与配色，而不是被当作真实上身效果

最后一项很重要。真人试穿属于 AI 生成的建模预览，它适合筛选搭配方向，但不能替代面料垂感、尺码和真实光线下的判断。

## 算清 API 与照片隐私的取舍

“数据全在本地”描述的是项目的存储方式。原始图、处理图和 JSON 数据保存在本地目录，但衣物抠图和换装生成仍会调用 OpenAI Images API。

这带来两个实际取舍。

一是成本。源材料没有提供单张处理价格，也没有给出一次建档会触发多少次调用，所以不能直接估算整柜衣物的费用。更可靠的办法，是用一套穿搭完成全流程，再根据 API 账单记录估算批量导入成本。

二是照片隐私。自拍参考图和穿搭照会参与 API 图像处理，不能仅凭本地落盘就判断整个流程只发生在设备内。导入前应查看当前官方 API 数据政策，并优先使用不包含住址、证件、屏幕内容和旁人的照片。

我的判断是，Wardrobe 更适合衣物数量较多、穿搭照片积累明显、愿意维护数字目录的人。衣服很少，或者不需要生成搭配预览，本地文件夹可能已经够用，没必要为自动抠图和生成流程增加 API 调用。

## 把第一套衣服变成判断样本

选一张边界清楚的穿搭照，跑完识别、抠图、本地落盘和真人预览，再检查分类准确度、抠图质量、账单记录与照片使用边界。

这套样本通过后，再决定要不要导入整个衣橱。数字衣橱真正省下来的，不是一次整理时间，而是以后每次找衣服、试组合和回看搭配时的重复劳动。
