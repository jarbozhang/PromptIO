# 中文为什么更费 Token？一项新方法让旧模型原地扩充词表

如果你在本地模型里处理中文，这个问题值得关注。同一句意思被切成更多 Token，不只会挤占上下文，还会增加生成延迟、计算量和能耗。

真正需要决定的，不是要不要追求一个更大的词表，而是现有模型的中文碎片化，是否已经严重到值得做一次词表扩充。

我更关心这项研究的工程价值。它没有要求从头训练模型，而是尝试保留旧 Token 的能力，在原检查点上增加新 Token，再通过两阶段训练恢复原有质量。

## 决定要不要动现有词表

分词器通常在预训练开始前固定。词表如何分配，很大程度上取决于当时的训练语料和部署重点。

后来加入的语言可能被拆得更碎。一个词被切成多个 Token，模型便要执行更多次解码，有限的上下文窗口也会更快被占满。

云端大模型可以容纳较宽的词表，因为嵌入矩阵和语言模型输出头在总参数中占比较小。紧凑模型的情况不同，这两块矩阵可能构成单 Token 解码带宽的明显负担，所以设备侧模型往往采用较小词表，并接受非重点语言的碎片化。

我的决策标准很直接。若产品主要处理代码、短指令或少量中文，改词表可能得不偿失。若输入包含长篇中文、越南语、印地语等内容，Token 膨胀已经影响上下文容量和响应速度，才值得继续评估。

## 判断旧能力能否被保住

这项方法最关键的设计，不是简单追加一批词，而是继续原分词器的字节对编码合并，也就是 BPE merges。

原有 Token 尽量保持为单个 Token，新 Token 则必须能够精确拆回一组旧 Token。旧嵌入行原样复制，新嵌入行使用对应旧子词嵌入的均值初始化。

这个约束很重要。新词不是凭空塞进模型，而是先借用旧子词已经学到的表示，再接受训练。研究采用两阶段适配，先只训练嵌入，再进行全模型持续预训练，以恢复源检查点的质量。

论文把这套方法用于 LFM2-8B-A1B 的持续预训练检查点，帮助形成带有 128K 词表的 LFM2.5-8B-A1B。它证明的是一条可行工程路线，但不能推出任何模型扩词后都会自动变快，也不能省掉质量回归。

## 用分词结果衡量真实收益

我不会只看词表大小做决定。128K 听起来很大，却不能直接回答中文是否切得更省，也不能回答新增矩阵带来的带宽成本是否划算。

更可靠的判断对象，是自己的真实输入。可以从客服对话、知识库文档、结构化字段和中英混合提示词中抽取一批样本，分别交给现有模型与候选模型的官方 tokenizer，记录同一段文本得到的 Token 数。

Qwen、Gemma 等可本地运行的模型都能成为对照，但比较时必须使用各自配套的 tokenizer，不能拿模型名称或参数量代替分词结果。还要同时观察词表规模、目标语料 Token 数、最大上下文占用和实际解码速度，单独优化其中一项容易做出错误选择。

## 分清哪些团队适合投入

适合考虑这条路线的，是能够控制 tokenizer 设计、持有模型检查点，并且具备持续预训练与回归评测能力的模型生产者。中文 Token 成本已经成为产品瓶颈时，扩词表可能同时改善上下文利用率和处理效率。

只负责调用模型的应用团队通常不适合直接改词表。嵌入矩阵、输出头、模型权重和 tokenizer 必须保持一致，随意替换很容易让 Token 编号与权重错位。对这类团队，更现实的选择是比较已有模型在业务语料上的分词结果，再选出更合适的检查点。

数据量有限、缺少旧语言回归集，或者设备内存和带宽已经吃紧的团队，也不该只为减少 Token 数扩词。新词表会扩大嵌入矩阵和输出头，省下的解码步数未必能覆盖新增带宽成本。

## 我的选择是先测，再决定是否扩词

我会把词表扩充视为模型生产阶段的专项优化，而不是应用侧的通用补丁。

对多数团队，我的选择是先拿真实中文语料比较 LFM、Qwen、Gemma 等候选模型的分词结果，再结合本地解码速度判断瓶颈。只有现有检查点不可替换、Token 碎片化明确拖慢业务，并且团队能完成两阶段训练和完整回归时，我才会选择原地扩词。

这项研究最有价值的地方，是把语言覆盖从一次性决定变成了可以重新评估的工程变量。现在该做的动作很小，取一批生产语料，记录不同 tokenizer 的 Token 数和延迟，把是否扩词从感觉题变成数据题。
