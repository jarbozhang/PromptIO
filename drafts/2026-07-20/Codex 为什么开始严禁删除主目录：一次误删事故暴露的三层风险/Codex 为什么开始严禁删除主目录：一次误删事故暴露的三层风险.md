# Codex 为什么开始严禁删除主目录：一次误删事故暴露的三层风险

如果你允许 Codex 直接操作本机文件，这次事故值得认真看。真正需要防范的已经不是代码写错，而是智能体把一个错误判断变成不可逆的文件操作。

公开讨论显示，一名开发者的主目录曾被误删，随后 Codex 的系统提示词增加了明确禁令，无论如何都不要执行 `rm -rf $HOME`。同一时期，源代码信息还显示上下文窗口从 372K 下调到 272K。

把两处变化放在一起看，能得到一套更实用的防护思路。模型能力、使用成本和本机权限属于三类不同风险，不能指望同一道提示词同时兜住。

## 还原误删是怎样走到不可逆的

这类事故通常不需要模型完全失控。它只要在任务目标、当前目录或清理范围上做错一次判断，再获得足够高的执行权限，风险就会沿着工具调用链落到真实文件上。

聊天模型给出错误命令时，人还可以停下来检查。编程智能体直接调用终端后，错误判断与执行结果之间少了一道人类确认。删除范围一旦指向主目录，代码仓库、配置文件、密钥材料和未同步文档都可能同时受影响。

系统提示词新增 `rm -rf $HOME` 禁令，说明产品侧已经把这一命令视为需要单独拦截的高危动作。但单独禁止一个字符串，只能覆盖已知事故形态。等价路径、目录变量展开、脚本间接调用，以及在错误工作目录执行清理命令，仍然可能造成相似结果。

## 把事故拆成三层失效

第一层是模型能力边界。上下文再长，也不能保证模型始终正确理解目录结构、用户意图和命令副作用。窗口从 372K 调整到 272K 的消息，被来源解释为处理 GPT-5.6 Sol 的计费异常，且此前已有恢复窗口的预告。窗口大小可以调整，删除后的本机数据却未必能恢复。

第二层是成本边界。上下文窗口、推理强度和工具调用都要受到资源约束。产品可能为了处理计费或运行问题临时调整能力参数，所以安全设计不能建立在某个固定窗口永远可用的假设上。

第三层是权限边界，也是破坏性最大的一层。只要智能体能读写整个主目录，它的一次误判就可能越过项目范围。模型是否聪明与它是否应该拥有这些权限，是两道必须分别回答的问题。

这里的关键判断很直接。模型负责提出和执行方案，操作系统与运行环境负责限制最坏结果。不能把权限控制降级成一句“请小心”。

## 为什么常见防护还不够

只在提示词里写“不要删除重要文件”，依赖的是模型持续遵循指令。系统提示词新增强禁令有价值，但提示词不是文件系统权限，也不是恢复机制。

只使用 Git 同样不够。Git 能恢复已经提交的代码，却管不到未提交文件、编辑器配置、环境变量、本地数据库和仓库之外的资料。误删如果连 `.git` 目录一起覆盖，本地版本历史也不能单独承担恢复职责。

每次危险操作弹出确认，也可能被命令包装绕开。一个看似普通的测试脚本或清理脚本，内部仍可能执行递归删除。确认机制必须看最终影响范围，而不只是最外层命令名称。

## 把修复动作落到执行边界

最有效的第一道防线，是让 Codex 只进入独立工作目录。测试仓库、临时构建产物和待处理文件放在这里，主目录中的个人资料、凭据和长期项目不向任务环境开放。条件允许时，再用容器、受限用户或文件系统沙箱收紧可写范围。

第二道防线是把版本控制前移。让智能体修改前检查工作区状态，重要节点形成提交，删除和批量改写后立即查看差异。未提交内容仍要单独保存，不能因为仓库启用了 Git 就默认数据已经安全。

第三道防线是独立备份。备份位置不能与工作目录共用同一删除范围，也不能只保留实时同步。实时同步可能把误删快速复制过去，带历史版本或快照的备份才有机会回到事故前状态。

高危命令还应由工具层拦截。递归删除用户目录、根目录、仓库上级目录，以及大量文件的操作，应默认拒绝或要求人工确认。规则要根据解析后的真实路径判断，不能只匹配 `rm -rf $HOME` 这一种写法。

## 留下一张事故卡片

- 事故对象，获得本机文件权限的编程智能体
- 主要损失，主目录文件被递归删除，结果可能不可逆
- 直接控制，隔离工作目录并限制可写路径
- 恢复控制，Git 提交、未提交文件保护、带历史版本的独立备份
- 阻断控制，在工具层识别真实路径并拦截高危删除
- 验收标准，即使模型判断错误，影响范围也不能越过当前任务目录

真正可靠的编程智能体，不是从不犯错的模型，而是犯错后只能损坏一个可丢弃、可恢复的工作区。检查一次 Codex 当前可写目录，比再补十句提示词更接近工程上的解决方案。
