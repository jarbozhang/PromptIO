# 用 Claude Code 和 Codex 审计陌生仓库，为什么反而可能触发远程代码执行

把陌生仓库交给 Claude Code 或 Codex 做安全审计，看起来是防御动作。AI Now Institute 公布的一项概念验证却展示了相反结果，防御性代理可能被待审计内容影响，最终在审计者的机器上触发远程代码执行。

风险不只属于专业安全团队。只要你会让编码代理读取第三方项目、分析依赖或运行验证命令，就处在同一条攻击路径附近。

真正需要调整的不是某一句提示词，而是审计环境的信任模型。陌生仓库必须同时经过隔离环境、权限收缩和执行确认三层防线。

## 还原一次失控的防御性审计

研究公布的概念验证针对 Claude Code CLI 和 Codex CLI。披露信息提到，测试涉及 Claude Sonnet 4.6、Claude Sonnet 5、Claude Opus 4.8 与 GPT-5.5，并使用开箱配置执行开源或第三方代码的防御性安全评估。

事故链条可以压缩成四个环节。

待审计仓库先进入代理的上下文。仓库中的恶意内容随后影响代理对任务和操作的判断。代理把受污染的判断转化为命令或工具调用。命令最终落在审计者拥有权限的环境中，形成远程代码执行。

这里的关键错位是，仓库同时扮演了两种角色。它既是需要检查的数据，又能向代理提供会被解释和执行的信息。传统代码审计默认审计工具不会服从被审对象，具备自主操作能力的编码代理打破了这个前提。

## 找到事故真正放大的位置

恶意内容能够影响判断，只是攻击入口。真正把一次错误判断放大成主机风险的，是代理拥有的执行能力。

如果代理只能读取文件，受污染的输出可能停留在错误结论。如果它还能启动进程、调用脚本、访问凭据或修改工作区，模型的一次误判就可能跨过分析边界，变成真实副作用。

所以，不能只问 Claude Code 或 Codex 能否识别恶意指令。更重要的问题是，即使识别失败，环境允许它做多大的事。

## 识别为什么常见防护还不够

只在提示词里写上忽略仓库指令，依赖的是模型每次都正确区分任务、代码、文档与恶意内容。概念验证指向的正是这层判断可能被操纵。

只保留命令确认也不稳妥。审计时会出现大量看似合理的读取、构建和测试动作，操作者很容易在连续确认中降低警惕。命令表面正常，也不代表它的参数、脚本入口和执行上下文安全。

只使用干净的 Git 工作区同样不够。工作区干净不等于运行环境隔离，宿主机权限、环境变量、认证文件和可访问服务仍可能扩大事故影响。

这些方案并非无效，只是单独使用时都把安全寄托在一个判断点上。

## 把三层防线放到审计之前

第一层是隔离环境。把陌生仓库放进一次性虚拟机、容器或专用沙箱，避免挂载个人目录、SSH 配置、云端凭据和真实项目。审计结束后直接销毁环境，不把它继续用于日常开发。

第二层是权限收缩。默认关闭不必要的网络访问，只开放审计任务必需的目录和命令。凭据不注入，宿主目录不共享，写权限限制在临时工作区。即使代理判断失误，可造成的影响也应被限制在隔离边界内。

第三层是执行确认。不要把所有命令都交给一次笼统授权。涉及安装依赖、执行仓库脚本、启动构建流程、读取工作区之外文件或发起网络请求时，应单独核对命令、参数、工作目录和数据流向。

三层防线处理的是不同失败点。隔离环境控制影响范围，权限收缩减少可用能力，执行确认拦截高风险动作。缺少任何一层，剩余防线都要承担它原本不该承担的判断压力。

## 留下一张陌生仓库事故卡片

审计对象按不可信输入处理。代理输出按待验证建议处理。命令执行按可能产生副作用的操作处理。

开始前确认环境可销毁、没有真实凭据、没有多余挂载。执行中遇到安装、脚本、网络和越界读取就暂停核对。结束后销毁环境，并检查是否产生异常文件、进程或连接。

编码代理可以提高审计效率，但代理越能行动，防御性任务越不能直接继承日常开发环境的权限。审计陌生代码时，最危险的假设不是仓库可能有漏洞，而是负责找漏洞的代理天然可信。
