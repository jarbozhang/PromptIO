# vLLM 0.25 大改后怎么升级：默认启用新运行器，旧版注意力实现正式移除

如果你的服务依赖 vLLM，这次升级不能只看新增模型。v0.25.0 把 Model Runner V2 设为所有稠密模型的默认执行路径，同时删除 PagedAttention，执行链路已经发生实质变化。

部署者需要回答三个问题。现有模型切到新运行器后能否保持稳定，旧配置是否仍依赖已经移除的注意力实现，出现性能或兼容问题时能否迅速退回原版本。

这次发布包含 558 个提交，来自 232 位贡献者，其中 64 位是新贡献者。变化很多，但真正影响升级决策的主线只有一条，vLLM 正在收拢默认执行路径，并把更多能力迁移到 Model Runner V2 上。

## 判断旧部署会被哪项变化击中

过去的升级思路常常是保留原执行路径，再逐项打开新能力。v0.25.0 改变了这个前提。

Model Runner V2 现在默认覆盖所有稠密模型。此前已经加入的量化模型支持继续保留，本次又增加 EVS、实时嵌入、Mamba 混合模型的前缀缓存、多模态前缀双向注意力，以及兼容完整 CUDA Graph 的动态推测解码。

另一边，PagedAttention 已被删除。发布说明给出的原因很直接，V1 和 Model Runner V2 后端已经成为标准路径，旧注意力实现不再保留。

| 变化 | 对现有部署的影响 | 升级时要验证的对象 |
| --- | --- | --- |
| Model Runner V2 成为稠密模型默认路径 | 未显式选择运行器的服务也可能进入新路径 | 启动、首轮请求、持续负载和显存表现 |
| PagedAttention 删除 | 依赖旧实现的配置或扩展失去兼容基础 | 自定义参数、补丁和内部封装 |
| 动态推测解码支持完整 CUDA Graph | 推测策略与图捕获可以组合 | 延迟、吞吐和输出一致性 |
| Transformers 后端性能提升 | 更多模型可考虑走统一后端 | 原生实现与 Transformers 后端的行为差异 |

这不是一次适合直接替换生产镜像的常规小版本。即使没有主动使用新功能，默认路径变化和旧实现删除也足以触发完整回归。

## 看懂哪些能力现在更接近可用

动态推测解码是本次最值得关注的能力之一。它现在能够与完整 CUDA Graph 配合，减少了部署者在推测策略和图捕获之间二选一的压力。

发布说明没有提供统一的性能数字，因此不能预设升级后一定更快。模型、草稿器、请求长度和批处理形态都会改变结果，收益需要放进自己的流量模型里测。

推测解码的覆盖面也在扩大。v0.25.0 加入面向异构词表的通用推测解码，并增加 DSpark 和 DFlash 草稿器。对于主模型与草稿模型词表不同的组合，这提供了新的验证空间，但不等于所有组合都能直接迁移。

Model Runner V2 的扩展也不只服务文本生成。实时嵌入、Mamba 混合模型前缀缓存和多模态前缀双向注意力，说明统一执行路径正在覆盖嵌入、混合架构与多模态负载。

Transformers modeling backend 则被官方描述为已经达到原生 vLLM 的速度，并新增 FP8 MoE 支持，修复 CUDA Graph 与嵌入缩放相关问题，同时迁移 GPTBigCode、Starcoder2 和 RoBERTa。这个判断来自版本说明，具体模型仍应分别回归，不能把后端层面的结论直接当成业务指标。

## 把升级验证压到真实流量模型

升级验证应围绕变化最大的边界展开，而不是把所有新模型都跑一遍。

先固定当前生产版本、模型权重、量化方式、启动参数和一组代表性请求，保存可比较的延迟、吞吐、显存峰值与输出结果。随后只替换 vLLM 版本，确认默认 Model Runner V2 能完成相同请求。

如果服务包含自定义注意力补丁、运行器选择逻辑或对内部接口的封装，需要优先搜索 PagedAttention 依赖。旧实现已经删除，这类依赖不能靠关闭新功能恢复。

准备回滚时，应保留旧版本镜像和对应配置，不要让新旧环境共享未经验证的配置变更。回滚目标也要明确，是恢复服务可用，还是恢复原来的性能曲线，两者的验收标准不同。

动态推测解码适合单独建立对照组。保持模型和请求集不变，再比较关闭与启用推测解码时的延迟、吞吐、显存占用和输出一致性。没有对照组，性能变化很容易被 CUDA Graph、批处理或运行器切换混在一起。

## 决定谁该升级，谁该暂缓

适合尽快验证 v0.25.0 的，是正在使用稠密模型、计划采用动态推测解码、依赖 Transformers backend，或者需要实时嵌入与多模态前缀能力的团队。新运行器已经成为默认路径，越晚验证，未来跨版本迁移时积累的变量越多。

应该暂缓直接切换的，是依赖 PagedAttention 定制、自定义内部接口较多、缺少代表性压测集，或者没有旧镜像回滚能力的部署。问题不在于新版本功能多，而在于默认执行路径和兼容边界同时变化。

我的判断是，v0.25.0 的价值不只是增加几个模型和解析器。它把 vLLM 的演进方向写得很清楚，统一运行器、统一解析框架，并让推测解码与 CUDA Graph 等优化能力能够组合使用。

部署者现在最有价值的动作，是从生产流量中抽取一组固定请求，在隔离环境里完成一次新旧版本对照。先验证默认运行器，再排查旧注意力依赖，最后单独评估动态推测解码，升级收益和风险才不会混成一个模糊结论。
