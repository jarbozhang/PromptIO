# 两个终端不用再复制粘贴：QoderCLI 跨会话协作是怎么做出来的

如果你经常同时开两个编码会话，最烦的动作可能不是写代码，而是在终端之间反复复制背景、进度和下一步任务。

QoderCLI 新增的跨会话消息功能，解决的正是这个交接问题。同一台机器上的两个会话可以互相发现、互相发消息，一个会话完成工作后，直接通知另一个会话继续处理。

更值得拆解的不是功能名称，而是它的开发过程。核心能力用约两小时做出 MVP，随后用数十条评审意见补齐细节，最终把测试交付扩展到 46 个用例。对多会话开发方式的改造，这条过程线比一份功能列表更有参考价值。

## 从重复交接里找到真正要消失的动作

故事开始于 8 月 7 日深夜。

作者有一个自动分析流程，会在 Claude Code 发布新版时拉取 changelog 和代码，再逐项研究新功能的实现。针对 Claude Code 2.1.224，这个流程生成了 13 份分析文档，其中一份长达 1011 行，主题就是同一台机器上的会话如何互相发现和传递消息。

第二天早上，作者看到 Claude Code 正在介绍这项能力，于是把已有分析文档交给 agent，让它为 QoderCLI 实现完整功能。这里的关键不是追着更新复刻，而是已经把原始实现拆成了可供 agent 使用的上下文。

没有这份分析材料，指令里的 full feature 很容易只得到一个能演示的壳。有了结构化研究结果，agent 才能沿着明确对象进入工程。

## 让工具进入流程，而不是停在演示里

实现通过作者的 one-shot skill 推进。约两小时后，MVP 完成，改动涉及 47 个文件、5513 行代码，并新增 152 个测试。

这组数字显示出的不是单纯速度，而是任务边界足够完整。跨会话协作并非加一个发送命令就结束，它同时牵涉会话发现、消息传递以及对应测试。功能第一次跑通时，测试已经进入交付物，而不是留到发布前补票。

MVP 发给团队后得到积极反馈，但开发并没有在这里结束。8 月 9 日暂停一天，8 月 10 日继续补细节，前后增加了 20 多个 commit，直到当晚才完成这一轮收口。

两小时做出核心，一天左右完成主要开发，不等于两小时直接上线。这个时间差，恰好是 agent 编程最容易被忽略的部分。

## 把另一个会话变成交叉评审者

细节补完后，作者开始使用 Claude Code、Codex 等工具，并让不同模型进行交叉 review，总计收到 40 多条建议。

这些建议随后被逐项修复，直到 8 月 11 日上午，分支交给同事评审时，基本没有再出现新的问题，只额外处理了一项。

这段过程改变了两个终端的关系。它们不再只是同时写两块代码，一个会话可以负责实现，另一个会话可以接收进度、审查结果或后续任务。跨会话消息因此不只是少复制几段文字，它让交接动作本身进入了可编排的开发流程。

我的判断是，多会话协作最有价值的地方并不是并行数量，而是交付信息能否完整流动。会话开得再多，如果背景仍靠人手搬运，增加的只是切换成本。

## 用测试交付判断功能是否真的完成

8 月 11 日，除了代码评审，agent 还生成了一份 1722 行的测试手册，交给测试同学使用，里面包含 46 个用例。当晚，这项功能随 QoderCLI v1.1.19 上线。

从 1011 行功能分析，到 152 个新增测试，再到 1722 行测试手册，这条链路把研究、实现、评审和验收连在了一起。最终变化的不只是 QoderCLI 多了一个能力，团队拿到的交付物也从代码分支变成了可审查、可测试、可继续接手的一整套材料。

要改造自己的多会话开发方式，可以从一次真实交接开始。选两个会话，让一个负责实现，另一个负责评审，记录中间仍需手动搬运的信息。那些反复复制的背景、状态和结论，就是最值得优先结构化的消息对象。

当会话能够发现彼此、传递任务并留下验收依据，两个终端才真正从两个窗口变成一条工作流。
