# Claude Python SDK 0.122 发布：这几个异步与流式修复值得马上升级

如果你的 Claude 应用跑在 AWS Bedrock 上，或者依赖流式工具调用，0.122.0 不是一次可以随手略过的小更新。它处理的不是新接口带来的新鲜感，而是异步服务里会拖慢请求、流式状态会积累错误、配置异常难以及时暴露这类工程问题。

对普通同步脚本，这个版本未必需要立刻插队升级。对高并发异步服务、Agent 工具链、文件上传流程和多客户端鉴权，升级优先级明显更高。

读完可以直接做出两个判断，当前项目是否命中修复范围，以及这次升级应该重点回归哪些调用链。

## 找出旧版本真正卡住的地方

AWS SigV4 签名原先可能占用异步客户端的事件循环。签名单次耗时未必显眼，但在并发请求中，同一个事件循环还要调度网络请求、流式读取和其他协程，一段同步工作就可能放大尾部延迟。

0.122.0 将 Bedrock 与 AWS 异步客户端的 SigV4 签名移出事件循环。这个改动最值得关注的不是签名速度，而是异步调度不会再被这段工作直接阻塞。

另一个旧问题藏在配置层。空字符串形式的 `ANTHROPIC_API_KEY` 或 `ANTHROPIC_AUTH_TOKEN` 过去可能被当成已经设置的凭证。新版本把空值视为未设置，让客户端按真正缺失凭证的路径处理，减少容器环境变量存在但内容为空时的误判。

## 看懂流式调用修了哪条事故链

这次流式修复覆盖了从事件接收、消息累积到工具输入解析的多个环节。

| 旧风险 | 0.122.0 的处理 | 开发影响 |
| --- | --- | --- |
| 流式消息累积时遗漏部分 `message_delta` 字段 | 累积时应用全部字段 | 最终消息状态更接近服务端事件序列 |
| 服务端工具使用块缺少 `input_json` 事件 | 补发对应事件 | 工具参数可以沿流式事件继续组装 |
| 工具输入 JSON 损坏时上下文不足 | 错误中加入上下文 | 更容易定位出错的工具块和输入 |
| 省略字段在累积结果里被错误填充 | 保持未设置状态 | 下游能区分未提供与显式空值 |
| `messages.stream()` 重复执行请求转换 | 每次请求只转换一次 | 避免转换逻辑产生重复副作用 |

这些修复放在一起看，指向的是同一件事。流式 Agent 不能只做到逐字输出，它还要可靠地还原消息状态、拼接工具参数，并在输入损坏时给出可定位的错误。

如果项目只是展示文本增量，影响可能有限。如果项目会在流中识别工具块、累积 JSON 参数并立即执行工具，这组修复直接落在关键路径上。

## 判断哪些能力现在更适合接入

Bedrock 客户端新增暴露 `beta.messages.parse`、`stream` 和 `tool_runner`，Vertex 也暴露了 `beta.messages.parse` 与 `tool_runner`。这让使用这些接入方式的项目可以沿更完整的消息解析和工具执行路径开发，不必只停留在基础消息请求。

文件参数也修了一处容易被忽略的问题。把 `PathLike` 放进文件元组时，新版本会读取路径指向的内容，而不是把路径对象当成普通值处理。依赖文件元组上传或批处理的代码，应把真实路径对象加入回归测试。

此外，客户端 `copy()` 后的令牌交换会继续绑定在各自客户端范围内。对于复制客户端并维护不同配置或生命周期的应用，这能降低鉴权状态意外串联的风险。

新版本还为 dream 创建加入 `output_behavior`，可以选择创建新的 memory store，或直接更新输入的 store。只有已经使用相关接口的项目需要单独评估这一变化。

## 决定现在升级还是继续观察

建议尽快升级并验证的项目包括 Bedrock 异步服务、依赖流式工具调用的 Agent、会复制客户端的多配置应用，以及通过文件元组传入 `PathLike` 的上传流程。这些项目命中的都是运行路径修复，继续停留在旧版没有明显收益。

可以等待常规升级窗口的项目，主要是低并发同步调用、只读取完整文本响应、没有工具流和文件元组的简单服务。即便如此，也应检查部署环境里是否可能注入空密钥，因为这项变化会让配置错误更早暴露。

我的判断是，0.122.0 的价值不在功能数量，而在它把几条 Agent 应用常见的隐性故障链缩短了。异步阻塞、流式状态偏差和工具参数解析失败，单独看都像偶发问题，叠在生产链路里却很难排查。

升级时不要只跑一次普通消息请求。选一条真实调用链，覆盖异步并发、流式工具输入和最终累积消息，再检查空凭证与文件路径参数的失败行为。通过这组回归，才算真正吃到这次版本修复。
