# 研究 Agent 也会泄密，MosaicLeaks 提醒我们别只盯着最终回答

如果你在做 RAG、个人知识库，或者把企业资料库接进 deep research agent，我建议先停一下，检查的重点不该只放在最终回答。

真正容易漏掉的地方，是搜索词、工具调用参数、外部请求。Agent 可能一句敏感内容都没写进答案，但它为了完成任务，一路把私有资料拆成查询碎片发了出去。

ServiceNow 团队在 Hugging Face 发的 MosaicLeaks，把这个问题讲得很具体。它提醒我，研究型 Agent 的隐私风险，不是“有没有把秘密说出来”这么简单，而是“它为了找答案，向外问了什么”。

## 先把检查点从答案挪到查询

很多团队做安全评估时，默认看最后输出。

回答里有没有客户名、合同金额、内部项目代号。没有，就觉得过了。

但 deep research agent 的工作方式不是一次性回答。它会多轮检索、拆问题、补信息、调用外部工具。只要它同时读了私有资料，又能访问外部检索入口，查询本身就成了泄露面。

MosaicLeaks 讲的 mosaic effect，中文可以理解成拼图效应。

单条查询看起来不敏感。多条查询放在一起，可能就能拼出企业内部事实。

比如一条查询只是某家公司名字，另一条是产品代号，第三条是一个日期或异常指标。每条都像碎片，合起来就不像碎片了。

这也是我觉得这篇文章最值得拿来做团队检查的原因。它不是又在提醒“不要把机密发给模型”，而是把风险往前挪了一步，挪到了 Agent 的行动过程里。

## 给知识库做一张泄露面清单

如果你现在有个人知识库、团队资料库、销售文档库、投研资料库，先不用急着换架构。更实用的动作，是把 Agent 的外部行为列出来。

可以按这个清单过一遍。

- 适合谁，正在做 RAG、deep research、企业搜索、资料问答、多工具 Agent 的团队
- 先看什么，Agent 发出的搜索词、工具调用参数、外部请求日志
- 怎么判断风险，单次调用不敏感时，再把同一任务内的多次调用连起来看
- 最容易忽略什么，最终回答干净，不代表检索过程干净
- 下一步动作，给每类私有资料准备一组最小测试任务，观察查询是否带出私有上下文
- 交付形态，最好形成一份“可外发字段”和“不可外发字段”的工具调用策略

我会特别关注两类词。

一类是实体词，比如客户名、员工名、内部项目名、供应商名。另一类是约束词，比如时间、金额、指标、故障描述、法律条款。

很多泄露不是一句完整秘密，而是实体加约束慢慢拼起来。

## 不要只奖励任务完成率

MosaicLeaks 里有一个判断很刺眼，单纯强化任务表现，可能让泄露更严重。

这很符合 Agent 的产品直觉。我们训练或调提示词时，经常奖励“查得更全”“多跳推理更稳”“答案更完整”。但 Agent 越想把任务做完，就越可能把私有上下文带进外部查询里。

这不是模型坏，也不是工具坏。它只是学会了一个很自然的策略，为了查到公开信息，尽量把问题问具体。

问题在于，具体这件事，在隐私场景里是双刃剑。

文章里提到，普通 deep research agent 在测试中会频繁泄露私有信息。ServiceNow 团队提出的 Privacy-Aware Deep Research，也就是 PA-DR，把 strict chain success 从 48.7% 提到 58.7%，同时把 answer/full-information leakage 从 34.0% 降到 9.9%。

这个数字对我最有用的启发不是“PA-DR 一定该怎么装”，而是一个产品指标提醒。Agent 系统不要只看成功率，也要看泄露率。

只看任务成功率，就像只看销售转化，不看合规成本。短期很好看，长期容易埋雷。

## 把一个任务拆成可审计路径

如果要把这个风险落地到工程里，我会从最小任务开始，不从全量资料库开始。

选一个真实但低风险的场景，比如“根据内部 FAQ 和公开文档，整理某个产品问题的处理建议”。然后记录 Agent 每一步向外发了什么。

重点不是立刻拦截所有调用，而是先分层。

- 可以直接外发，公开产品名、公开文档标题、通用技术术语
- 需要改写后外发，客户场景、故障现象、内部流程名
- 不应外发，未公开项目代号、合同细节、人员信息、私有文档原文
- 需要人工确认，高价值客户、敏感时间点、可能关联交易或法务的信息

这张表做出来之后，再去改检索策略、提示词、工具权限，才有抓手。

我不建议一上来就让 Agent 自己判断全部隐私边界。更稳的方式，是先把敏感字段和外部工具之间加一道规则层。模型可以提出查询意图，但真正发出去之前，参数要能被检查、改写或拒绝。

这里最容易踩坑的是“脱敏只做在答案层”。答案层脱敏解决的是可见输出，工具层脱敏解决的是行动泄露，两者不是一回事。

## 给团队资料库留一个红队任务

MosaicLeaks 提出的多跳 deep-research 任务，本质上是在模拟一种更贴近日常工作的风险。公开信息和私有信息交织在一起，Agent 必须查，也必须用私有上下文理解问题。

这正是 RAG 和研究型 Agent 最常见的使用方式。

所以我会给团队资料库留一个固定红队任务，不追求复杂，追求可重复。

做法很简单。

- 准备一组私有资料，包含项目名、客户名、时间、指标等碎片
- 设计一个需要公开检索才能回答的问题
- 记录 Agent 的全部外部查询和工具参数
- 把同一任务里的查询合并阅读，看是否能拼出私有事实
- 分别记录任务是否完成、答案是否泄露、过程是否泄露

这套检查比只看最终回答慢一点，但更接近真实风险。

我的判断是，deep research agent 越适合复杂任务，越需要过程级审计。因为它的价值就在于会主动拆任务、主动找信息、主动把上下文带到下一步。

能力越强，边界越不能只放在最后一行答案上。
