# vLLM 0.25 升级指南：默认执行路径变了，部署前先看这几项

如果你用 vLLM 部署稠密模型，0.25.0 不是一次适合直接替换生产镜像的常规升级。Model Runner V2 成为默认执行路径，旧 PagedAttention 已被删除，原先稳定运行的配置需要重新验证。

这次升级的收益也很明确。Transformers 建模后端已被优化到接近原生 vLLM 后端的性能水平，MRv2 又补齐多项能力，使用非原生模型实现时的性能取舍有望缩小。

真正要做的决策不是“要不要追新版本”，而是现有服务能否从新默认路径获益，同时把兼容风险和回滚成本控制在可接受范围内。

## 判断默认路径变化会碰到哪些服务

vLLM 0.25.0 将 Model Runner V2 设为所有稠密模型的默认执行路径。它不再只是可选后端，而是稠密模型升级后首先进入的执行路径。

MRv2 在上一版本量化模型支持的基础上，又增加了 EVS、实时嵌入、Mamba 混合模型的前缀缓存、多模态前缀双向注意力，以及兼容完整 CUDA Graph 的动态推测解码。

这些能力覆盖生成、嵌入、多模态和推测解码等不同负载。对正在使用相关能力的服务，升级可能带来更统一的执行路径。对只运行固定稠密模型、且当前延迟和吞吐已经达标的服务，新功能本身并不足以抵消切换默认后端的验证成本。

判断重点应放在实际请求形态。离线批处理、在线生成、嵌入接口和多模态请求不能共享一份笼统结论，每类负载都需要用原有输入和服务参数复核。

## 检查旧注意力实现是否仍是隐含依赖

旧 PagedAttention 已在 0.25.0 中删除。发布说明给出的原因很直接，V1 和 MRv2 后端已经成为标准路径，旧实现不再保留。

这项变化比“默认值调整”更彻底。默认值还能通过配置绕开，被删除的实现则不能继续充当兼容退路。如果现有部署依赖旧注意力实现的行为、配置组合或排障经验，升级风险会集中在启动、显存占用、批处理表现和长上下文请求等运行环节。

因此，回滚条件要在升级前确定。只要关键模型无法启动、核心请求结果异常，或生产约束下的延迟、吞吐、显存表现未达到现有基线，就应保留旧版本镜像和原配置，停止扩大流量。这里的基线来自自己的服务，不应拿发布说明里的功能列表代替。

## 评估 Transformers 后端能否减少适配成本

过去选择 Transformers 建模后端，常见取舍是模型接入更灵活，但性能可能落后于原生 vLLM 实现。0.25.0 的发布说明称，该后端现在已达到原生 vLLM 后端的速度水平。

同时加入的还有 FP8 MoE 支持、CUDA Graph 与嵌入缩放修复，并迁移了 GPTBigCode、Starcoder2 和 RoBERTa。这给需要快速接入 Transformers 模型实现的团队提供了更有吸引力的路径。

但“达到同等速度”不能直接替代本地基准。模型架构、精度、并发、输入长度和硬件都会改变最终结果。更合理的判断是，把后端性能差距视为值得重新测量的变量，而不是已经在所有部署中消失的问题。

## 区分适合升级与适合观望的人

适合优先验证 0.25.0 的，是正在使用稠密模型，并且需要实时嵌入、Mamba 混合模型前缀缓存、多模态前缀注意力或动态推测解码的团队。依赖 Transformers 建模后端，或准备接入本次迁移模型的服务，也有较明确的验证价值。

更适合观望的，是现有服务深度依赖旧 PagedAttention 行为、缺少可重复性能基线，或没有保留旧镜像与配置的部署。关键业务若无法提供隔离环境和分批流量，也不适合把这次升级当作普通补丁处理。

版本还新增了多种模型、统一的流式解析引擎、异构词表推测解码，以及 Rust 前端的 HTTPS、mTLS 和监督能力。不过这些变化不应混入同一次生产验证，否则出现偏差时很难判断究竟是哪一层发生了变化。

## 我的选择是验证升级，不直接替换

我会把 0.25.0 当作执行架构切换，而不是功能补丁。先固定模型、硬件、精度、请求样本和服务参数，只比较当前版本与 0.25.0 的启动结果、输出正确性、延迟、吞吐和显存表现。

只有新默认路径通过现有服务基线，且回滚镜像、配置与触发条件都已准备好，才进入分批放量。Transformers 后端则单独建立一组对照，避免模型实现变化和执行路径变化同时干扰判断。

对多数生产部署，最有价值的动作不是立刻升级，而是把一个代表性稠密模型送进隔离环境。能否在同一套验收条件下稳定通过，会比功能数量更快给出答案。
