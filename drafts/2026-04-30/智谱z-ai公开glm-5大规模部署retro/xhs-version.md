# 智谱主动公开 GLM-5 翻车 retro，国内大模型公司这次开了个好头

国内大模型公司主动写线上事故复盘的，我印象里这是第一次。

不是发布会自吹，是"我们的模型在生产环境真的输出过乱码，原因是底层缓存被另一个请求的网络写入覆盖了"这种级别的事后透明化。

智谱昨天在 z.ai 挂了一篇 Scaling Pain，把过去几周 GLM-5 在 coding agent 高并发下踩过的坑全摊开。我做过几年大模型 serving，从头读完后背一阵发凉。

## 异常长什么样

三月开始，GLM-5 线上出现三类异常，乱码、复读、生僻字。听起来像长上下文降智，但智谱没上任何降精度优化。难受的是标准环境复现不出来，本地同一个 bad case 跑几百次都不出。

我以前遇到过这种情况，大概率不是模型权重的事，是基础设施。模型 bug 通常稳定可复现、跟输入相关，这边反过来，跟系统压力强相关、跟请求内容无关。

智谱继续把线上压力顶到峰值，才在每万次请求里稳定出 3-5 次异常。万分之三到万分之五，对一个每天扛数亿次 coding agent 调用的服务来说，就是每天几万到十几万次脏输出。

## 监控这事本身就先卡住了

复读好查，正则就行。乱码和生僻字真难，启发式漏判误伤严重，模型判别器跑大规模消融吃不消。

智谱最后的切入点很妙，**用一个性能优化指标反向监测异常**。在异常发生时，这个指标的两个分量同时呈现极端模式，刚好可以做异常检测的拦截信号。

把性能优化指标当质量监控用，这个 idea 我之前真没想到过。监控习惯停在 perplexity、output entropy 这些层面，没想过性能侧的指标天然带"两个模型互相比对"的属性，做异常检测特别合适。

## 翻车现场，超时回收引发的脏数据覆写

这段是我读完最有共鸣的，完全是 SRE 视角能想象的剧本。

智谱引擎有个超时回收机制，请求处理超过预算就 abort，回收资源。听起来很合理，要控尾延迟。

问题是，**abort 信号没正确传回另一边**。前一个请求被 abort 掉、资源标记可复用之后，新请求拿到了同一块地址。但前一个请求之前发出的网络写入还在飞，正好落到已经分给新请求的那块显存上。

新请求的 KV Cache 被脏数据覆写了一部分，输出乱码。

这个 bug 恶心在跟代码逻辑无关，跟时序有关。abort 了就回收，逻辑没问题，但异步通信跟内存复用之间没建立明确的先后关系，飞行中的写入会跨过本不该跨的边界。

修复加同步握手，异常率从 0.1% 降到 0.03% 以下。

类似问题在分层缓存模块也出现了一次，两个并行的执行流之间数据依赖没显式声明，下游早于上游启动，读到没初始化的数据。智谱把 fix 提了 PR 给开源社区（SGLang PR #22811）。

## 社区怎么看

知乎"大模型部署"话题下有几个做 SGLang 二开的同学在讨论那个 PR，说自己部署里也遇到过偶发乱码，复现不出来一直归因到"模型不稳定"。**这个 retro 帮国内一批团队定位了悬案**。

智谱社区里有用户问，GLM-5 之前被吐槽降智会不会就是这个 bug。官方没正面回，但从时间线看可能性很大。

## 我的判断

第一，**国内大模型公司里，智谱这次主动写线上事故 retro 开了个不错的头**。把开源 PR 也贴出来，是真的把社区当队友。

第二，**coding agent 的 serving 比普通 chat serving 难一个数量级**。chat 一次几千 token，coding agent 平均输入 70K+，每个环节都被推到极限，chat 时代的推理引擎假设全部站不住。国内大部分团队还在按 chat 的负载形状做能力规划，这个 gap 一两年内会很明显。

第三，**性能优化和正确性的边界比想象中更模糊**。每个为了快引入的新机制，都带一个新同步点，漏一个，表现成的不是"慢"是"输出乱码"，这是最难调的那种 bug。

## 你可以做的事

如果你在做 LLM 推理基础设施，

1. 把 z.ai 这篇 Scaling Pain 全文读一遍，对着自己的架构画一画 abort 路径。
2. 检查所有多执行流并行的地方，确认同步关系显式声明了。
3. 用 SGLang 的话跟一下 PR #22811。

scaling law 推能力往前走，工程把能力变成可靠的服务，这中间隔着的就是这些没人愿意写、但写出来全行业都受益的 retro。
