# 12 个 Agent 记忆系统实测后，一个反常识结论：花哨架构不一定赢

如果你正在给 Agent 做长期记忆，最容易多花钱的地方，不是模型，而是把记忆系统做得太漂亮。

我看到这篇论文结果时，最有价值的不是“12 个系统谁赢了”，而是它直接打碎了一个很顺手的直觉，记忆架构越复杂，Agent 就越聪明。

论文把 Mem0、Letta、Zep、Cognee、MemOS、MemTree、A-MEM、LightMem 等 12 个记忆系统放在一起，又拿 Long Context 和 Embedding RAG 做基线，跑了 5 类负载、11 个数据集。最后的结论很克制，没有通用赢家。

这对工程落地反而更有用。你不用急着在项目里堆图结构、分层索引、全局重组和多阶段维护，先判断自己的瓶颈到底在哪里。

## 误解一，Agent 记忆越像大脑越好

很多人做 Agent 记忆，第一反应是模拟人的记忆，把短期记忆、长期记忆、情节记忆、语义记忆都摆上来。

这套语言听起来很完整，但论文换了一个更工程的看法，把 Agent 记忆当成数据库来拆，表示与存储、抽取、检索与路由、维护。

这个视角很关键。因为数据库不问“像不像人”，只问一件事，当前任务的主导瓶颈是什么。

在 DB-Bench 这类数据库操作任务上，最反常识的结果来了。裸的 Long Context 拿到 48.20 EM，朴素的 MemoChat 也赢过不少精致记忆系统。

也就是说，复杂记忆并不会自动带来更高准确率。有些任务需要的是把足够完整的上下文放进去，而不是提前把信息拆成一堆看起来高级的记忆单元。

我会把这个结果翻译成一句工程判断，先别问“该不该上 Mem0 或 Zep”，先问“这个任务是不是已经被上下文窗口解决了一半”。

## 误解二，检索就是把最相关的一条找出来

RAG 用久了，人会默认检索的目标是排序，把最相关的 chunk 放到最前面。

但 Agent 记忆不完全是这个问题。很多任务不是找一句答案，而是要把分散证据重新拼回一个状态。

论文里一个很典型的对比是，证据距离被拉远时，图结构和层级结构明显更稳。A-MEM 的 Recall@10 达到 85.9，而 Embedding RAG 的 Answer-F1 从 37.1 掉到 7.4。

这不是说图结构在所有场景都该上，而是提醒我们，扁平向量检索擅长“相似内容召回”，不一定擅长“跨片段重建事实”。

如果你的 Agent 只是查用户最近说过什么，简单 RAG 可能够用。可如果它要追踪一个项目多轮变化、多个实体关系、事实更新前后状态，那记忆系统的组织方式就会影响答案质量。

这里的误解不是 RAG 不行，而是把所有记忆问题都当成 RAG 问题。

## 误解三，维护越积极越聪明

我以前也容易高估“维护”这件事。看到系统会自动总结、合并、重写、全局协调，就觉得它更像一个真正的长期记忆层。

论文的数据把这个幻想压得很实。

成本主要由维护范围决定，而不是结构名字决定。LongBench 上，LightMem 稳在 17.3 秒；做全局协调的 Mem0、MemoChat、MemoryOS、A-MEM 延迟到了 374 到 552 秒。

这就是 20 到 30 倍的差距。

如果你的产品是离线研究助手，这个延迟可能还能忍。但如果是多轮客服、代码助手、CRM 助理、销售跟进 Agent，每次对话都等全局记忆刷新，用户体验会先崩。

所以更准确的判断是，记忆维护不是越勤快越好，而是越贴近任务边界越好。局部更新、保守整合，往往比全局重组更适合在线系统。

## 误解四，摘要能省钱，所以应该尽早压缩

这篇论文里还有一个特别容易被忽略的点，别急着压缩。

保留原文胜过摘要。压缩后 Substring-EM 从 26.0 掉到 10.7。抽取也不能只抽“干净事实”，上下文一丢，MemOS Fast 有 25.5 EM，Fine 只有 2.5。

这对做产品的人很刺耳。因为我们都想省 token，想把历史对话变短，想把用户资料整理成几条漂亮字段。

但记忆不是笔记软件。Agent 后面要用这些信息推理、比对、更新，有时一句看似冗余的上下文，正是区分旧事实和新事实的依据。

论文还提到一个普遍毛病，过去的幻觉。事实更新后，系统仍然可能返回旧值。

这就解释了为什么激进压缩和延迟刷新会危险。它们表面上让记忆更整洁，实际上可能让系统更自信地记错。

## 我会怎样调整选型

如果只看这篇论文，我不会得出“某个系统最强”的结论。它更像一张排雷图，告诉我每类方案该放在哪种任务里。

长上下文适合先做基线。只要任务规模和成本允许，先用 Long Context 跑出可接受结果，再决定要不要引入记忆层。

Embedding RAG 适合事实片段相对独立的查询。它便宜、简单、好排查，但不要期待它自动处理复杂状态重建。

Mem0、Letta、Zep 这类记忆系统适合需要长期用户画像、偏好、实体状态和多轮任务延续的 Agent。但上线前要单独测延迟、事实更新和旧值覆盖。

图结构或层级结构适合证据分散、关系复杂的场景。比如项目管理 Agent、研究助理、代码库长期维护助手，这些任务里“证据怎么组织”比“第一条召回多像”更重要。

LightMem 这类局部维护思路值得关注。论文结果里它的延迟表现很突出，说明记忆系统不一定要全局大整理，很多时候小范围维护更接近真实产品需求。

我的判断很简单，先用最朴素的方案打基线，再为具体失败买复杂度。不要反过来，先买一套复杂记忆架构，再到处找任务证明它有用。

## 把验证压到一个真实任务

如果你已经在做 Agent，我建议拿一个重复出现的业务任务来测，而不是只跑问答 demo。

比如用户资料更新、项目状态跟踪、长期偏好记忆、订单状态变更、代码仓库背景记忆。选一个就够。

然后只看四个指标。

任务答对率，看新旧事实冲突时能不能返回新值。

延迟，看每轮对话增加多少等待。

维护成本，看写入、合并、刷新是不是会拖慢主流程。

可追溯性，看错误答案能不能定位到是哪段记忆造成的。

这四个指标比“用了什么记忆架构”更接近上线后的真实问题。

读完这篇论文后，我对 Agent 记忆的态度反而更保守了。复杂架构不是不能用，但它应该是失败后的处方，不该是开局默认配置。

真正可靠的 Agent 记忆，不是记得更多，而是在该更新时不恋旧，在该保留时不乱压缩，在该检索时能把证据组织回来。
