# 开源权重也可能被管住，团队选模型前要看清三类依赖

如果你在给产品选底座模型，开放权重不能只看能不能下载。真正会卡住团队交付的，往往是公司能不能托管、调用、采购，以及出问题后有没有替代路径。

X 上 @emollick 转述的判断很直白。美国政府即使不阻止个人下载权重、在本地运行，也可能通过公司侧限制，让美国公司无法使用、提供访问或托管这些模型。

这对团队选型的提醒很实际，别把文件可得性当成长期可用性。一个模型能躺在硬盘里，不代表它能稳定进入你的产品、合同和上线流程。

## 把可用性拆成三张账

第一张是许可证账。

团队要看的不是许可证名字好不好听，而是目标场景能不能覆盖。能不能商用，能不能改，能不能分发，能不能把能力包装成服务，最好都落到评审材料里。

第二张是服务商账。

源材料里最关键的一点在这里。限制不一定要从个人下载入口下手，只要公司不能使用、不能提供访问、不能托管，产品侧就会被切到很窄的运行空间。

第三张是供应链账。

模型仓库、推理服务、云托管、采购系统、审计记录，都是团队把模型变成产品的一部分。任何一层断掉，项目都可能从能跑变成不能交付。

## 画出公司侧的失效路径

安全审查不需要制造恐慌，只需要把失效路径画出来。

- 路径一，权重已经下载，本地 demo 能跑，但主托管方不再提供托管。研发环境没坏，生产入口断了。
- 路径二，产品没有直接托管权重，只通过第三方推理服务调用。服务商无法继续提供访问后，API 路径断掉。
- 路径三，工程团队能跑，采购和合规不能签。模型质量没有变化，但组织侧已经不可用。
- 路径四，团队把业务逻辑和某一家服务商绑得太紧。替换模型时，变成改产品而不是改配置。

这些不是模型能力问题，而是依赖边界问题。开放权重给了团队更多空间，但不会自动替你解决公司侧约束。

## 给候选模型加控制点

适合放进模型选型表的，不只是效果、速度和成本。下面这组控制点更适合团队评审时直接收藏。

- 许可证原文进评审材料，记录允许的使用场景、分发方式、商用限制和责任人。
- 托管方不只列一家，至少写清主路径、备用路径和切换成本。
- 调用层保留抽象，不把模型名、供应商 endpoint 和业务逻辑绑死。
- 采购和合规状态纳入发布检查，别等上线周才问能不能签。
- 降级方案提前定好，模型不可用时是换模型、关功能，还是转人工审核。

这套检查不复杂，但能过滤掉很多看起来很自由、实际很脆弱的方案。

## 上线前跑一遍替换验证

把当前模型当成可替换依赖，而不是永久基础设施。选一个低风险工作流，把四个故障演练一遍。

- 只能本地运行时，业务是否还能接受延迟、硬件和运维成本。
- 主托管方不可用时，备用推理路径多久恢复。
- 第三方 API 断开时，调用层是否能切到另一个兼容接口。
- 采购审批暂缓时，是否有合规可用的临时方案。

演练完别只看能不能跑通，还要看谁批准、谁维护、谁记录变更。真正能上线的模型，不只是能回答问题，还要能被团队稳定管理。

## 不要把开放当成免疫

我认为，开放权重的价值不是天然免疫限制，而是让团队多一层自救空间。它能提高迁移和自托管的可能性，但挡不住服务商、采购和供应链层面的约束。

团队下次评估模型时，可以把问题问得更工程化一点。权重能下载后，公司还能不能合法、稳定、可替换地使用它。

如果答案写不清，这个模型还不能算长期可用。
