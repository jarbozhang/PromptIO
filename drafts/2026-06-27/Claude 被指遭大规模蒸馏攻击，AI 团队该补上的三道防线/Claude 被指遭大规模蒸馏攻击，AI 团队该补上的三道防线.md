# Claude 被指遭大规模蒸馏攻击，AI 团队该补上的三道防线

如果你在做模型服务、API 平台，或者企业内部 Agent，Claude 这次被指遭遇的蒸馏攻击，不只是 Anthropic 的新闻。

我更关心另一个问题，你的模型能力、工作流接口和高质量回答，会不会被一批低成本账号慢慢搬走。

按 X @dotey 的整理，Anthropic 已向美国参议院银行委员会和白宫致信，指控阿里巴巴旗下通义千问 Qwen AI 实验室相关方，在 4 月 22 日到 6 月 5 日之间，用约 25,000 个虚假账号和 Claude 交互超过 2,880 万次。信件称攻击目标集中在 Claude 的软件工程和 Agent 推理能力。阿里巴巴未予置评。

## 把现场还原成四个风险信号

这类事故最容易被写成一句话，有人拿 Claude 当老师训练学生模型。这个说法不算错，但对防守方不够用。

我会把它拆成四个信号。

账号层，约 25,000 个虚假账号不是单点滥用，而是账号农场级别的容量。请求层，2,880 万次交互横跨 4 月 22 日到 6 月 5 日，说明问题不只是一波峰值流量，而是长周期采样。能力层，目标不是普通闲聊，而是软件工程和 Agent 推理。条款层，材料里提到这些操作触及 Anthropic 服务条款和地域限制。

最危险的地方在第三层。

普通问答被搬走，损失的是内容。软件工程和 Agent 推理被系统性采样，损失的是产品最贵的能力曲线。一个团队如果把代码修复、任务规划、工具调用、长链推理都开放在同一条 API 上，却只按普通调用量收费和限流，风险口子会比想象中大。

## 根因不是模型太聪明，而是出口太干净

蒸馏攻击的核心不是破解模型参数。它更像沿着公开服务的正常出口，把高质量输入输出对持续收集起来。

这也是它难防的原因。每个请求单独看，可能都像普通用户在问代码、问架构、问 Agent 怎么拆任务。可当这些请求被放到账号族群、时间窗口和任务模板里看，图案才会浮出来。

同一材料里还有一个对照。Anthropic 在 2 月点名过 DeepSeek、MiniMax 和 Moonshot AI，称三方使用约 24,000 个假账号产生了 1,600 万次交互。相比之下，这次被指的交互量达到 2,880 万次，接近此前三方合计的两倍。

这让我觉得，防守不该只问有没有异常账号，而要问输出是不是正在被拼成训练集。

## 只封账号和限流不够

很多团队第一反应会是风控账号，超过阈值就封。这当然要做，但它只挡住最粗的滥用。

账号可以拆散，请求可以降频，任务可以换表达。真正的蒸馏请求会努力装成正常用户，因为它要的不是打爆服务，而是稳定拿到足够多的高质量答案。

只靠关键词也不够。攻击者未必会直接写我要蒸馏你的模型。他们会问代码评审、bug 定位、repo 规划、测试生成、Agent 工具选择。这些恰好也是正常开发者最常问的问题。

只靠服务条款更不够。条款能给后续处置提供依据，但如果它没有接进账号审核、API 风控、日志留存和客户分层，等发现时，输出可能已经流走很久了。

## 把三道防线做进系统里

第一道防线看账号族群。不要只看单个 key 的调用次数，要看注册时间、调用节奏、任务相似度、失败重试、账号之间的问题重合度。一个账号不异常，不代表一组账号不异常。

第二道防线看请求模式。把代码生成、Agent 规划、长链推理、工具调用这几类高价值能力单独打标签。它们可以正常开放，但应该有更细的速率、配额和审计规则。

第三道防线看能力出口和条款执行。对高价值输出做分层，不同客户、不同场景给不同深度的结果。服务条款里写清楚不能用输出训练竞争性模型，也要有对应的检测、记录和处置流程。

我认为很多企业 AI 团队还少一件事，把自己的 API 当成可被反向采样的资产来设计。你不是只在交付回答，也是在暴露能力边界。

## 留一张事故卡片

这次事件可以压成一张复盘卡。

触发器是多账号、长周期、相似任务的高频交互。

核心靶点是软件工程能力和 Agent 推理能力。

易错判断是把它当成普通滥用，只做单账号封禁和粗颗粒限流。

修复动作是账号族群画像、请求聚类、能力分层、条款执行日志一起上。

复盘问题只有一个，你的模型输出，能不能被别人用足够低的成本收集成训练材料。

如果答案不确定，就别等到 2,880 万次交互之后才开始查日志。
