# Gemini Spark 把 24/7 agent 直接塞进 Gmail 国内邮箱助理们要尴尬了

上周出差回来，收件箱积了 87 封未读邮件。客户的、内部的、订阅的、招聘的，混在一起。我没逐封打开，而是在 Gmail 里点开了昨天 Google I/O 刚发的 Gemini Spark，让它"先帮我看完，挑出今天非回不可的，剩下的按主题归一下"。

二十分钟后我回到工位，Spark 已经在屏幕里摆好了一张小清单。三封需要今天回的客户邮件，每封下面挂了一段候选回复草稿。五封需要本周决定的，标了截止日期。七封订阅类的合并成一行摘要，问我要不要直接归档。

不是 chatbot，是个真的在替我跑活的东西。

## Spark 到底是不是一种新东西

Google I/O 2026 上发布的 Gemini Spark，TechCrunch 给它的定义是"24/7 agentic personal assistant"，底座用的是 Gemini 系列模型，外面套了一层从 Google Antigravity 项目里抽出来的 agent harness。

agentic harness 这个词翻译过来就是"agent 外壳"，决定了 Spark 跟以往那些 AI 邮件助手的根本差异。

Gmail 早就有 Smart Compose、Smart Reply、AI 摘要，但那些都是被动的。你点开一封邮件，它给你写两句候选回复；你打开搜索框，它帮你补全。说到底还是你按一下、它跑一下的工具。

Spark 是常驻的。即便我没打开 Gmail，它也在后台扫新邮件、识别意图、生成草稿、攒成清单等我回来确认。The Verge 把它跟 Daily Brief 一起划进了 Google "always-on AI" 这条线，always-on 意思就是这玩意没有"会话开始/结束"，它就在那儿跑。

差别不是模型变强了，是交互范式从"chat"变成了"agent"。Chat 是你来一句它一句，agent 是你设个目标它自己跑完。

## 实测三个场景

第一个场景，**批处理邮件回复**。我把"客户咨询类邮件，按公司分组，每组生成一份统一回复模板，把对方提到的具体问题列出来让我勾选"这个指令丢给 Spark。三分钟它给了我五组草稿，每组顶上一行写着公司名和邮件数量，下面是合并后的回复初稿，再下面是每个客户具体的差异点。我只需要在差异点上勾选哪些回应、哪些跳过，然后让它批量发送。

如果让我手动做，光是把五家公司的邮件整理出来就要二十分钟。

第二个场景，**周报抽取**。我让它扫过去七天的"我发出去的邮件 + 我标星的邮件 + 内部 CC 我的邮件"，归一份"本周做了什么、对接了谁、有什么未决事项"的初稿。这个事我以前每周五下午要花一小时。Spark 给的草稿大概有 70% 可用，剩下 30% 是它判错的优先级，我手动调一下就行。

第三个场景，**重要事件提醒**。一封三周前的邮件里，客户提到了"五月底我们再约一次同步"。Spark 自己把这条信息提了出来，挂在我的日历入口边上，距离截止还有十天的时候主动提醒了我。这种"埋在邮件正文里、没有显式日程"的提醒，是 Smart Compose 之类的被动工具做不到的。

## 国内的邮件 AI 现在在做什么

国内主流邮箱和协同工具里，飞书、钉钉、QQ 邮箱、网易邮箱大师都在 AI 这条线上发了功能，但侧重点跟 Spark 不太一样。

飞书的 AI 助手目前更聚焦在**文档和会议**这两个场景，会议纪要、文档摘要、跨文档检索这块做得比较深。邮件这块飞书本来用户基数就小，AI 入口主要是结合飞书消息生态。

钉钉的 AI 在做**企业内部知识检索和工作流自动化**，AI 助理可以接表单、接审批、接智能体应用市场，方向更偏 B 端工作台。邮件场景在钉钉的产品矩阵里权重不高。

QQ 邮箱今年也上了 AI 写邮件、AI 摘要的功能，定位更偏**单封邮件的轻量协助**，写一封英文邮件、提炼一封长邮件的要点，这类点状能力做得不错。

网易邮箱大师走的是**会员订阅 + AI 增值**的路线，国内 to C 邮箱里 AI 渗透比较积极的一家。

跟 Spark 的差距体现在两层。一层是**常驻 agent vs 单点功能**，国内目前主要在"我点一下、AI 跑一下"的模式上做体验优化，"24/7 后台代我跑"这种 agent 形态在邮件场景还没看到公开产品。另一层是**底座生态**，Gmail 本身是 Google Workspace 的中枢，Spark 能顺着这条线打通日历、Docs、Drive。国内邮箱很多时候是孤立产品，跟办公套件、IM、日历的耦合度没那么深。

这不是说国内做不出来，是产品形态还在不同的赛道上。飞书钉钉走的是"协同工作流 + AI"，国内邮箱产品走的是"邮件单点 + AI"，跟 Spark 这种"邮箱即 agent 入口"是三种不同的产品观。

## 我的判断

邮件这个场景对 agent 来说几乎是天作之合。

**信息密度极高**，一封邮件可能藏着合同条款、约定时间、对方诉求、潜在风险这些关键信息。但**人类处理频次又被压得很低**，绝大多数白领的邮箱都在堆积、漏看、错过。这种"内容值得细看、注意力却跟不上"的状态，正是 agent 介入最有杠杆的位置。

Spark 的意义不是"AI 又增加了一个使用场景"，而是 Google 在用 Gmail 这种全球十亿人在用的产品做 agent 形态的大规模验证。如果 24/7 agent 在邮箱里站住了，下一步就是日历、文档、IM、客服，整条协同工作流都会被这种形态改造。

我认为国内未来一年会出现类似形态的产品，但不一定从邮箱出发。更可能从**飞书或钉钉这种已经有完整办公生态的入口**长出来。原因很简单，国内 to B 协同的核心入口从来不是邮箱，而是 IM 加文档。

风险也要提一句。The Verge 那篇文章标题就叫《Google 的 AI 未来需要信任，也需要你的个人数据》。一个 24/7 在背后看你所有邮件的 agent，说到底是把整个收件箱的访问权给了模型方。Spark 之后 Google 怎么解释数据使用、怎么提供企业级隔离方案，是这条产品线能不能在严肃企业市场站住的关键。

## 怎么试

如果你有 Google 账号，Gmail 网页端会陆续推送 Gemini Spark 的接入，I/O 后第一批 rollout 给了 Google AI Pro 和 Ultra 订阅用户。功能入口在 Gmail 侧边栏。

国内场景如果想试类似的"邮箱 agent"体验，目前的可行路径有三条。

一是飞书或钉钉里把邮件接进来，挂 AI 助手做摘要和草稿，路径最短，但只能做到被动协助，不是 agent 形态。

二是自己用 OpenRouter 跑一个简易 agent。OpenRouter 上的 Gemini 系列、Claude 系列、DeepSeek 系列都能调，国内可直连。配合一个 IMAP 接口的脚本，写一个最小可跑的 demo，给自己每天扫一次收件箱、归类、生成草稿、推送到企业微信或飞书。这条路适合 AI 工程师周末试一下。

三是关注国内邮箱厂商的更新节奏。腾讯邮和网易邮箱大师都在持续推 AI 功能，今年下半年大概率会有更接近 agent 形态的版本出来。

我自己这周打算用 OpenRouter 跑第二条路。等做完会写一篇带代码的实测，看看一个 100 行脚本能不能在中文邮箱场景里复刻 Spark 80% 的体验。

如果你也想试，留言告诉我你的邮箱日均收件量、最希望 agent 帮你处理的第一件事是什么。我把这些场景纳入我自己的 demo 设计里。

那 87 封积压邮件后来怎么样了？我点了"全部按 Spark 建议执行"，三分钟清空了收件箱。剩下的时间，我开始写这篇稿子。
