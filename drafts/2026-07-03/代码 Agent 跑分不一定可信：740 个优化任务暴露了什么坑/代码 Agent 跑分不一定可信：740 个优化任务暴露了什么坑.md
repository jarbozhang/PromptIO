# 代码 Agent 跑分不一定可信：740 个优化任务暴露了什么坑

如果团队正在用代码 Agent 榜单做选型，我会先把这篇论文丢进评审会。

它不告诉你哪个 agent 更强，它提醒的是另一件事，某些高分可能只是机器、规则和任务覆盖率共同挤出来的结果。

arXiv 上这篇 Are Performance-Optimization Benchmarks Reliably Measuring Coding Agents? 审了 GSO、SWE-Perf、SWE-fficiency 三个仓库级性能优化 benchmark。研究对象不是玩具题，而是 740 个真实仓库优化任务，跑在四类常见 Google Cloud 机器上。

我更愿意把它看成一次选型事故复盘。事故现场不是 agent 写错代码，而是团队拿一个不稳定的分数做采购证据。

## 把事故现场还原成 740 个任务

这类 benchmark 的逻辑看起来很工程化，给真实仓库打补丁，再比较未优化基线、官方参考补丁和公开提交的运行时间。

问题是，性能优化最怕微小波动。

论文回放了官方参考补丁。多数任务能复现执行，但能在每一种机器回放里都满足原 benchmark 有效性规则的任务数量，GSO 只有 39/102，SWE-Perf 只有 11/140，SWE-fficiency 是 411/498。

SWE-Perf 最脆，论文给出的原因很直接，很多参考补丁带来的运行时变化接近零。一个接近零的改进，本来就很容易被机器状态、噪声和计时误差吞掉。

## 追到根因看机器和规则

我看到 11/140 这个数字时，第一反应不是某个榜单没价值，而是这个分数不该孤立使用。性能题和功能题不同，功能题通常看测试过不过，性能题还要问，在哪台机器上快，快多少，波动多大。

论文把三类问题拆开了。第一类是跨机器复现，四类 Google Cloud 机器上，同一个参考补丁不总是稳定满足规则。第二类是计分规则，GSO 和 SWE-fficiency 的公开提交重叠，但排名并不总认同。

八个共同公开提交形成 28 对两两比较，官方排名有 9 对结论不同。

第三类是任务权重。SWE-fficiency 的计分规则会让最差的十个任务拿到 58.5% 到 82.8% 的高权重。你想想看，一个 agent 在少数高权重任务上碰巧占优，榜单总分就会被拉得很漂亮。

## 常见采购动作为什么不够

常见做法是截一个 leaderboard，挑前三名进试用，再让供应商解释模型架构和上下文长度。我现在会把这个动作判为半成品。

原因不复杂，榜单告诉你聚合结果，没告诉你这个结果有多少来自稳定可复现的任务，有多少来自计分规则，有多少来自已经被公开提交覆盖得差不多的题。

论文里还有一个很容易被忽略的数字。对 10 个公开提交逐任务查看后，在 GSO 和 SWE-fficiency 的 450 个可回放有效任务里，至少一个提交追平或超过参考补丁的任务占 85.3%，也就是 384/450。至少一个提交超过未优化基线的比例是 99.8%，449/450。

这不是说 agent 已经解决性能优化。更合理的读法是，很多任务已经被公开提交追平或超过参考补丁，榜单继续上涨时，可能并不等于 agent 在更难问题上突破了。

## 把跑分改成团队验收

如果我要在团队里用这类 benchmark，分数只会放在第二屏。第一屏我会放四个问题。

- 能不能拿官方参考补丁在自己的机器或云资源上复现有效性
- 单个任务的性能提升是否大过噪声，接近零的改进单独标记
- 榜单总分能否拆成每个任务的贡献，避免少数高权重任务带偏
- 公开提交已经覆盖的任务占多少，未解决的剩余缺口在哪里

采购或选型时，我会把候选 agent 先丢到团队真实代码的一小组性能任务里。任务要有未优化基线、人工认可的参考补丁、固定机器配置、重复运行统计和有效性规则。

跑不出这些，排行榜名次只能当线索，不能当依据。

如果预算只够做一个动作，我会优先做复现实验。因为复现不过，后面的价格、上下文、IDE 接入都只是把一个不稳的前提包装得更漂亮。

## 留一张事故卡片

- 事故名称，代码 Agent 跑分误用
- 触发条件，团队只看 leaderboard 总分，没有重放参考补丁
- 表面症状，同一类 agent 在不同 benchmark 上排名不一致
- 关键证据，740 个任务跨四类 Google Cloud 机器回放，GSO 39/102、SWE-Perf 11/140、SWE-fficiency 411/498 在每次跨机器回放里满足原规则
- 修复动作，先复现，再拆权重，再看未覆盖任务，最后才进入采购讨论

我喜欢这篇论文的地方，是它没有喊 benchmark 无用。它只是把一个工程常识摊开，性能分数只有在可复现、规则透明、任务覆盖率清楚时，才配进入决策桌。

下次看到代码 Agent 跑分上升，我会先问一句，哪一部分是能力，哪一部分只是 benchmark 的脾气。
