OpenClaw 这次从 GitHub Trending 里冒出来，我最先看的不是 star 数，而是 README 里那句，Your own personal AI assistant. Any OS. Any Platform.

源材料给了一个很明确的方向，仓库主题里还有 own-your-data。对想要自己掌控数据的国内 AI 用户，这几个词比又一个聊天窗口更关键。

先把边界说清楚。本篇来自 GitHub 仓库和 README，不是完整亲测评测。我没有在本机跑完安装，也没有接入真实微信、QQ 或飞书账号，所以不会写速度、稳定性、成本、延迟这些体验结论。

我能确认的是仓库信息。OpenClaw 是 TypeScript 项目，源材料记录 star 374883，fork 78106，创建于 2025-11-24，最后推送是 2026-05-27。GitHub 简介把它定位成运行在自己设备上的 personal AI assistant，README 说它可以在已有的聊天渠道里回复，也可以在 macOS、iOS、Android 上说话和听声，并提供一个可控的 live Canvas。

我真正感兴趣的是它的工作方式。OpenClaw 不是只做一个网页聊天框。README 里说 Gateway 只是 control plane，产品本体是 assistant。用国内用户的话讲，就是把入口、通道、会话、工具、技能和事件调度放进一套你自己能部署和检查的系统里。

这也是我会尝试它的原因。我们现在用 AI，经常被迫在两个极端之间选。要么用云端成品，省心但很多东西不在自己手里。要么自己拼一堆脚本，灵活但维护压力很大。OpenClaw 想走中间路线，助手在自己设备上跑，模型和渠道按配置接。

但别误会，它不等于完全离线。README 里还提到 OpenAI 的 OAuth 订阅，并说明支持多个 provider 和 model，要选自己信任且已经在用的提供方。所以如果你的目标是所有推理都在本机，OpenClaw 不是凭 README 就能证明满足条件的方案。它更像一个 local-first 的个人助理框架，数据和入口尽量回到你能控制的设备和配置里。

我会按这个顺序搭。

第一件事，只跑最小闭环。README 推荐 Node 24，也支持 Node 22.19 以上。安装路径很直接，`npm install -g openclaw@latest`，然后跑 `openclaw onboard --install-daemon`。这个 onboard 会引导设置 gateway、workspace、channels 和 skills，并把 Gateway daemon 装成常驻服务。

第二件事，不急着接所有聊天软件。README 支持的渠道很长，WhatsApp、Telegram、Slack、Discord、Google Chat、Signal、iMessage、Matrix、飞书、LINE、WeChat、QQ、WebChat 都在列表里。我的做法会是先用 `openclaw gateway status` 确认服务，再用 `openclaw agent --message 'Ship checklist' --thinking high` 问一条本地测试消息。能跑通这一步，才继续碰真实渠道。

第三件事，把安全默认值先看完。OpenClaw 连接的不是玩具入口，而是真实 DM 和群组入口。README 明确提醒 inbound DMs 要当成不可信输入。默认策略里，未知发送者会收到 pairing code，bot 不直接处理消息，要通过 `openclaw pairing approve <channel> <code>` 批准。这个设计对国内用户很重要，因为一旦你把个人助理接到微信、QQ 或飞书，权限边界就不是工程洁癖，而是事故边界。

如果我要正式用，会先做三个限制。只接一个低风险渠道。只给 assistant 一个干净 workspace。非 main 会话用 sandbox。README 里提到 Docker 是默认 sandbox backend，也列了典型允许和拒绝的工具范围。这个部分比好不好玩更值得先读。

所以我对 OpenClaw 的判断很克制。它看起来不是下载就变成私人 Jarvis 的消费品，而是给愿意动手的人准备的个人 AI 助手底座。它真正吸引我的地方不是 star 数，而是三个词，own your data。

今天能做的下一步很简单。别先幻想一套全自动生活管家，先把 Gateway 跑起来，发一条本地 agent 消息，再决定要不要接第一个真实渠道。能守住这个顺序，很多后面的坑会少一半。
