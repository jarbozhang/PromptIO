# Mac 本地跑模型别忽略这次 llama.cpp 更新：一个无推理操作也会触发的内存泄漏

如果你的 Mac 应用会反复加载、切换或卸载本地模型，这次 llama.cpp 更新值得尽快检查。问题不在长时间推理，也不需要先把 GPU 跑满。模型加载后即使一次 GPU 推理都没执行，直接释放也可能留下没有正确解除驻留的 Metal 内存。

这条边缘路径常见于模型预检失败、任务取消、热切换和启动探测。表面上看，模型对象已经销毁，进程也完成了正常清理，但系统级 wired memory 仍可能没有同步回落。

真正需要防的不是一次明显的崩溃，而是这种能够重复发生、又容易被常规测试漏掉的资源泄漏。llama.cpp 的 b10188 发布修复了这条路径，并加入了围绕系统级 wired memory 的回归测试。

## 还原没有推理却占住内存的现场

典型事故链条很短。

应用加载模型，Metal 后端让相关内存进入驻留状态。随后，业务层因为取消、配置检查失败或模型切换而释放模型，GPU 操作尚未发生。清理流程执行了，但解除内存驻留所依赖的路径没有被触发。

于是出现一个很反直觉的结果。业务代码看到的是模型已经释放，系统看到的却可能仍有一部分内存处于 wired 状态。

这类问题在单次启动测试中未必明显。真正危险的是桌面应用、模型管理器或常驻服务不断重复加载和释放模型。每轮遗留一点，最终表现可能只是可用内存逐渐变少，用户却很难把它和某次未执行的推理联系起来。

## 找到 Metal 清理路径缺失的原因

这次修复指向的根因很具体，模型在没有任何 GPU 操作的情况下被释放，Metal 内存可能没有正确 unwire，也就是解除 wired 驻留。

正常推理路径会提交 GPU 工作，相关资源状态随之推进。边缘路径的问题在于，模型已经完成加载，却在首次 GPU 工作发生前退出。原本隐含在 GPU 工作流程里的清理条件没有出现，释放模型也就不等于完整释放底层驻留资源。

修复采用了一个针对性的办法，在使用 residency sets 的条件下运行一段 dummy work，让所需的资源生命周期得以完成。发布记录同时提到，这段逻辑只在 residency sets 被使用时运行，并通过条件编译包裹相关函数，避免把修复无差别扩散到其他构建路径。

这里的工程教训很清楚。资源生命周期不能默认依附于主成功路径。只要加载与首次执行之间允许取消，系统就必须单独验证零次执行后的释放行为。

## 为什么常见内存测试抓不到它

很多模型应用的内存测试集中在推理期间，观察峰值、上下文增长、键值缓存和多轮生成后的回收。这样的测试会经过 GPU 操作，刚好绕开本次问题对应的触发条件。

只检查进程内指标也不够。Metal 资源是否真正解除驻留，需要观察系统级 wired memory，而不是只看业务对象是否析构、模型句柄是否为空，或者进程报告的普通内存是否下降。

llama.cpp 为此补上的回归测试有两个关键变化。测试开始测量系统范围的 wired memory，并且该回归测试始终参与构建。它验证的不是模型能否完成一次推理，而是模型在没有 GPU 操作时释放，系统资源能否正确回落。

这比给清理函数补一行调用更重要。修复关闭了当前缺口，回归测试则防止未来重构再次把这条罕见路径拆开。

## 把修复落实到 Mac 本地应用

使用 llama.cpp Metal 后端，并且存在动态加载或卸载模型的应用，应优先核对当前依赖是否包含 b10188 对应修复。若依赖来自固定提交、预编译包或上层封装，还要确认实际链接的 llama.cpp 版本，而不是只更新仓库记录。

升级后的验证应复现原始事故路径。加载模型后不提交 GPU 推理，直接释放模型，再观察系统级 wired memory 的变化。为了区分正常波动与持续遗留，可以重复相同生命周期，并比较多轮后的整体趋势。

验证时还应保留一组正常推理后释放的对照路径。两条路径都能回收，才能说明应用没有把资源清理偶然绑定在首次推理上。

事故卡片可以压缩成四行。

- 触发条件　模型完成加载，尚未执行 GPU 操作便被释放
- 表面现象　对象已销毁，但系统级 wired memory 可能没有回落
- 修复信号　依赖版本包含 b10188 的 Metal unwire 修复
- 回归标准　零次 GPU 操作和正常推理两条释放路径都不出现持续累积

Mac 本地模型应用最难查的内存问题，往往不是推理跑得太久，而是推理根本没开始。把零次执行纳入资源生命周期测试，才能让释放模型真正等于归还资源。
