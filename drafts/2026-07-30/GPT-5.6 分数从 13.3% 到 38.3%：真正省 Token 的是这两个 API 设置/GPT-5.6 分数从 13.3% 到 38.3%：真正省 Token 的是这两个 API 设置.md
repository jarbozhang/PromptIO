# GPT-5.6 分数从 13.3% 到 38.3%：真正省 Token 的是这两个 API 设置

同一个 GPT-5.6 Sol、同一套 ARC-AGI-3 公开题目，成绩却能从 13.3% 变成 38.3%。模型没有更新，改变的是评测程序如何保存响应状态、如何处理塞满的上下文。

这次复盘对 API 用户更重要的提醒，不是某个榜单又涨了多少，而是多轮任务可能正在为错误的状态管理付费。模型每一步都重新理解任务，既会损失正确率，也会重复消耗 Token。

如果你的 Agent 会连续操作、调用工具或执行长任务，可以重点检查两个地方，上一轮响应有没有真正接回去，上下文满了以后究竟是压缩还是直接删除。

## 还原分数掉到 13.3% 的现场

问题发生在评测程序 harness，而不是题目或模型本身。

模型每完成一步，写给自己使用的私有思考就被整段丢弃。到了下一步，它虽然还能看到部分对话，却无法延续上一轮推理，只能重新判断当前局面。

这类损失在单轮问答里未必显眼，但 ARC-AGI-3 需要模型持续观察、尝试动作并根据结果修正策略。每一步都从头理解，相当于不断支付探索成本，却没有积累出稳定的任务状态。

第二个故障出现在上下文达到容量阈值之后。旧程序直接删除最早的消息，过去执行过哪些操作、哪些尝试已经失败，也会逐渐消失。

事故链条因此形成。

保留不了上一轮推理，模型重复分析。上下文满后再删除早期记录，模型失去操作历史。任务越长，重复推理和遗忘越严重，增加推理档位只能用更多 Token 补偿状态断裂。

## 找到两个真正的根因

第一个根因是响应状态没有连续传递。

修复方式是使用 Responses API，把上一次响应的 ID 作为 `previous_response_id` 传入下一次请求。这样，连续任务不再被拆成互不相干的独立调用，推理状态可以沿响应链延续。

第二个根因是把上下文管理理解成简单截断。

开启 compaction 后，上下文达到阈值时，系统会把已有信息压缩成浓缩状态，再让任务继续运行。它保留的是后续决策仍然需要的信息，而不是机械删除最早的一段记录。

一个负责接住上一轮，一个负责在长任务里保住过去。两者处理的是不同阶段的状态丢失，缺少任何一个，长链路都可能继续泄漏性能。

## 解释为什么提高推理档位仍然不够

常见补救是发现结果不好后，把推理强度从高调到最高。这个办法可能增加单步搜索量，却修不好断裂的任务记忆。

复盘中的数据很直接。旧程序在最高档时，每局输出约 290 万 Token。调整响应状态和压缩策略后，这个数字降到约 49 万 Token。

更关键的是，新程序在高档就取得了旧程序最高档的同等分数，两种组合的 Token 消耗相差约 12 倍。这说明旧方案购买的并不全是更深推理，其中相当一部分是在为重复理解和历史丢失买单。

所以，推理预算不是状态管理的替代品。给一个持续失忆的 Agent 更多 Token，只会让它更认真地重新开始。

## 把修复动作落到自己的多轮任务

排查时不要只盯总 Token，也要对照每一步请求的状态传递方式。

检查响应链是否连续。确认后续请求引用了上一轮响应，而不是把若干可见消息重新拼成一次全新的调用。

检查上下文溢出策略。确认达到阈值后使用 compaction 保留任务状态，而不是从头删除消息。

检查动作历史是否仍可用。连续操作任务至少要保住已执行动作、关键观察、失败尝试和当前目标，否则模型很容易重复操作。

检查推理档位是否在掩盖故障。若提高档位带来 Token 激增，却没有稳定改善长任务结果，应先审计 harness，而不是继续增加预算。

这次事故最值得留下的判断是，模型评测和 Agent 成本不能只归因于模型。调用层如何维护连续性，本身就是能力的一部分。

事故卡片可以压成一句话，分数异常下降并伴随 Token 暴涨时，先查响应状态是否断链，再查上下文是否被粗暴截断。
