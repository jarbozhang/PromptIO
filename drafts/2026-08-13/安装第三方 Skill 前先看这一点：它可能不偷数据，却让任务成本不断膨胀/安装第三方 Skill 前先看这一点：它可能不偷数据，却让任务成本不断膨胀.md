# 安装第三方 Skill 前先看这一点：它可能不偷数据，却让任务成本不断膨胀

装第三方 Skill 时，我过去最关注的是它会不会读取敏感文件、执行危险命令。看完 Convergent Detour Hijacking 这项研究后，我会再加一项检查，它是否在诱导 Agent 多走一段看似合理、实际无用的调用链。

这种攻击不必偷走数据，也不必破坏最终答案。任务照样完成，账单和等待时间却悄悄膨胀。对正在搭 Agent 工作流、开放第三方 Skill 安装，或者按 token 和执行时间付费的团队，这比一次明显报错更难发现。

读完可以直接拿走三层控制办法，安装前审查描述与指令，运行时限制预算，执行后检查调用链有没有绕路。

## 找出藏在正常结果里的成本风险

论文把这种攻击称为汇聚式绕路劫持，也就是 Convergent Detour Hijacking，简称 CDH。

它利用了 Skill 的渐进披露机制。Agent 通常先读自然语言描述，决定该选哪些 Skill，再读取入选 Skill 的指令正文，规划后续调用。第三方发布者因此获得了两个连续的影响点。

第一个影响点负责进入候选集。恶意描述会把自己包装成与当前任务高度相关的协调组件，让模型觉得它应该和合法 Skill 一起出现。

第二个影响点负责拉长路线。指令正文沿用描述里的理由，虚构若干看似必要的依赖，再把无关但正常的 Skill 招进执行链。绕路结束后，它还会回到原始路线，让任务继续完成。

这正是风险最隐蔽的地方。结果正确，只能证明 Agent 到达了终点，不能证明它走的是合理路线。

## 看懂一条绕路是怎样形成的

我会把 CDH 的失效路径拆成四个连续动作。

- 伪装相关性，描述声称自己负责校验、协调、格式转换或上下文准备
- 获得规划权，正文把这些说法改写成必须执行的前置依赖
- 招募多余组件，Agent 调用更多良性 Skill，产生额外 token、等待时间和工具费用
- 重新汇入主链，攻击组件让流程回到原任务，最终结果仍可能正确

论文在多个大语言模型后端、491 个留出任务以及单任务和多轮条件下评估了这种路径。在 DeepSeek-V4-Pro 上，匹配的协调组件被选中的比例达到 80.02%。

在命中协调组件且任务完成的运行中，token 消耗增加 66.91%，端到端执行时间增加 92.45%，而整体任务完成情况仍然相近。

我的判断很明确。只用任务成功率评估 Agent，会漏掉一类重要问题。安全指标里还要有轨迹完整性和成本安全，也就是它为什么调用、调用了谁、花了多少资源，以及这些步骤是否真的必要。

## 把控制点放进安装和运行环节

安全审查不该只搜索明显的危险命令。对第三方 Skill，我会检查描述与正文之间是否形成了一套自我证明的调用理由。

安装前可以保存这张审查卡。

- 描述审查，警惕过度宽泛的适用范围，以及协调、增强、验证所有任务之类的表述
- 指令审查，找出没有技术依据的强制前置步骤、依赖声明和重复校验
- 权限审查，确认它能调用哪些 Skill、工具和模型，默认采用最小调用范围
- 路径审查，要求维护者说明每个依赖解决什么问题，以及删除后会损失什么
- 成本审查，为单次任务设置 token、工具调用次数、执行时间和付费接口上限

这些检查不能证明 Skill 一定安全，但能让恶意描述更难仅凭自然语言取得额外规划权。

运行时还要把预算做成硬约束。超过最大调用深度、重复调用阈值或累计 token 上限时，流程应暂停并记录原因，而不是继续相信模型生成的依赖说明。

## 让调用链自己暴露异常

只有总账单，没有逐步轨迹，很难区分复杂任务和恶意绕路。我会给每次 Skill 调用至少记录六项信息。

- 调用者与被调用 Skill
- 触发调用的原始任务
- 模型给出的调用理由
- 输入与输出 token
- 执行耗时和可计费工具次数
- 下一步是否重新回到原始任务链

观测时重点找三种信号。某个协调 Skill 在大量不同任务中频繁出现，同一理由连续触发多个组件，以及中间调用明显增加但最终交付物没有对应变化。

还可以做一次反事实验证。移除可疑 Skill 后重放同一批任务，比较完成率、token、耗时和调用深度。如果结果基本不变而资源明显下降，这段依赖就缺少保留理由。

## 用四组任务完成上线前验证

正式开放第三方 Skill 前，我建议准备一组小规模基准，不追求覆盖所有业务，只验证它是否会稳定制造绕路。

- 直接任务，只需要一个合法 Skill 即可完成
- 相邻任务，语义与可疑 Skill 接近，但并不需要它参与
- 多轮任务，观察早期描述是否会影响后续规划
- 移除对照，同一任务分别在启用和禁用该 Skill 时运行

验收不要只看答案对不对。还要比较 Skill 选择率、调用深度、token、端到端时间和任务完成情况，并为每项设置可接受区间。

第三方 Skill 的风险边界不能停在数据泄露和命令执行。现在就选一个准备安装的 Skill，把它的描述、指令正文和依赖调用放在一起审查，再用十几个固定任务跑一次启用与禁用对照。只要结果相近而成本曲线明显分叉，就该暂停安装并追查那段多出来的路线。
