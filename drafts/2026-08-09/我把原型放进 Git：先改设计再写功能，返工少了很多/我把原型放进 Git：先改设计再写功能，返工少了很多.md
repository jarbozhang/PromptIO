# 我把原型放进 Git：先改设计再写功能，返工少了很多

功能写得越来越快以后，我反而更容易在界面上返工。按钮放哪里、流程怎么走、状态怎么反馈，这些问题如果边写代码边决定，改动很快就会穿过组件、接口和数据结构。

后来我把顺序倒了过来。每次增加功能，先修改本地 React 原型，确认设计变化，再进入正式实现。真正帮我减少返工的，不是生成代码更快，而是把决定做在代码变贵之前。

这套链路适合正在用 Claude Code、Codex 等开发代理做产品的人。读完可以直接改造自己的仓库，让原型、需求和最终界面沿着同一条版本记录前进。

## 把功能需求先变成可看的界面

最初的做法很简单。第一版先用 Claude Design 产出 UI 原型，打磨后保存到本地，再配合 Baoyu-Design Skill 维护。

当我要增加一个功能时，不再直接让开发代理修改正式代码，而是让它先动原型。比如增加一个筛选入口，原型阶段要先回答入口放在哪里、默认状态是什么、空状态怎么处理、操作后页面如何反馈。

这些决定只停留在需求文字里时，很容易被不同的人理解成不同版本。变成可运行的 React 原型后，讨论对象就具体了。哪里别扭，打开页面就能看到，修改成本也远低于功能完成以后再推翻。

这里有个很现实的问题。生成式设计不会自动带来好设计，不懂交互的人仍然可能难以描述自己想要什么。我的处理方式不是把判断交给 Skill，而是把任务缩小到一条用户路径，逐个确认入口、过程、结果和异常状态。

## 让 Git 记录每一次设计决定

这条链路真正变得稳定，是在原型进入 Git 之后。

Claude Design 的产出包含 React 代码和结构化 JSON 数据。每次调整原型，Git 都会留下清晰的差异。新增了哪个组件，删除了哪个状态，字段结构如何变化，不再依赖会议记忆或聊天记录。

我会把一次功能修改拆成一条连续的场景链。

需求进入仓库 → 原型发生变化 → git diff 审阅变化 → 确认交互 → 正式功能实现 → 对照原型验收

这样做以后，diff 不只是代码审查材料，也成了设计审查材料。它把一句模糊的“这里再优化一下”，压成了可以逐行确认的变更。

评论里有人把同样的方法用在策略参数调整上，先在测试环境做对比，看清 diff 后再进入正式环境。他提到，过去八个月里曾因图省事直接修改而踩过三次坑。场景不同，教训却一致，可视化差异省掉的时间，通常会在返工时加倍还回来。

## 让开发代理沿着已确认的变化实现

原型确认后，我才让开发代理修改正式功能。此时它拿到的不再是一句抽象需求，而是现有界面、目标界面和两者之间的差异。

这会明显缩小代理需要猜测的空间。它可以参考原型组件结构，也可以顺着 diff 判断哪些交互被新增、哪些状态被调整。开发任务从“替我设计并实现”，变成“按已经确认的设计完成实现”。

后来，这套顺序被写进 AGENTS.md 或 CLAUDE.md。只要提出修改或增加功能，默认动作就是先更新原型，等待确认后再进入功能代码。规则进入仓库后，它不再依赖我每次提醒，原型与实际功能也更容易保持同步。

我的判断是，开发代理越快，这道闸门越重要。代理可以很快写出一套完整实现，但如果方向没有确认，速度只会让错误扩散到更多文件。

## 看交付物到底发生了什么变化

过去，一项功能的交付物通常只有需求描述和最终代码。设计判断散落在聊天、截图和临时决定里，很难追溯为什么这样做。

采用这条链路后，交付物变成了四个彼此对应的部分。

需求描述负责说明目标，React 原型负责呈现交互，Git diff 负责记录变化，正式代码负责交付能力。任何一环发生调整，都能回到仓库里找到依据。

这也改变了评审方式。团队不必等功能全部完成才发现流程不顺，可以在原型阶段讨论产品，在 diff 阶段确认变化，在实现阶段关注工程质量。不同问题被放回了成本更低的位置。

它并不能消除所有返工。数据约束、性能问题和真实用户行为仍可能迫使设计调整。但至少可以减少一类很常见的浪费，界面还没想清楚，代码已经铺开了。

## 用一个真实需求改造现有仓库

挑一个近期准备增加的界面功能，不要直接进入正式组件。先在仓库里建立可运行的 React 原型，让开发代理完成一次设计修改，再审阅 `git diff`。

确认入口、状态和反馈都符合预期后，把这次差异交给开发代理实现。验收时同时打开原型和正式界面，检查两边是否仍然一致。

如果这条路径跑通，再把“先更新原型、确认后实现”写进 AGENTS.md 或 CLAUDE.md。真正值得固化的不是某个设计工具，而是这条顺序，先让设计成为可审阅的版本，再让代码成为它的实现。
