# 本地模型也要关工具权限：llama.cpp 新增 Docker 隔离后该怎么用

本地运行模型，不等于工具调用天然安全。只要模型能够读写文件、执行命令，错误参数和越权操作就可能直接落到宿主机上。

llama.cpp 的 b10328 版本加入了初步的 Docker 工具隔离支持。对正在搭建本地 Agent 的人，这次更新最实用的价值，是把模型推理和工具执行拆成两个不同的权限区域。

我会把它当成一道新的上线门槛。启用之前，至少要确认挂载目录、容器权限，以及工具输入输出边界。否则只是把命令搬进容器，风险并没有真正关住。

## 找出模型能够碰到的资源

我审查本地 Agent 时，第一件事不是看模型参数，而是列出工具可以接触的资源。

文件工具能读哪里，能写哪里，命令工具由谁启动，容器能否访问宿主机服务，这些问题比模型是不是在本地更重要。模型只负责生成调用意图，真正改变系统状态的是工具执行层。

一个常见失效路径是，应用把整个项目目录挂进容器，并开放读写权限。模型原本只需要修改临时文件，却也能覆盖配置、密钥引用或构建脚本。Docker 隔离仍然存在，但授权范围已经大到失去意义。

我会按下面这组对象逐项确认。

- 输入目录，只挂载任务真正需要读取的文件
- 输出目录，与源码、配置和凭据目录分开
- 临时目录，允许任务写入，并在任务结束后清理
- 网络入口，没有明确需求时不向工具容器开放
- 宿主机接口，不挂载 Docker socket 或其他高权限控制接口
- 凭据来源，不把无关环境变量和密钥传入容器

## 沿着一次错误调用检查失效路径

隔离设计不能只验证正常任务。我更关心模型给出错误工具参数时，系统会发生什么。

例如文件工具收到 `../../` 一类越界路径，命令工具拿到额外参数，或者工具输出包含超长内容和敏感文件片段。单靠提示词要求模型谨慎，挡不住解析差异、提示注入或模型误判。

风险链条通常是这样的。

模型生成工具参数，服务端完成解析，Docker 内的工具开始执行，挂载目录或网络权限放大影响，执行结果再被送回模型。任何一环缺少约束，都可能让一次普通错误变成持续性的文件修改或信息暴露。

b10328 的发布记录显示，这项能力仍是初始支持，并涉及工具输入输出隔离与 Docker 运行方式的区分。我的判断是，现在适合建立验证基线，不适合看到“Docker”几个字就默认已经获得完整安全边界。

## 把控制点放在模型之外

真正有效的控制应该由服务端和容器配置执行，而不是依赖模型自觉。

目录权限要用只读挂载和独立输出目录落实。命令范围要在工具定义或执行入口收紧。工具参数要经过结构化校验，拒绝未声明字段、越界路径和不符合预期的参数组合。

输出同样需要控制。工具返回内容应设置大小上限，区分标准输出与错误输出，并在送回模型前处理密钥、令牌和本地路径等敏感信息。容器退出码、超时和被拒绝原因则要进入日志，方便判断问题来自模型、工具还是隔离策略。

容器自身还应遵循最小权限原则。

- 使用非特权用户运行工具
- 只开放任务需要的文件系统权限
- 设置执行超时、内存和进程数量限制
- 明确是否允许网络访问
- 使用一次性容器或可清理的任务环境
- 保留拒绝记录，但不在日志中泄露敏感内容

## 用越权任务做上线前验证

我不会用“成功读取一个文件”作为验收。更有价值的测试，是故意让工具尝试触碰边界。

准备一个不含真实凭据的测试目录，放入允许读取、允许写入和禁止访问的样本文件。然后让工具分别执行正常读写、路径穿越、访问未挂载目录、超时命令、超大输出和受限网络请求。

上线前至少确认这些结果。

- 允许读取的文件可以正常读取
- 输出只能写入指定目录
- 路径穿越和符号链接绕行会被拒绝
- 未声明的命令或参数不会执行
- 超时任务能够被终止，不残留后台进程
- 超大输出会被截断或拒绝
- 工具失败不会自动扩大权限重试
- 日志能够定位失败环节，又不会记录凭据内容

先用一个低风险工具跑完这组验证，再考虑扩大工具集合。每增加一个挂载目录、网络入口或命令能力，都应重新检查权限边界。

本地模型解决的是数据和推理部署位置，工具隔离解决的是执行权限。两者不是同一件事。b10328 提供了一个值得验证的新控制层，而真正决定安全性的，仍是你给容器开了哪些门。
