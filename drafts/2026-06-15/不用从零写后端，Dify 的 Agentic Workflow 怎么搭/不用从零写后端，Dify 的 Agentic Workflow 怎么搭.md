# 不用从零写后端，Dify 的 Agentic Workflow 怎么搭

如果你是小团队，手里最常见的不是“做一个宏大 Agent 平台”，而是三个很碎的需求，客服问答、资料整理、内部问答。它们共同点很烦，数据散、流程变、后端排期永远不够。

Dify 值得看，不是因为它把 Agentic Workflow 这个词讲得多新，而是它把低代码工作流、知识库检索、MCP 工具和模型接入放到同一个可视化平台里。对小团队来说，这更像一个先交付原型再逐步加固的工作台。

信息来自仓库和官方文档，更稳的起点是按下面这套路线搭，先让业务跑起来，再决定哪里值得写代码。

## 先选一个最小场景

不要一上来做“公司级智能助理”。我会先从三类场景里选一个入口。

- 客服问答，适合 FAQ 稳定、人工重复回复多、答案需要引用资料的团队
- 资料整理，适合会议纪要、产品文档、客户材料堆在不同目录里的团队
- 内部问答，适合新人反复问制度、接口、项目背景的团队

这三个场景都能用 Dify 的同一套组合，工作流负责步骤，知识库负责上下文，模型负责理解和生成，MCP 负责把外部数据和工具接进来。差别只在于，客服更重回答边界，资料整理更重结构化输出，内部问答更重权限和来源可追溯。

我的判断很简单，先别追求“全自动”。先把一个固定问题链路做稳，例如用户提问、检索知识库、判断是否需要调用工具、生成回答、人工复核。

## 把流程拆成能看见的节点

Dify 的官方定位是开源的 agentic workflow 开发平台，可以用可视化方式定义流程，接入已有工具和数据源，并部署应用。仓库信息里也能看到它围绕 low-code、workflow、RAG、MCP、model orchestration 这些方向展开。

小团队真正省时间的点在这里，不用先搭一整套后端服务，再写队列、状态机、日志面板。你可以先在工作流里把业务动作画出来。

可收藏的搭法是这样。

- 输入节点，接收用户问题或待处理资料
- 知识库检索，查 FAQ、产品文档、内部手册
- 条件判断，判断能否直接回答，还是进入人工复核
- 工具调用，通过 MCP 或内置工具拿最新数据
- 模型生成，把检索结果和工具返回压成可读答案
- 输出节点，给用户、客服台或内部系统返回结果

客服场景里，输出要短，最好带来源。资料整理场景里，输出要固定格式。内部问答场景里，回答不确定时宁可提示去看原始文档，不要装作知道。

## 知识库别一上来全量导入

RAG 最容易被高估。很多团队会把所有文档一次性丢进去，然后期待它变成“公司大脑”。结果往往是，检索命中文档很多，答案却不稳定。

Dify 文档里提到，知识库可以作为信息源挂到应用里，增强模型的上下文理解，也支持通过 API 从文本创建文档，并选择索引方式、文档形态和处理规则。这个能力够用，但前提是你要先整理边界。

我会这样处理三类材料。

- 客服 FAQ，先放高频问题和标准答案，不放历史聊天大杂烩
- 资料整理，先放模板和少量样例，不把所有原始文件混在一起
- 内部问答，先放制度、接口说明、项目 README，暂缓放口径未定的草稿

这里最容易踩坑的不是技术，而是资料治理。知识库不是垃圾桶。文档越乱，工作流越像一个很会说话但不可靠的实习生。

## 需要外部动作时再接 MCP

MCP 的价值是把外部工具和数据源变成 AI 应用可调用的接口。Dify 文档里写到，它可以连接 MCP server，把数据库、文件系统等外部资源作为工具导入，并支持使用 HTTP transport 的 MCP server。Dify 也支持把应用发布成 MCP server，让其他助手或开发环境调用。

这对小团队的启发是，别把 Agent 只理解成聊天框。它更像一条有工具权限的业务链路。

客服场景可以接订单或工单查询。资料整理可以接文件系统或文档库。内部问答可以接项目资料和已有应用。公开文档能支撑的边界是，Dify 提供 MCP 工具接入和发布能力，具体能接哪些系统，要看你自己的 MCP server 和权限设计。

我的建议是，只有当“回答必须依赖实时数据”时再接 MCP。静态资料能用知识库解决，就别急着把工具链搞复杂。

## 模型接入先按任务分层

Dify 文档里有模型 provider 的开发说明，包含调用、流式返回、凭证校验、token 计算和错误映射等能力。对普通小团队来说，重点不是立刻开发一个新 provider，而是先把模型选择放进工作流设计里。

我会按任务拆模型。

- 分类判断，用便宜、响应快的模型
- 知识库问答，用稳定、上下文能力足够的模型
- 长文整理，用更擅长结构化和长上下文的模型
- 高风险输出，加人工复核，不把决定权完全交给模型

低代码不是不写代码，而是把代码留给最该写的地方。比如企业权限、数据清洗、专用 MCP server、内部系统回写，这些才是工程团队应该投入的部分。

## 把最小版本交付出来

如果只想先做一个能演示的版本，我会按这个顺序走。

1. 打开 Dify 仓库和官方文档，确认部署方式、应用类型和知识库入口
2. 选一个场景，只做客服、资料整理、内部问答里的一个
3. 准备 20 条真实问题和对应资料，不要超过一个业务范围
4. 搭一个最短工作流，输入、知识库检索、模型生成、输出
5. 给每个回答加“不确定就返回原文入口”的规则
6. 只有遇到实时数据需求，再考虑接 MCP server
7. 找 3 个同事试问，把答错的问题回收到资料和流程里

交付形态也别想复杂。客服可以先是内部客服助手。资料整理可以先是固定模板生成器。内部问答可以先是新人问答入口。能被一个团队每天用起来，比功能图画得漂亮更重要。

我的最终判断是，Dify 适合小团队做“业务流里的 Agent”，不适合一开始就拿来幻想通用智能员工。先让它在一个窄场景里稳定减少重复劳动，后面再慢慢加工具、加权限、加观测。

本文为 AI 辅助整理，关键事实已按公开来源核对。下一步别收藏完就停，先拿一个业务问题做最短链路，跑不稳的地方，就是你真正需要工程投入的地方。
