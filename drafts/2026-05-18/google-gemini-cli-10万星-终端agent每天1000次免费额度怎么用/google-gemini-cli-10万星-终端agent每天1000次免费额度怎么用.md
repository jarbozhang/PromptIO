# Google Gemini CLI 10 万星 终端 agent 每天 1000 次免费额度怎么用

Google Gemini CLI 已经不是小工具了。

今天补充源里，google-gemini/gemini-cli 显示 10 万多 stars、1.3 万多 forks。README 写得很直接，个人 Google 账号有免费档，60 requests/min、1000 requests/day，支持 Gemini 3 和 1M context，可以通过 npx、npm 或 brew 安装。

AI 编程工具这个主题已经很拥挤，但 Gemini CLI 仍然值得单独写。原因不是它一定比 Claude Code 或 Codex 更强，而是 Google 品牌、免费额度和终端 agent 这三件事放在一起，对开发者很实用。

## 免费额度该花在哪里

每天 1000 次请求听起来很多，但如果你让 agent 长时间乱跑，也很快会被消耗掉。

我更建议把 Gemini CLI 放在“低风险、高频、可验证”的任务里。

第一，读仓库。让它总结目录结构、入口文件、测试命令、配置文件和主要模块。

第二，写脚本。比如日志清洗、文件批处理、Markdown 格式整理、简单 API 调用样例。

第三，改文档。README、安装步骤、CLI 帮助文案、错误提示，这些任务验证成本低。

第四，做二次检查。你已经写完代码后，让它从另一个角度看边界条件、异常处理和测试缺口。

这些任务不需要它掌管整个项目，但可以帮你省下很多重复劳动。

## 不要把它当唯一主力

last30days 拉到的社区反馈很混合。

有人在 Antigravity 终端里大量使用 Gemini CLI，觉得 CLI 足够处理很多任务。也有付费用户抱怨它长期不可用、响应慢、输出不稳定。还有人把 Claude Code、Codex、Gemini CLI、OpenCode 放在一起横向比较，讨论工作流可迁移性。

这组反馈很重要。它提醒我们，Gemini CLI 的正确位置不是“唯一主力”，而是一个便宜、方便、可随时切入的终端 agent。

如果你已经有 Claude Code 或 Codex，Gemini CLI 可以承担外围任务。比如先让它读文档、查重复、整理 issue、生成初稿，再把关键修改交给你更信任的工具。

## 怎么安排一天 1000 次

我的分配会很简单。

上午用它读项目和整理计划。把一个陌生仓库丢给它，让它给出模块地图、运行方式和风险点。

下午用它做批量小任务。比如给 20 个脚本补使用说明，给一组 Markdown 统一格式，给测试失败日志做摘要。

晚上用它做复盘。把今天的 diff、测试输出、错误日志交给它，让它列出明天该查的 5 个问题。

这样用，1000 次额度不会被浪费在漫无目的的聊天里。

## 需要避开的任务

不要让免费 CLI 处理高风险改动，比如数据库迁移、权限逻辑、支付流程、生产配置和密钥相关文件。

不要把私密数据直接丢进去。终端工具很顺手，越顺手越容易忘记数据边界。

不要把模型输出当测试。agent 说通过不算通过，最终还是要跑项目自己的测试、lint 和人工审阅。

## 我的判断

Gemini CLI 的意义，是把 Google 模型变成一个低成本的终端工位。

它不需要在每个复杂任务上赢过 Claude Code 或 Codex。只要它在读仓库、写小脚本、整理文档和二次检查上足够便宜、足够快，它就有位置。

如果你今天要试，别先让它重构整个项目。先在一个非核心仓库里跑三件事，生成项目地图、修一段文档、总结一次测试失败。能稳定交付这些，再把它放进日常工具箱。
