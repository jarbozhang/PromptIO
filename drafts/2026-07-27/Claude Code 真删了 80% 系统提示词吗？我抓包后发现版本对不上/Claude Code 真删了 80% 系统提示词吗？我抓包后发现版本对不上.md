# Claude Code 真删了 80% 系统提示词吗？我抓包后发现版本对不上

如果你在用 Claude Code，那个“系统提示词删掉 80%”的说法先别急着变成配置结论。

真正影响你判断的，不只是删了多少，而是哪一代开始删、什么模型会走短提示词，以及工具描述还占着多少上下文。把版本和路由条件拆开后，我发现一句正确的话，也可能让人得出错误的操作建议。

读完这篇，你可以用一个本地 HTTP 服务复现抓包，再决定要不要打开 `CLAUDE_CODE_SIMPLE_SYSTEM_PROMPT=1`。至于响应速度和代码风格，现有数字还不够下结论，需要单独做对照测试。

## 误解不在 80%，而在版本归因

抓包记录里的三组数字很直观。

Opus 4.7 收到 15,225 个字符，Opus 4.8 收到 4,467 个字符，Opus 5 收到 7,694 个字符。

只看首尾，很容易说成 Opus 5 把系统提示词缩短了 80%。可真正发生大幅缩减的是 4.7 到 4.8。到了 Opus 5，系统提示词反而比 4.8 增加约 72%。

80% 也不是凭空来的。只计算手写策略正文，旧路径有 12,443 个字符，新路径有 2,308 个字符，降幅约 81%。被移除的内容包括任务执行、谨慎操作、文本输出、工具使用和语气风格等大段规则，随后被一节只有五条规则的 `Harness` 取代。

所以我会把原说法改得更准确一些。Claude Code 确实准备了一套缩短约 80% 的提示词，但切换早在 4.8 路径上发生，Opus 5 又针对新问题补回了规则。

## 模型越强，越不需要规则吗

这个推论也不完整。

短提示词把一整套注释规范压成了一句，让生成代码贴近现有项目的注释密度、命名和惯用写法。它不再逐项规定模型该怎么做，而是要求模型读取周围代码，自行适配。

但 Opus 5 随后新增了 `Delivering work` 和 `Corrections`，合计约 3,755 个字符。这两段在 Claude Code 2.1.215 和 2.1.216 中还不存在，到 2.1.220 才通过仅面向 Opus 5 的能力开关加入。

其中 `Corrections` 处理的是一个很具体的问题。模型可能长篇标记并解释自己先前的错误，让用户看到的过程显得反复。模型能力变了，产品里的失效方式也跟着变，系统提示词便成了按模型附加的小块补丁。

我的判断是，强模型减少的是通用行为说明，不是产品约束。Agent 团队真正该做的，不是一次性删光规则，而是区分哪些规则仍在约束产品体验，哪些只是替旧模型兜底。

## 抓到请求，才能知道自己走了哪条路

Claude Code 会同时携带长短两套提示词，再根据模型标识和提供方选择路径。判定里存在硬编码的子串与型号名单，未被识别的模型标识可能回到约 15K 字符的旧提示词。

使用 Bedrock、Vertex 或自定义 base URL 时也不能只看模型名称，因为路由还会检查提供方。配置里写着新模型，不等于请求一定拿到短提示词。

复现路径并不复杂。

1. 在本地启动一个最小 HTTP 服务，保存收到的请求体。
2. 服务收到请求后直接返回 400，不必真的调用模型。
3. 把 `ANTHROPIC_BASE_URL` 指向这个本地地址。
4. 执行 `claude -p "hi" --model 模型id`。
5. 从请求体中分别提取 system prompt 和 tools，再按同一口径比较字符数。

如果想强制验证短提示词，可以设置 `CLAUDE_CODE_SIMPLE_SYSTEM_PROMPT=1`。来源记录显示，在 Opus 4.5 上打开它后，收到的内容与 4.8 默认路径几乎逐字相同，仅模型名和知识截止日期不同。

## 别用字符数替响应速度下结论

系统提示词缩短，不等于总上下文按同样比例下降。同一个分流开关还会改变工具描述，其字符数从 53,328 降到 37,167。工具定义仍然比系统提示词大得多。

因此，看到 81% 就推导出明显提速或成本同步下降，并不严谨。字符数也不能直接替代 token 数，更不能替代首 token 延迟和完整任务耗时。

我会把验证拆成三个观察面。

固定模型、仓库、任务和会话状态，分别运行默认配置与短提示词配置。记录输入 token、首 token 延迟和总耗时，判断上下文成本与响应速度。再选同一个小型改动，检查注释密度、命名方式、改动范围以及是否贴合现有代码，判断代码风格有没有漂移。

每组至少重复几次，避免把网络波动或缓存差异当成提示词效果。现有源材料给出了字符差异和路由机制，没有提供这三项对照结果，因此不能提前写成性能收益。

## 该调整的不是一个开关，而是判断方法

如果你维护自己的 Agent，最值得复用的不是“删掉 80%”这个数字，而是逐条撤掉历史规则，再用固定任务观察行为是否退化。

先抓一次真实请求，确认模型最终拿到的是哪套提示词。然后只改变 `CLAUDE_CODE_SIMPLE_SYSTEM_PROMPT`，用相同任务比较 token、延迟和代码差异。没有稳定收益，就保留默认配置，不必为了提示词更短而更短。

系统提示词不是越少越先进。更准确的目标，是只留下当前模型仍然需要、产品又能验证其价值的约束。
