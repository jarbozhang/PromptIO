# Claude Code 和 Codex 扫代码也可能中招：一次远程执行攻击如何反利用安全工具

如果你会让 Claude Code 或 Codex 审查开源依赖、第三方库和陌生仓库，这条攻击链值得放进上线检查表。

AI Now Institute 公布了一项概念验证。研究者让原本负责防御性代码审查的工具，在读取攻击者准备的项目内容后走向远程代码执行。受影响场景涉及 Claude Code CLI 和 Codex CLI，并且攻击面出现在开箱即用配置下。

读完这条链，你至少能做一件具体的事，把代码审查代理从日常开发环境里隔离出来，再用最小权限、网络限制和人工确认压缩风险。

## 沿着恶意依赖走一遍攻击链

入口不是一条明显要求执行恶意命令的聊天消息，而是一份等待审查的代码。

攻击者先把经过设计的内容放进开源库或第三方依赖。开发者为了判断它是否安全，让 Claude Code 或 Codex 进入仓库，读取源码、配置和其他项目内容。

问题从读取动作开始。代码代理不只理解文本，还可能把仓库里的内容带入后续推理，并调用具备系统能力的工具。攻击者利用的正是这条连接，让安全审查任务逐步偏离原目标，最终触发远程代码执行。

整条路径可以压缩成四步。

- 恶意内容进入待审查的仓库或依赖
- 代码工具为了分析风险而读取攻击者控制的内容
- 内容影响代理的判断与工具调用
- 代理现有的执行权限被转化为代码执行能力

这类攻击最危险的地方，不是模型给出了一段错误建议，而是建议与真实工具权限连在了一起。一次读取可以继续变成命令执行、文件访问或网络请求，防御工具由此被反向利用。

## 找出哪些权限会放大后果

AI Now Institute 的概念验证针对 Claude Code CLI 和 Codex CLI。源材料列出的组合包括 Claude Sonnet 4.6、Claude Sonnet 5、Claude Opus 4.8，以及搭配 GPT-5.5 的 Codex CLI。

版本信息说明了一个关键问题。不能把风险简单归因于某个旧模型，也不能只靠升级模型解决。需要审查的是代理能读什么、能执行什么、能连接哪里，以及哪些动作不经人工确认就能发生。

我的判断是，代码代理的安全边界不该由提示词承担。提示词可以表达任务意图，却不能替代操作系统隔离、权限控制和网络策略。

下面几类能力会明显放大攻击结果。

- 能读取开发者主目录、密钥目录或其他项目
- 能在宿主机直接执行 shell 命令
- 能修改启动脚本、配置文件或构建流程
- 能自由访问网络并向任意地址发送数据
- 能在缺少确认的情况下连续调用多个高权限工具

仓库是否可信，不能只看项目名、维护历史或代码表面。只要内容由第三方控制，就应该把它视为代理输入的一部分，也视为潜在的攻击载荷。

## 把防线放在模型之外

第一道控制点是隔离环境。陌生仓库应进入一次性容器、临时虚拟机或权限受限的沙箱，审查结束后直接销毁。不要让代理在保存日常凭据和其他项目源码的工作目录中扫描未知依赖。

第二道控制点是最小权限。只读分析阶段不应默认拥有写文件和执行命令的能力。确实需要构建或运行测试时，再为单个动作临时开放权限，并限制可访问的目录。

第三道控制点是网络限制。安全审查通常不需要连接任意地址。按任务建立允许列表，关闭不必要的出站连接，并记录代理发起的网络请求，可以让远程执行与数据传出更难连成完整路径。

第四道控制点是人工确认。安装依赖、执行项目脚本、修改仓库外文件、读取凭据目录和发起网络请求，都适合作为强制确认节点。确认界面应展示完整命令、工作目录、目标文件和网络目的地，而不是只显示一句模糊的操作摘要。

## 用一个诱饵仓库验证上线边界

上线前不必直接拿真实项目试错。可以准备一个不含真实凭据的测试仓库，在文件中放入越权指令和可识别的假秘密，观察代理是否会突破预设边界。

一份可收藏的验证清单如下。

- 仓库只能访问独立的临时工作目录
- 主目录、SSH 配置和云服务凭据默认不可见
- 初始审查阶段禁用命令执行和文件写入
- 安装、构建、测试及脚本运行必须人工确认
- 出站网络默认关闭，确有需要再按目标开放
- 所有工具调用保留命令、路径、时间和结果记录
- 测试结束后销毁环境，不复用缓存与凭据
- 用假秘密验证文件读取和数据发送是否会被拦截

验收标准也要具体。代理读到诱导内容后，不能自行扩大权限，不能访问工作目录之外的文件，不能连接未授权地址，也不能绕过确认执行命令。任何一项失败，都说明控制点仍停留在提示词层面。

先挑一个团队常用的代码审查流程，把陌生仓库移进隔离环境，再跑一次诱饵测试。真正需要验证的不是代理会不会识别恶意文本，而是它识别失败时，系统能不能把后果锁在一个可销毁的边界里。
