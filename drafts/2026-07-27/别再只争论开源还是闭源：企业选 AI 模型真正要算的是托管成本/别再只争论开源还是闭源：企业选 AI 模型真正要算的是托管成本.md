# 别再只争论开源还是闭源：企业选 AI 模型真正要算的是托管成本

如果你的团队正在选企业 AI 模型，我建议暂时放下开源还是闭源的争论。采购前更该回答的问题是，你们究竟要购买托管服务，还是接手一套训练、推理与安全基础设施。

这个视角会直接改变预算表。模型权重只是其中一项，真正持续消耗资源的还有微调软件、推理服务、GPU、存储、安全、可靠性和运维团队。

我会把这次选型写成一份取舍备忘录。目标不是选出抽象意义上更好的模型，而是确认哪些责任值得自己承担，哪些责任交给服务商更划算。

## 把争论改写成一项经营决策

开源模型的价值很明确。企业可以在模型之上继续训练，把自己的数据与行业知识带进去，也能保留更强的控制权。开放研究、数据与权重还会增加竞争，推动市场提供更多选择。

但拿到开放权重，并不等于拿到一套可以稳定服务客户的系统。

继续训练需要相应的软件和服务，部署阶段还需要推理框架。源材料提到了 Tinker 一类训练服务和 SGLang 一类推理软件，而且这条链路上的组件并非全部开源。

因此，我不会再问团队是否想拥有模型，而会问一个更具体的问题，我们是否愿意拥有模型运行所需的全部责任。

## 判断定制价值能否覆盖整条链路

第一个维度是微调带来的业务价值。

如果企业数据和领域知识能形成明显差异，额外训练就可能值得投入。此时，模型选择不能停在权重许可证，还要继续追问训练工具由谁提供、数据如何进入训练流程、训练后的模型如何评估，以及谁负责把它部署成稳定服务。

这里容易出现一种错觉。团队以为选择开放权重是在减少依赖，实际却可能把依赖从模型 API 转移到训练平台、推理框架、硬件供应和内部工程能力上。

我的判断很直接。只有当定制能力会持续影响产品竞争力时，企业才有充分理由接住这条更长的链路。若需求只是调用通用智能完成摘要、分类或内容处理，API 价格未必是浪费，它也购买了大量被隐藏起来的工程工作。

## 把 GPU 和存储放回同一张成本表

第二个维度是基础设施的总拥有成本。

训练完成后，模型还要面向客户提供推理服务。企业可以与推理服务商合作，也可以控制自己的硬件和存储。但如果控制权是最初选择开放权重的主要原因，那么把运行环节完全交给第三方，可能仍然无法满足目标。

选择自建，就要继续处理 GPU 容量、存储、部署、扩缩容、故障恢复和资源利用率。成本不只来自购买或租用硬件，还来自长期维护，以及能否招到合适的人。

我更关心的是利用率而不是单次报价。托管 API 把一部分固定成本变成按使用付费，自建则可能在稳定且足够大的负载下体现价值。没有真实业务负载，单独比较每百万 token 或单张 GPU 的数字，很容易得到一份精确但无用的结论。

## 决定谁对安全与可用性负责

第三个维度是责任归属。

模型进入客户流程后，可用性和可靠性会变成业务问题。自建团队不仅要让服务跑起来，还要处理安全、容量和持续维护。能力更强的开放模型也需要更审慎的部署方式，安全栈不能被当成上线前才补的附件。

托管服务的价值之一，就是由供应方承担一部分运行责任。企业付出的代价则是控制范围受限，并接受对方提供的接口、服务能力和商业条件。

这不是技术信仰题，而是责任分配题。真正需要写进采购材料的，不只是模型指标，还包括故障由谁响应、数据和存储由谁控制、GPU 容量由谁保障、安全措施由谁维护。

## 哪些团队适合自建，哪些更适合托管

适合自建的团队，通常把模型能力当作产品核心，拥有能形成差异的数据与知识，也愿意长期建设训练和推理团队。它们需要更强的硬件、存储与部署控制，并能承担可靠性和安全责任。

更适合托管服务的团队，往往需要尽快把智能能力接入业务，不想配置专门的训练和推理团队，也愿意用 API 费用交换交付速度与较少的运维负担。

还有一类团队适合混合路径。关键数据和定制训练保留较强控制，通用任务继续使用托管能力。不过，混合方案不会自动降低复杂度，它只是把责任切成了不同区块，接口、数据流与故障边界仍要写清楚。

## 我的选择是先买服务，再用证据争取自建

如果业务还没有稳定负载，也没有证明微调能创造持续差异，我会先选托管服务。这样做不是否定开放模型，而是避免在需求尚未成立时，提前组建训练、推理和运维体系。

当调用规模、数据控制或定制收益开始成为明确约束，我才会重新计算自建。届时拿来决策的应是实际负载、可靠性目标、人员成本和控制要求，而不是对开源或闭源的偏好。

采购会前，我建议把原来的模型对比表增加六列，微调、推理、GPU、存储、安全、运维。每一列只回答两件事，谁负责，失败后谁处理。填不清这十二个答案，就还没有算清企业 AI 的真正成本。
