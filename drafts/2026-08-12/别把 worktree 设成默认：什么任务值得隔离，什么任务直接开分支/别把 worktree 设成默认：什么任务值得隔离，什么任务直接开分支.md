# 别把 worktree 设成默认：什么任务值得隔离，什么任务直接开分支

Agent 能并行写代码之后，很多团队顺手把 worktree 设成了默认。每个任务一份目录，互不干扰，看起来很整洁。

代价也很具体。仓库多复制一份，依赖可能重新安装，服务需要占用新的端口，测试环境也要重新准备。任务只改两三个文件时，隔离成本甚至高于开发成本。

真正要决定的不是 worktree 好不好，而是这个任务值不值得拥有一套独立工作区。判断时看四件事就够了，任务时长、文件重叠、依赖体积和并行启动成本。

## 判断任务会占住工作区多久

宝玉分享的选择很明确。普通任务用分支，或者直接在当前分支并行处理。worktree 主要留给耗时较长的 PoC，验证期间还要继续做其他工作，结束后就删除目录。

这个边界比一刀切更实用。

一个十几分钟就能收尾的小修改，即使单独建 worktree，也很难收回创建目录、准备依赖、同步配置和清理现场的成本。长时间 PoC 则不同，它可能反复试验、修改配置，甚至几小时都不适合合回主线。此时隔离能避免探索代码长期占住当前目录。

任务时长不是精确计时，而是在判断它会不会形成一段独立生命周期。需要多轮试错、可能随时推倒重来的任务，更适合 worktree。能快速提交或丢弃的任务，分支通常已经够用。

## 估算文件重叠，而不是只数任务数量

两个 Agent 同时工作，不等于一定会冲突。一个修改支付模块，另一个补文档，文件交集很小，共用当前目录未必有问题。

反过来，如果两个任务都要改依赖清单、数据库结构、核心配置或同一批入口文件，冲突概率会明显上升。即使代码能自动合并，测试结果和运行状态也可能互相覆盖。

原帖提到，Claude Code、Codex 这类编码 Harness 遇到冲突时，可以等待另一个任务完成后再继续。这能缓解部分并发写入问题，但等待只能处理显性冲突，不能替你识别共享配置、端口和生成文件之间的隐藏耦合。

因此，worktree 应该优先服务高重叠任务，而不是服务所有并行任务。任务数量只是表象，修改范围才决定隔离价值。

## 把依赖和启动成本算进决策

讨论中最具体的反对意见来自一个 monorepo 场景。把 worktree 设为默认后，各目录中的依赖需要重新准备，时间和磁盘占用都很可观，最终又改回当前仓库优先。

另一种经验则指出，使用 pnpm 硬链接可以降低空间占用。两种反馈并不矛盾，它们说明 worktree 的成本高度依赖项目结构和工具链。

依赖很轻、启动脚本已经支持自动分配端口、测试数据互不影响时，多一份 worktree 的成本有限。大型 monorepo、多个本地服务、重型构建缓存和复杂环境配置，则会把一次目录隔离放大成一套环境复制。

所以，创建 worktree 前要问的不是还能不能多开一个，而是新工作区能否低成本启动并独立验收。如果答案不明确，默认隔离往往只是把代码冲突换成环境维护。

## 分清谁适合隔离，谁适合留在当前目录

适合使用 worktree 的，是耗时较长的 PoC、高文件重叠任务、需要独立运行和测试的改动，以及明确采用一个工作区对应一个 PR 的团队流程。这些任务从隔离中获得的稳定性，通常能覆盖准备成本。

不适合默认使用 worktree 的，是短时修复、文档调整、互不相干的模块修改，以及依赖庞大却没有共享缓存和自动启动能力的项目。此时直接使用当前目录或普通分支，更省时间，也减少无效磁盘占用。

还有一种容易忽略的情况。手里本来就有多个独立项目可并行推进，就不必为了同时做事，强行在同一个仓库里制造多套工作区。

## 我的选择是让隔离成为升级选项

我会把当前目录或普通分支作为默认路径。只有任务预计持续较久、修改范围明显重叠，或者必须维持独立运行状态时，才升级到 worktree。

这个选择承认 worktree 的价值，但不给它免成本待遇。隔离不是免费的安全感，它需要依赖复用、端口管理、测试环境和清理机制共同支撑。

可以从最近三个并行任务开始复盘。记录它们持续多久、是否改过同一批文件、是否重复安装依赖、是否需要同时启动。若多数任务都短且低重叠，就保留当前目录优先。若等待和互相覆盖已经影响交付，再把高冲突任务迁到 worktree。

让任务证明自己需要隔离，比让每个任务先承担隔离成本更合理。
