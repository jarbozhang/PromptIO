# Codex Code Review 从 58% 到 98%：真正该写进 AGENTS.md 的不是代码规范

如果你的团队已经用 Codex 写代码，却仍靠资深工程师守住那些不能改的字段、不能记录的数据和看似奇怪的旧设计，这份参考卡值得直接放进仓库改造计划。

带规则的 Codex Code Review，在包含已知规则违规和安全反例的评测集中召回了 98% 的目标 finding，基线是 58.3%。真正拉开差距的不是多写一份代码规范，而是让模型知道哪些改动看似正常，实际会产生隐蔽后果。

读完你可以做一件具体的事，把一次历史缺陷改写成有作用域的 AGENTS.md 规则，再用三个对照改动检查它是否真的提升审查质量。

## 判断一条知识是否该进入 AGENTS.md

我会先问一个问题，这条规则如果删掉，会不会改变一次真实的审查结论。

如果答案是否定的，它多半只是风格偏好。格式、命名形式、机械约束和能够稳定编码的检查，继续交给测试、linter 和 CI。让模型重复做确定性工具擅长的事，只会增加噪音。

适合写进 AGENTS.md 的知识通常同时满足三个条件。

- 改动能通过编译或常规测试，却可能造成实际后果
- 判断依赖仓库历史、集成关系或数据边界
- reviewer 已经在不同 PR 里反复解释过

我认为，AGENTS.md 更像一份审查契约，而不是另一份代码风格手册。它负责保存只有熟悉仓库的人才知道的判断依据。

## 用三个例子改写隐性知识

第一类是兼容性契约。

Codex app-server 有一个标记为 experimental 的内部通知 `rawResponseItem/completed`，但 Codex Cloud 已经在消费它。把 wire name 从 `completed` 改成 `done`，编译可能通过，diff 也像普通清理，下游却会静默失联。

这种规则不能只写成“禁止改名”。更有效的表达应该包含受保护的集成面、改动后果和安全路径，例如保留旧名称，或者增加向后兼容的新事件。

第二类是数据边界。

源材料给出的典型起点是客户数据不能进入日志。这类约束不能只靠“谨慎处理数据”这种宽泛提醒。规则需要限定到实际处理相关数据的目录，并说明审查时要关注数据是否跨过日志边界。

第三类是历史设计约束。

仓库里常有一些看起来可以顺手整理的旧字段、事件名或接口。它们之所以保留，可能不是因为没人重构，而是仍有下游依赖。适合记录的是“这个集成面为什么必须保持兼容”，而不是绑定某个随时会变化的函数名。

这三类知识的共同点很明确。模型从当前 diff 里推不出完整背景，但只要拿到准确上下文，就有机会指出真正危险的改动。

## 把检查项压缩到短而有用

我会用下面这张发布前检查卡审一遍新增规则。

- 后果是否具体，能说明漏检会破坏什么
- 作用域是否足够窄，服务级规则是否放进对应目录
- 是否描述稳定结果，而不是绑定易变化的实现细节
- 是否给出安全替代路径，而不只是禁止动作
- 是否无法被测试、linter 或 CI 更可靠地执行
- 是否来自真实缺陷或 reviewer 反复解释的问题

根目录规则适合整个仓库都成立的约束。服务或模块专属知识应进入嵌套的 AGENTS.md，让 Codex 只在相关文件变化时应用它。

规则越宽，注意力竞争越严重。源材料特别强调审查不只看覆盖率，还要同时观察克制、保持和可操作性。抓到目标违规只是第一步，不能因此对安全改动频繁误报，也不能漏掉规则之外的普通 bug。

## 识别规则已经写坏的信号

最明显的失败信号，是每个沾边的改动都会触发同一条提醒。这通常说明规则没有划清适用范围，或者只写了抽象原则。

另一个信号，是 finding 能引用规则，却无法指出具体位置、优先级和替代方案。作者看完仍不知道怎么改，这条规则就没有完成审查工作。

还要留意一种更隐蔽的退化。加入规则后，Codex 只盯着规则违规，原本能发现的普通 bug 反而被忽略。评测里的 Retention，就是专门检查这种情况。

遇到这些信号，我不会继续堆解释，而会收窄作用域、补充安全路径，或者删除持续制造噪音的规则。

## 用历史缺陷做最小验证

最小验证不需要一次改完整个仓库。选一个已经发生过、后果明确的缺陷，提炼两到三条规则，然后准备三个改动。

- 触发样本，重现那类违反规则的危险改动
- 安全反例，改到相近代码，但没有破坏不变量
- 无关改动，确认规则不会抢走普通审查的注意力

验收时看四项结果。

- Coverage，目标违规是否被找到
- Restraint，安全反例是否保持安静
- Retention，规则之外的普通 bug 是否仍能发现
- Actionability，finding 是否给出规则依据、位置和处理路径

我建议从最近一次“代码没错，但系统还是坏了”的缺陷开始。找到当时 reviewer 口头补充的那句背景，把它放到最接近受约束代码的位置，再跑完这组三元测试。

AGENTS.md 的价值，不在于让 Codex 记住更多规定，而在于把资深 reviewer 脑中的历史上下文变成仓库可执行的审查依据。
