# 吴恩达的 Loop Engineering，AI 产品别只写 prompt，要设计三层反馈循环

很多 AI 产品卡住，不是模型不够强，也不是 prompt 写得不够玄，而是团队把 AI 当成一次性生成器。

吴恩达最近讲的 Loop Engineering，真正值得产品开发者盯住的地方，不是又造了一个新词，而是把 AI 产品开发拆成了三层循环。写代码只是最底层，人的判断和用户反馈才决定它能不能长成产品。

如果你正在用 coding agent 做原型、内部工具、SaaS 功能或创作者工作流，这个视角很有用。它提醒你，别只问 AI 能不能把页面写出来，要问规格、测试、开发者判断和用户反馈有没有形成闭环。

## 把一次生成改成一段可验证的工程循环

故事可以从一个很普通的开发场景开始。

你想做一个给孩子练打字的小 app。过去你会先写需求，再自己搭界面、写逻辑、调样式、修 bug。现在你可以把产品规格交给 coding agent，让它写代码、运行、测试、修问题，再继续改。

这就是第一层循环，Agentic coding loop，工程执行循环。

它的速度最快，也最容易让人兴奋。AI 不再只是回答“这段代码怎么写”，而是能连续工作一段时间。它可以按规格实现功能，打开浏览器检查页面，跑测试，发现行为不对再改，直到接近目标。

但这一层有一个前提，规格必须清楚，目标必须可验证。

如果你只说“做一个好看的打字练习 app”，agent 会很勤奋地迭代，却未必朝正确方向走。它可能把动画做得很花，把奖励机制做得很复杂，最后偏离真正的使用场景。

更稳的做法，是把任务压成可验证的交付物。

比如练习流程能不能开始，输入错误时有没有反馈，完成一轮后是否进入结算页，家长能不能看到孩子的进度。能写成测试标准的，就不要只写成形容词。

AI 越能执行，规格和 evals 越重要。因为执行成本下降后，方向错误会被更快放大。

## 让开发者从修按钮，移动到判断产品

第二层循环，是 Developer feedback loop，开发者反馈循环。

它比工程执行慢一些，可能是几十分钟到几小时一次。开发者不再只是在旁边盯着按钮坏没坏、布局歪没歪，而是开始判断这个产品该往哪里走。

在打字练习 app 这个例子里，agent 可以自己写页面、补测试、修交互细节。但“猫咪服装解锁机制”要不要做，“家长登录流程”应该放多重，“视觉风格”该更像游戏还是学习工具，这些都不是单靠测试能决定的。

这时人的作用不是传统意义上的“品味”二字能概括的。

吴恩达更倾向用 context advantage，语境优势，来描述开发者的价值。我觉得这个说法更准确。因为产品判断不是凭空审美，而是你知道谁在用、什么时候用、为什么会放弃、哪些摩擦会毁掉体验。

一个很典型的误区，是把开发者反馈循环降级成“给 agent 提 bug”。

这样当然有用，但太窄了。更关键的问题应该变成，孩子会不会愿意继续练，家长会不会觉得这个功能有必要，解锁机制是在增强动机，还是在打断学习。

这层循环让开发者的位置上移。不是离代码更远，而是离产品结果更近。

## 等真实用户把方向校准回来

第三层循环，是 External feedback loop，外部反馈循环。

它最慢，也最接近真实世界。找朋友试用，做 alpha 测试，上线给真实用户，看行为数据，收集客户反馈，做竞品分析，都属于这一层。

前两层循环解决的是“能不能更快把东西做出来”。第三层问的是“做出来以后，有没有人真的需要”。

这也是 AI 编程时代最容易被跳过的一层。

因为 agent 把原型做得太快了，开发者很容易产生一种错觉，只要连续改几轮，产品就自然变好了。可真实用户不会因为你迭代得勤奋就买账。孩子可能不在意你设计的奖励，家长可能更关心练习记录，老师可能需要完全不同的管理入口。

外部反馈循环的价值，是把产品从开发者脑内拉回使用现场。

它不一定很重。早期可以只是让几个目标用户试一遍，看他们在哪里停住，哪些功能他们根本没注意，哪些地方他们会用自己的语言重新描述需求。

这层反馈慢，但它决定产品方向是不是有效。

## 交付物不再只是代码，而是一套循环系统

Loop Engineering 给我的启发是，AI 产品开发的交付物变了。

过去我们习惯交付代码、页面、功能列表。现在更应该交付一套能持续运转的循环系统。

规格能不能被 agent 理解，测试能不能约束低层行为，开发者能不能定期校准产品判断，用户反馈能不能回到下一轮规格里。这些东西加起来，才是 AI 产品真正的生产方式。

这也解释了为什么很多团队明明已经在用 coding agent，效果却差很多。

差距不只在模型，也不只在 prompt。有人把 agent 当高级补全工具，有人把它放进工程循环里，再用人的语境优势和用户反馈不断校准。后者才更接近可持续的产品开发。

如果你现在要把这个方法放进自己的项目里，不需要先搭一整套复杂系统。可以从一个小功能开始，把三层循环写到同一张任务卡里。

交付物可以这样拆。

- 工程循环，给 agent 一份明确规格，加上能跑的测试或验收标准
- 开发者循环，每隔一轮检查产品判断，而不是只检查 bug
- 外部循环，找真实使用者完成一次核心流程，记录他们卡住的位置
- 回流动作，把用户反馈改写成下一轮规格，而不是只放进备忘录

这不是清单崇拜，而是为了防止 AI 开发变成“生成很多东西，却没人负责方向”。

我的判断很简单，未来更强的开发者，不只是会把 agent 叫起来干活的人，而是能设计好反馈循环的人。

prompt 能启动一次生成，loop 才能养出一个产品。
