# OpenClaw 和 Codex 也能端到端训练了：OpenForgeRL 带来了什么

如果团队已经用 OpenClaw、Codex 这类智能体处理真实任务，却发现训练系统只能看到孤立的模型输入和输出，OpenForgeRL 值得研究。

它解决的不是如何再搭一个智能体，而是如何把现有推理框架完整接入监督微调和强化学习，让多轮推理、工具调用以及环境反馈成为可训练的轨迹。

我更关心一个实际决策。团队是否应该为此引入代理层、远程容器和 Kubernetes 编排。读完论文给出的数据流与组件边界，基本就能判断自己的智能体是否到了需要端到端训练的阶段。

## 判断一，把一次训练任务的数据流走通

传统训练栈擅长处理规则明确的请求与响应，但 OpenClaw、Codex 不是只调用一次模型。它们会保留状态，连续调用工具，还可能拉起多个进程，与文件系统、浏览器或其他运行环境交互。

OpenForgeRL 在推理框架和模型之间放入一个轻量代理。OpenClaw 或 Codex 发起模型调用时，请求先经过代理，再由代理提供模型响应，同时把调用记录成标准强化学习代码库可消费的训练数据。论文以 veRL 为例，但关键设计并不依赖某一个推理框架。

一条 rollout 的数据流可以压缩成下面这条链路。

任务进入独立环境 → 推理框架多轮调用模型与工具 → 代理模型调用并记录轨迹 → 环境返回执行结果 → 标准训练栈读取数据并更新模型。

这套设计最有价值的地方，是把推理和训练解耦。智能体仍在真实使用的 harness 和环境里执行，训练端不需要重新实现 OpenClaw 或 Codex 的状态机。

## 判断二，隔离成本是否配得上任务复杂度

代理层只解决记录问题。真正棘手的是 rollout 可能修改文件、启动进程、操作网页，甚至让不同任务互相污染。

OpenForgeRL 用 Kubernetes 编排器为每次 rollout 启动独立的远程容器。每个训练任务拥有自己的运行环境，结束后可以单独回收。对工具型智能体、浏览器智能体和计算机操作智能体，这种隔离不是附加功能，而是保证训练数据可信的基础条件。

代价也很直接。团队要承担容器镜像、集群调度、环境初始化、日志以及失败回收的工程复杂度。任务越短、工具越少，这部分固定成本越显得重。任务越长、状态越复杂，隔离的收益才越明显。

论文覆盖了工具或 claw 型智能体，以及多模态 GUI 浏览器和计算机操作智能体。OpenForgeClaw 使用数百到数千个任务训练后，在 ClawEval 达到 31.7 pass^3 和 55.9 pass@3，在 QwenClawBench 达到 33.7。OpenForgeGUI 在 OSWorld-Verified、Online-Mind2Web 和 WebVoyager 上分别达到 37.7、63.0 和 72.3。

这些结果证明框架能支撑复杂环境训练，但不能替团队回答基础设施是否划算。

## 判断三，现有智能体有没有可学习的闭环

我会检查三个组件边界是否已经存在。

第一，推理框架是否能稳定完成多轮模型调用，并让这些调用经过统一入口。第二，每次任务是否能在可重建、可隔离的环境中运行。第三，任务是否有明确结果，能够形成奖励或通过判定。

缺少任意一项，引入 OpenForgeRL 都可能只是把尚未稳定的智能体搬进更复杂的集群。尤其当任务成功标准仍靠人工感受，记录再完整的轨迹也很难转成可靠训练信号。

反过来，如果团队已经积累重复任务，能自动判断成功与失败，而且现有智能体的主要瓶颈确实来自多轮决策，那么代理模型调用、保存完整轨迹和隔离执行环境就能连成训练闭环。

## 哪些团队适合，哪些团队暂时不适合

适合引入的团队，通常已经有持续运行的 harness，任务涉及文件、工具、浏览器或桌面环境，并且需要并行生成数百到数千条 rollout。它们关心的是模型能否在真实执行链里学会更好的策略，而不只是提升单轮回答质量。

暂时不适合的情况也很清楚。智能体仍在频繁改流程，任务数量很少，结果无法自动验收，或者团队没有维护容器编排系统的能力。此时更值得先稳定任务定义与评测，而不是提前建设训练平台。

## 我的选择，先验证闭环，再决定是否上规模

如果我负责一个中小团队，我不会因为 OpenClaw 和 Codex 可以端到端训练，就立即部署完整方案。我会先挑一个重复率高、结果可自动判定、环境容易重建的任务，确认模型调用能被统一代理，轨迹能够还原一次完整决策，容器隔离也不会破坏工具链。

这三个条件同时成立，我才会考虑扩大 rollout 数量并接入强化学习。否则，问题多半还在任务与评测，而不是训练框架。

OpenForgeRL 给智能体团队带来的最大启发，不是所有 harness 都该训练，而是训练条件终于可以按组件边界检查。先画出一次任务的数据流，再看代理、轨迹、隔离和奖励是否闭合，这比先搭集群更接近正确决策。
