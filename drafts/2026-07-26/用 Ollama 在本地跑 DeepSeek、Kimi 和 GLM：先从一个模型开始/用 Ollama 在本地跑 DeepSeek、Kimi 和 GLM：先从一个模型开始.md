# 用 Ollama 在本地跑 DeepSeek、Kimi 和 GLM：先从一个模型开始

如果你想验证电脑能不能本地运行大模型，最有效的起点不是同时下载 DeepSeek、Kimi 和 GLM，而是选一个模型，完成一次对话，再观察内存变化。

这个闭环足够回答三个实际问题。Ollama 能否正常启动，当前硬件能承受多大的模型，以及本地推理是否适合你的使用场景。

做完后，你会得到一个可重复的本地验证路径。后面更换模型时，只改模型选择，不必重新设计整套流程。

## 把目标压缩成一次本地对话

Ollama 是一个用 Go 编写的开源项目，官方仓库列出的模型范围包括 DeepSeek、Kimi-K2.6、GLM-5.2、Qwen、Gemma、MiniMax 和 gpt-oss 等。

模型很多，但第一次运行不适合做横向比较。下载多个模型会同时放大存储、内存和排错成本，一旦失败，很难判断问题来自安装、模型规模还是机器资源。

更稳妥的最小场景只有四个动作。

- 从 Ollama 官方仓库进入对应系统的安装入口
- 在官方模型库中选择一个目标模型
- 复制该模型页面当前提供的运行命令
- 输入一个容易核对答案的短问题，完成一轮对话

问题可以选成固定格式，例如要求模型把一段文字压缩成三点，或者解释一小段代码。第一次不要提交长文档，也不要追求复杂推理，目标只是确认完整链路能够工作。

## 按一条路径完成安装和运行

安装完成后，先确认 Ollama 服务能够启动，再从官方模型页面选择 DeepSeek、Kimi 或 GLM 中的一个。具体模型标签以页面当前展示为准，避免凭旧教程手写名称。

运行命令通常会触发模型文件下载。这个阶段要给磁盘空间和下载过程留出余量，不要因为终端短时间没有回复就重复执行多个下载任务。

模型进入交互状态后，输入准备好的短问题。收到完整回答，再退出会话并重新启动同一个模型。第二次仍能正常进入，才说明这条路径具备基本可重复性。

这份操作卡可以直接用于验收。

- 安装完成后，Ollama 可以正常启动
- 目标模型能够完成下载并进入交互状态
- 短问题能够返回完整答案
- 会话期间系统没有因内存压力明显失去响应
- 退出后可以再次启动同一个模型

## 用内存变化决定模型规模

本地运行最容易忽略的不是模型名称，而是资源余量。打开系统自带的任务管理或活动监视工具，在模型启动前、加载后和生成回答时分别观察内存占用。

不必急着追求一个漂亮数字。真正需要记录的是机器有没有开始频繁使用交换空间，其他应用是否明显变慢，以及回答生成时系统能否继续正常操作。

如果模型加载后已经接近资源上限，处理方式应当是降低模型规模，而不是继续增加上下文或同时启动更多程序。

可以按这个顺序收缩任务。

1. 关闭暂时不用的高内存应用
2. 在同一模型系列中改选更小的可用版本
3. 缩短输入内容和单次对话长度
4. 一次只运行一个模型
5. 重新执行同一个短问题，比较资源变化

我的判断是，本地模型的第一次成功不该用回答质量定义，而该用可重复运行定义。能稳定启动、完成回答、退出并再次进入，比一次塞进最大的模型更有价值。

## 避开四个常见误判

第一个误判是把下载完成当成运行成功。模型文件存在于磁盘，并不代表内存足以加载它。

第二个误判是同时尝试多个模型。DeepSeek、Kimi 和 GLM 都可以成为后续选项，但首轮验证只需要一个，否则排错变量会迅速增加。

第三个误判是只看空闲内存。模型生成期间的系统响应、交换空间变化和其他应用状态，同样是验收的一部分。

第四个误判是照搬旧命令。模型名称和可用标签应从 Ollama 当前模型页面复制，仓库说明和官方文档才是可验证入口。

完成首个模型闭环后，把使用过的模型名称、测试问题和内存变化记下来。下一次再换 DeepSeek、Kimi 或 GLM，继续使用同一道题，你就有了一条真正可比较的本地模型基线。
