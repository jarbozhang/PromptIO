# Codex 免费重置次数可以攒着用了，什么时候用最划算？

Codex 这次改动，对我最直接的提醒是，别再把免费 reset 当成“看到就点”的按钮了。

OpenAI 在 X 上说，Codex rate limit resets 现在可以保存到之后再用。Go、Plus、Pro、Business 用户会先拿到一次免费 reset。

如果你平时用 Codex 写代码、改项目、查 bug，这个变化不只是多送一次机会。它更像是把一次“额度回血”从系统自动安排，变成你自己排班。

## 先把免费 reset 留给长任务

我会把这次免费 reset 当成一张应急工单券，而不是日常消耗券。

短任务不太值得用。比如让 Codex 改一个小组件、补一个单测、解释一段报错、整理一个 README，这些任务通常可以拆开做。额度用完了，等下一轮恢复也不太影响节奏。

真正值得用 reset 的，是那种已经进入上下文、停下来会断片的任务。比如大范围重构、跨文件 bug 排查、从日志一路追到根因、把一个半成品功能收口到可跑。

这些任务最怕中途卡住。不是因为模型不会继续，而是你重新唤起上下文也要花时间。免费 reset 用在这里，省下来的不是几次请求，而是一整段专注窗口。

## 我会按这 4 类任务排优先级

如果你也只有一次免费 reset，可以直接按这个顺序判断。

- 最值得用，长链路排查。比如 CI 失败、线上异常复盘、多个模块互相影响的问题。
- 很值得用，中大型重构。比如目录拆分、类型修正、接口迁移、旧逻辑清理。
- 可以考虑用，交付前收尾。比如让 Codex 帮你跑完剩余 TODO、补测试、改文档、处理边界。
- 不建议用，碎片化问答。比如单个 API 怎么写、一段代码为什么报错、生成几个脚本片段。

我的判断很简单，reset 要用在“上下文越长越值钱”的地方。

如果一个任务可以十分钟后无损恢复，就别急着用。如果一个任务中断后要重新解释项目结构、目标和失败路径，就该把 reset 留给它。

## 不同用户可以这样安排

Go 和 Plus 用户，我会更保守一点。

这类用户更容易把 reset 当作“今天多玩一会儿”。但 Codex 真正有价值的地方，往往不是多问几句，而是帮你把一个复杂任务推进到结束。所以我的建议是，至少留到当天最重要的代码任务再用。

Pro 用户可以稍微激进一点。

如果你本来就把 Codex 当主力编程助手，reset 可以放在工作流后半段。前面让它做探索、定位、拆方案，等进入批量修改和测试修复阶段，再决定要不要用。

Business 用户更适合把它当团队排班工具。

不要每个人各用各的。更合理的方式是，给团队约定几类高优先级场景，比如发布前修复、遗留系统重构、复杂回归排查。谁遇到这类任务，谁再动用 reset。

## 这里最容易踩坑

最容易浪费的用法，是刚看到免费 reset 就点掉。

这会让 reset 退化成“多一点额度”，而不是“关键时刻不断流”。OpenAI 这次说的是可以保存到之后再用，重点就在“之后”。

第二个坑，是把 reset 用在没有准备好的任务上。

如果你还没整理目标、没贴关键文件、没跑过失败命令，直接让 Codex 开工，reset 只是放大混乱。更好的做法是先把输入准备好，再启动长任务。

我会在用之前先写 5 行任务卡。

- 当前目标是什么
- 哪个命令失败了
- 相关文件有哪些
- 不希望改哪里
- 最后交付标准是什么

这 5 行写清楚，reset 才像加班券。写不清楚，它就只是一次更贵的聊天。

## 把 reset 留给交付段

如果你现在就想调整自己的 Codex 用法，我建议先别急着点 reset。

先打开你最近一个卡住的项目，挑一个“中断成本最高”的任务。不是最难的那个，也不是最酷的那个，而是你最不想重新解释第二遍的那个。

然后把它拆成三段。

第一段，让 Codex 看现状，列出它需要确认的文件和命令。第二段，让它做最小修改并说明风险。第三段，再决定要不要用 reset 把测试、修复和文档一起收尾。

这样用，免费 reset 才真的有省钱效果。

我对这次改动的看法是，它没有改变 Codex 能做什么，但改变了你安排 Codex 的方式。以前额度像闹钟，到点就响。现在它更像一张可以留到深夜项目收尾时再用的通行证。

别把它花在热身上。

留给真正要交付的那一段。
