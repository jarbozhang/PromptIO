# 先改原型再写代码：我用 Git Diff 让产品设计和实际功能始终同步

如果你在用 Agent 开发产品，却经常遇到设计稿、需求描述和实际功能各走各的，这套流程值得试一次。

我的做法是把 React 原型当成产品设计的可版本化事实源。每次增加或修改功能，都先改原型、确认交互，再让代码实现跟随已经确认的差异。

它解决的不是画页面的问题，而是让产品决策留下可读、可比较、可追踪的记录。

## 把功能需求交给原型处理

项目第一版，我会先用 Claude Design 做 UI 原型。产出的不是一组静态图片，而是 React 代码和结构化 JSON 数据，可以放到本地继续维护。

原型打磨好以后，我会配合 Baoyu-Design Skill 管理它。开发新功能时，我不再直接进入功能代码，而是先在本地原型中完成变化。

比如要增加一个操作入口，我会先看它应该出现在哪个页面，点击后进入什么状态，原有信息层级是否需要调整。等这些问题在原型里说清楚，功能边界才算稳定。

这样做看起来多了一道工序，实际是在更便宜的位置处理产品分歧。交互还没确定时，改原型通常比改完业务逻辑再返工更轻。

## 让 Agent 默认走同一条路径

刚开始，这套流程依赖我每次主动提醒。只要忘记说一句，Agent 仍可能直接修改功能代码，原型便从事实源退化成一份过期展示。

后来我把规则写进 `AGENTS.md` 和 `claude.md`。当我提出修改或增加功能时，Agent 默认先维护原型，等原型确认后再进入实现。

工作顺序由此固定下来。

需求进入原型，交互在原型里收敛，确认后的变化进入功能代码。原型不再是项目启动时用一次的附件，而是持续参与开发的产品资产。

这一步对 Agent 工作流尤其重要。Agent 很擅长执行明确任务，但如果团队没有规定谁先变化、谁跟随变化，它也会同时面对需求文字、旧原型和现有代码三个答案。

把顺序写入项目规则，相当于明确告诉它，设计变化先落在原型，功能实现再参考已经确认的结果。

## 用 Git Diff 看清产品到底改了什么

React 原型还有一个关键优势，它天然适合进入 Git。

当页面结构、组件或结构化数据发生变化时，`git diff` 会把前后版本的差异直接摆出来。我可以看到哪些元素被增加，哪些结构被调整，哪些状态发生了变化。

这比对着两张图片找不同更接近开发语言。视觉变化被转换成代码和数据差异，Agent 也能沿着这些差异理解需要落实的功能范围。

功能确定后，我不会再把一句模糊需求重新解释一遍，而是让 Agent 参考原型的 diff 结果进入代码实现。原型负责表达已经确认的设计，diff 负责交代变化，实现代码负责把变化落到真实功能里。

整个交付物也随之改变。以前交付的是一版界面和一份功能代码，现在还多了一条可追踪的产品决策链。

## 别让原型变成第二套产品

这套方法最容易失效的地方，不是原型做得不够精致，而是原型和功能代码同时被当成可以独立修改的入口。

如果一个小改动直接落进功能代码，原型没有同步，下一次 Agent 再参考原型时，就可能把已经完成的变化当成不存在。两套事实源一旦形成，维护成本会迅速回来。

我的判断是，原型不需要承载所有工程细节，但必须准确表达用户能看到、能操作、能确认的产品状态。至于接口、数据持久化和异常处理，仍然属于功能实现阶段。

边界划清以后，原型不会变成另一套完整应用，却能继续承担产品设计的事实源。

## 用一次小改动验证这条链路

可以从一个范围明确的需求开始，例如增加一个按钮、调整一次表单流程，或者补充一个页面状态。

先让 Agent 修改 React 原型，确认交互和信息层级，再检查 `git diff` 中发生了哪些变化。设计确认后，让 Agent 参考这份差异修改实际功能，最后核对原型与功能是否表达了同一个结果。

不要急着把整个项目重做成原型驱动。先跑通一次完整变化，看看团队能否稳定遵守原型先行、差异确认、功能跟随这三个动作。

当原型始终跟着产品一起变化，它才不只是设计预览，而是代码开工前那份已经确认的答案。
