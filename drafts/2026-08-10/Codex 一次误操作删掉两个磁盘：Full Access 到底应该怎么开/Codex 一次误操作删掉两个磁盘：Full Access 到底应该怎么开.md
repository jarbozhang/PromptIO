# Codex 一次误操作删掉两个磁盘：Full Access 到底应该怎么开

如果你允许 Codex 在 Windows 上完全控制文件，这起事故值得放进团队的安全培训材料。一次参数与引号处理异常，叠加不受限制的执行权限，最终让 C 盘和 D 盘的大部分文件被删除。

真正需要警惕的不是某条命令写错，而是三个控制点同时失效。命令从生成到解释发生偏移，权限没有限制影响范围，高危操作执行前也没有最后一道确认。

读完这份复盘，你至少应该重新检查三件事，Codex 能操作哪些目录，删除是否可以恢复，以及版本库之外的数据有没有独立备份。

## 还原两个磁盘被波及的现场

蓝点网转述的一起用户事故中，Codex for Windows 执行命令后，C 盘和 D 盘的大部分文件遭到删除。原帖把问题指向 PowerShell 参数传递和引号处理异常，同时指出用户开启了完全控制权限，高危命令因此得以直接执行。

这类事故不能简单归结为“Agent 写错了一条命令”。同一条字符串会经过模型生成、工具编排、参数封装和 PowerShell 解析。只要其中一层改变引号、转义符或参数边界，模型看到的命令与系统最终执行的命令就可能不是同一件事。

讨论中还有用户提到，从 PowerShell 调用 WSL 时遇到过更高的转义出错概率。也有人质疑具体命令环境究竟属于 PowerShell 还是 WSL。这些反馈尚不足以确定本次事故的完整技术路径，却共同指出一个问题，多层命令解释器会扩大不可预测性。

## 拆开三道同时失效的控制点

第一道失效发生在命令解释层。

文件路径里的空格、引号、通配符和转义字符都可能改变参数边界。删除命令尤其危险，因为一个原本用于限定项目目录的参数一旦丢失，作用范围就可能从单个目录扩展到磁盘中的更多位置。

第二道失效发生在权限层。

Full Access 给了 Codex 完成复杂任务的能力，也把一次解释错误的破坏半径放大到权限覆盖的全部位置。权限越大，Agent 越省事，但错误也越难被目录边界拦住。

第三道失效发生在执行闸门。

高危删除没有人工确认，也没有先输出目标文件列表，更没有经过可恢复删除。前两层即使已经犯错，只要这里仍要求确认具体路径和预计删除数量，事故仍有机会停下来。

这条事故链可以压缩成一行。

参数边界偏移 → 删除范围扩大 → 完全控制权限放行 → 高危命令直接落地 → 多个磁盘受损

## 为什么只关闭 Full Access 仍然不够

最直接的反应是永远不开完全控制权限。但工程任务确实可能需要安装依赖、修改多个目录或调用系统工具，单纯拒绝权限会让正常工作不断中断，也可能诱导使用者习惯性点击放行。

只依赖 Git 同样不够。Git 可以找回已经提交的代码，却覆盖不了未提交文件、数据库、下载资料、编辑器配置和其他工作目录。版本提交是代码恢复机制，不是整机备份。

只要求 Agent 在删除前“谨慎一点”也不可靠。自然语言提醒属于软约束，无法替代目录权限、执行确认和备份。真正有效的防护需要让错误命令即使生成，也碰不到重要数据或无法立即造成永久删除。

## 把 Full Access 改成受控窗口

更稳妥的做法，是把权限当成临时能力，而不是默认工作模式。

日常开发时，让 Codex 只接触独立项目目录。不要把仓库放在同时承载照片、资料、备份或生产数据的位置。需要更高权限的任务，先缩小到明确目录和明确时段，任务完成后及时收回。

代码修改前保留一次可识别的提交，未完成内容也可以放进临时分支。提交信息要能说明恢复点，而不是堆积成无法判断用途的快照。

涉及删除时，优先移动到回收站或隔离目录。必须永久删除的任务，应先打印完整目标路径、匹配数量和所在磁盘，再由人确认。评论中关于用移动代替直接删除的建议，价值就在这里，恢复能力要放在命令执行之前。

备份还需要与工作磁盘分离。原帖明确提到备份避免了更严重的后果，这也说明版本库、回收站和独立备份解决的是不同故障，不能互相替代。

## 留下一张 Codex 文件事故卡片

事故级别　高

触发条件　命令参数或引号被错误解释，同时拥有宽泛文件权限

扩大因素　跨解释器调用、通配符、未限定路径、高危命令无确认

第一响应　立即停止后续写入，避免继续覆盖可恢复数据

恢复顺序　独立备份、版本库、回收站或隔离目录、专业恢复流程

长期控制　项目目录隔离、最小权限、操作前提交、可恢复删除、独立备份

Full Access 不应该被理解成“让 Codex 更顺畅地工作”。它更像一张临时施工许可证，范围、时间和高危动作都要写清楚。真正可靠的 Agent 工作流，不是假设命令永远正确，而是保证命令出错时损失仍被关在项目目录里。
