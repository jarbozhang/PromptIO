# 用 OpenAI 做一个本地 AI 衣橱：拍照建库、自动搭配还能预览试穿

衣服不少，却总在穿固定几套的人，可以关注 Wardrobe 这个开源项目。它把衣橱整理变成了一条图像工作流，拍摄穿搭照，拆分单件衣物，保存到本地目录，再生成新的搭配预览。

我更在意的不是让 AI 推荐一件上衣，而是它能不能把散落在相册里的衣服变成可管理的数据。Wardrobe 给出的答案很具体，原图、处理后的衣物图和 JSON 数据都保存在本地 `data/` 目录。

按下面的最小路径走完，你可以得到一个能继续扩充的数字衣橱。生成的抠图、搭配图和试穿图均有 AI 参与，适合辅助整理与预览，不应当作面料、尺寸和真实上身效果的精确证明。

## 选一套最容易验收的穿搭

我会从一套结构清楚的穿搭开始，上衣、裤子和鞋子都完整入镜，彼此遮挡尽量少。目标不是一次导入整个相册，而是确认系统能否把一张照片拆成三件可识别、可复用的单品。

准备材料可以压到四项。

- 一张能看清上衣、裤子和鞋子的穿搭照
- 一张用于试穿预览的自拍参考图
- 可用的 OpenAI API key
- 本地 Node.js 项目运行环境

这里的交付物也很明确，不是一张看起来不错的合成图，而是三件独立衣物进入目录，并且留下对应的本地图片和 JSON 记录。

## 跑通拍照到建库的操作路径

项目公开的启动路径很短。

```bash
git clone https://t.co/kw9Za3NBih
cd wardrobe
npm install
# 配置 OPENAI_API_KEY，并准备自拍参考图
npm run dev
```

导入穿搭照后，Wardrobe 会识别其中的上衣、裤子和鞋子，再调用 OpenAI Images API，把单件衣物处理成接近产品图的独立素材。处理结果与原始图片会留在本地 `data/` 目录，衣橱记录则写入 JSON 数据库。

如果已经积累了一批穿搭照片，还可以使用项目提供的 Codex CLI 技能，让它处理指定图片目录。例如把 `~/Pictures/outfits` 里的衣服导入衣橱，由工作流完成抠图和建库。

我的判断是，批量导入应该放在单张照片验收之后。只要分类、抠图或文件记录有一个环节不稳定，直接处理整个目录只会把人工返工放大。

## 用一套新搭配检查结果

建库完成后，从衣橱中选择几件单品，让系统生成搭配 Lookbook。随后加入自拍参考图，查看这些衣物组合到人物身上的试穿预览。

我会按下面四项验收。

- 衣物边缘是否完整，有没有把手臂或背景误当成衣服
- 上衣、裤子和鞋子的分类是否对应原图
- 本地目录中的处理图与 JSON 记录能否一一对应
- 搭配图和试穿图是否保留了单品的主要颜色与轮廓

试穿图通过验收，只代表它能帮助判断配色和整体方向。真实尺码、垂坠感、材质反光与身体贴合程度，仍然要靠实际穿着确认。

## 把 Images API 成本记到每次导入

这条链路的成本来自 OpenAI Images API 调用。一次穿搭整理可能包含多件衣物抠图，继续生成 Lookbook 和真人试穿，还会增加图像生成次数。

现有项目介绍没有给出每一步的实际调用明细，也没有提供可直接套用的单套成本，因此不能据此写出固定金额。更稳妥的核算方式，是用一套穿搭做成本样本，分别记录衣物拆分、搭配生成和试穿预览产生的调用，再决定是否批量导入。

我会把成本拆成三笔，而不是只看最终图片数量。

- 建库成本，单件衣物识别与抠图产生的调用
- 搭配成本，生成一组 Lookbook 产生的调用
- 试穿成本，把搭配应用到自拍参考图产生的调用

这样才能回答一个实际问题，继续导入十套衣服时，主要费用究竟来自建库，还是反复生成预览。

## 避开本地衣橱的四个坑

第一是把本地保存理解成图片不会离开设备。项目会调用 OpenAI Images API 处理图像，本地 `data/` 目录解决的是结果与数据库的存放位置，不等于处理过程完全离线。

第二是直接使用包含家庭环境、证件、屏幕内容或其他人的原图。上传前应裁掉无关背景，只保留完成衣物识别所需的画面。

第三是把自拍参考图当成普通素材。它属于敏感程度更高的个人数据，建议使用专门拍摄、背景简单且不含其他人的照片，并控制备份与共享范围。

第四是把生成效果当成购买依据。AI 试穿适合缩小搭配选择，但不能替代尺码表、材质信息和真实试穿。

我的下一步动作会很克制，只导入一套上衣、裤子和鞋子，保留处理前后文件，记下这一轮的 API 调用，再决定要不要把整个衣橱交给这条工作流。数字衣橱真正有用的起点，不是生成了多少张图，而是每件衣服终于有了可查、可组合的记录。
