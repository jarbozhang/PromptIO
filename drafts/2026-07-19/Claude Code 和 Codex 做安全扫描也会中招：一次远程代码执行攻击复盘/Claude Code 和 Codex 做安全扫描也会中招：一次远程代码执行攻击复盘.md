# Claude Code 和 Codex 做安全扫描也会中招：一次远程代码执行攻击复盘

把第三方仓库交给 Claude Code 或 Codex 做安全扫描，看起来是在防御，执行过程却可能反过来攻击扫描者的机器。

AI Now Institute 公布的 Friendly Fire 概念验证显示，Claude Code CLI 和 Codex CLI 在审查开源库或第三方依赖时，可能被劫持并触发远程代码执行。研究涉及 Claude Sonnet 4.6、Sonnet 5、Opus 4.8 与 GPT-5.5，攻击面对的是开箱配置，而不是刻意放开的高危环境。

对经常审查陌生仓库的工程师，真正有用的结论不是停用代码代理，而是改变运行边界。读完可以直接检查三件事，扫描任务是否与工作机隔离，代理权限是否收缩，危险动作是否必须人工确认。

## 看清恶意依赖怎样进入扫描任务

传统代码审查容易把仓库理解成一组等待阅读的文件。代码代理看到的却是一个可交互环境，里面可能包含依赖、脚本、配置、说明文件和能影响工具行为的内容。

当代理为了完成安全检查而读取仓库、分析依赖并调用工具时，攻击者获得了一条新的输入通道。恶意内容不必正面突破模型，它只要让防御任务沿着错误路径继续执行，就可能把一次静态审查变成主机上的真实操作。

这类风险的关键反差在于，扫描者主动打开了不可信对象，并授予代理理解代码和执行动作的能力。任务目标是找漏洞，权限边界却可能允许漏洞先利用扫描环境。

## 沿着失效路径找到真正的控制缺口

可以把这次攻击面压成一条事故链。

不可信仓库进入扫描环境，代理读取其中的代码与项目材料，恶意输入影响后续决策，工具调用越过纯阅读边界，命令在拥有工作机权限的环境中运行，最终形成远程代码执行。

其中任何一环被截断，攻击都难以走到终点。问题往往不是模型单独做错一次判断，而是多个默认条件叠加，仓库内容被当成可信上下文，工具拥有执行能力，运行环境保存着凭证，网络和文件系统又没有隔离。

只盯着提示注入检测并不够。即使模型大多数时候能够识别诱导，只要失败一次的代价是读取密钥、改写文件或运行载荷，整个方案仍缺少工程上的容错层。

## 把扫描任务关进一次性环境

最有效的控制点位于模型之外。第三方仓库应被视为主动攻击者控制的输入，扫描环境则按处理恶意样本的标准配置。

这份上线前控制清单可以直接用于团队评审。

- 使用一次性容器或虚拟机，每次任务结束后销毁
- 不挂载个人目录、SSH 配置、云凭证、浏览器数据和生产代码
- 默认禁止出站网络，确有需要时只开放任务所需的目标
- 使用非特权用户运行，不提供宿主机套接字和管理权限
- 将文件系统写入范围限制在临时工作目录
- 把命令执行、安装依赖、运行项目脚本和网络请求设为人工确认动作
- 保留工具调用、命令、文件变更与网络访问记录
- 为扫描任务设置时间、进程、内存和磁盘上限

人工确认不能只是弹出一个笼统的允许按钮。确认界面至少要让审查者看见将执行的命令、工作目录、环境变量范围、网络目标以及可能写入的位置，否则确认只是在把自动风险改成人工误点。

## 用攻击式验收替代功能式验收

很多团队验证代码代理，只检查它能否找到漏洞、生成报告。安全验收还要验证它被仓库内容诱导后能否造成损害。

准备一个无敏感数据的测试仓库，在其中放入会诱导代理读取目录外文件、访问网络、执行项目命令或修改非工作区文件的内容。验收重点不是模型有没有识破每条指令，而是即使模型接受了诱导，隔离层仍能阻止动作完成。

合格结果应当很具体，目录外文件不可读，未授权网络不可达，危险命令停在确认闸门前，临时环境销毁后没有状态残留，审计记录能还原代理尝试过什么。

如果其中一项依赖代理自己保持警惕，它就还不是稳定的安全控制。模型判断适合辅助发现风险，权限系统才负责限制事故半径。

## 把防御型代理当成不可信执行者

这次研究给 Agent 应用的启发很直接。任务名称叫安全扫描，不会自动让执行过程变安全。代理同时接触不可信输入和高权限工具时，防御目标甚至会成为攻击者设计诱导路径的依据。

上线前，挑一个第三方测试仓库跑完整验收。先撤掉工作机凭证和宿主机挂载，再关闭默认网络，最后逐项确认所有执行动作都能被阻断或审计。能在模型判断失败后依然守住边界，才算真正完成了安全扫描环境。
