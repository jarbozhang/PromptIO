# 产品经理也能做 AI 评测，先用三步搭一个最小 eval 流程

AI 产品最麻烦的不是模型偶尔答错，而是每次改 prompt、换模型、调检索参数，都不知道到底变好了，还是只是看起来更顺眼。

如果你是产品经理、独立开发者，或者小团队里那个要拍板上线的人，这套最小 eval 流程可以直接抄。它不要求一开始做复杂平台，先用少量样本、一个对齐过的 LLM 评审器、每次配置变更都跑一次评测，把“我感觉可以”改成“这版失败率有没有降”。

我会把 Eugene Yan 的 Product Evals in Three Simple Steps 拆成一套落地顺序，三张表，一条评测链，四个验收标准。重点不是追求满分，而是让每次产品改动都有同一把尺子。

## 选一个会影响上线判断的最小场景

不要一上来评测整个 AI 产品。我会先挑一个最容易伤用户信任的场景，比如客服摘要是否忠于原文、RAG 回答是否引用到正确材料、助手是否在该拒绝时拒绝。

这个场景要满足三个条件。

- 输入和输出能被保存下来
- 好坏边界能被人类标注
- 评测结果会影响上线决策

如果一个指标只是看着漂亮，改了也没人行动，它不是第一版 eval 的好对象。第一版要盯失败，因为失败才是产品信任被打穿的地方。

## 用一张样本表把好坏边界钉住

Eugene Yan 建议从表格开始，我很同意。别急着上平台，第一版用 spreadsheet 反而更容易逼团队把标准说清楚。

| 字段 | 怎么填 | 用来判断什么 |
| --- | --- | --- |
| input | 用户问题、任务或上下文 | 复现实验入口 |
| output | 当前模型输出 | 被评测对象 |
| metadata | 文档来源、用户类型、任务标签 | 帮标注者理解场景 |
| label | pass 或 fail，必要时 win、lose、tie | 最终监督信号 |
| reason | 一句话说明失败点 | 反过来改评审器 prompt |

标签别急着做 1 到 5 分。原文里一个很实用的判断是，细分分数很难校准，人和 LLM 评审器都会纠结 3 分和 4 分的边界。大多数团队最后还是要一个通过率，所以 pass/fail 更适合起步。

样本量也别只看总数。原文给的经验是，最好有 200+ 总样本，并且至少 50 到 100 个失败样本。因为只有 5 个失败样本的几百条数据，没法训练你识别真正会坏掉的地方。

失败样本怎么来，优先从真实请求和较弱模型的输出里找。强模型合成缺陷可以启动项目，但如果数据全是合成出来的夸张错误，评审器可能会学会抓戏剧化问题，却漏掉产品里更脏、更普通的失败。

## 把 LLM 评审器对齐到一个维度

有了标注表，下一步才是写 LLM evaluator。我的做法是，一次只评一个维度，比如忠实性、相关性、拒答是否正确、语气是否合规。

不要做万能评审器。一个 prompt 同时评 5 到 10 个维度，看起来省事，后面几乎一定难调。它判错时你不知道是标准没写清楚、样本不够，还是某个维度被另一个维度带偏。

更稳的流程是这样。

- 把标注数据切成开发集和测试集，例如 75% 用来调评审器，25% 留着验收
- 每个维度一个 evaluator prompt
- 输出只要 label 和 reason，先别让它写长篇解释
- pass/fail 任务看 precision、recall 和 Cohen’s Kappa
- 如果是 A/B 输出比较，把 control 和 treatment 顺序对调跑两次，防止位置偏差

这里我会优先盯 fail 的 recall。评审器偶尔严一点，还能人工复核；真正危险的是缺陷从评测里溜走。

Cohen’s Kappa 不要幻想一开始就很高。原文提到，0.4 到 0.6 已经是相当可用的对齐，0.7 以上很好；人类标注者之间有时只有 0.2 到 0.3，而且疲劳后可能漏掉很多缺陷。评审器的目标不是完美裁判，而是可重复、可扩展的产品尺子。

## 每次改配置都跑同一条评测链

最小 harness 不需要花哨，它只要做四件事。

- 读取同一批 input-output 样本
- 按维度并行调用 evaluator，注意速率限制
- 汇总通过率、失败率、关键维度分数
- 输出一行结果，方便贴到表格里长期追踪

这一步最适合产品经理参与，因为你需要维护的是改动台账，不是只看一场 demo。

| 改动项 | 记录方式 |
| --- | --- |
| prompt 模板 | 版本号和一句变化说明 |
| 检索参数 | top-k、过滤条件、重排设置 |
| 模型选择 | 模型名和关键参数 |
| 数据集版本 | 样本来源和样本数 |
| 评测结果 | 总通过率、fail recall、主要失败类型 |
| 结论 | 上线、继续调、回滚 |

评测链真正有用的地方，是每次改配置都跑。改 prompt 跑一次，换模型跑一次，调 RAG 参数也跑一次。否则 eval 只是一次汇报材料，不是产品迭代系统。

## 用四条验收标准挡住自嗨

我的判断很简单，第一版 eval 流程能不能用，不看它有多自动化，看它能不能拦住拍脑袋上线。

可以用这四条验收。

- 同一批样本重复跑，结果大体稳定
- 失败样本能被抓到，fail recall 不只是好看
- 评审器和人工标签的分歧能被解释
- 每次配置改动都有记录，结果能横向比较

样本数也要跟上线标准对齐。原文给了一个很直观的例子，如果目标是缺陷率低于 5%，200 个样本里观测到 3% 缺陷，95% 置信区间大约是 0.6% 到 5.4%，上界已经超过 5%，还不能很有底气。样本翻到 400 时，上界降到约 4.7%，判断才更稳。

别把这当数学炫技。它提醒小团队一件事，样本太少时，评测结果只是方向感，不是上线许可。

## 常见坑不要等到上线前才发现

第一个坑，是把评测做成大而全项目。更好的做法是先选一个会影响信任的场景，跑通标注、评审器、harness，再扩维度。

第二个坑，是把 LLM evaluator 当成权威。它需要被人类标签校准，也需要保留测试集，不能在同一批样本上反复调到看起来漂亮。

第三个坑，是只在发布前跑一次。eval 的价值在反馈回路。原文提到一个团队花约 4 周搭评测链，接下来 2 周跑了几十个实验，之后几个月跑了几百个实验。它省下来的不是一次人工检查，而是每次产品改动后的犹豫时间。

如果你现在只有半天，我建议只做一个动作，拉出最近一次 prompt 改动前后的 200 条样本，按上面的字段表标 50 个失败样本。等这张表能稳定更新，最小 eval 流程就已经开始工作了。
