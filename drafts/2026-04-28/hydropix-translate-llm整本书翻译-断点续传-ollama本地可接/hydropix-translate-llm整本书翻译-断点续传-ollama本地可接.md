# 一个开源工具用 LLM 翻译整本书，断点续传不限大小，国内可接 Ollama

我手里有一本 800 页的英文技术书，想翻译成中文当资料看。

打开常见的几款云端翻译产品，按字符报价，算下来一本书光翻译费就够买半张 4090 的零头。再看大小限制，30M 以内、50 万字以内、单次最多 10 万字，挑哪条都过不去。

折腾了半天最后用上的，是 GitHub 上一个叫 `hydropix/TranslateBooksWithLLMs` 的开源项目。1.2k star，作者是法国一个 Magic Design Studios 的技术美术总监，业余写的工具。

它干的事情非常朴素，把一本书切成小块，丢给你指定的 LLM 翻译，再按原格式拼回来。听起来好像没什么稀奇，但藏在三个细节里的设计，是我后来愿意把它常驻在工作流里的原因。

## 第一个细节，断点续传

这是我最先在意的功能。

跑长文档翻译，最怕的不是慢，是跑到 70% 网络抽风、API 报 429、或者你不小心 Ctrl+C 关了终端。前面几个小时白费，token 也白烧。

`TranslateBooksWithLLMs` 默认开 checkpoint，每个 chunk 翻译完落盘一次。中途挂掉，下次同一个命令再跑一遍，它会从上次的位置接着往下走。我做过一次实验，故意在 50% 的位置 kill 掉进程，重启之后日志里清清楚楚显示「跳过前 N 个已完成 chunk」，没有重复消耗一个 token。

这件事说起来简单，做起来其实需要把"翻译状态"和"原文结构"分开存。很多自己写的脚本一上来就把翻译好的句子直接 append 到目标文件，崩溃一次整个文件就废了。

## 第二个细节，格式保留

工具支持 EPUB、SRT、DOCX、TXT 四种格式。

EPUB 不是简单的 txt，里面有目录、章节、字体样式、有时候还有图片描述。SRT 字幕文件更麻烦，每条字幕都带着精确到毫秒的时间码，你只翻文字、时间码必须一秒不差地保留。

我试了一个 1080P 电影的英文 SRT，2000 多条字幕，翻完之后时间轴完全对得上，直接拖进播放器就能看。这个体验比某些专业字幕翻译软件还顺滑，因为它根本没让 LLM 去理解时间码，时间码是程序级别保护起来的，LLM 只看到纯文本。

EPUB 也是一样的逻辑。它把书拆成 HTML 片段送进模型，翻译完再用原来的 XML 结构包回去。所以你拿到的不是一堆乱码堆在一起的 txt，而是一本可以直接导进多看、Apple Books、微信读书的成品 EPUB。

这一点我觉得是绝大多数自制翻译脚本的死穴。能跑通翻译只是 30% 的工作，剩下 70% 是怎么把翻译结果塞回原始文档结构里不出错。

## 第三个细节，provider 是真正的 provider

它支持的后端列表很长，Ollama、OpenAI、Gemini、Mistral、DeepSeek、Poe、OpenRouter，还有任意 OpenAI 兼容端点（llama.cpp、LM Studio、vLLM 都行）。

对国内用户来说，这个组合非常友好。

如果你电脑上跑得动 Ollama，直接 `ollama pull qwen3:14b` 装个国产模型，本地翻译，0 成本 0 联网。Qwen 系列的中文输出质量目前在我看来比 Mistral、Gemma 这些海外开源模型靠谱。

如果你电脑跑不动 14B，又不想被某些云端服务的字符费坑，国内可以走 OpenRouter，把目标模型选成 DeepSeek-V3 或者 Qwen3-Max，按 token 计费，翻一本 30 万字的书大概几块钱人民币。

```
python translate.py -i book.epub \
  --provider openrouter \
  -m deepseek/deepseek-chat \
  -sl English -tl Chinese
```

就这一行命令。

`.env` 里配一次 API key，下次直接复用。MAX_TOKENS_PER_CHUNK 默认 400，翻译质量和速度的平衡点比较合理，但如果你用的是上下文窗口大的模型（Gemini 2.5 那种），可以调到 2000 以上，每个 chunk 带更多上下文，术语前后一致性会好很多。

## 一个我踩到的坑

刚开始我用 Ollama 跑 qwen3:14b 翻一本 700 页的小说，跑到第 200 页发现一个问题，主角的名字在不同 chunk 里被翻成了三个不同的中文。

这不是这个工具的问题，是所有「分块翻译」的通病。每个 chunk 是独立请求，模型不知道前一个 chunk 把"Aria"翻成了"艾莉亚"。

解决办法是开工具自带的 glossary 功能，在翻译前先扫一遍全文提取专有名词，建一个术语表，每个 chunk 请求的时候把术语表注入到 system prompt。我自己手动维护了一份小说人名表，效果立刻就稳了。

## 我的判断

我认为这类工具的真正价值不在「翻译质量超过 DeepL」这种维度上比拼，DeepL 的句子流畅度短期内还是没人能超过。

它的价值在于把翻译变成一个**可控、可中断、可定制**的管道。

你可以指定模型，可以塞自定义 prompt，可以加术语表，可以本地跑也可以云端跑，可以翻 100MB 的 EPUB 也可以翻 100KB 的字幕。这种自由度是任何 SaaS 翻译产品给不了的，因为他们的商业模式就建立在「按字符收费 + 限制大小」上。

而开源 + 本地 LLM 的组合，正好把这个商业模式的根挖掉了。

对独立开发者、技术译者、字幕组、想读原版资料的研究者来说，这是一类长期需求被一类长期供给堵着的窘境。`TranslateBooksWithLLMs` 不是第一个解决方案，但它是我目前用过工程化做得最完整的一个。

如果你 GitHub 上 star 过一堆 LLM 翻译脚本但都没真正跑通过整本书，这周末花 30 分钟把 Ollama 装起来试试。回头你会发现，那本一直拖着没看的英文书，可能这周就能看完了。
