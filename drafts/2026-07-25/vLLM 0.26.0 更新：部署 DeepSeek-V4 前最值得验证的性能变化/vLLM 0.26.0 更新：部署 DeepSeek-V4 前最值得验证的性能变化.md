# vLLM 0.26.0 更新：部署 DeepSeek-V4 前最值得验证的性能变化

准备部署 DeepSeek-V4 的团队，vLLM 0.26.0 最有价值的部分，不是新增了多少模型，而是把路由、稀疏计算和多硬件适配同时往前推了一步。

这次更新直接碰了混合专家模型推理的几个高成本环节。专用路由内核带来 2.94% 的端到端每输出词元耗时改善，`fused_topk_bias` 内核达到 1.5 至 2 倍性能，移除冗余 repeat 和 copy 又改善了 1.8% 的端到端每输出词元耗时。

这些数字还不能直接等同于业务吞吐提升。更实用的做法，是把 0.26.0 当成一次明确的复测信号，重新测吞吐、首字延迟、显存占用和硬件兼容性，再决定是否升级生产环境。

## 判断旧瓶颈是否落在路由链路

DeepSeek-V4 这类混合专家模型，计算量并不只由参数规模决定。每个词元要经过专家选择、路由和数据搬运，内核启动、Top-K 选择以及重复复制都会进入关键路径。

vLLM 0.26.0 的优化组合很有针对性。

| 变化 | 发布说明中的结果 | 应关注的部署指标 |
| --- | --- | --- |
| DeepSeek-V4 专用路由内核 | 端到端 TPOT 改善 2.94% | 稳态吞吐、TPOT |
| `fused_topk_bias` 融合内核 | 内核性能达到 1.5 至 2 倍 | 解码阶段耗时、GPU 利用率 |
| 移除冗余 repeat 和 copy | 端到端 TPOT 改善 1.8% | 显存带宽压力、TPOT |

这里要避免一个常见误判。单个内核快 1.5 至 2 倍，不代表服务吞吐也会同比增长。端到端收益还会受到批大小、输入输出长度、张量并行配置和请求并发度影响。

## 检查稀疏推理是否真正变得可用

0.26.0 同时加入了稀疏解码和稀疏预填充优化。相比只优化一个热点内核，这类变化更可能影响不同请求形态下的性能曲线。

长输入、短输出的任务主要观察预填充阶段。短输入、长输出的任务则更容易暴露解码和路由开销。两类流量混在一个平均数里，很可能把优化效果冲淡。

ROCm 路径还增加了用于 HCA 预填充的两阶段压缩器，并为 AMD 和 XPU 增加 DSpark 推测解码支持。这表明 DeepSeek-V4 的优化并非只围绕一种硬件路径展开，但发布说明没有给出各硬件组合的统一端到端结果。

所以，AMD、XPU 或混合硬件环境更应该关注功能是否正确启用、是否发生回退，以及相同请求集下的延迟分布，而不是直接套用 CUDA 路径的数字。

## 把升级前后压到同一组指标

升级判断需要固定模型、硬件、并行配置、请求数据和并发度。否则，版本变化与配置变化会混在一起，结果很难解释。

建议至少保留四组对照数据。

| 指标 | 要回答的问题 | 容易误判的地方 |
| --- | --- | --- |
| 吞吐 | 相同并发下，每秒完成的词元是否增加 | 只看峰值，不看持续负载 |
| 首字延迟 TTFT | 预填充优化是否改善用户等待 | 输入长度分布发生变化 |
| 每输出词元耗时 TPOT | 路由和稀疏解码是否改善稳态生成 | 把 TTFT 混入平均延迟 |
| 峰值显存 | 融合与复制移除是否改变显存压力 | 批大小或缓存配置不一致 |

兼容性要单独记录，包括模型能否加载、目标精度是否正常、路由内核是否生效、稀疏路径是否回退，以及推测解码在对应硬件上能否稳定运行。

若业务还使用 LoRA，也应增加一次生成质量回归。0.26.0 支持为生成模型使用 fp32 `lm_head`，并扩展到 LoRA 路径，同时提供 ROCm `torch.mm` 快速路径。它更接近准确性与兼容性改进，不能只用吞吐测试代替验证。

## 决定哪些团队值得立即验证

已经在评估 DeepSeek-V4、服务成本主要落在高并发生成，或正在使用 AMD 与 XPU 路径的团队，值得尽快建立 0.26.0 对照环境。这次更新覆盖的正是路由、稀疏推理和多硬件执行链路。

只运行稠密模型、当前瓶颈来自网络或业务排队的服务，不必因为几个内核数字立刻升级。内核优化只有进入真实关键路径，才会转化成可见收益。

我的判断是，0.26.0 更像一个值得验证的 DeepSeek-V4 部署基线，而不是无需复测即可替换生产版本的答案。它给出了清晰的优化方向，也留下了必须由具体硬件和流量形态回答的问题。

最合适的动作，是从现有请求中抽取一组固定样本，在相同配置下分别跑当前版本与 0.26.0。先拿到吞吐、TTFT、TPOT、峰值显存和兼容性记录，再讨论升级收益。
