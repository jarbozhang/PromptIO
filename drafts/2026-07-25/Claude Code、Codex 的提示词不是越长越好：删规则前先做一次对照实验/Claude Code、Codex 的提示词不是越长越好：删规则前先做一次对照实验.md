# Claude Code、Codex 的提示词不是越长越好：删规则前先做一次对照实验

如果你的 Claude Code 或 Codex 总在规则之间打架，改了又改，问题未必是提示词还不够详细。它也可能已经详细过头了。

我更愿意把提示词精简当成一次工程实验，而不是一场大扫除。挑一个真实代码任务，同时测试厚重规则、精简边界和按需加载三种配置，再用完成质量、冲突次数、Token 消耗与返工量决定哪些内容该留下。

这样做的收益很直接。你不会因为一句“提示词越短越好”就贸然删掉安全边界，也不会继续为一份越来越厚的 AGENTS.md 或 CLAUDE.md 支付上下文成本。

## 厚规则并不等于高控制力

常见误解是，Agent 犯过一次错，就应该补一条规则。几个月后，文件里既有“尽量自主完成”，又有“任何改动都先确认”，既要求“保持改动最小”，又要求“顺手清理相关问题”。

每条单独看都有道理，放在一起却需要模型先做一次规则仲裁。真正执行代码任务之前，它得判断哪些约束优先、哪些示例仍然适用、哪些要求只属于旧项目。

原帖提到，面向更强模型的 Claude Code 系统提示词曾大幅精简，代码评测几乎没有下降。帖子的核心判断不是提示词越短越先进，而是强模型已经能从代码库和工具反馈中推断大量常规做法，重复说明反而可能限制探索范围。

我认同这个方向，但不认同直接把长文件删到只剩三句话。长度不是目标，减少无效决策才是目标。

## 用同一个任务拆穿长度幻觉

我会选一个结果容易验收、又需要读懂仓库的任务，例如给现有接口增加一个参数，同时补测试、更新调用方并通过项目检查。不要拿改错别字做实验，那种任务测不出上下文设计的差别。

然后建立三份独立配置，每次从相同提交开始，并尽量保持模型、任务描述和工具权限一致。

| 配置 | 提供给 Agent 的上下文 | 想验证的问题 |
| --- | --- | --- |
| 厚重规则 | 当前完整规则、固定流程、示例和禁令 | 更多预设是否真的减少错误 |
| 精简边界 | 只保留安全限制、仓库特例和验收要求 | 模型能否从代码自行推断常规做法 |
| 按需加载 | 精简边界，加可调用的测试与审查 Skills | 延迟加载能否兼顾质量与上下文成本 |

三轮都交给 Agent 独立完成，不在中途暗示哪种配置更好。任务结束后再统一检查代码、测试、过程记录和最终说明。

这不是为了给 Claude Code 与 Codex 排名。实验对象是你自己的上下文配置，以及它在真实仓库里制造了多少帮助和阻力。

## 别只盯着 Token 数字

把规则从几千 Token 压到几百 Token 很醒目，但单看压缩率很容易得出错误结论。少消耗一些上下文，却多返工两轮，并不划算。

我会同时记录四项结果。

| 指标 | 具体记录方式 |
| --- | --- |
| 完成质量 | 验收条件通过多少，是否引入回归，改动是否符合仓库习惯 |
| 冲突次数 | Agent 是否反复询问、摇摆方案，或明确提到规则矛盾 |
| Token 消耗 | 输入上下文与整个任务的消耗分别记录，避免只看启动成本 |
| 返工量 | 人工指出的问题数、补丁轮次，以及被撤销的无效改动 |

还有一个容易漏掉的信号，Agent 是否能解释自己的取舍。如果结果碰巧通过，但它依赖了错误假设，这条规则仍然不能轻易删除。

我的判断标准很朴素。精简后质量持平，冲突与消耗下降，这条规则大概率只是重复信息。精简后错误稳定复现，而且错误无法从代码、测试或工具说明中推断，这条规则才有资格回到常驻上下文。

## 该删的不是经验，而是错误的加载位置

很多团队把所有经验都塞进启动文件，因为担心 Agent 用到时找不到。结果是数据库迁移规范、前端截图要求、发布检查和文档格式每次任务都一起加载。

更准确的做法是按使用频率重新分层。

常驻上下文保留安全绝对项、仓库独有约束、不可从代码发现的坑，以及明确的完成标准。代码审查、发布流程、专项测试等低频知识放进 Skills，在任务需要时加载。能由测试、类型系统、格式化工具或 CI 表达的要求，则尽量交给工具执行。

这也解释了为什么“搭好工作环境”比“写好员工手册”更接近现在的上下文工程。文档负责提供判断所需的独特信息，工具负责给出确定反馈，模型负责处理两者之间的选择。

## 让删除动作也能随时撤回

真正危险的不是删规则，而是删完没有记录，也没有办法判断退化来自哪里。

我会把三份配置都纳入版本控制，为每条删除项留下简短理由，并保存实验任务、验收结果和返工记录。某项约束一旦暴露出稳定退化，就恢复它，或者把它改写成测试与按需 Skill。

下一次准备给 AGENTS.md 或 CLAUDE.md 再加一条规则时，先拿同一个任务跑完这组三路对照。能被代码读出来的，不必重复讲。只有无法推断、无法自动验证、遗漏后代价明确的信息，才值得长期占用上下文。
