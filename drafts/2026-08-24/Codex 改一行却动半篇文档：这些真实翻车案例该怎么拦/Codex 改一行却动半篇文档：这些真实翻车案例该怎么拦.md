# Codex 改一行却动半篇文档：这些真实翻车案例该怎么拦

如果你用 Codex 改过代码，却在提交前发现 README 被顺手重写、旧方案还躺在文档里、版本状态已经过期，这篇复盘对应的就是你的工作现场。

真正危险的并不是改动很大，而是改动看起来都通顺。审查者容易把注意力留给代码，文档里的范围扩张、事实漂移和漏改却悄悄进入提交。

读完可以得到一套更具体的拦截思路，把范围控制、事实一致性和用户可见文案纳入同一次审查。

## 还原一次失控的文档修改

KC 在长期 review Codex 的过程中，反复抓到几类问题。任务原本只要求修改一点内容，Codex 却可能重写半篇 README。讨论时出现的中间思路和已经放弃的方案，也可能被保留在最终文档中。

另一类问题更隐蔽。同一个事实散落在多个位置，某次修改只更新了其中一处。或者长期文档写死了版本与当前状态，今天正确，过一段时间就变成过期信息。

代码完成也不代表交付完成。功能行为改变后，`--help`、README、MCP description 等用户可见入口可能仍然描述旧行为。诊断信息如果无节制地输出，真正有用的内容反而会被大量文本淹没。

这些事故有一个共同点。单看某一句往往没有明显错误，放回整个产品和仓库才会发现不一致。

## 找到事故链条里的四个断点

文档失控通常不是一次离谱生成，而是四个判断连续缺席。

**任务边界没有被固定。** Codex 看到相邻段落存在表达问题，便可能把局部修改理解成整体优化。重写后的文字也许更顺，却扩大了本次提交的责任范围。

**讨论材料没有退出最终产物。** 方案探索允许保留分支、猜测和被否决的方向，交付文档却需要呈现当前有效结论。两种文本混在一起，读者无法判断哪条仍然成立。

**事实缺少单一归属。** 同一状态被复制到 README、帮助文本和工具描述中，每增加一个副本，就增加一个漏改入口。版本号和阶段状态写进长期文档后，还会自然积累时效风险。

**用户可见文本被当成附属品。** KC 总结得很直接，用户可见文本就是产品行为。命令帮助、README、MCP description 和 diagnostics 不是代码之外的装饰，而是用户理解系统的接口。

## 为什么只要求少改一点还不够

在提示词里写一句“只修改必要内容”，只能表达偏好，不能形成验收标准。模型仍然需要判断什么叫必要，而这个判断恰恰容易扩大。

只检查 `git diff` 的行数也不够。小范围修改可能留下旧事实，大范围修改也可能包含合理的同步更新。真正需要审查的是每一处变化是否由任务触发，以及所有用户可见入口是否保持一致。

把规则做成固定 skill 能降低重复提醒的成本，但评论里也有人提出，这类规则像模型补丁，模型行为调整后可能需要随之更新。还有用户会用 benchmark 对原始 Codex 和自己的配置做 A/B test。这个分歧很重要，规则不能只靠感觉长期沿用，还需要用稳定任务反复验证。

## 把提交前审查改成四次对照

修复重点不是继续堆更多写作指令，而是把审查对象拆开。

第一遍对照任务范围。逐个检查修改文件和段落，追问它是否服务本次需求。若答案只是“顺便更清楚”，应从当前提交移出，避免审查范围被稀释。

第二遍对照有效方案。搜索讨论过程中的候选方案、临时状态和废弃路径，确认最终文档只保留当前结论。无法确定的内容宁可回到决策记录，也不要混进面向用户的说明。

第三遍对照事实来源。检查版本、状态、默认值和能力描述是否被多处复制。能够引用稳定入口时，减少手工重复。必须重复的事实，则把所有副本列入同一次变更检查。

第四遍对照用户入口。功能行为发生变化时，沿着用户实际看到的界面检查 `--help`、README、MCP description 和 diagnostics。验收问题不是“代码是否完成”，而是“用户是否还会被旧文案带向错误操作”。

诊断输出还要额外检查信噪比。保留能帮助定位问题的信息，避免让大量低价值内容遮住关键线索。

## 留下一张可复用的事故卡片

**事故表现**

局部任务扩成 README 重写，废弃方案进入最终文档，长期状态逐渐过期，功能完成后用户可见文案仍停在旧版本。

**触发条件**

任务边界模糊，事实多处复制，文档与代码分开验收，生成结果只检查语句是否通顺。

**拦截位置**

提交前分别核对改动范围、有效方案、事实归属和用户入口，再用一个稳定任务验证规则是否仍然有效。

**放行标准**

每处改动都能对应当前需求，没有失效方案残留，时效信息有维护路径，所有用户可见描述与实际行为一致。

Codex 写得快，审查就更不能只看它写了什么。还要看它顺手改了什么、忘了同步什么，以及哪些今天正确的句子会在未来悄悄失效。
