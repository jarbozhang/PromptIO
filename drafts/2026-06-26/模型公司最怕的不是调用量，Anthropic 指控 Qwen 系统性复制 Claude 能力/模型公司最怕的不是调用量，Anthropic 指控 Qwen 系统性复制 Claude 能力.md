# 模型公司最怕的不是调用量，Anthropic 指控 Qwen 系统性复制 Claude 能力

我看到 Anthropic 这封信，第一反应不是“又一场模型公司口水战”。

真正刺眼的是那组数字，约 25,000 个虚假账号，4 月 22 日到 6 月 5 日，超过 2880 万次 Claude 交互。

如果这件事最终被证实，它提醒所有做 API、模型服务和 Agent 平台的团队一件事，调用量不一定都是收入，有些调用量是在把你的核心能力一点点抽走。

这篇我不把它写成谁赢谁输。更值得复盘的是风险链条，一个高价值模型为什么会被系统性复制，常见的账号封禁和额度限制为什么不够，以及团队应该怎样重新看待“异常行为”。

## 把异常调用当成能力外流现场

Anthropic 致信美国参议院银行委员会和白宫，指控阿里巴巴旗下通义千问 Qwen AI 实验室关联方对 Claude 发起大规模蒸馏攻击。

公开报道提到，CNBC 和 Reuters 获取的信件显示，相关方在 4 月 22 日到 6 月 5 日之间，通过约 25,000 个虚假账号与 Claude 进行了超过 2880 万次交互。Anthropic 称目标集中在 Claude 的软件工程和 Agent 推理能力。

我觉得这里最值得警惕的不是“2880 万次”本身，而是它背后的组织方式。

一次普通滥用可能是刷量、套利、薅额度。一次蒸馏攻击更像是有计划地采样，一个问题簇接一个问题簇地逼近模型的高价值能力区，再把输出整理成训练材料。

Anthropic 今年 2 月曾公开点名 DeepSeek、MiniMax 和 Moonshot AI，称三家通过约 24,000 个假账号产生了 1600 万次交互。现在这次被指控的单一关联方交互量，接近前一次三家合计的两倍。

从风控角度看，这不是一个“账号太多”的问题，而是“能力被批量查询”的问题。

## 拆开蒸馏攻击的事故链条

蒸馏攻击 adversarial distillation，可以先理解成一个很朴素的动作，拿强模型当老师，大规模提问，收集回答，再用这些问答训练另一个模型。

它危险的地方不在于某一次提问泄露了什么秘密，而在于重复足够多次以后，攻击者拿到的不是单条答案，而是一片能力边界。

软件工程和 Agent 推理尤其适合被抽取。因为这类能力不是只回答事实，而是体现在任务拆解、工具选择、错误恢复、代码修改、测试判断这些连续动作里。

一次“帮我修 bug”的对话可能只是一条样本。上百万次变体以后，就可能覆盖大量真实工程场景。

我会把这条事故链拆成四段。

账号层，攻击者用大量虚假账号绕开单账号限制。

任务层，问题不是随机闲聊，而是集中打向高价值能力，比如代码、Agent、推理。

采样层，重复生成不同难度、不同上下文、不同失败形态的输出。

训练层，把模型输出重新包装成自己的训练数据或评测材料。

这就是为什么模型公司最怕的不是单纯调用量大。调用量大可以扩容，可以计费，可以限速。系统性复制会把研发投入变成别人的捷径。

## 账号和额度为什么挡不住这类风险

很多团队第一反应会是，限流、封号、实名、验证码。

这些当然要做，但如果风控只停在账号维度，很容易漏掉真正的攻击意图。

25,000 个账号分摊 2880 万次交互，平均下来每个账号也可以伪装得不那么夸张。单账号看起来像重度用户，整体放在一起才像一台采样机器。

额度也一样。额度解决的是“每个入口能用多少”，不解决“这些入口是否在共同完成同一个抽取任务”。

对模型服务来说，异常不一定是同一 IP、同一账号、同一时间的尖峰。更麻烦的是跨账号的相似任务、相似 prompt 变体、相似输出目标，以及长期稳定地打向某几个高价值能力区。

我认为这件事给 API 团队的最大提醒是，风控不能只盯身份，还要盯意图。

如果一个平台把最强的代码修复、Agent 编排、复杂推理能力开放成 API，又没有对任务簇和输出用途做长期画像，那它看到的只是收入曲线，攻击者看到的是训练集。

## 修复动作要从“防薅羊毛”升级到“防能力采样”

做模型服务的团队，可以把这次事件当成一次风控桌面演练。

第一层是账号可信度，不只是注册门槛，还包括账号之间的关联图谱。大量账号如果共享相近任务模式、调用节奏、失败重试方式，就不该被当成完全独立的用户。

第二层是任务相似度，尤其要看跨账号 prompt 是否在围绕同一能力反复变形。比如大量软件工程题、Agent 工具调用题、代码评审题持续出现，就要进入更细的风险审查。

第三层是能力热区保护。不是所有能力都同等敏感。普通问答、格式转换、摘要任务和高阶代码推理，对公司资产的价值完全不同。越接近核心能力，越需要更强的速率、审计和用途约束。

第四层是输出采样异常。蒸馏不只需要输入，也需要稳定拿到高质量输出。如果某批账号持续追求可训练的完整答案，比如标准化步骤、代码解释、失败修复轨迹，就要把它当成信号。

第五层是同业情报共享。源材料提到 Anthropic、OpenAI 和 Google 已经联合共享蒸馏攻击情报。这个动作说明，大模型公司的风险边界已经不只在自家控制台里。

这里有个现实矛盾，风控太松，能力被抽取。风控太紧，正常开发者体验会变差。

所以我不赞成一刀切地把所有高频调用都打成风险。更合理的做法是把“高频”升级成“高频加高相似度加高价值能力命中”。只有三者叠加，才更像系统性采样。

## 这场复盘给小团队的提醒

很多小团队会觉得，蒸馏攻击是 Anthropic 这种模型公司的烦恼，跟自己关系不大。

我反而觉得，小团队更应该早看这件事。

因为今天被蒸馏的是 Claude 的软件工程和 Agent 推理能力，明天也可能是某个垂直模型的行业知识库、某个 Agent 平台的工作流模板、某个 SaaS 的自动化策略。

只要你的产品把高价值判断包装成可调用接口，就会遇到同一个问题，用户是在使用能力，还是在搬运能力。

我会给团队留一张事故卡片，适合放进 API 风控评审里。

事故名称，系统性能力抽取。

可见症状，调用量增长，账号分散，单点异常不明显。

真正风险，高价值能力被批量采样，输出进入对方训练或产品流程。

最容易漏掉的信号，跨账号任务相似、能力热区集中、prompt 变体稳定、输出格式适合再训练。

修复优先级，先做能力热区分级，再做跨账号任务聚类，最后把异常调用从计费问题提升为资产保护问题。

可以接受的摩擦，对高风险任务增加审计、速率和用途校验。

不能接受的盲区，只按账号、IP、额度判断风险。

这次指控还有政治和商业背景。源材料提到，Anthropic 同时在和美国政府就模型访问限制发生分歧，也正处在秘密提交 IPO 申请后的敏感阶段。阿里巴巴对此未予置评。

这些背景会影响事件走向，但不影响工程判断。

如果你在做模型 API 或 Agent 应用，别只问今天有多少调用。更该问的是，最贵的那部分能力，正在被谁、用什么节奏、以什么任务结构反复访问。

调用量进账以前，先确认它不是一条能力外流管道。
