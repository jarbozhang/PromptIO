# 智谱居然把 GLM-5 上线踩的坑写出来了，国产大厂这次有点东西

刷技术社区看到 z.ai 官博一篇标题就把人扎醒，《Scaling Pain of Coding Agent Serving》，副标题是"Debugging GLM-5 at Scale"。

我点进去之前心里是有预期的。国内大厂写故障复盘，大多停在"我们遇到挑战、克服困难、继续前进"这种公关稿水平。能把生产事故拆到时序图、把锅指给自己代码、还把修复链接挂出来的，国内一只手数得过来。

结果智谱这次是真的写了。我读完最大的感觉是，国产 AI 公司终于开始走"把工程经验主动公开"这条路了。

## 故事是这样的

GLM-5 系列在 3 月开始在线上观察到三类异常输出，乱码、重复、罕见字符。这三个症状一上来就有迷惑性，长上下文场景下"质量下降"长得就是这样，很多人第一反应是模型本身退化了。

智谱团队第一步反应很关键。他们没有上来调精度、没有动模型，先回答了一个更基础的问题，**这到底是模型问题还是基础设施问题。**

判断方法也朴素，模型问题在固定输入下应该稳定复现。他们把用户报的 bad case 抓回本地跑了几百次都没复现。直到把系统压力调到极限态，这下出来了。**异常率每万次大概 3 到 5 次**，且与请求内容无关、只跟系统压力相关。

定性清楚了，这是高并发推理系统里的一致性 bug。

## 一个让我拍桌子的细节

异常输出本身很难自动检测。乱码和罕见字符用正则会有大量误报，用模型分类器又跑不起对照实验。

智谱团队的破法很妙，他们把**投机解码的指标拿来当异常信号用**。

投机解码本来是个性能优化，一个小模型先猜几个字、大模型验证决定是否接受。但他们在事故现场发现这两个指标跟异常类型有非常稳定的对应关系，乱码的时候接受率极低，重复的时候接受率极高。

于是他们直接上线策略，生成到一定长度后如果信号异常就主动终止，把请求扔回去重试。

一个原本只用来加速的优化，被改造成了在线质量监控信号。这是教科书级的工程师思路，**把已经在系统里的、低成本的、副产品级别的信号拿来兜底**，比新加一个分类器优雅得多。

## 真正的 bug 是什么

我挑一个最经典的讲。

他们的推理系统拆成两段，前一段处理输入，后一段做输出。为了控制延迟，如果前段超时没完成，后段会主动放弃、回收已分配的内存槽位。

问题是这个"放弃"信号没正确传回前段。后段这边把槽位回收给新请求用了，**但前段之前发起的跨节点数据写入还在飞**，最后落地的时候写到了已经被新请求占用的那块内存。新请求的状态被破坏，输出就异常了。

修复方案就是加显式同步，确保所有飞行中的写入都完成才能复用内存。修完之后**异常率从约 0.1% 降到 0.03% 以下**。

这个 bug 让我想到的不只是修复本身。它揭示了**任何引入了内存复用 + 跨节点异步写的架构都需要明确的时序约束**，这一点放进推理工程师的知识库，对所有走类似路线的国产推理引擎都有价值。

## 我的判断

这篇 blog 的真正价值不在 bug 本身，而在三件事。

**第一，国产大厂主动写生产事故复盘文档了。** 过去要看这种内容只能去 OpenAI、Anthropic 的 blog 翻，或者去开源项目的 issue 区考古。智谱这次主动写出来，等于把国产推理工程师的知识库补上了重要一块。

**第二，它把修复 PR 提给了开源社区。** 国产大厂以前对开源是"我能用就行"，这次智谱明确把改动回馈给上游开源项目，这种姿态对生态健康度的意义远超技术细节本身。

**第三，投机解码当异常监控信号这个技巧白给了。** 任何在生产系统里已经存在的"模型自我验证"信号，都可以反过来当质量监控用。Inference engineer 看完会有不少新想法。

要泼一点冷水的话也有。文中给的数据点都是智谱自己的口径，没有第三方复现。但作为一篇生产事故复盘，**信息密度已经远高于国内同行的平均水平**。

国内做 Coding Agent 的团队越来越多，写代码的 agent 一旦上量，长上下文 + 高并发的所有坑都会被踩一遍。这种主动公开的姿态，希望多看到几家。

最后留个钩子，致谢里出现了中科院计算所的体系结构团队。智谱这次合作背后那条产学研链条，值得单独写一篇。
