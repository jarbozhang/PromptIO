# Claude Opus 5 接入 Python SDK：动态增删工具会改变什么

如果你的 Python Agent 会在运行中切换工具、控制权限或处理额度回退，Anthropic Python SDK 0.120.0 值得进入验证队列。

这次更新不只是增加 Claude Opus 5。更关键的变化，是 SDK 开始暴露工具新增与移除区块、`tool_change` 事件，并扩展客户端回退信用令牌类型，同时加入服务端回退的默认选项。

读完可以得到一个直接判断。只调用固定工具的普通应用不必因版本号立即迁移，依赖动态工具集或回退链路的 Agent，则应该尽快跑一轮最小验证。

## 旧接口把工具当成静态配置

许多 Agent 的工具列表在请求发出前就已经确定。模型能调用哪些函数、连接哪些服务，通常由客户端一次性提交。

这种方式适合固定流程，却难以表达运行中的变化。例如用户完成授权后新增一个工具，进入敏感步骤时临时移除写入能力，或者任务结束后撤销高权限工具。

旧版本缺少专门的工具变更区块和事件时，应用往往只能自己维护状态，再从普通流式内容中推断工具集是否变化。日志、界面状态和实际执行权限容易出现偏差。

## 新版本把三类变化放进接口

0.120.0 的发布说明列出了三项功能更新。

| 变化 | 接口层新增内容 | 对 Python 应用的直接影响 |
| --- | --- | --- |
| 模型接入 | 增加 `claude-opus-5` 模型 | 可以在 SDK 支持的模型类型与请求接口中选择新模型 |
| 工具变化 | 增加工具添加、移除区块和 `tool_change` 事件 | 流式消费者可以显式识别工具集变化 |
| 回退机制 | 扩展客户端回退信用令牌类型，并增加服务端回退默认选项 | 回退决策有了更完整的类型表达和服务端配置入口 |

这里最重要的不是多了一个事件名称，而是 Agent 运行时状态开始获得更明确的协议表达。

应用不必把工具变化只藏在自己的内存状态里。事件处理器、审计日志和交互界面可以围绕同一种变化信号更新。不过发布说明没有给出完整的事件字段和执行顺序，落地代码仍应以 0.120.0 对应的类型定义与官方文档为准。

## 动态工具终于能进入可观测链路

动态增删工具适合三类场景。

一类是按权限开放能力。用户完成某个授权步骤后，Agent 才获得读取日历或写入工单的工具。

一类是按任务阶段收缩权限。分析阶段保留读取工具，确认执行后短暂开放写入工具，完成后再移除。

还有一类是按环境调整能力。某个依赖暂时不可用时，运行中的工具集需要同步变化，界面与日志也要知道工具已经退出。

`tool_change` 事件让这些变化更容易被单独处理。工程上的启发很明确，工具列表不应再被视为只读启动参数，而应被当作需要记录、校验和展示的运行时状态。

但事件出现不等于权限控制已经自动完成。真正执行工具前，应用自身仍要做授权检查。模型可见的工具集、服务端允许的工具集和执行器实际放行的工具集，三者必须一致。

## 回退机制要验证失败路径

客户端回退信用令牌类型得到扩展，同时新增服务端回退默认选项。这会影响依赖回退策略的请求链路，但简短发布说明不足以确认所有触发条件、优先级和计费行为。

升级时不要只验证正常响应。更有价值的是主动制造一次可控失败，观察客户端配置、服务端默认值和最终返回结果如何配合。

尤其要检查旧代码是否对令牌类型做了封闭枚举、是否假设回退只由客户端决定，以及监控系统能否区分主路径与回退路径。否则请求虽然成功，成本归因和故障判断仍可能失真。

## 把升级验证压到一个短任务

用一个测试 Agent 完成单轮任务即可覆盖主要变化。给它两个无副作用工具，在流式会话中记录全部事件，触发一次工具新增和一次工具移除，再模拟一次回退条件。

验收时只盯四个结果。

- `claude-opus-5` 能否通过当前 SDK 的模型参数与类型检查
- 工具变化是否产生独立区块与 `tool_change` 事件
- 事件到达后，本地工具注册表是否与执行权限同步
- 回退发生时，客户端设置、服务端默认行为和日志记录是否符合预期

若项目只使用固定模型与固定工具，继续停留在 0.119.0 的迁移压力有限。若项目已经自己拼接动态工具状态，或者依赖多层回退，0.120.0 的价值更高，因为它可能减少自定义协议和隐式状态。

我的判断是，这个版本真正值得关注的不是 Claude Opus 5 进入模型列表，而是工具变化与回退决策开始成为正式接口的一部分。Agent 要走向长期运行，动态能力和失败路径都必须能被观察。

升级前保留一份现有事件样本，再用同一任务跑 0.120.0。对比事件序列、工具状态和回退日志，比直接替换生产依赖更能说明它是否值得立即采用。
