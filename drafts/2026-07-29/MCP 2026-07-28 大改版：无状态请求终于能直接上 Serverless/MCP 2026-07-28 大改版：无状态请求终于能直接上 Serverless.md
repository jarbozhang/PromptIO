# MCP 2026-07-28 大改版：无状态请求终于能直接上 Serverless

如果你的团队正在维护 MCP 服务，这次更新需要看的不是又多了几个接口，而是原来的会话假设还能不能成立。

2026-07-28 版本把 MCP 从有状态双向协议改成无状态请求与响应协议。负载均衡、Serverless 部署、用户确认和网关鉴权由此获得了更直接的实现路径，依赖 session ID、HTTP+SSE 或动态客户端注册的代码则进入迁移范围。

好消息是，旧能力不会立刻消失。MCP 首次引入正式废弃策略，至少保留 12 个月过渡窗口。团队现在要做的是辨认影响面，把协议迁移放进正常排期，而不是等旧传输不可用时被动处理。

## 把请求从固定实例上解开

旧版 MCP 客户端连接服务端时，需要先握手并取得 session ID，后续请求继续携带这个标识。这个设计适合持续连接，却会让一次会话和某台服务器实例形成绑定。

到了多实例环境，问题就很具体。负载均衡器不能随意把后续请求送到其他实例，服务端还要保存或同步协议层会话状态。Serverless、边缘计算以及 CDN 后的弹性实例，都很难发挥原本的调度优势。

新版本让每个请求独立携带协议版本和客户端信息，请求可以落到任意实例。MCP 服务器因此更接近普通 HTTP 服务，实例扩缩容和故障切换不再先被协议会话卡住。

我认为这是本次改版最重要的变化。它没有消灭状态，而是把状态从协议层移回业务层。

如果工具确实需要跨请求保存进度，规范建议由工具生成句柄 handle，再让模型在后续调用中传递。维护方需要检查的不是有没有状态，而是状态当前藏在哪里。凡是依赖 session ID 查找任务、缓存或用户上下文的逻辑，都应该评估能否改成显式句柄。

## 让用户确认不再依赖长连接

删除资源、创建付费项目等操作，经常需要在执行中途暂停，等待用户补充信息或确认风险。旧协议通常依靠不断开的双向流维持这段交互。

新版本加入 MRTR，也就是多轮往返请求。服务端可以返回需要输入的状态，客户端拿到用户回答后重新发起请求。一次确认因此被拆成多个独立请求，不必为了等待用户而占住连接。

这个变化对 Agent 应用很关键。高风险工具调用需要清晰的确认点，但确认机制不该迫使整条执行链长期挂在同一实例上。MRTR 把人类确认保留下来，同时让后端继续采用无状态调度。

迁移时，我会重点查看三类代码，等待用户输入的双向流、依赖连接存活的超时逻辑、把确认上下文只放在内存里的实现。它们都可能需要改成可恢复的请求状态与业务句柄。

## 把鉴权判断前移到网关

请求头新增 Mcp-Method 和 Mcp-Name 后，网关与防火墙可以直接按方法和名称做路由、鉴权，不必先解析 JSON 请求体。

这会让 MCP 服务更容易进入现有基础设施。团队可以在请求到达业务实例之前，根据工具名称或方法应用访问策略，也能减少网关理解协议正文的成本。

授权部分还要求验证授权服务器的 issuer 参数，用来避免授权服务器混淆问题。动态客户端注册 DCR 已正式废弃，客户端元数据文档 CIMD 成为替代方向。

对维护方而言，这不是只升级 SDK 就能结束的改动。网关规则、授权服务器校验、客户端注册流程和安全测试都需要一起检查。尤其是自行实现授权流程的项目，不能只确认请求还能通，还要确认 issuer 验证确实生效。

## 用过渡窗口拆开迁移风险

Roots、Sampling、Logging 已被标记为废弃，旧版 HTTP+SSE 传输也进入废弃轨道，但它们至少还能使用 12 个月。TypeScript、Python、Go、C# 四个一级 SDK 已同步更新，Rust SDK 以 beta 状态跟进。

新规范包含破坏性变更，迁移成本会随项目对会话标识符、旧传输和废弃能力的依赖程度变化。SDK 团队根据早期测试反馈简化了迁移流程，但生产项目仍应逐项评估。

我会把团队分成三种处理节奏。

| 当前实现 | 建议节奏 |
| --- | --- |
| 强依赖 session ID 或实例内存 | 尽快做影响分析，并验证显式句柄方案 |
| 使用 HTTP+SSE、DCR 或废弃能力 | 在过渡窗口内建立替代路径和回归测试 |
| 已接近无状态 HTTP 架构 | 升级 SDK 后验证请求头、授权和 MRTR 行为 |

AWS 的 Amazon Bedrock AgentCore、Microsoft Foundry、Cloudflare Workers 和 Google Cloud 已宣布支持新规范，Figma、Supabase、Honeycomb 等工具厂商也在跟进。生态开始切换，并不等于每个生产服务都该立即全量升级。

更稳妥的动作是选一条真实但低风险的工具调用链，验证无状态路由、跨请求句柄、用户确认和网关策略。验收通过后，再逐步迁移依赖旧会话与旧传输的部分。

12 个月不是等待期，而是把协议、业务状态和基础设施分开改造的排期空间。先找出代码里所有隐含的会话依赖，迁移工作就已经完成了最难的一半。
