# “电报体”真能省 65% Token 吗？240 次编程任务只省了 8.5%

如果你给 Claude Code 或 Codex 加过“少说废话”的压缩指令，这组结果值得看。它能帮你分清两件经常被混在一起的事，聊天回复变短，和一次编程任务真的更省。

Caveman 的 README 声称可节省 65% 的输出 Token。JetBrains 用 Claude Code 跑 SkillsBench 的 86 个真实编程任务，装与不装 Skill 各跑一遍，同任务、同模型、同预算，累计约 240 次计费试验，花费 106 美元。强制每次回复都启用后，输出 Token 只减少了 8.5%。

我看到这里，最先盯住的不是 65% 和 8.5% 的反差，而是分母。8.5% 仍然只是输出 Token 的变化，不是完整任务账单。要决定是否启用，我会同时看总 Token、任务完成率和每个成功任务成本。

## 误解不在短回复，而在把局部当成全局

Caveman 做的事很直白，让 Agent 删掉冠词、客套和连接词，只保留技术要素。普通聊天原本可能回答五段，压成几句话后，输出减少一大半并不奇怪。

65% 就来自这类聊天场景。问题是，编程 Agent 并不只聊天。

它还要读取系统提示、Skills、MCP 定义、代码文件和工具返回结果。它会搜索仓库、修改文件、运行测试，失败后再读日志、重试和解释。对话框里最后露出的几句话，只是整条任务链的末端。

所以我不怀疑电报体能压缩文字。我怀疑的是，把文字压缩率直接当作任务成本降幅。

## 把那 8.5% 放回完整任务里

JetBrains 的测试已经尽量给 Caveman 发挥空间，甚至强制它在每次回复中生效。在这组测试设定下，8.5% 可以看成偏乐观的输出压缩结果。日常按条件触发，覆盖率还会更低。

完整账单更接近下面这条关系。

`总 Token = 输入侧上下文 + 输出侧内容 + 返工产生的新轮次`

输入侧包含系统提示、文件内容、Skills、MCP 和工具结果。输出侧除了给开发者看的说明，还可能包含工具调用参数。一次追问又会让 Agent 重新读取信息、调用工具并生成回答。

只削短最后的说明文字，就像差旅预算里机票、酒店和打车都没动，只取消每天一瓶水。数字会下降，但很难成为主要成本策略。

## 短到失去关键信息，节省会变成返工

“Fixed auth. Tests pass.” 看起来干净利落，却没有告诉我修的是登录过期、权限校验还是刷新令牌，也没有说明跑了一个单元测试还是完整测试套件。

如果改动碰到数据库、兼容性或安全边界，我还得继续追问。Agent 随后可能重新读取文件、再跑测试、再解释一次，前面省下的几十个 Token 很快就被吃回去。

电报体能够成立，依赖双方共享足够多的背景。“母病速归”只有四个字，收报人却知道母亲是谁、家在哪里、为什么要回来。编程任务面对不断变化的代码和陌生上下文，这种默契并不稳定。

我的判断是，啰嗦并不总是浪费。有些解释承担的是纠错功能，帮助开发者及时发现 Agent 理解错了任务、漏跑了测试，或者把局部修复误报成完整交付。

## 用三个指标重跑自己的任务

我会把压缩指令做成一个 A/B 变量。固定模型、预算、任务集、代码版本和验收口径，只改变是否启用电报体，然后把整条任务链记入结果。

| 判断维度 | 记录方式 | 通过条件 |
| --- | --- | --- |
| 总 Token | 累计每个任务的输入与输出 | 不能只统计最后一条回复 |
| 任务完成率 | 使用同一套测试与验收标准 | 压缩前后不能靠降低完成率换节省 |
| 每个成功任务成本 | 总成本除以成功任务数 | 失败、追问和重试全部入账 |

工具调用次数和重试轮数也要留着，它们能解释成本为什么变化。如果输出下降，但完成率也下降，或者追问与工具调用增加，就不能得出“更省”的结论。只有总 Token 和每个成功任务成本一起下降，完成率又保持稳定，这个开关才适合你的工作流。

我更愿意让 Agent 在进度播报里简短，在交付结果里保留改了什么、验证了什么、还有什么风险。真正值得优化的，通常是少加载无关的 MCP 和 Skills、控制输入上下文、减少走错方向后的返工。

选一组你每周都会重复的真实任务，按相同条件跑一次对照。等数字落到“每个成功任务成本”，再决定电报体该不该常开。
