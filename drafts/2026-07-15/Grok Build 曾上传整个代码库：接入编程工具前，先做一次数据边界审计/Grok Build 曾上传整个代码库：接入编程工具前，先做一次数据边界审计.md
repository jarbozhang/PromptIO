# Grok Build 曾上传整个代码库：接入编程工具前，先做一次数据边界审计

让编程代理进入真实仓库前，最该问的不是它会写多少代码，而是它能碰到哪些文件，以及哪些数据会离开本机。

这起 Grok Build 事件把风险链展示得很完整。Cereblab 披露，CLI 曾打包整个代码仓库并上传到 Google Cloud，范围包括被要求不要打开的文件，以及研究人员所说的已从历史中删除的秘密。The Verge 报道称，公司随后关闭了这项行为。

对团队最有用的动作，是把事件改写成一次数据边界审计。在受控仓库里检查当前版本的文件访问与网络行为，再复核忽略规则、密钥清理、网络出口和最小权限。

## 把三个边界分开画

一个 `.gitignore` 不能同时承担提交、读取和传输三种控制职责。

- 提交边界决定哪些文件进入版本记录，忽略规则主要服务这一层。
- 读取边界决定代理进程能打开哪些路径，需要操作系统权限、沙箱或独立工作区约束。
- 传输边界决定哪些内容可以离开本机、发往什么地址，需要网络策略和可核查的日志。

事故里最关键的信号，是被要求不要打开的文件仍进入了上传范围。自然语言约束可以指导代理，却不能代替文件权限和出口控制。

审计对象应覆盖已跟踪源码、被忽略或未跟踪的文件、环境配置、凭据文件、`.git` 元数据，以及历史记录中残留的秘密。这些是需要主动排查的风险面，不是对事故文件范围的追加推断。

## 沿四个节点还原失效链

1. CLI 为编码任务收集仓库上下文。
2. 打包范围扩大到整个代码仓库，没有停在任务所需文件。
3. 数据包被上传到 Google Cloud，其中包括读取约束之外的文件和已删除的历史秘密。
4. 事件报告后，研究人员观察到服务端返回 `disable_codebase_upload: true`，代码库上传不再触发。

这条链里，云服务商并不是核心问题。真正的失效发生在收集和打包阶段，数据范围没有被硬控制挡住。

服务端开关降低了当前风险，但它仍是远端可变配置。客户端更新、配置变化或服务行为调整后，团队不能仅凭一次关闭记录就永久放行。

## 把控制点放到传输之前

接入真实仓库前，可以按下面几层收紧权限。

- **控制可见范围**，在一次性工作区或隔离环境运行，只挂载任务需要的目录，不让进程默认看到个人密钥目录、凭据缓存和相邻仓库。
- **清理秘密痕迹**，同时扫描工作区与 Git 历史。发现真实密钥后优先轮换，再处理文件和历史记录，删除文本不能撤销已经泄露的凭据。
- **分开验证规则**，分别测试 `.gitignore`、工具自己的排除规则和文件系统权限。没有进入提交记录，不等于代理无法读取。
- **限制网络出口**，为代理进程设置必要地址的允许列表，记录目标域名、连接时间和异常流量。没有业务需要时，不给它任意上传通道。
- **缩小身份权限**，使用专用账号、短期凭据和只读令牌，不让编码任务默认继承生产环境权限。
- **管理版本变化**，固定通过审计的客户端版本。版本、配置或服务策略变化后，重新执行边界测试。

## 用受控仓库验收当前版本

准备一个不含真实业务代码的一次性仓库，放入四类虚假标记。

- 正常源码中的标记
- 被 `.gitignore` 排除的标记
- 明确禁止读取文件中的标记
- 曾提交、随后从当前工作区删除，但仍留在测试历史中的标记

所有标记都应是无效随机字符串，不能拿真实密钥充当探针。随后只交给 Grok Build 一个边界明确的小任务，例如读取指定说明文件并修改一个无关文本。

验收不能只看最终回答有没有提到标记。还要观察进程打开了哪些文件、是否生成整库归档、连接了哪些地址，以及请求内容、日志或临时文件里有没有出现受限标记。

如果只能看到加密连接而无法核对请求内容，就把结果记为内容未知，不能直接判定通过。研究人员当时观察到上传已不再触发，你的环境仍需用当前客户端、当前配置和实际网络策略重新确认。

把文件读取、仓库打包和数据传输拆成可观察、可拒绝、可复验的控制点，才足以说明编程代理可以进入真实仓库。最具体的动作，是用不含真实秘密的一次性仓库跑完这张审计卡，并把结果写进团队的接入门槛。
