北京拿出43.6平方公里让 AI 参与规划：开发者可以这样提交方案

如果你会用 Claude Code、Codex 一类编程智能体，这次值得关注的不是让 AI 画一张未来城市效果图，而是如何把研究、设计、规则检查和方案提交组织成一条完整工作流。

项目网站将场景设在北京海淀，讨论范围约 43.6 平方公里，从北五环延伸至北京北站，涉及京张铁路遗址公园及周边高校、科研机构、产业和生活区域。开发者面对的是一片真实城区，而不是普通的虚拟沙盘。

更有意思的入口是 GitHub。Open City 项目把任务书、城市资料、字段和校验规则整理成适合智能体读取的结构，并用 Pull Request 接收方案。项目网站和仓库自述称该征集“由海淀主导”，但它们并非政府门户域名。参与者仍应核对项目说明、组织者身份、成果授权和后续采用路径，不要仅凭社交媒体转述判断其行政属性。

从一名开发者接到规划任务开始

设想一名开发者打开项目仓库。他没有城市规划团队，也不准备直接生成一张宏大的概念图，而是先让智能体阅读任务边界、区域资料和提交规则。

它要处理的不只是空间布局。公开信息提到的方向包括整条创新带的总体概念、产业生态、医疗与教育场景、公共空间、城市地标、铁路文化保护，以及面向开发者的长期运营机制。

这一步已经改变了任务性质。过去，智能体常被放在写代码、检索资料或操作软件的局部环节里。到了城市方案场景，它必须同时理解历史、产业、空间、公共利益和工程约束，还要留下可追踪的推理与修改记录。

开发者真正要做的，是把一个过大的命题切成智能体能够验证的研究单元。例如选择京张铁路文化保护与公共空间衔接，限定一段区域，明确资料来源、利益相关方和验收条件，再让智能体展开工作。

让工具进入研究与设计链条

智能体可以先梳理仓库里的结构化资料，把土地、交通、产业、文化和公共服务信息按空间范围关联起来。接着研究相似案例，提出设计假设，并检查每条建议是否能从已有资料中找到依据。

一条更可靠的场景链可以这样展开。

  • 研究输入，列出使用的数据、规划文件和案例来源
  • 场景定义，说明服务对象、具体地点与当前矛盾
  • 设计提案，把空间动作、智能体能力和运营方式连接起来
  • 规则自检，逐条核对任务要求、提交格式和明显冲突
  • 证据索引，让评审者能够回到原始资料检查结论
  • PR 提交，把方案正文、图表、引用和修改记录放进可审阅结构

这里最容易出现的问题，是智能体生成了完整叙事，却没有建立证据链。城市设计里的流畅表达不能替代规划依据，更不能替代施工可行性、审批要求和居民意见。

评论中有一个判断很准确。真实城区要通过的关卡，不只是智能体能否自圆其说，还包括市政流程、工程条件和实际使用者的反馈。这些恰好是普通基准测试很少覆盖的部分。

把交付物变成可评审的 PR

如果最终交付仍是一份长文档，GitHub 只是换了一个上传入口。更有价值的变化，是把城市方案拆成可以比较、讨论和修改的对象。

一个可评审的提交，至少应让人看清几个部分。

  • 方案覆盖哪段区域，哪些范围没有讨论
  • 每个关键判断引用了什么资料
  • 哪些内容是事实，哪些内容是设计假设
  • 方案触及哪些群体，可能产生什么冲突
  • 哪些规则已经检查，哪些仍需专业人员确认
  • 修改前后发生了什么变化，为什么接受这次修改

当这些内容进入版本控制，评审者看到的就不只是一张最终效果图，还能看到方案如何形成、哪些意见被吸收、哪些假设被推翻。

这也是智能体进入复杂公共项目后最值得复用的部分。它不必取代规划师，却可以承担资料整理、方案分解、证据关联和一致性检查，把人的精力留给利益协调、专业判断与责任决策。

在提交之前核对入口身份

这次讨论里存在一个不能略过的信息边界。项目网站和 GitHub 组织页都称，这是面向真实片区的开源征集，并写明“由海淀主导、open-city.ai 负责整体策划、Agent 基础设施与技术执行”；但目前可直接访问的主要材料来自项目方网站和 GitHub，而不是政府门户页面。

因此，开发者不该因为仓库提供了 PR 流程，就把“项目方声明”自动等同于政府公告。更稳妥的做法是交叉核对项目主页、仓库 README、公开任务书和主办信息，确认组织者身份、成果授权、评审机制以及后续采用路径。

如果这些关系尚未写清，仍可以把它当成一次面向真实城市资料的协作实验，但不能把社区提交与正式应征混为一谈。项目越接近公共建设，来源、权限和责任边界越需要留在交付物里。

从一个可验证片区形成方案

个人开发者不需要一开始覆盖 43.6 平方公里。更合适的动作，是选择一个具体片区和一个明确问题，用现有资料完成一份小而完整的方案，再检查它能否经得起追问。

例如围绕遗址公园的一处公共空间，要求智能体给出使用场景、空间动作、数据依据、文化保护考虑和潜在冲突。完成后逐项核对引用，删除没有依据的数字，再让另一轮智能体扮演评审者，专门寻找规则遗漏和论证跳跃。

最终提交的价值，不在于智能体写了多少内容，而在于一个陌生评审者能否沿着文件、证据和修改记录，还原方案是怎样形成的。

先确认入口，再选定片区，最后提交一份能被逐条审阅的 PR。城市不是一段提示词能够生成的，但城市方案可以从一次有证据、有边界的提交开始。
