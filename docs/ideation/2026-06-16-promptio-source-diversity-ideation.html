这份文档回答一个具体问题：现在内容到底从哪些来源来，配置里预期有哪些，实际进入选题池和最终文章的又有哪些，以及怎样把它扩成一个合格的内容入口。

Grounding Context

外部接口核对

  • GitHub REST API 可作为 repo、release、issue、PR、contents、statistics 的官方入口；现有脚本只用了 search repositories 的一小块能力。
  • arXiv 官方 API 支持程序化读取论文元数据，但官方示例建议请求之间等待 3 秒，适合低频研究源，不适合高频热榜。
  • Product Hunt API 2.0 是 GraphQL，公共内容可用 client-level token 读取；它比 RSS 更适合拿 votes、topics、tagline 等结构化字段。
  • RSSHub 有知乎、B站等社交媒体 routes，但部分 route 标注反爬严格或需要自建 Cookie；它适合做备用和重点账号订阅，不适合作为无状态公共热榜依赖。

Ranked Ideas

1. 把素材池改成“来源配额 + 入口健康表” 2. 从单 source 选题升级为 story package 3. 中文需求源单独建一条稳定采集链 4. 把 GitHub 拆成五种信号，而不是一个大类 5. 让 X 只负责角度和反馈，不负责事实主线 6. 建一个“备用源货架”，按内容形态而不是平台名接入 7. 给 selector 加多样性闸门，防止每日稿件同质化

1把素材池改成“来源配额 + 入口健康表”

Description: 每日生成前先写入 runs/{date}/manifest.json 的 source_health 和 source_mix：配置数量、实际落盘数量、过滤后可发布数量、进入 selector 数量、最终入选数量。然后按来源类别给 selector 前 160 条做软配额，避免 GitHub 和少数高权重 RSS 挤掉中文需求源、应用源和采用信号。

Axis: 选题入口

Basis: direct: 06-16 可发布 source 为 673 条，但进入 selector 前 160 后只剩 RSS 83、GitHub 33、X 24、Release RSS 19、PyPI 1；最终入选 GitHub 5、X 2。scripts/daily.js 先按 sourcePriority() 排序再 slice(0, limit)。

Rationale: 当前“素材很多”是表象，真正决定文章的入口是排序后的前 160。没有配额，任何新增源都可能只是落盘好看，实际被截断。

Downsides: 需要先定义来源 taxonomy；配额过硬会牺牲当天真正好的 GitHub 爆点，所以应该是软配额和健康报告，不是机械均分。

Confidence 92%Complexity Medium

2从单 source 选题升级为 story package

Description: selector 不再只输出一个 file，而是输出 primary_source、corroborating_sources、demand_signal、use_case_signal、missing_evidence。一篇文章至少有事实源和读者需求源两个层次；没有需求源时，只能写短评或工具卡，不写“值得你马上用”的强行动稿。

Axis: 内容形态

Basis: direct: 2026-06-14 既有 ideation 已指出“选题单位与证据要求冲突，schema 以单个 source file 为单位，导致证据厚度没有成为数据结构”。最近 06-15/06-16 的 Dify、n8n、Ollama、Hermes 多数都是单 GitHub source 驱动。

Rationale: 多样性不只是多抓平台，而是让每篇文章有多种证据角色：官方事实、社区反馈、中文需求、可复现入口、反例或坑点。否则新增 100 个源也会被模型压成同一种“仓库摘要”。

Downsides: 会增加选题阶段复杂度；早期可以只要求 1 个 primary + 1 个 supporting，不必一次做完整 claim ledger。

Confidence 90%Complexity Medium

3中文需求源单独建一条稳定采集链

Description: 把中文平台从“可选补充”提升为每日入口的一等公民。第一阶段不追求全平台评论抓取，只抓平台热榜和重点账号标题：知乎热榜/问题、B站 AI 区视频标题、微博热搜/话题、掘金/少数派/InfoQ 中文技术文章、即刻/公众号人工清单。每条只作为需求信号，不直接复述平台争议。

Axis: 来源覆盖

Basis: direct: CLAUDE.md 写明定位已转为“帮中国 AI 用户发现能立刻动手的东西”，但 06-16 TrendRadar 失败，最终没有任何中文平台热榜 source 入选。external: RSSHub 社交媒体 routes 覆盖知乎和 B站，但部分 route 需要 Cookie 或有反爬标记，适合自建备用。

Rationale: 小红书文章需要“读者为什么关心”的场景感。GitHub 能给事实，中文平台能给需求语言和痛点词。缺少这层，标题和结构容易都长成工具说明书。

Downsides: 平台抓取要注意合规和稳定性；应先抓公开热榜/标题级元数据，避免采集个人隐私或诱导互动内容。

Confidence 88%Complexity Medium

4把 GitHub 拆成五种信号，而不是一个大类

Description: GitHub 仍然是可访问、可核验、平台安全的主源，但需要拆开：Trending 爆发、Release 新能力、README 能力边界、Issue/PR 真实问题、Discussions/Examples 使用方式。openclaw/Hermes 这类重点项目，应固定走“release → README → issue/PR → examples”的 package，而不是只读 trending 摘要。

Axis: 内容形态

Basis: direct: 06-15/06-16 最终 14 篇中 GitHub 类来源 12 篇；其中 openclaw、Hermes、Ollama、Dify、n8n 重复出现。external: GitHub 官方 REST API 提供 repository、release、issue、pull request、contents、statistics 等端点，现有 pipeline 主要只用 search repositories。

Rationale: 不是少用 GitHub，而是别让 GitHub 只贡献“项目名 + stars + description”。拆成信号后，同一个仓库也能写出版本变化、使用边界、问题修复、迁移路径、生态插件等不同角度。

Downsides: 需要更多 API 调用和缓存；对无关仓库不能全量深挖，应只对入围候选或 watchlist 做二次展开。

Confidence 87%Complexity Medium

5让 X 只负责角度和反馈，不负责事实主线

Description: X 来源按角色分层：官方账号给 announcement，研究者给解释框架，中文 KOL 给使用场景，home timeline 给热点线索。写作时 X 只能作为“有人这样理解/这样用”的角度来源，事实必须回到 GitHub、官方文档、release、API 文档或可核验页面。

Axis: 内容形态

Basis: direct: 06-16 保存 X 213 条，但最终只入选 2 条；x-home-* 文件大量存在，来源混杂，从 AI KOL 到非 AI 账号都有。当前 selector 没有明确区分账号类型和信号角色。

Rationale: X 很适合补“为什么现在有人关心”，但如果让它直接当主事实，文章容易变成转述动态或观点拼贴。角色分层后，它能提升多样性，又不会降低可信度。

Downsides: 需要维护账号标签和质量评分；home timeline 噪音大，必须比账号 watchlist 更低权重。

Confidence 78%Complexity Low

6建一个“备用源货架”，按内容形态而不是平台名接入

Description: 备用源不要简单追加平台列表，而要按缺失的内容形态补：产品发现、采用数据、中文需求、官方变更、教程案例、监管/商业信号。每个形态至少有主源和备用源，且定义失败时的降级内容模式。

Axis: 备用与降级

Basis: direct: 06-16 TrendRadar 失败、PyPI 部分 429、多个 RSS 404/403，实际内容仍能生成但变成 GitHub/X 主导。external: Product Hunt API 2.0 提供 GraphQL 和公开内容 token；arXiv API 可程序化读取论文；RSSHub 可为部分中文平台生成 feed。

Rationale: 备用源的目标不是“今天多几条素材”，而是防止某个入口失败时内容模式塌缩。例如中文需求源失败，就不要写“大家都在用”；只写工具更新和验证路径。

Downsides: 源越多，越需要维护健康检查和去重。没有 source health 的备用源只会增加噪音。

Confidence 82%Complexity Medium

7给 selector 加多样性闸门，防止每日稿件同质化

Description: topic selection 后加一个 diversity pass：同一天最多 3 篇同一 source class，最多 2 篇同一主题簇，至少 2 篇非 GitHub 主源，至少 1 篇中文需求信号支撑；如果不满足，就要求 selector 重新选或降低当天篇数。

Axis: 选题入口

Basis: direct: 06-15 七篇里 6 篇 GitHub 类，06-16 七篇里 5 篇 GitHub 类；Dify、n8n、Ollama、Hermes、OpenClaw 连续出现，结构相近。

Rationale: 目前 REACH 分数会把“中文读者能动手的开源工具”全部推高，结果不是没好题，而是好题长得太像。多样性闸门让编辑口径从“逐题高分”转成“当天内容组合合格”。

Downsides: 当天好素材很少时可能牺牲质量；因此闸门应该允许“降低篇数”，而不是强行填满 7 篇。

Confidence 89%Complexity Low

预期、实际、可加入备用源

当前预期来源

  • 主事实源：RSS、GitHub Search/Trending、arXiv、GitHub Releases、官方博客。
  • 观点和使用反馈：X 账号列表、X home timeline。
  • 中文需求：TrendRadar 计划覆盖知乎/B站/微博/抖音等，但当前没有稳定落地。
  • 采用信号：PyPI 下载趋势；配置里没有 npm、Hugging Face downloads、Docker pulls、VS Code marketplace 等。
  • 商业/产品信号：Product Hunt RSS、VC 博客、TrustMRR，但目前没有结构化抓取和入选保障。

当前实际来源

  • 真正自动稳定：RSS、GitHub Search API、arXiv。
  • 额外运行才有：GitHub Trending 页面、PyPI、X、TrendRadar。
  • 已不适合发布面：Reddit、HN、OpenRouter。它们可以内部观察，但不能进入标题、正文、frontmatter 或相关链接。
  • 最终支配文章：GitHub。06-15 和 06-16 两天 14 篇中，GitHub 类来源 11 篇，X 2 篇，RSS 1 篇。

Rejection Summary

#被否决方向原因
1继续扩大 RSS 列表当前 51 个 RSS 已有大量失败和重复旧内容；不解决健康检查、截断和配额，只会扩大噪音。
2重新启用 Reddit/HN/OpenRouter 作为发布源与现有平台风险规则冲突；可以内部观察，不能进入发布面。
3单纯降低 GitHub 权重GitHub 是最可核验、最安全的主源；问题不是 GitHub 太多，而是没有拆信号角色和配套需求源。
4每天强制固定 7 篇当来源多样性不足时，强行填满会制造同质化；应允许当天降到 3-5 篇高质量组合。
5用大模型自己补“社区声音”没有真实来源时会编造反馈；source health 应直接约束内容模式。
