Daily Content Pipeline 流程分析：问题、简化路径与增强点

本报告基于 PromptIO 仓库内的 skill、脚本、prompt、历史计划与内容质量规则做证据化发散，再对候选方案逐项批判、合并、排序。结论不是“加更多步骤”，而是把现有文档化流程收敛成少数可执行、可恢复、可审计的中间产物。

一句话结论

首选方案是建立 Assignment Desk Run Manifest。 它把“每日无人值守内容生产”从散落在 skill、prompt、脚本里的隐式流程，变成一个可恢复的状态机：每个选题从 candidate 到 evidence-ready、draft-ready、qa-ready、publishable 都有明确状态、失败原因、补证路径和发布许可。

在此基础上，流程可以简化为 5 个稳定产物：

SourceItems→ StoryPackage / Assignment→ ClaimLedger / ArticlePlan→ Draft + QAReport + PlatformPassport→ WikiPatch + PublishReceipt

Grounding Context：证据基础

仓库内观察

  • .claude/skills/daily-content-pipeline/SKILL.md 描述了端到端无人值守流程：RSS/GitHub/arXiv、X/Bird、wiki-informed scoring、last30days、并行写作、QA 三轮质修、平台标记、wiki 更新和 commit。
  • scripts/pipeline.js 实际是 fetch-only：它只做采集、lock、source existence skip 和自动 commit，不跑选题、生成、QA、发布 gate、wiki patch。
  • scripts/daily.js 做顺序选题和生成，但 selection schema 是单个 file；而 scoring prompt 要求 2-3 个互证源。
  • config/prompts/qa-check.md 与 scripts/lib/l1-replace.js 已有 QA/合规规则；但 scripts/publish.js 没有形成强制 QA/platform gate。
  • wiki 更新被放在 daily path 中直接执行，但缺少 patch queue、registry 和 quarantine 边界。

历史经验与外部类比

  • 历史计划强调：初稿 → L1 机械替换 → 独立 QA agent → 最多 3 轮质修 → 人工审核/失败状态 → commit。
  • LLM 自评分不可靠，分数更适合作排序；硬闸门应由机械可验证状态、证据厚度、QA 结论与平台 passport 驱动。
  • 新闻自动化实践中，AP/Reuters/WaPo/BBC 的共同点不是“大模型一步到位”，而是 assignment desk、结构化数据、claim/evidence tracking、docs-as-code、长尾自动化与审计边界。
  • 典型失败模式包括：把采集源当事实源、缺 claim ledger、模板变量泄漏、scaled low-value content、外部内容 prompt injection、wiki 长期记忆污染。

当前流程的主要问题

1
文档流程大于可执行流程。 skill 描述了完整无人值守链路，但现有脚本主要覆盖采集、顺序生成和发布打包，缺中心编排器。
2
两套路线上下文不一致。 skill 里是 10 个子代理并行、QA 三轮、wiki 更新；daily.js 更像一个轻量顺序脚本。
3
选题单位与证据要求冲突。 scoring prompt 要求多源互证，但 selection schema 以单个 source file 为单位，导致“证据厚度”没有成为数据结构。
4
QA/合规规则存在，但没有闭环。 prompts、L1 替换、平台标记都在，但 publish gate 没有强制消费这些状态。
5
wiki 写入风险偏高。 daily path 直接更新长期知识库，容易把未发布、未 QA 通过、或 blocked 事实写成“组织记忆”。
6
soft-fail 没有转化为编辑信号。 外部依赖失败时流程能继续，但稿件不知道缺了社区证据、平台趋势或价格/下载量等关键上下文。
7
规则重复，未来会漂移。 prompt、skill、脚本中都写了合规/质量约束；缺少单一规则源和脚本化 gate。

Ranked Ideas：推荐方案排序

1

Assignment Desk Run Manifest

Axis: 编排Confidence 88%Complexity M

建立每日 run manifest 和 per-topic assignment manifest，把每个选题的状态、证据需求、生成状态、QA 状态、平台许可、wiki patch、发布 receipt 全部挂到同一个可恢复对象上。

依据skill 声称端到端无人值守，而 pipeline.js 是 fetch-only，daily.js 是顺序生成；缺少中心控制面。外部 newsroom automation 也普遍先有 assignment desk / planning layer。
为什么值得做统一文档流程与可执行流程；自然容纳 core path vs enhancer path、stop-the-press alert、失败恢复、per-topic retry。
潜在代价需要定义 manifest schema，并改造 daily/single/publish/wiki 读取同一状态；初期会增加少量结构化文件。
建议落点先新增 runs/YYYY-MM-DD/manifest.json，只接入 source health、story package、QA status、publish passport 四个字段，不一次性重写所有脚本。
2

Story Package Builder

Axis: 证据模型Confidence 84%Complexity M

在 scoring 前先把 SourceItems 聚合成 story package：主源、佐证源、社区证据、可写角度、证据缺口、不可写边界都显式列出。选题单位从“一个 file”升级为“一组证据”。

依据daily.js selection schema 是单个 file，但 scoring prompt 要求 2-3 个互证源，天然不匹配。
为什么值得做减少薄证据成稿；让 last30days、X/Bird、wiki recall 都成为补强 package 的输入，而不是独立步骤。
潜在代价需要聚类、去重、相似度或人工可理解规则；package 过度聚合会让新鲜度下降。
建议落点先做启发式聚合：同 repo / 同产品 / 同关键词 / 同日期窗口；没有 2 个以上证据源的选题进入 evidence_needed。
3

Claim Ledger

Axis: 证据模型Confidence 82%Complexity M/H

正文生成前先生成 claim ledger：每个可验证断言绑定 source snippet、URL、置信度、可写范围和 unknown boundaries。稿件只能使用 ledger 中已许可的断言。

依据现有 prompt 已要求禁止虚构事实；外部 claim verification 实践显示，无 ledger 的自动写作最容易把“看起来合理”写成事实。
为什么值得做让 QA 从抽象评价变成逐条查证；可直接支持事实纠错、引用审计、wiki patch 过滤。
潜在代价claim extraction 和证据绑定本身也会出错；需要最小 schema 与抽样审计。
建议落点先只要求 8-15 条核心 claims，不覆盖所有句子；未入 ledger 的事实性句子在 QA 中直接标红。
4

Platform Passport / Publish Gate

Axis: QA/发布Confidence 90%Complexity L/M

让 publish.js 成为真正的执行闸门：读取 QA 状态、平台 passport、L6/XHS 合规、blocked reason、人工批准状态；没有明确 publishable 就不产出发布包。

依据meta 与 QA prompt 已有平台字段和 L6 规则，但发布脚本没有看到强制消费这些状态。
为什么值得做这是事故防线中收益最高、改造面较小的一步；把“规则写在 prompt 里”变成“发布前必须通过”。
潜在代价历史 draft 可能缺字段；要决定缺字段时默认 blocked 还是 legacy allow。建议保守默认 blocked。
建议落点不推翻当前 L6 主稿硬门槛；先增加 --force 或 manual_approved 作为显式例外路径。
5

QA Repair Task Loop + Scripted Mechanical Gates

Axis: QA/合规Confidence 80%Complexity M

把 L1 禁词、合规词、metadata、平台 passport 等机械规则脚本化；LLM QA 只审语义、结构、读者价值和事实链，并输出 repair_tasks、目标段落、验收条件和轮次 diff。

依据l1-replace.js 已经存在，prompt 中又重复定义了大量规则；历史经验指出 LLM 自评分不能作为硬阈值。
为什么值得做减少 QA prompt 膨胀与漂移；让三轮质修变成可执行任务列表，而不是反复“重写得更好”。
潜在代价需要统一规则源和测试样例；repair task 过细会增加生成成本。
建议落点先定义 qa.report.json：mechanical_gates、semantic_findings、repair_tasks、round、overall_pass。
6

Wiki Patch Queue

Axis: wiki治理Confidence 78%Complexity M

daily 不再直接改长期 wiki，而是产出可审阅、可回放、可 lint 的 wiki patch。registry 只登记 published 或 QA-pass 的事实；blocked、quarantine、draft-only 信息不污染长期记忆。

依据skill 把 wiki update 放在 daily path 中；历史经验强调 docs/solutions 和 wiki 需要防止低质量自动写入。
为什么值得做保护长期知识库质量；把“学到什么”与“今天临时看到什么”分离。
潜在代价wiki 更新会有延迟；需要 patch apply / lint tooling。
建议落点新增 wiki/patches/YYYY-MM-DD/*.md 或 JSON patch；weekly job 批量审阅并合并。
7

Source Health Ledger / Dependency Preflight

Axis: 外部依赖Confidence 76%Complexity L/M

每日开始时运行 preflight，记录 bird/X、TrendRadar、PyPI、OpenRouter、GitHub、last30days 等依赖健康；并把缺失源映射到内容模式降级，例如“无社区证据时禁止写社区反应”。

依据现有采集脚本多采用 soft-fail，能保命但不能告诉后续环节证据缺口；last30days 成本也不应每题固定触发。
为什么值得做把外部失败从日志事件变成编辑上下文；按证据缺口触发补采，而不是机械跑满所有增强步骤。
潜在代价需要定义源类型对内容模式的影响；有些依赖失败可能只是临时网络抖动。
建议落点manifest 中增加 source_health 与 content_mode_constraints；三次失败才进入 degraded mode。

推荐实施顺序

  1. 第 1 步：先做 Publish Gate。 改造面最小、风险收益最高：没有 QA/passport 就不发布。
  2. 第 2 步：引入 Run Manifest。 先把每日运行状态和选题状态结构化，不急着重写生成逻辑。
  3. 第 3 步：把单 file 选题升级为 Story Package。 让多源互证成为数据结构。
  4. 第 4 步：为高风险稿件启用 Claim Ledger。 不必一开始覆盖所有稿件；先覆盖 API、价格、benchmark、安全、合规相关主题。
  5. 第 5 步：QA repair tasks 与 wiki patch queue。 当状态机稳定后，再把 QA 质修和长期知识库治理接入。
不建议的方向：不要把现有 skill 里的所有步骤再硬编码一遍；也不要先追求 10 个子代理并行。现在最缺的是“状态边界、证据边界、发布闸门”，不是更多生成并发。

最小可行目标

如果只做一个小版本，建议目标是：

  • 新增 runs/YYYY-MM-DD/manifest.json，记录 source health、story packages、draft ids、QA status、platform passport、publish receipts。
  • publish.js 在没有 qa.overall_pass === true 和平台 status === "primary" / manual_approved 时直接失败。
  • daily.js selection 输出从 {file} 改为 {package_id, primary_source, corroborating_sources, missing_evidence}。
  • QA 输出 repair_tasks，三轮质修围绕任务关闭，而不是泛泛重写。
